Three filters, cheap to expensive: how a duplicate finder avoids hashing your whole disk

Tanggal: 2026-11-11

Every duplicate file finder starts with the same obvious plan: hash every file, group by digest. It is correct, it is simple, and on a real drive it is unusable.

Here is the naive baseline, measured on a 1.09 GB working folder with 877 files:

21 seconds for one gigabyte. A 500 GB drive is three hours, and that is before you count the USB drive that spins down every 30 seconds.

The fix is not a faster hash. SHA-256 is already fast enough — the CPU is not the bottleneck, the disk is. The fix is not reading the bytes at all for the files that cannot possibly be duplicates.

os.stat gives you the size without opening the file. Two files with different sizes are not duplicates, full stop. This filter costs one syscall per file and eliminates the majority of a normal folder.

Only buckets with more than one member survive. On a typical disk that is a small fraction of the file count — photos, videos, and documents almost all have unique sizes.

Files that share a size are the only candidates left. For those, read 4 KB and hash that.

4 KB is not a magic number. It is the point where the cost of the read is negligible compared to opening the file at all, and where formats diverge: JPEG headers, ZIP local headers, MP4 ftyp boxes, and Office files all differ within the first few hundred bytes. Two files that agree on both size and first 4 KB are either duplicates or deliberately constructed to look like them.

Whatever is still standing gets read end to end and hashed properly.

The point of this stage is not speed. It is that this is the only stage allowed to decide a file gets deleted, and it uses a cryptographic digest, not CRC32, not a size match, not a filename pattern. Duplicate cleaners get one-star reviews for exactly one reason: they deleted something that was not a duplicate.

Same folder, same machine, three filters instead of one:

2.1x on 1.09 GB. That number is unimpressive, and it is worth being honest about why: this folder is small and it is full of build artefacts that genuinely collide on size. The ratio is not a constant — it is a function of how much of your disk is unique. On a photo library where every file is a different size, filter 1 alone removes almost everything and the speedup is an order of magnitude. On a folder of copied installers it approaches 1x, because most of the data really is duplicate and really does have to be read.

The metric that matters is not files hashed. It is bytes read, and filters 1 and 2 exist to make that number small.

Hard links. st_nlink > 1 means several names point at one inode. They are not duplicates — deleting either name frees nothing, because the data is still referenced. A finder that reports them as duplicates and "cleans" them gives the user a fake number and zero reclaimed space.

Long paths. MAX_PATH is 260 characters and open() fails past it. Prefixing with \\?\ bypasses the limit, but only for absolute paths, and only on Windows:

The 240 threshold, not 260, leaves room for the prefix itself and for the path separator that gets appended.

Four stages, about 40 lines of logic, and the expensive one runs on a third of the files or fewer. The same shape works for photo libraries, backups, and the Downloads folder everyone has been meaning to clean since 2019.

FileDedupe is a Windows duplicate file finder that uses this pipeline. Free on the Microsoft Store. Code excerpts above are from the shipping scanner.
