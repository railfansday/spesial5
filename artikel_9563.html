MSK Standard to Express In-Place Upgrade: How It Works and What to Check

Tanggal: 2026-11-23

Moving a Kafka cluster to a different broker type used to mean standing up a new cluster, mirroring topics and cutting clients over. On 20 November AWS launched an in-place upgrade from MSK Standard brokers to Express brokers. Same cluster ARN, same endpoints, no client changes. Here is how it works going by the launch post and the upgrade docs. I have not run it.

You start the upgrade on a provisioned cluster. MSK adds Express brokers matching the count and size of your Standard brokers, so for a while the cluster runs both. Topics move across using Kafka's own replication protocol, the same mechanism as a scale-out rebalance. Then you either decommission the Standard brokers or roll back.

The docs say consumer offsets are kept and each message keeps its topic, partition and offset. AWS says Flink and Kafka Streams carry on without reprocessing or duplicates.

You start it from the cluster page in the console ("Upgrade to Express") or with the UpdateBrokerType API. The docs recommend an upgrade readiness assessment first, and it can run any time.

A related launch the same day: Standard brokers now support Kafka 4.2, with in-place rolling upgrades for provisioned clusters. But the Standard-to-Express path is for 3.9 KRaft only.

The upgrade has no charge of its own. You pay for both broker types while it runs, and AWS says it takes hours. Budget for that overlap.

AWS's savings claims do not agree with each other. The announcement says M8g is up to 30% cheaper than M7g. The upgrade doc says up to 15% lower compute cost. I could not find anything reconciling the two, so I would model with the lower figure. The doc also says the broker-side cross-AZ data movement cost goes away on Express, which it quantifies as 50% lower cross-AZ transfer costs. Express pricing per hour and per GB was not in what I read, so check the MSK pricing page.

Performance claims are vendor numbers: up to 3x throughput per broker, faster scaling and recovery. Treat them as a reason to test, not a forecast.

Run the readiness assessment on every cluster this week, even if you are not upgrading. It costs nothing to know what blocks you. Then pick a non-critical cluster, use controlled mode, move one low-traffic topic, watch lag and latency for a day, then batch the rest. Keep the Standard brokers until you are bored of looking at dashboards.
