I think that sums it up well. Like you said, it's been known for 20 years ... and yet it's still relevant today. AI is forcing us to deal with our tech debt.

Yeah, crypt() *should* return a NULL pointer, *not* some arbitrary string when there's a fault. Entirely musl's bug.

For legacy reasons, Crypt() is not allowed to return a null pointer. Some old applications do not expect a null pointer and will crash. On error, it instead returns a string that starts with *. In GNU C the string starts with * and then has a partial, invalid hash. In Musl C it just has the *. Crypt() never returns * on success.

No, if you read the man page for crypt, a failed return is supposed to start with the "*" character while a successful run will not contain a * character anywhere. GNU libc returns a * followed by additional characters while musl C only returns the *. OpenSSH failed to check whether the crypt output started with *, signaling an error.

The way I read this is that libraries like OpenSSH are now run through security checking AI models, but those models can't catch issues in parent libraries like musl. The kind of unexpected breakout from tunnel vision like https://xkcd.com/538/ [xkcd.com]
