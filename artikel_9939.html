'Gheist' Weaponizes GitHub Tokens to Steal Cloud Secrets

Tanggal: 2026-11-06

An ongoing supply chain attack is harvesting credentials and sensitive data from thousands of developer repositories.

An ongoing attack is abusing compromised GitHub tokens to harvest cloud secrets and credentials from thousands of developer repositories, bringing into focus how compromised developer accounts can provide a gateway into enterprise cloud environments.

Dubbed "Gheist," the campaign has left more than 13,500 malicious branches — or versions of a project's code — across more than 850 compromised GitHub accounts, according to a report published over the weekend by Wiz Research.

The campaign affects everything from personal projects to private enterprise repositories, although public repositories are protected by safeguards GitHub introduced in July, according to the report.

"The control GitHub added is focused on protecting public repositories from workflow abuse vectors," Wiz researcher Rami McCarthy tells Dark Reading. However, "once an enterprise credential is compromised, that control doesn’t apply," he adds.

Wiz also found overlap between Gheist-affected GitHub accounts and other abuse campaigns, including repository-based malware distribution, attempts to exploit GitHub Actions for computing resources, and possible infections linked to other malware operations.

This overlap — which distinguishes Gheist from similar campaigns — suggests stolen developer tokens may be reused or shared among threat actors, "demonstrating the complexity and activity of this threat landscape," McCarthy says.

The campaign relies on a workflow named "sync-check," which is committed to each repository accessible through a stolen token, the researchers wrote.

"The workflow seeks to print the repository’s secrets into its own workflow log," they wrote. "Then, the tool downloads the log through the GitHub API and deletes the run seconds later. The tool's API requests carry the user agent 'gheist,' which gives the campaign its name."

Wiz began tracking the activity Sept. 15 and said the operation remains active and evolving as of Oct. 24. The researchers reported the activity to GitHub, and about two-thirds of the implicated accounts are no longer available, which "likely indicates response activity," according to the report.

The tokens appear to have come primarily from two sources: infostealer malware and credentials exposed in earlier software supply chain compromises, the researchers noted.

GitHub tokens authorize users and applications to access repositories, code, and administrative functions, making them valuable to attackers seeking to compromise projects and organizations.

Gheist uses stolen GitHub tokens to create branches named "ci-sync-" followed by six characters. The attackers then add the GitHub Actions workflow at .github/workflows/sync-check.yml, using the commit message "ci: sync config," according to the report.

"The commit is unsigned and authored as the token's owner," the researchers wrote. The resulting push event triggers a workflow that attempts to print environment variables and repository secrets into its log. The attack encodes the output using Base32 before retrieving the logs through the GitHub API and deleting the workflow run seconds later.

"Because the secrets leave through GitHub's own API, there is no attacker domain or outbound connection to block," the researchers explained.

A key finding is that Wiz observed successful attacks in private repositories and enterprise environments, where the public-repository safeguard did not apply. Most GitHub-targeted activity, by contrast, primarily affects public repositories, McCarthy tells Dark Reading.

"The attack succeeded in the environments organizations considered safest because a credential issued to a human months ago still carried full write authority," says James Matchett, head of security at supply chain security firm Cloudsmith, in an email interview. "'Private' is not a control. Scoped, short-lived credentials, a tight inventory of what can push and pull, and the discipline to rotate after every incident are the control.”

Wiz observed the attackers cycling through tokens belonging to multiple users and automation accounts, and cloning private repositories before planting malicious workflows. Within hours, cloud credentials from the same organization were used to enumerate AWS Secrets Manager, the researchers added.

Wiz estimates that the campaign affected "on the scale of a dozen companies," McCarthy says. However, "we have not seen consistent or automated abuse outside of mass cloning of GitHub repositories and the core credential theft," he says.

Token abuse is an increasingly common way for attackers to infiltrate organizations through the developer pipeline. Research presented at Black Hat Europe last year found that some of the most significant software supply chain incidents over the preceding year involved threat actors exploiting GitHub flaws. Defenders therefore must treat developer projects as critical organizational assets.

To defend against Gheist and other forms of token abuse, Wiz urged security teams to hunt for malicious GitHub Actions workflows, rotate exposed secrets, and treat compromised self-hosted runners as potential infrastructure breaches.

More specifically, defenders should look for branches named "ci-sync-" followed by six characters, where the only change is a new .github/workflows/sync-check.yml file with the commit message "ci: sync config," the researchers advised. Administrators also should review GitHub audit logs for workflow runs on "ci-sync-*" branches that were deleted within a minute of completion, as well as activity from the user agent "gheist."

For broader protection against GitHub token abuse, Waseem Ahmed, head of engineering at security firm Secure.com, recommends that organizations "replace long-lived personal access tokens with GitHub Apps or short-lived fine-grained tokens" and "require reviewers on any environment that holds production secrets." These measures can help limit attackers' ability to access sensitive credentials even if they obtain valid tokens.
