Debugging OAuth Redirect Loops Caused by Oversized HTTP Cookies

Tanggal: 2026-11-24

Last week, we spent almost four hours tracking down a login bug that made zero sense on paper.

Our dashboard users signing in with Google or Discord were getting thrown into an infinite redirect loop. They would hit sign in, pick their Google account, authorize it, watch the screen flash for a second, and then land right back on the empty login form.

No error message. No red toast. No failed requests in Chrome's network tab. Nothing in the console either.

Meanwhile, plain old email-and-password logins worked perfectly. Same database, same API server, same users. If an account logged in with a password, it went straight to the dashboard. If that exact same account clicked "Sign in with Google", it got kicked right back to square one.

To explain why this happened, you have to look at how we split our frontend and backend. The client dashboard runs on one subdomain, and the core API runs on another.

When someone signs in with an email and password, the frontend just fires an asynchronous POST request to our auth endpoint. The API checks the credentials, returns a 200 with the user profile and session data right in the JSON response body, and the frontend JavaScript saves that into localStorage and routes to the dashboard.

OAuth can't do that because the initial handoff isn't an in-page fetch request. The user gets bounced to Google's consent screen on google.com, and Google bounces them back to our API callback route on our API subdomain.

During initial development, this worked every single time. We created test accounts, clicked through OAuth, and landed on the dashboard without an issue.

The bug only showed up when we started testing with older, heavily used accounts.

When one of us tried to log in with an account we had been using for weeks across multiple laptops and phones, the redirect loop kicked in immediately.

But we checked our flags, and we were already using SameSite=Lax, Secure, and an explicit parent domain. That should have been completely fine under modern browser specs.

Then we thought we might have a race condition in our frontend code. We had an event listener in the login view listening for window focus events to catch popups, so we wondered if the tab was gaining focus mid-redirect and wiping state.

We removed that listener, tested again, and the loop was still there.

Eventually we opened Chrome DevTools, turned on "Preserve log" in the Network tab, and watched the whole redirect chain step by step.

That user record had an array called sessions. Every time a user logged in, our database pushed an entry tracking their device, IP, user-agent string, and login time.

On a brand new test account with one session, that whole JSON object was around 300 bytes. It easily fit inside the 4KB limit. But on our personal accounts, which had logged in dozens of times during testing, that session array had 10 or 15 items. The raw JSON alone grew to about 2.6KB.

Every quote turns into %22. Every bracket turns into %7B or %7D. Every colon turns into %3A. Every comma turns into %2C.

In practice, percent-encoding regular JSON inflates the byte size by about 2.4 times.

Email and password login never had this problem because the user data returned in the HTTP response body has no 4KB limit. The frontend read the body, saved it to localStorage, and navigated cleanly.

Third, we updated our frontend auth hook to check the URL query parameters on mount. If it sees auth_success=true, it immediately fires a background fetch request to our user profile endpoint to pull the full user object over a normal HTTP body.

As soon as that request finishes and localStorage is updated, the frontend calls window.history.replaceState to scrub the query parameters out of the URL bar so the user never sees them.

The biggest lesson for us was just how quiet browser networking failures can be.

If your backend throws a 500 or your React code throws an exception, you get an immediate alert or a red error in your console.
