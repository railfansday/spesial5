Circular Dependencies Between Modules in a Database: A Real Dependency, or One Table in the Wrong Module?

Tanggal: 2026-11-15

Posted on Nov 15 • Originally published at schemity.com

Disclosure: I build Schemity, a desktop ERD tool - this post is from our blog and uses it for the examples.

TL;DR: A cycle between modules is counted from two things: the foreign keys, and the list that says which table belongs to which module. On a 34-table PostgreSQL store split into seven modules, ten cycles fell to three when addresses moved to the accounts module and to zero when stock_levels moved to shipping, with no constraint changed. A cycle is a real dependency when every table already sits with the module that writes it; then one foreign key has to go, or the two modules are one.

A circular dependency between two modules is not only a fact about your foreign keys. It is a fact about your foreign keys and about the list that says which table belongs to which module, and changing that list can remove the cycle without touching the database. So before you break a dependency, check whether one table is filed in the wrong module.

I measured it on a 34-table PostgreSQL 18.3 store with 43 foreign keys, split into seven modules. That split gave ten cycles between modules. Moving addresses from shipping to accounts left three. Moving stock_levels from catalog to shipping left none. Not one constraint changed. This post shows the query that counts the cycles, how to tell which tables are worth moving, and what a cycle looks like when no move can remove it.

Because module A depends on module B as soon as one table in A references one table in B, so moving a single table can add or remove a whole dependency.

Tools that check module structure treat a cycle as an error. Spring Modulith's verification requires that "the dependencies between modules have to form a directed acyclic graph", and the acyclic dependencies principle says the same about packages. Those checks read the code. The database has the same graph, drawn by foreign keys, and those checks never read it.

Here is the part of the store that matters. A user has addresses, a user has a default address, and a warehouse has an address:

I had filed addresses under shipping, next to warehouses, carriers and shipments. That one choice makes accounts depend on shipping (users.default_address_id) and shipping depend on accounts (addresses.user_id). File addresses under accounts and both of those keys stay inside one module. The keys are the same; the cycle is gone.

Two limits before you trust it on your own database. The join is an inner join, so a table missing from table_domains drops out of the count without an error, and conrelid::regclass::text writes a table outside the search_path as shop.addresses and a mixed-case or reserved name in double quotes, so the mapping has to spell names the same way. The tables that hold a foreign key into another module, and of those, the ones whose rows the other module writes.

Counting is a poor guide, and I checked that by brute force. With 34 tables and seven modules there are 204 ways to move one table to another module. A script tried all of them against the ten cycles:

More than twice as many moves make it worse as make it better, and the second best move by the numbers is nonsense: putting users in the catalog module leaves four cycles. A low count proves nothing about whether the table belongs there.

So ask who owns the rows, and use the count only to confirm. Two questions settle most tables:

A third option is to give the contested table a module of its own. That does not help when two tables reference each other. I put addresses alone in a new locations module and got four cycles, one of them accounts > locations, because users and addresses point at each other. Two tables that reference each other form a cycle wherever you draw the line between them; they can only share a module, or lose one of the two keys.

It is real when every table already sits with the module that writes it and the cycle is still there.

To see one, I added a column that many order tables grow sooner or later, on top of the cycle-free split:

The cycle query returns one row, orders > shipping: shipments.order_id points one way and the new column points back. Both tables are where their writers are: the order flow writes orders, dispatch writes shipments.

The move test agrees. I ran the 204 single moves again and exactly one clears the cycle: moving orders into the shipping module, which leaves an orders module without its orders table. Moving two tables together, shipments and shipment_items into orders, clears it as well, and that is not a table changing module. It is shipping losing its shipments, which is merging the two modules under another name.

For a real cycle one direction has to go. Here the back reference is the weak one: the latest shipment of an order is the row in shipments with the highest id for that order_id, so a query can derive it and the column can be dropped. Dropping only the constraint and keeping the column does not count: the reference is still there, the catalog query just stops seeing it, as it already fails to see orders.coupon_id. When neither direction can go, merging the two modules is the honest answer: they were one module all along.

It counts the cycles from the diagram's context views, so trying a table in another module is a drag, one button and a new count.

Schemity is database design software that reads your live database, shows the impact of every schema change before it runs, and keeps the diagram as a file in Git. To understand your schema at the module level it has two pieces. A context view is a saved, focused view of the schema that shows only a subset of entities and the relationships between them. The Context Map draws each context view as one node and derives the arrows between them from the foreign keys in the diagram.

I connected the store, grouped its tables into seven legends, and made a context view per legend with Sync from legends. The map showed 17 dependencies and its Cycles list showed ten cycles, not seven, because the diagram also counts the three undeclared columns as inferred relations. Clicking an arrow lists the keys behind it, which is the list you need for the ownership questions above.

Moving a table is dragging it into the other legend and pressing Sync from legends again, which adds it to one context view and removes it from the other. After addresses moved, the map showed 15 dependencies and three cycles. After stock_levels moved, 14 dependencies and none.

An AI agent can do the same reading over the local MCP server. get_context_views returns the dependencies, the keys behind each and the cycles. The built-in prompt Organize a diagram by domain groups the tables from your codebase, puts a table several domains use with the domain that writes it, and ends by asking the agent to say, for each cycle, whether one table looks like it belongs in another domain or the dependency is real.

Schemity does not make that call itself. It lists every cycle the same way and does not mark one as a boundary cycle and another as real. The count is computed; the ownership decision is yours.

Check the module list before you change the schema.

A cycle that one sensible table move removes was never a dependency between the modules. List the foreign keys behind both directions. If one of them sits in a table the other module writes, move the table and count again. If every table is where it belongs, drop or turn around one key, and say in the review which one and why.

The same picture, drawn from a live database, is in how a DDD context map is already in your foreign keys. Once the cycles are gone, the remaining arrows are the keys that cross a boundary, and whether to keep foreign keys between modules is the next decision. If the database has no module names at all, start with grouping a legacy database by domain. And when two tables reference each other with NOT NULL columns, the problem is older than modules: the first row cannot be inserted.
