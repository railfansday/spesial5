Nondeterminism in Futhark

Tanggal: 2026-11-06

Last week I attended IFL2026, which was probably one of the best conference experiences I have ever had. One of the many good presentations was by Michael Haddon, who presented The Replay Lattice, which is a type system for floating-point reproducibility. The type system was presented for a demonstration language called Lane, but it inspired me to think more carefully about nondeterminism in Futhark (there is some), and what it might cost to get rid of it.

I often use the terms âdeterminismâ or âdeterministicâ when explaining why I think data parallel programming is such a good paradigm, so perhaps it is surprising to see me write a blog post about nondeterminism in Futhark. But as is so often the case with such bold promises, they often tend to get a little weaker once you look closely enough. Michael Haddonâs work defines some nomenclature that is helpful for this discussion:

Exact means that the computation produces the same result every time, guaranteed. (Michael describes this as matching the âserial referenceâ, which I think is not the best way of looking at it, but thatâs a question of perspective)

Replay means that if you rerun the computation with the same âscheduleâ (in some sense âmachineâ), you will get the same result, but other machines may give different results.

Approx means potentially nondeterministic results.

The kind of nondeterminism we are talking about here is not the kind of free-form nondeterminism that arises from classic shared-state concurrent programming. Indeed, both Lane and Futhark are pretty much exclusively concerned with the kind of nondeterminism that arises from floating-point rounding errors. The simplest example is the non-associativity of addition:

If we have an array of numbers we need to sum, then the result depends on the order in which you sum them. When parallelising a summation, you often do things like split the numbers into blocks, sum each block on a separate processor, then combine the partial results. This changes the order of addition, and hence the result. Now, an important point is that there is no reason to think that the parallelised result is numerically worse than a serial left-to-right summation, but it will be different. Further, an efficient implementation will likely choose a number of chunks somewhat proportional to the number of processors on the machine, which means the result may also be different on other machines (but again, not necessarily worse). This corresponds to the âReplayâ class of nondeterminism. Finally, the partial results may be combined using atomic instructions, which may be resolved in a different order when the program is rerun on the same machine. This is then âApproxâ.

Even in this simple example of summing a bunch of numbers, we encounter both classes of nondeterminism. Note that none of them are ârace conditionsâ in the usual sense of the program sometimes just malfunctioning: the point is that the result changes, but given that the result is in some sense already âwrongâ (due to roundoff error), the main issue is that there are cases where we care about getting the same âwrongâ result every time.

So in Futhark, ostensibly a deterministic language, where does the nondeterminism come from? There are a few sources. Some of them come when programmers violate mandated constraints (but which are unchecked for various reasons), and others are basically down to floating-point roundoff error.

Let us start by considering language abuse. The worst but also least interesting case is using the #[unsafe] attribute to disable safety checks, after which you can do arbitrary memory reads and writes. This can be avoided by passing --safe to the compiler, or perhaps by just not doing this kind of cowboy coding in the first place. If you are a good enough programmer that your code does not need any safety checks, why not just go and write in C? Those folks never make mistakes.

And yes, I do realise the irony of insisting on an unsafe scatter after making fun of C programmers for using an unsafe language.

Anyway, letâs move on to reduce. Parallel reductions, just like parallel scans, histograms, and so on, work only if the provided operator is associative and in some cases also commutative. This is documented but unchecked - in Futhark you can do a reduce with an arbitrary operator of the right type, and it just might give you nonsensical or nondeterministic results. It is a common error among new Futhark programmers to treat reduce as a general fold and use operators that are not associative, but it seems not to show up so much among more experienced programmers. The reason we do not check for associativity is that it is impossible, and even when it is possible it remains hard - well beyond what a practical type checker is capable of. It is not too hard to empirically test associativity and other properties, and so it seems that this source of nondeterminism is not so problematic in practice.

That actually concludes the list of âtrueâ nondeterminism in Futhark, and in both cases we can wash our hands and blame the programmer. Of course, there is one rather important caveat hereâ¦

Strictly speaking, floating-point addition is not associative, and so we could just declare that reduce (+) 0 on floating-point numbers is simply wrong. However, Futhark is not mainly intended as a framework for explaining why the program you wrote is wrong, but rather as a practical tool for parallel programming, and clearly people want to sum floating-point numbers. Indeed, summing and multiplying floating-point numbers is worth trillions of currency units these days!

As such, Futharkâs reduce (and similar functions) do not say that the result you get back is completely arbitrary in case the provided operator is nonassociative. Instead, they say that the result you get back is some arbitrary ordering of applying the operator to the input elements. The precise ordering is unspecified (weâll return to this), but it will be some order, and if the function is associative, it just so happens that the order does not matter for the final result.

The application order chosen by Futhark depends on the backend and the hardware. With the c backend, it will be a straightforward left-to-right loop across the input array. With the GPU backend, it will split the input into chunks, sum them separately, and combine the partial results. The number of chunks depends on runtime queries of the GPU hardware topology, and can also be configured by the user via tuning parameters. Since the chunking strategy (the âscheduleâ) depends on the hardware and the input size, repeatedly re-running the same reduction on the same system will consistently give the same result - the âReplayâ case in Michael Haddonâs terminology. This is not a language guarantee, but it is how it is implemented right now.

There is a reason we donât implement reduce like that, of course. In a quick experiment for summing 100 million numbers, I observe that using reduce (+) 0 is almost 3x faster than sum_tree on an MI100 GPU. The gap can be narrowed by using blocking to reduce the number of GPU kernels necessary, but ultimately the fastest way to perform a reduction does depend on fine details of the hardware, and when your operator is not truly associative, that will result in observable differences.

The same situation arises with Futharkâs other basic building blocks. I suspect reduce is actually the best case, in the sense that a hand-written version can approach the performance of the built-in one. For scan, I know that the compilerâs fancy decoupled lookback is much faster than anything that can be written in Futhark itself, and for reduce_by_index a fully deterministic implementation involves a sort and a segmented reduction, which is wildly slower than the code produced by the compiler, which makes careful use of atomic instructions.

This does make me wonder if one could write a Futhark library that replaces all the SOAC implementations with guaranteed deterministic implementations, and what the performance of that might be across the benchmark suite, but that will have to wait for a future post.
