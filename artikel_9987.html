Prove your AI agent guardrails work

Tanggal: 2026-11-27

You ask a coding agent to clean up one repository. If it has broad permissions, it may also reach your home directory, use your development credentials, and send requests to services you never approved. That gap between the task and the access you grant can turn a routine coding session into a data leak or lost work.

In Sandboxing Claude and MCP, Hrittik walked through running Claude Code and an MCP server inside Docker Sandboxes using its command-line interface, sbx. That walkthrough started with outbound access blocked, allowed the endpoints needed for the task, and inspected requests to other destinations, including telemetry. The useful part was seeing an actual request fail at the network boundary.

Now extend that workflow to a team. Models and providers will change, but the access rules still need to hold. A sandbox limits what an agent can reach on one machine. Organization governance adds shared rules, a managed way to run agents, and records of policy decisions. In this post, we’ll look at how one laptop can affect the whole organization, review two reported incidents, and connect them to four Docker controls: network policy, filesystem policy, managed credentials, and MCP access. Then we’ll test the network and filesystem controls with a simple bank administrator demo.

If an agent exposes a developer’s SSH key or cloud token, every system that accepts that credential may need investigation. The security team must work out what left the machine, replace or revoke exposed credentials, and check whether anyone used them. Deleted work can also halt development. Keep backups of work that has not yet reached the repository.

The compliance consequences depend on the data and the organization. A personal data breach can trigger GDPR notification duties, subject to the applicable risk thresholds. HIPAA has separate requirements for covered entities and business associates following breaches of unsecured protected health information. India’s DPDP framework also includes breach duties, but those provisions are scheduled to take effect in May 2027. For a SOC 2 examination, the question is whether the relevant controls operate as described. SOC 2 is not a breach-notification law.

Data sovereignty adds another question: where does the data go, and who controls it? Before approving a model API endpoint, establish where prompts and outputs are processed and stored, who can access them, and which contracts and laws apply. A provider’s nationality alone does not answer those questions. Network policy can restrict the destination, but it cannot prove how the provider handles data after receiving it.

This gets harder when developers choose and configure agents independently. A rule on one laptop may be missing on the next. An ignore file may stop one component from reading a file while another component includes it in an upload. Written policy needs matching controls in the software that runs the agent.

In July 2026, developers reported two incidents where a coding agent went far beyond its task. In one, data left the machine. In the other, files were deleted from it.

In an X post that has since been deleted, a user said Grok had uploaded their entire user directory, including SSH keys, a password manager database, and personal files. A Hacker News discussion brought wider attention to the claim. The home-directory claim remains the user’s account. The separate investigation below tested repository uploads.

Researcher Cereblab intercepted Grok Build CLI traffic and found a background upload running alongside the coding task. In a test with a 12 GB repository, about 5.1 GiB had left the machine before the capture stopped, and the upload was still running. The data went to Google Cloud Storage. Fake secrets planted in the repository also appeared in the traffic without being hidden. At the time, turning off “Improve the model” did not stop the repository uploads.

In a reproducible follow-up, the researcher rebuilt the repository from a captured Git bundle, an archive of tracked files and Git history. The bundle included files the agent had been told not to read. Telling the model not to read a file didn’t stop the CLI from packaging and uploading it in the background.

There was a subsequent change. The researcher’s updated timeline says whole-repository uploading was disabled server-side on July 13 and remained off when retested on July 22.

The fix does not change the lesson. A coding agent is more than the model. It includes the CLI and any background processes, and those can act without the model asking. Give the whole application only the access its task needs. This is the principle of least privilege.

On July 10, Matt Shumer wrote: “GPT-5.6-Sol just accidentally deleted almost ALL of my Mac’s files.” He shared the agent’s acknowledgment and confirmed that Full Access was enabled. His follow-up described the loss of his home directory.

A separate experiment shows why blocking one command is a fragile response. Developer LinearUncle reported that, after a plugin blocked rm, the agent tried unlink, find -delete, and apply_patch. A later attempt to move files to Trash through the GUI failed on permissions; a call to Node’s fs.unlink succeeded. The plugin’s own documentation describes it as an additional guardrail and recommends sandboxing and backups.

The common issue is excessive access. A model can choose a different tool, and a background process can run outside the model’s visible workflow. Filesystem and network boundaries need to constrain both.

Docker Sandboxes runs each agent in a microVM, a lightweight virtual machine with its own Linux kernel and Docker Engine. A workspace mount shares a host directory with the sandbox. A proxy on the host checks outgoing connections against network policy. The isolation documentation explains these boundaries.

That gives a developer a useful starting point. Share the project needed for the task, restrict outbound access, and inspect failures before adding permissions. Unnecessary telemetry endpoints can remain blocked while the required model and package services are allowed.

Choose mounts carefully. A writable mount shares real host files, so changes and deletions inside it affect your machine. Check additional mounts too, including shared agent skills where enabled. Docker’s clone mode gives the agent a private copy of a Git repository so you can review its commits before bringing them back. Isolation limits access, but files in a writable host mount still need backups. Clone mode still exposes the host repository for reading, including ignored files. Keep secrets outside it.

Local settings leave a rollout problem. A teammate can choose different rules or run an agent directly on the host. The organization needs a managed way to run agents, a way to require its use, and visibility into which sessions it covers.

Figure 1. Organization and team policies govern access for enrolled, licensed sandbox sessions.

Docker AI Governance lets administrators manage sandbox rules and MCP access centrally. MCP, short for Model Context Protocol, connects agents to tools and data sources. Administrators define policies in Docker Home. On developer machines, sandbox mount checks, the host proxy, and Docker’s MCP gateway enforce the relevant rules. This gives teams shared access rules and records they can review when something goes wrong.

Network policies allow or deny destinations such as domain names, IP addresses, and IP ranges written in CIDR notation. For a restricted workflow, start with access denied and allow only the destinations the task needs. Under organization governance, local allow rules cannot grant extra access. Deny rules win, and developers can add local network restrictions.

This can block a background upload to an unapproved destination. But an approved hostname may still handle several kinds of traffic. In the Grok investigation, model requests and storage uploads used different URL paths on the same hostname, so a hostname-only allow rule would not distinguish them. Docker AI Governance now supports more granular network policies: on an allowed host, rules can match the HTTP method, URL path, and query parameters. For example, a policy can permit an agent to open a GitHub pull request while blocking requests to merge it. These finer-grained rules complement filesystem restrictions, which limit the data an application can collect and send.

Filesystem policies control which host paths may be mounted. A writable mount needs both read and write permission; a read-only mount needs read. If a filesystem deny rule and an allow rule match the same request, the deny wins. The decision happens when the sandbox is created. Once a writable mount exists, the agent can modify or delete files within it, regardless of whether it uses rm, a patch tool, or a programming language API.

For proxy-managed credentials, the host proxy adds authentication to outbound requests. The agent can authenticate to an approved service without receiving the raw secret inside the microVM. Credentials can also be scoped to a named sandbox.

This reduces the need to paste API tokens into prompts or store them in the workspace. The protection applies to proxy-managed credentials. A real token placed in an environment variable, a mounted file, or a passthrough login response may still be visible inside the sandbox. Limit what each credential can access and how long it stays valid. Storing a token through the proxy does not change its permissions or expiry.

MCP access policies govern server registration and subsequent requests through Docker’s MCP gateway. With MCP enforcement active, access requires an explicit permit, and a forbid rule overrides it. Administrators can control tool calls, resource reads, and prompt retrieval, rather than treating an approved server as permission to do everything it offers.

Registration and use are separate decisions. Blocking new registrations does not stop access to a server that is already registered. Rules checked on each request handle that case. Direct connections to remote MCP servers also need network controls because they bypass Docker’s gateway. Check where each server runs too: local stdio servers run on the host, outside the sandbox VM. Their host access needs separate review.

Figure 2. Network, filesystem, credentials, and MCP controls apply to the whole agent application.

Administrators manage organization and team policies in Docker Home. Group mapping can keep Docker teams in sync with the organization’s identity provider. Policy updates take up to five minutes to reach developer machines. Network changes then apply to new requests. Filesystem changes require removing and recreating affected sandboxes because existing mounts keep their original access.

Sign-in enforcement is also part of deployment. IT distributes it through endpoint management so developers must authenticate as members of an approved organization. This prevents personal-account bypass within sbx. Your endpoint controls also need to cover agents launched outside that managed workflow.

Putting AI governance policies in place is only the first step. The real challenge is making sure those policies are practical, consistently enforced, and easy to verify as more developers start using coding agents. A few good practices can help teams reduce unnecessary access, apply the right restrictions to different workloads, and maintain visibility into what agents are doing. Here are five recommendations to keep in mind when rolling out Docker AI Governance across your organization:

The same questions apply when agents run in continuous integration (CI) jobs or other environments: which host files can they access, which services can they reach, and which credentials can they use? Check which controls each environment supports and repeat the tests there. A policy on a developer’s laptop does not automatically protect an unrelated container or production cluster.

For security teams, useful evidence connects a licensed, signed-in user to an active policy, a blocked action, and a record they can find. Check sign-in enforcement and license coverage alongside policy. An empty audit dashboard may mean some sessions were never covered.

Sandboxing limits an agent’s access on one machine. Governance applies shared rules to managed sessions across the organization. Providers will fix individual failures, but the next failure may look different. Limit which files, services, and credentials it can affect, then test those limits and check the records.

Start with the local sandboxing walkthrough, inspect your rules with sbx policy ls, and run the bank demo with your platform or security team. Use the Docker AI Governance documentation and announcement to plan a small rollout. Expand it after you have checked both the blocked actions and the audit records.
