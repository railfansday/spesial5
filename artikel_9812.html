Retries Without Double Effects: Idempotency Keys for LLM Tool Calls

Tanggal: 2026-11-06

An LLM agent decides to call your create_refund tool. The request times out. The agent framework retries, or the model simply asks for the same tool call again on its next turn. Did the customer get one refund or two?

Timeouts don't tell you whether the first attempt ran. That was true for every HTTP client long before LLMs, and the fix is the same: make the side-effecting operation idempotent, so repeating it is safe. What changes with agents is how often the repeat happens and how hard it is to notice afterwards.

Only the first one is usually configured on purpose. The other two show up in logs as "the agent did it twice".

The IETF draft The Idempotency-Key HTTP Header Field (draft-08, dated 22 October 2026; still an Internet-Draft, not an RFC) describes the common pattern. Its stated aim is to "make non-idempotent HTTP methods such as POST or PATCH fault-tolerant". The client sends a unique key with the request, and the server remembers what happened for that key.

Stripe's Idempotent requests documentation (no date shown; read 2026-11-05) shows one production policy. For its v1 API it says keys are removed after they are at least 24 hours old, and that retries with the same key return the saved response, "including 500 errors". It suggests V4 UUIDs and warns against putting sensitive data such as email addresses in keys.

For agents, the critical question is who generates the key. If the tool wrapper generates a fresh UUID on every call, a model-initiated repeat gets a new key and runs again. The key has to represent the intended effect, decided once.

A practical rule: derive the key when the agent plans the action, store it with the step, and reuse it for every retry of that step. If the model asks for "the same refund" in a later turn, the loop can match it to the existing step instead of minting a new one.
