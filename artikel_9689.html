Why signature verification alone cannot prevent cross-API token replay.

For API developers and security architects building resource servers behind a shared identity provider.

An access token can be correctly signed, issued by a trusted authorization server, and still unexpired, yet be the wrong credential for the API receiving it. When several APIs trust the same issuer, a resource server that verifies the signature but skips the audience check may accept a token that was minted for a completely different service. Nothing looks broken: authentication succeeds, standard authentication logs may show no obvious failure, and the trust boundary between APIs has already failed.

This is not a weakness in OAuth itself. It is a failure to enforce the boundary that OAuth token validation is designed to provide. The scenario below is hypothetical, uses fictional hostnames, and is built from publicly documented specifications. It illustrates a configuration weakness, not a confirmed vulnerability in any specific product.

A valid token is not necessarily a valid token for your API.

Centralized identity is operationally convenient. One authorization server may serve dozens or hundreds of APIs, and those APIs often share validation libraries, issuer configuration, and public signing keys.

A digital signature answers one question:

Was this token signed by a trusted authority, and is its content unchanged?

Audience validation answers a different question:

Was this token intended for this resource server?

A token can pass the first check and fail the second.

Cryptographic validity and authorization validity must be evaluated separately.

When a token lists multiple audiences, it may be accepted by more than one resource server. This broadens the potential impact if the token is disclosed, although each API must still independently enforce scopes and authorization policies.

RFC 9700 recommends restricting a token to a single resource server where feasible, or otherwise to a small set.

Several OAuth and JWT specifications address this security boundary.

RFC 8707 allows a client to identify the protected resource it wants to access.

The authorization server can use this information to issue an audience-restricted token for that resource.

RFC 9068 requires resource servers using that profile to validate that the aud claim contains an identifier the resource server expects for itself.

A token that does not contain an acceptable audience must be rejected.

The specification also defines the at+jwt token type to help distinguish access tokens from other JWTs.

RFC 9700 recommends audience-restricting access tokens to reduce the risk of a stolen or leaked token being replayed against an unintended resource server.

The principle across these specifications is consistent:

A resource server must not accept an access token only because it trusts the issuer. It must also confirm that the token was intended for it.

Do not relax token-type checks merely to make an otherwise incompatible token pass validation.

In production, the verification key must also come from a trusted, securely configured source, and the API must enforce scopes and endpoint-level authorization.

Audience validation is essential, but it does not replace those checks.

Normal workflows may continue working when audience validation is missing.

Legitimate users receive legitimate tokens, APIs respond, and authentication dashboards show expected activity.

Monitoring that focuses only on signature and issuer validation may not distinguish a token presented to its intended API from one presented to a different API and accepted by mistake.

Both requests involve authentic tokens from the same trusted issuer.

The absence of signature failures can create a false sense of security.

Monitoring should therefore ask not only whether a token is valid, but whether it is valid for the resource receiving it.

Audience validation and scope enforcement solve different problems.

An API that checks audience but ignores permissions can still expose sensitive operations.

Secure API authorization requires multiple controls working together.

Each resource server should maintain an explicit list of acceptable audience identifiers.

Tokens intended for unrelated services should be rejected.

Trusted issuers must be explicitly configured.

Do not derive issuer trust from untrusted token content.

Use trusted verification keys and an explicit allow-list of signing algorithms.

Never let a token select an arbitrary verification key or disable signature verification.

Validate exp and other applicable time-based claims.

Short-lived access tokens reduce the potential exposure period when bearer tokens leak, although they do not correct missing audience checks.

A token intended for an API should authorize only the operations that its subject or client is permitted to perform.

Resource servers must enforce permissions at the endpoint and object levels.

An OpenID Connect ID token is intended to convey authentication information to the client.

It should not be accepted as an API access token merely because its signature is valid.

Explicit access-token typing, such as at+jwt, helps distinguish token purposes.

Audience restrictions limit where an access token can be used.

Sender-constrained mechanisms, such as mutual TLS (RFC 8705) or Demonstrating Proof of Possession (DPoP, RFC 9449), can additionally restrict who can successfully present it.

These controls address different aspects of token replay and provide stronger protection when combined.

Security telemetry should capture audience-validation failures and other token rejection reasons without logging raw bearer tokens.

Repeated wrong-audience requests may indicate integration mistakes, misconfiguration, or attempts to cross API trust boundaries.

Zero Trust emphasizes continuous verification and limiting implicit trust.

An API that accepts any token from a trusted issuer reintroduces the kind of implicit trust that Zero Trust architectures are intended to reduce.

A centralized identity provider provides a common trust foundation, but every resource server still needs to enforce its own authorization boundary.

The same principle applies to service-to-service communication, microservices, cloud-native workloads, and machine identities.

As organizations expand their APIs and automated integrations, resource-specific token validation becomes increasingly important.

The question should not simply be whether a request carries a valid token.

It should be whether that token is valid for this resource, this operation, and this security context.

Treat audience validation as a mandatory security control, not a library default that developers assume is enabled.

Make it part of API security reviews and test it explicitly, just as authentication itself is tested.

A valid digital signature proves that a token is authentic and has not been modified.

It does not prove that the token was issued for every API that trusts the same authorization server.

The solution is not to abandon centralized identity or JWT-based access tokens.

It is to validate tokens completely: issuer, signature, expiration, token type, audience, and the permissions required by the requested operation.

Never confuse trust in an issuer with trust in every token that issuer creates.

A secure API verifies who issued a token, which resource it was issued for, and what it permits.
