Automating Google LSA Lead Ratings Through the Google Ads API

Google Local Services Ads (LSA) lead feedback can be submitted programmatically through the Google Ads API using LocalServicesLeadService.ProvideLeadFeedback(). But building reliable automation around this method requires more than sending a rating request. Agencies must preserve lead identity, translate CRM outcomes into Google's supported survey enums, check whether feedback has already been submitted, and maintain an auditable record of every API operation.

This creates an interesting engineering problem: how do you turn subjective CRM lead-quality assessments into valid, traceable feedback without sending inaccurate or duplicate classifications to Google?

For agencies managing hundreds or thousands of leads across multiple client accounts, manual rating is difficult to scale. Automated submission can reduce operational work, but poorly designed automation can introduce a different problem: systematically sending incorrect feedback.

The right architecture needs a validation layer between the CRM and Google's API.

Google exposes lead feedback submission through the LocalServicesLeadService service.

It accepts a ProvideLeadFeedbackRequest and returns a ProvideLeadFeedbackResponse.

The request contains three important components:

Records the advertiser's satisfaction rating

Contains additional satisfaction or dissatisfaction information

Union field; provide the applicable details

The survey_details field supports either survey_dissatisfied or survey_satisfied. These are alternative branches of a union field, so an integration should not attempt to populate both in one request.

Do not confuse a CRM's operational status with the advertiser's satisfaction rating.

For example, a lead marked BOOKED may be a satisfactory lead, but a booking is not automatically proof that the advertiser wants to submit a particular satisfaction rating. The business's actual assessment should drive the feedback.

Similarly, a lead marked UNQUALIFIED does not automatically mean VERY_DISSATISFIED. The reason for that classification matters.

This separates business logic from API serialization and makes the integration easier to test when Google's enum definitions change.

Google exposes the lead_feedback_submitted field on the LocalServicesLead resource.

An integration can retrieve this field through a Google Ads API query before attempting submission.

The returned resource name can be matched against the CRM's stored Google lead identifier.

This is a useful control, but it should not be treated as a complete duplicate-prevention mechanism.

It is equally important to distinguish feedback submission from billing changes. The fact that an advertiser has submitted a lead rating does not, by itself, establish that the lead's billing status has changed. This distinction is discussed in whether GLSA billing status changes after Lead Rating feedback submission.

There is a possible race condition: two workers can retrieve the same lead, both observe false, and both attempt submission.

That is why the agency should maintain its own submission state in addition to Google's Boolean field.

Consider an agency processing 5,000 leads across several client accounts.

A scheduled worker retrieves leads that have not been rated and places them into a processing queue. If two workers pick up the same lead simultaneously, both may attempt to submit feedback.

A basic database check is not enough unless the operation is atomic.

An internal state machine could look like this:

CRM data and Google lead identity are being checked

Temporary failure; retry may be appropriate

Request requires correction or manual review

Google reports feedback has already been submitted

The application should enforce a unique processing key based on the Google customer ID and lead resource name.

A database transaction or atomic conditional update can reserve that record for one worker.

However, there is an important distributed-systems issue.

Suppose the API accepts the request, but the network connection drops before the application receives the response. The worker cannot immediately know whether Google processed the submission.

Blindly retrying the request could create a duplicate attempt.

The correct response is to mark the operation as having an unknown outcome, retrieve the lead again, and inspect lead_feedback_submitted before deciding what to do next.

Do not assume that ProvideLeadFeedback offers an application-controlled idempotency key unless Google explicitly documents one.

A successful API response is not a complete audit trail.

A separate feedback ledger can preserve this information.

The ledger should be append-oriented. If a classification changes before submission, record the correction. If an API request fails, preserve the failed attempt and its error details rather than overwriting the original event.

That makes it possible to reconstruct the complete lifecycle of a lead-rating operation.

It also helps agencies investigate differences between CRM reporting and Google's lead feedback records.

Agencies frequently manage multiple Google Ads customer accounts under a manager account.

A feedback automation system should therefore separate the agency's internal client identity from Google's customer ID.

The API request must be executed with valid authorization and access to the customer account that owns the lead.

The method requires the adwords OAuth scope, but having that scope alone does not grant access to every client account. The authenticated user or application must also have the necessary Google Ads account permissions.

For security and operational control, each client's feedback queue should be processed within its own authorization context. A failure in one account should not block feedback processing for unrelated clients.

This also makes it easier to isolate permission errors, audit individual client activity, and prevent cross-account lead attribution mistakes.

Google Ads API integrations need a version-management strategy.

The current documentation provides the v26 method reference, while earlier versions have their own resource and enum definitions.

An agency should not assume that a successful implementation against one version will remain valid indefinitely.

The value of this separation becomes clear when Google adds or changes an enum. The agency should be able to update its mapping and validation layer without redesigning its CRM integration.

Google's current Local Services API documentation also explains how lead resources are retrieved and how feedback status is exposed.

The complete system can be organised into six layers.

This architecture separates the business decision from the API operation.

That distinction is essential. The CRM determines what happened to the lead. The classification layer determines whether that outcome can be represented accurately using Google's survey model. The API adapter handles submission. The audit ledger preserves the evidence.

The architecture described here is a recommended implementation pattern, not Google's internal system design.

Google's ProvideLeadFeedback method gives agencies a way to submit LSA lead ratings programmatically. But the difficult part is not making the API request. It is ensuring that the request represents the correct lead, reflects a defensible business assessment, uses supported enum values, and is not submitted repeatedly.

Agencies should treat lead feedback as a controlled data pipeline rather than a background task that copies CRM statuses into Google Ads.

A reliable implementation needs identity resolution, explicit enum mapping, pre-submission validation, concurrency control, error classification, and an auditable submission history.

As LSA management becomes increasingly integrated with the Google Ads API, these controls will matter more to agencies managing multiple accounts and large lead volumes.

The objective should not be to submit more lead ratings automatically. It should be to submit accurate, traceable feedback that the agency can explain and audit later.
