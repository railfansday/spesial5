Some of us haven't migrated from gopher yet.

Generally, LAMP still makes up a lot of the internet, nginx has taken a subset that is internet facing and needs nothing more than routing to an application of some description. However, Apache and mod_rewrite, mod_php, mod_perl etc is still very much alive and kicking.

I wouldn't say use Apache for everything, unless you need the features you can get from its modules then use something skinny, perhaps removing those modules is all you need, then you'll eventually have something closer to nginx anyhow :)

That's why this CVE isn't that big a deal in practice... "everything" has a cache in front of the actual server, so the internet can't see what is serving it anyway.

It's what I learned in the early '00s and that's what I'm sticking with!

Also, I don't load the mod_http2 module because I am an old man who yells at clouds.

We use Micro Focus's COBOL web server. I don't know what language the server is written in, but it does such a great job I've never had to hassle with it since we started using it twenty years ago. I even have Puppet scripts to setup new instances that have never been used except to create dev and QA environments. It just works.

LOL I've had an old Apache running for random reasons and figured it is just static content and not even TLS.

If you'd forgotten you wouldn't know you have it installed, though.

It isn't clear to me that this allows arbitrary remote code execution in otherwise-safe Apache configurations

The bug isapr_table_setn(req->headers, "Content-Length", "0");And the fix isapr_table_setn(r->headers_in, "Content-Length", "0");so it is clearly a bug.

But the context is: /* If we have a content-type, but already seen eos, no more                                   * data will come. Signal a zero content length explicitly.                                   */

So, until later when we see an actual description of the problem, it doesn't look to me like it would allow arbitrary execution unless you're already allowing arbitrary execution and protecting it with some sort of access control. It seems more likely that it could allow execution of protected APIs in situations where they're running on the same server that also allows direct public connections. That's a pretty dubious setup to start with.

These days you should always have a thin caching layer in the front anyways, the public internet shouldn't actually be able to talk to the web server that's generating the content. So if this bug affects you... Bad sysadmin! No Biscuit!

Also, r is the sanitized/massaged request that's being built, req is the original request that was passed in. This is an example of something I'd hope to test for: is the data we're not supposed to change being changed? I guess the, "Change languages every 5 years... for security!" people will snear," That could have been prevented with a better type system." Which is true, but here I'd rather have lower overhead and more stable code. This particular function may not need to be changed again in the next 30 years. I'd rather that than have new bugs all the time because things are being rewritten to be "safer." Better is as here, to rake it over the coals until it's perfected.

The really good news is that the bug is in http2, not apr.
