Maak v1.0.0 :: infinitely extensible command runner, build sys in Lisp

Tanggal: 2026-11-19

maak is a command runner, and its task list is a Lisp file. You write maak.scm, a perfectly normal Lisp (Guile Scheme) module, and every procedure in it becomes a task you can name on the command line. There is no DSL to learn and no second language to keep in your head: the build is the program.

The docstring is the entry maak --list prints. The lambda list is the argument grammar. Tasks call each other with a function call, not a subprocess that re-parses a file. There is no second language, and nothing to keep in sync between the task list and the code that runs.

You can also use plain static Maak files, maak.yaml, maak.toml and maak.json work with the same --list, --plan and --watch and running of course.

maak --plan deploy -- example.org runs nothing and prints the typed plan: each argv, working directory, environment, elevation, and whether it would run in the background. With --json the same plan is a versioned object a CI job can archive or diff.

maak explain deploy prints the call graph (what deploy calls, what calls deploy), the load path, the escalation, and which .env file wins for each variable. It answers "why did this run as root" without making you read the file.

There is also maak --watch TASK, which re-runs and reloads the file on change, and maak --list --json, the versioned task description that the Emacs, Neovim, Vim, VS Code, Helix, IntelliJ, Zed and Sublime integrations all read.

Supporting many features for common development and devex, cargo and rustup, uv and pyproject, npm/pnpm/yarn, Maven and Gradle, Guix and Nix (a pinned Guix resolves to a value a task can decide on, not a string another tool re-reads), Podman/Docker and Compose, git, tar and zip, curl and wget, GNU gettext, Emacs Lisp packaging, sift, and Veritas.

I'd love to hear your thoughts, critique and ideas! More improvements to come for sure, now actively looking into improving some shell completions and more things 😄
