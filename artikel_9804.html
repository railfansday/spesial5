Taming Autonomous AI Agents with Rootless Docker

Autonomous coding agents such as Claude Code, Cursor, Cline and their MCP-wired cousins ask before running shell commands by default, but that gate erodes fast in practice. Developers allowlist docker once, switch on auto-approve for long tasks, or wire an MCP server that calls the Engine API directly with no prompt at all. When agents inherit a Docker CLI pointed at a rootful daemon, every docker run, docker exec and socket-mounted sidecar becomes a privileged execution path on the host. Rootless Docker, Linux user namespaces and cgroups v2 together form a containment layer for agent-driven container workloads, provided agents are wired to the right socket and can't fall back to the system daemon.

The Docker Engine API is root-equivalent. Any process that can open /var/run/docker.sock can create a privileged container, bind-mount the host filesystem, or escape through device nodes. Mounting the socket :ro doesn't change this. A read-only bind mount protects the socket file, not the HTTP requests sent through it.

Autonomous agents amplify that blast radius. A single prompt like "reproduce the CI failure in Docker" can cascade into:

The failure mode isn't a malicious operator. It's a probabilistic tool-caller with shell access and incomplete context. A "helpful" retry loop that re-pulls images, recreates networks and restarts Compose projects looks like routine automation in the transcript and like a change storm on the host. The defense has to be structural: demote the daemon itself, then put a quota on every container it creates.

Rootless Docker runs dockerd and containerd inside a user namespace created by RootlessKit. Every request an agent makes crosses these layers:

Rootless mode depends on subordinate ID ranges in /etc/subuid and /etc/subgid:

RootlessKit builds the namespace's ID map from two sources. Container UID 0 maps to the invoking user's own host UID, for example 1001 for deploy. Container UIDs 1 through 65536 map to the subordinate range, so container UID 1 is host UID 100000, and so on.

Root inside a container is therefore never root on the host. A process that escapes a container holds the deploying user's privileges, and files that container root creates on bind mounts are owned by that user. The rule that follows: run agent workloads under a dedicated, low-privilege service account, never a developer's personal login, so that "the user's privileges" means almost nothing.

dockerd-rootless.sh starts the daemon under rootlesskit, which creates the namespaces, applies the ID mapping through the setuid helpers newuidmap and newgidmap, and starts the networking helper.

Rootful Docker attaches containers to a host bridge (docker0) and programs host iptables as real root. Rootless Docker can't. Its network lives inside RootlessKit's own namespace, connected to the host by a user-mode network stack. That's slirp4netns when installed, and otherwise gvisor-tap-vsock; pasta is available experimentally. Container traffic leaves the host as ordinary sockets owned by the unprivileged user.

Containers egress as the deploying user, not as the host's packet-filter authority. Host firewall policy is therefore a separate concern: don't assume egress restrictions you never configured.

User namespaces stop privilege escalation; cgroups v2 stops resource exhaustion. Rootless Docker applies cgroup limits only when running with cgroup v2 and systemd. In that case, docker info reports Cgroup Driver: systemd. If it reports none, rootless Docker silently ignores --memory, --cpus and --pids-limit.

Even with systemd, the user's slice typically receives only the memory and pids controllers. cpu and io limits require extra delegation, configured system-wide in section 6.

Most agent configurations and MCP servers default to /var/run/docker.sock, the rootful system socket. Rootless Docker listens elsewhere:

If DOCKER_HOST is unset and the client falls back to the system socket, every rootless boundary you built is bypassed. Agents running as systemd user units, IDE extensions or MCP child processes often inherit a minimal environment that lacks XDG_RUNTIME_DIR.

A resolution order that holds up in production:

Wrappers and MCP servers should stat the runtime path before connecting. Pair that with a deny rule if the socket's peer credentials (SO_PEERCRED) show UID 0 when the agent expected a user daemon. IDE-spawned children usually inherit HOME but not XDG_RUNTIME_DIR. Setting DOCKER_HOST explicitly in the MCP server definition matters as much as the rootless install itself.

Rootless isn't a substitute for an application-level policy proxy. It's the execution substrate that makes a compromised or confused agent survivable. Keep the MCP tool surface narrow, and use rootless Docker so whatever still reaches the Engine API can't trivially become host root.

Process limits belong in cgroups through --pids-limit, not in an nproc ulimit. Under user namespaces, nproc counts processes per host UID, so containers would share one budget with each other and with the daemon.

These limits apply to the daemon's own processes: dockerd, containerd, RootlessKit and the network helper. Containers get their own systemd scopes, limited per container.

Don't add NoNewPrivileges=true to this unit. RootlessKit needs the setuid helpers newuidmap and newgidmap to build the ID mapping, and NoNewPrivileges stops them from gaining privileges, so the daemon fails to start. Clients choose the socket through DOCKER_HOST, so setting it in this unit has no effect.

--network none is the right starting point for build and test agents that don't need egress. Open networking only when the task requires it. Dropping all capabilities and running as nobody closes the obvious privilege ladders even inside the user namespace.

Rootless dockerd, subordinate ID mappings, user-mode networking and cgroups v2 quotas turn agent container access from an implicit root grant into a bounded, observable workload. The remaining gap is the agent's client side. An MCP server that still resolves /var/run/docker.sock quietly undoes all of it.

docker-mcp-guardian is an open-source MCP server that gives Claude and similar agents read-mostly access to Docker. It's read-only by default, resolves restart deny-lists by canonical container name, withholds secrets from inspect output, and bounds every daemon call with a timeout. It also implements the resolution order from section 4: an explicit DOCKER_HOST, then the rootless socket, and the rootful socket only with GUARDIAN_ALLOW_ROOTFUL=true. With no acceptable endpoint it fails closed instead of connecting.
