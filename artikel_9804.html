Automate Excel Reports with Python and openpyxl

Tanggal: 2026-11-21

Posted on Nov 21 • Originally published at logicstack.org

openpyxl is a Python library that reads and writes Excel files (.xlsx) without Excel installed. It matters because the sales report is still an Excel file in most workplaces, and rebuilding the same report by hand every month wastes hours. In this tutorial we build a monthly sales report from code, with live formulas, a summary sheet and a chart.

We build a monthly sales report workbook called sales_report.xlsx. It has a Sales sheet with eight rows of sales data, a Revenue column that uses a live formula in every row, a totals row, frozen header panes and an auto filter. It also has a Summary sheet with one total per region, conditional formatting that highlights big totals, and a bar chart. The finished workbook holds 201 units sold and a grand total of $29,647.98, and it opens in Excel, LibreOffice and Google Sheets.

The numbers are small on purpose, so every total can be checked by hand: North $11,890.50, South $8,991.70, East $5,205.00 and West $3,560.78, for a grand total of $29,647.98.

We need Python 3.12 and pip. We tested every step on Python 3.12.3 with openpyxl 3.1.5, and the last step also uses pandas 3.1.1. No Excel install is needed anywhere in this tutorial, because openpyxl writes the .xlsx file directly. Create a folder for the project and move into it:

We start with a plain Python list of tuples, the kind of data that comes from a database query, an API or a CSV file. Each tuple is one sale: region, product, units sold and unit price. Then we create a workbook, take the active sheet, name it Sales, and append the header row and the eight data rows. The openpyxl documentation shows this same pattern in its first example, with Workbook, the active sheet, append and save, so this is the standard way to start a file.

Nothing is saved yet. The workbook only exists in memory until we call wb.save, which is handy because it means a mistake halfway through costs nothing. The sheet now has nine rows: one header row and eight data rows.

This step is the whole point of using openpyxl instead of writing plain values. Any string that starts with = is stored as an Excel formula, not as text. We put =C2*D2 in the Revenue cell of each row, so Excel multiplies units by unit price when the file opens. Then we add a totals row with =SUM formulas for the units column and the revenue column.

The totals row lands on row 10, so the formulas read =SUM(C2:C9) and =SUM(E2:E9). Because total_row is computed from the length of SALES, the range stays right when the data grows.

A report that nobody wants to open is a report nobody reads. We give the header row a dark blue fill with white bold text, format the price and revenue columns as money with two decimals, set sensible column widths, freeze the header row and add an auto filter. Freezing the header means it stays visible while someone scrolls through hundreds of rows, and the filter lets them narrow the sheet to one region without touching the data.

Two details matter here. First, number formats are display settings, not values: the cell still holds 899.0, and Excel shows it as 899.00. Second, column widths are set in character units, so a width of 14 fits a money value like 11,890.50 with room to spare. A column that is too narrow shows ### in Excel, which is the classic sign of a report built without widths set.

pandas is the better tool for the arithmetic, and openpyxl is the better tool for the workbook. pandas can write a dataframe to .xlsx, but it writes values, not a finished report: no live formulas, no conditional formatting, no charts, no frozen panes and only basic styling. The pandas documentation states that pandas uses openpyxl as its engine for .xlsx files, so the two libraries are partners, not rivals. Our rule is simple: pandas computes the numbers, and openpyxl places them in a workbook that looks deliberate. Step 6 shows that split in action.

The Sales sheet is the detail. The Summary sheet is the answer. We create a second sheet, write one row per region, and use a SUMIF formula in each row so the totals stay live: =SUMIF(Sales!A2:A9, A2, Sales!E2:E9) adds up every revenue cell whose region matches the label in column A. A grand total row uses =SUM(B2:B5). Then we add conditional formatting that fills any regional total above 8,000 in light green, and a column chart of revenue by region.

Our run printed saved sales_report.xlsx, and the file is 7,979 bytes. The North and South totals clear 8,000, so those two cells get the green fill when the file opens. The chart is a native Excel chart, so it updates when the numbers change, which a pasted image never does.

Before trusting the file, we read it back with openpyxl and print what is actually stored. This step caught the single most important fact in this tutorial, so do not skip it.

openpyxl writes formulas but never calculates them, because it has no calculation engine. A normal load returns the formula text, which is why E2 reads back as =C2*D2. Loading with data_only=True asks for the cached result instead, and our file has never been opened in Excel, so no cached result exists and every formula cell returns None. Nothing is broken: the number simply has never been computed by anything yet. Open the file in Excel or LibreOffice once and save it, and data_only=True returns real numbers from then on. Until then, compute the values in Python when code needs them. Our check did exactly that and confirmed the numbers: a grand total of 29,647.98 and 201 units, which match the hand calculation from the start of this tutorial.

The same trap waits inside pandas. pandas reads .xlsx files through openpyxl, so a formula column arrives as empty values. We read our file with pandas 3.1.1 and the whole Revenue column came back as NaN, all nine rows of it. The fix is the same: compute the column in pandas with df["Revenue"] = df["Units"] * df["Unit price"], and treat the workbook as layout, not as a source of calculated values.

The last step puts the split from the earlier question into code. pandas groups the sales by region and sums the revenue, and those numbers should match the SUMIF formulas in the workbook exactly. There is one trap, and our first run walked straight into it: the totals row is a label row, not data, so groupby counted it as a fifth region called Total with 0 revenue. Filtering it out before the groupby fixes the result.

The pandas totals match the SUMIF formulas exactly: North 11,890.50, South 8,991.70, East 5,205.00 and West 3,560.78. Two independent calculations agreeing is a real check, not a feeling, and it is the check we would run before sending any report to a client.

First, read the sales rows from a real CSV file instead of a list, so next month means swapping one file, not editing code. Second, add one sheet per region with its own chart, using the same loop that built the Summary sheet. Third, put the month in the filename, like sales_report_2026_11.xlsx, and schedule the script to run on the first of each month, so the report builds itself while the team is still having coffee.
