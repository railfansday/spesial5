EveBox agent keys and browser sessions protect different evidence paths

Tanggal: 2026-11-23

EveBox gives analysts a server UI, an API, and agent-connected packet capture workflows for Suricata events. The convenience comes from several forms of access: a browser session, HTTP basic authentication, agent keys, and credentials for an Elasticsearch or OpenSearch backend.

Each path has a different purpose. Treating them as interchangeable can leave a capture agent unable to connect or, worse, expose an evidence path that the team thought was protected by UI authentication.

The EveBox server documentation states that first startup generates a self-signed TLS certificate and an admin user with a random password. The password is written to the startup log. The server can also be started with authentication and TLS disabled for testing.

Capture that first-start log before it rotates or disappears. Store the generated credential in the approved secret system and verify that the default account is still controlled. Test deployments should not reuse production data or expose the no-authentication mode beyond an isolated network.

Use a managed certificate when users or agents need reliable server identity. A self-signed certificate is acceptable only when trust is explicitly distributed and monitored.

The EveBox packet-capture documentation says agent keys are independent of the web interface's authentication.required setting. An agent must present a valid key even when browser authentication is disabled.

That separation is useful for automation, but it creates two inventories. Browser users need named accounts and session review. Agents need identities, key ownership, and revocation procedures. Do not assume that turning off browser authentication also disables ingestion.

Assign a distinct key to each agent. Record the server-side key name, the host that holds it, the data source, and the expected connection time. If an endpoint is rebuilt, revoke or replace its key as part of the change.

The EveBox API includes event data, packet capture, and file-download workflows. A generic analyst session may be suitable for reviewing alerts but not for downloading every stored PCAP. Define which accounts can read metadata, which can retrieve payloads, and which can export evidence.

Require authentication on the API where the deployment supports it. Put the server behind an authenticated reverse proxy only after confirming how the proxy forwards client addresses and authentication context. Keep the agent endpoint on a separate network path from analyst browsers where possible.

The server environment includes URLs and credentials for Elasticsearch or OpenSearch. Those credentials let EveBox read the event index. If EveBox is compromised, the backend credential may be available to the attacker even if the browser login remains protected.

Use a backend account with the smallest permissions needed for event search. Restrict its source addresses to the EveBox server. Rotate the credential separately from user accounts and agent keys.

Log agent connections, failed key attempts, PCAP downloads, and administrative changes. Alert when a new agent appears, when a key is used from an unexpected address, or when one account downloads an unusual volume of packet data.

Back up the server configuration and key inventory. Test restoration of the UI and an agent connection separately. A recovered UI that cannot accept evidence is only half of the service.

Where is the first-start admin password? Are browser authentication and TLS enabled? Which agent keys exist and who owns them? Can an analyst download every PCAP? Which backend account does EveBox use? Are agent and browser networks separated?

EveBox combines a human-facing console with machine-to-machine evidence ingestion. Secure each path according to the authority it grants.
