Why Direct Browser Thumbnail Uploads Fail: CORS, Private Buckets, and Presigned Limits

Tanggal: 2026-11-21

A direct browser thumbnail upload to private object storage can fail even when its presigned URL is valid, because the browser still enforces CORS and the uploaded image still needs authorized delivery.

Short answer: for large gaming media, presign one private upload only after verifying control of the bucket's browser policy; for small originals and resize jobs, accept the file on the backend and generate thumbnails there. A signature grants temporary access. It doesn't configure CORS, create a permanent public image URL, coordinate overwrites, or resize an image.

Infrai is one candidate for the signing boundary when an app wants one REST API whose backing vendor can change without forcing storage-specific calls through the codebase; that plain HTTP, self-describing surface needs no storage SDK. The limitation comes first, though — a browser flow is a bad fit wherever the team cannot establish the exact CORS policy it needs.

Test the authorization request and the byte transfer as separate operations. First, a trusted backend asks storage for a short-lived write grant scoped to a bucket and unique object key. Second, the browser sends the bytes to the returned URL without the platform API key. If a command-line upload works but the page does not, that result narrows the problem rather than contradicting itself: command-line clients do not enforce browser CORS.

The preflight is the important third actor. Before a cross-origin PUT, the browser may send OPTIONS with the page origin, intended method, and requested headers. Storage has to allow that combination. A valid signature cannot make a disallowed origin acceptable, and a broad Access-Control-Allow-Origin response cannot repair a bad signature. They are different gates.

This is where generic “CORS error” advice wastes time. A hypothetical 403 visible in the Network panel points toward signature scope, expiry, method, key encoding, or headers. A CORS rejection can prevent JavaScript from reading a useful response at all. Record the exact production origin and requested headers, then reproduce the preflight in a real browser; don't infer browser compatibility from a successful server-side request.

This storage workflow has a presign route, while the task's application boundary does not expose self-service CORS configuration as a dependable step for the browser team. That makes the decision crisp: use the signed upload only in an environment where the required policy is already established and verified. Otherwise proxy through the backend or choose a specialist whose CORS control is directly available to the team.

Private upload and private display are two authorizations. After the original lands, a trusted worker validates it, generates the required thumbnail sizes, and writes each output under a new key. The application database records which source and variants belong to the player. When the UI needs an image, the backend issues a signed read or proxies the response; there is no public or public-read ACL model here, and public_url remains null.

That is useful for player-created media awaiting moderation, account-bound screenshots, and unreleased game art. It is not suitable for a public image host, a static website, or a social asset that needs one permanent anonymous URL. Stick with a delivery product or direct object-store setup designed for public distribution in those cases.

Unique keys matter more than they first appear. Imagine two avatar tabs opened for the same account. Tab A uploads a square crop, tab B uploads a newer crop, and their processing jobs finish in reverse order. If both target players/42/avatar.png, the final object can represent the older selection. Strict If-Match conditional writes are unavailable, and object versioning or object lock cannot recover the overwritten value. Give every source a generated key such as players/42/uploads//source.png; let the database decide which upload is current; generate variants beneath that upload prefix; then move the player's logical pointer in one database transaction. Storage holds bytes. The database owns intent.

For small resize work, that rule often favors a backend upload. One original enters trusted code, validation happens once, and one worker creates all variants. Browser-generated variants appear to spare compute, but they spread image-library differences, retry state, and output validation across untrusted devices. For very large originals, direct upload earns its extra control-plane work by keeping those bytes away from application request handlers. The threshold isn't universal.

The server, not the browser, calls POST /v1/storage/object/presign/{bucket}/{key}. The example below contains both halves of the contract: a backend helper mints a 15-minute PUT ticket, and browser code sends the file to that ticket. It uses the documented operation and expiry fields, handles rate limits without a tight loop, and makes a retry identify the same signing operation.

The second request deliberately omits Authorization: Bearer . The signed URL carries its own temporary credential; forwarding the platform key crosses a security boundary for no benefit. The application should also choose the bucket and key, cap allowed size and content type before signing, and retain uploadId as the stable retry identity.

For very large files or unreliable networks, a multipart workflow can retry parts independently instead of restarting the whole object. AWS documents that model clearly. It also creates more state: the app must create the upload, track parts, complete successful sessions, and abort abandoned ones. Infrai does not supply an automatic cleanup rule for multipart fragments, so explicit cleanup belongs in the workload design. Thumbnail-sized files rarely justify it.

The comparison is not a price leaderboard. It asks who owns browser policy, whether private delivery matches the product, and how much provider-specific code the team accepts.

The platform's primary argument in this comparison is contract stability: swapping the vendor behind the capability does not change the application's REST call. Infrai also uses one key and one bill across supported backend capabilities, instead of another SDK credential and invoice for the team to maintain. I would try it for private, signed media when that narrow boundary matches. I would stay direct with AWS S3 for object lock or provider-native policy control, and choose a dedicated media delivery service for permanent public thumbnails and built-in transformations.

There are other boundaries to price into the decision. Lifecycle expiration has a one-day minimum, so it cannot express hour-level deletion. Object listing filters by prefix rather than searchable metadata, which makes the application database the right index. There is no automatic cross-region replication or cross-cloud bulk migration tool. These aren't footnotes; any one of them can outweigh integration simplicity for a regulated or globally replicated workload.

Collect source-size percentiles, bytes crossing the app tier, preflight rejection rate by origin, completed uploads, time to first usable thumbnail, resize CPU, writes per accepted image, signed reads, proxy or CDN egress, and abandoned multipart sessions. Keep failed preflights separate from failed signed writes. Otherwise one red “upload failed” counter hides the architectural decision you need to revisit.

Then compare two production-shaped paths for a week: backend upload plus server resize, and direct original upload plus asynchronous validation and resize. Include engineering time spent on CORS, credential rotation, retries, cleanup, and provider-specific code. Downstream delivery may dominate both. I'm not sure which line item wins for a particular game — a few huge source images can distort the average — so use p50, p95, and total bytes rather than a sample file on office Wi-Fi.

The ship-first rule is plain: start with backend-mediated uploads for small resize jobs; introduce direct presigned transfer only when large-object traffic is a measured app-tier burden and the browser policy is under control. That recommendation optimizes the operating system around storage, not one request price.
