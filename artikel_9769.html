Tanggal: 2026-11-20

Building RedLine: An Offline-First Mobile Experience for ERPNext Sales Representatives

Field sales teams rarely work in ideal network conditions.

Sales representatives visit customers, create orders, collect payments, check outstanding balances, and move between warehouses. They often work in areas where internet connectivity is unreliable or completely unavailable.

For an ERP system like ERPNext, this creates a practical challenge: how can field employees continue working without constantly depending on a live connection to the central server?

This was the problem we wanted to solve when building RedLine, an open-source Flutter mobile application designed specifically for ERPNext field sales operations.

In this article, I'll explain the architecture behind RedLine, the technology choices, the offline synchronization engine, and some of the engineering decisions we made to handle real-world business operations.

ERPNext provides a powerful business management platform, but field sales operations introduce requirements that are different from traditional desktop workflows.

Now imagine the representative loses internet connectivity halfway through the day.

A conventional mobile application that depends on API requests for every action becomes almost useless.

We wanted RedLine to provide a different experience.

The application should remain useful even when the server is unavailable.

This led us to adopt an offline-first architecture rather than simply adding caching to a traditional online application.

RedLine is an open-source mobile extension for ERPNext, developed by Red Tech For Technology.

It is built with Flutter and designed for field sales representatives and their managers.

The application integrates directly with ERPNext and provides a mobile interface for daily sales and field operations.

The interface currently supports Arabic (RTL) only. English (LTR) localization is not available yet.

We selected technologies that provide a balance between performance, reliability, and maintainability.

One important decision was to use Drift instead of relying entirely on in-memory state or temporary local storage.

Drift provides a structured SQLite-based persistence layer, which is essential when queued operations must survive application restarts.

This is probably the most important part of RedLine.

A common approach to offline support is to cache API responses and display them when the device loses connectivity.

However, this does not solve the problem of creating new transactions offline.

We needed a system capable of storing user actions locally and synchronizing them with ERPNext when connectivity returned.

Our architecture separates local operations from remote synchronization.

When a supported action is performed offline, the application stores the operation locally instead of immediately sending an HTTP request.

One lesson we learned is that detecting an active network connection is not the same as confirming that the ERPNext server is reachable.

A device might be connected to Wi-Fi while the server is down.

For this reason, RedLine combines connectivity monitoring with an actual server reachability check.

The synchronization engine does not start simply because the operating system reports an active network connection.

Queued operations are processed sequentially in chronological order.

This helps preserve the intended order of operations and makes synchronization behavior easier to track and debug.

Offline-first applications introduce an important challenge: not every business operation is safe to execute offline.

For example, consider two representatives attempting to sell the same inventory or a representative trying to collect a payment against an invoice whose balance has already changed.

If the application blindly accepts every financial transaction offline, it can create inconsistencies between the mobile application and ERPNext.

We therefore distinguish between operations that can safely be queued and operations that require immediate server validation.

Building RedLine taught us several important lessons about offline-first enterprise applications.

1. Network connectivity is not server availability.

A device can have internet access while the ERPNext server is unreachable. A real reachability check is necessary.

A reliable offline application needs persistent local data, an action queue, synchronization policies, and clear failure handling.

3. Not every operation should be available offline.

Financial integrity is more important than allowing every transaction to be created without connectivity.

Users should understand what is pending, what failed, and what has been synchronized.

5. Mobile workflows should be designed around actual users.

Field representatives need fast, simple interfaces. They should not have to navigate a full desktop ERP experience on a small screen.
