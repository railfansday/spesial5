Quoting from the article: > Package-based OSes generally provide the user with a large number of regularly updated software packages (many thousands) with complex dependencies, which are composed into a working OS on the final machine it is deployed on. Installations in this style tend to vary greatly from system to system. Even with an identical selection of packages for the target system, the installation/update order, the stateful update logic and the file system data structures generally mean that the bytes that hit the disk on each machine are always different. This is called drift. > Systems put together this way are hence not reproducible, not predictable, and hard to compare and analyze which is essential for tracking down security issues. The second paragraph does not logically follow from the first paragraph. It is just a complete non-sequitur, but the word "hence" suggests otherwise. Systems put together this way can be reproducible, predictable, easy to compare and analyze. Side note: with ASLR, in-memory layout is not predictable, but only very few people complain about that and image-based OS don't make ASLR predictable either. There also is little conceptual difference between a flattened view of layered file system images for an image-based OS or a pre-flattened file system image for a package-based OS, just the time of flattening differs. One could even make a case that creating a flattened view of multiple file system layers at runtime is less reproducible than having a pre-flattened file system which is identical on every boot (at least in the read-only case). OTOH, maybe the Amutable people really have a hard time comparing and analyzing systems with package-based OSes. In that case, maybe their own solution is the only one they can easily work with, and hey... it is valid to create a system they can understand. That's the beauty of FOSS. I just wish they wouldn't bash choices different from their own.

By the time you start an upgrade and by the time it's actually done globally, there very well could have been a package update that came in at the end which the beginning ones did not receive. Many times, it's immaterial, yes -- distributions have done a great job at versioning and keeping non-breaking changes out of versioned releases, but it's a variance nonetheless. Not only packages, but even config changes within a fleets config management system can flow changes into it that the first round didn't, as changes get picked up. Often we don't have the convenience of downtime when managing baremetal systems, which something like Kubernetes abstracted away, but something still has to run baremetal. Amutable's core idea itself is not new, image-based and immutable cores have been around for a long time. What I find most interesting about their approach is the comprehensive approach they are taking with it, from offering a control plane and verification across the entire stack. I've seen these ideas employed in production individually, but am interested to see where they take it when it's coming entirely from the ground up.

I am unsure if AOS does it like this, but what Lennart has always been working towards is that the UEFI verifies the kernel (UKI) using the public key, which then verifies the /usr/ partition (which is read-only), which then loads the rest. "the rest" here would be the factory reset part, which is the only really modifiable part (also EFI variables get reset).

So say the nation state enrolled some kinda public key into the mutable part of the system (/var/ or possibly /etc/ but it sounds like it is also read-only) so that the system now also loads some of their system extensions or so, a factory reset would basically wipe those keys (and the extensions). /usr/ can't be enrolled, since that is pinned by the verity root hash and changes in the data would cause errors during reading by the kernel and the UKI is "pinned" by you (or I guess in the case of Amutable them) signing new UKIs. This is assuming you can prevent the nation state from enrolling their keys in your UEFI. But even if they did enroll their own keys in the UEFI the PCR values would be different, resulting in the mutable LUKS partitions not being automatically unlocked, so your mutable data is still inaccessible.

So as long as the cryptography implementations are sound and not bypassed by some 0-days it should be sound for the most part. Unless they are able to get below the bootloader it should be fine (but at that point they don't even need your PIN).

Do tell me if I maybe missed some attack vector which could possibly still exploit something.

I have a project where I turn Debian packages into erofs layers as a performance hack, and the non-reproducibility of packages is a bit overstated.
