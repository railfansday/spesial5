A reconciliation-first approach to CDC into Redshift, and where GoldenGate and AWS DMS pipelines actually go wrong.

Cutover night. The row counts match to the last digit. Somebody posts a green checkmark in the channel and everyone goes to bed.

Three days later, finance asks why order totals for one region are off by a few thousand dollars. Nothing is down. Nothing alerted. The counts still match. That’s the problem.

The pattern is familiar to anyone who has moved a busy database onto a new platform. The pipeline gets built, the full load finishes, change data capture (CDC) hums along, and the team picks the one check that’s easy to run: count the rows. Counts catch missing data. They say nothing about data that arrived wrong, arrived twice, or never got its update.

This article is about the checks I’d automate before trusting either GoldenGate or AWS DMS to feed Redshift, and the lag arithmetic that tells you when the pipeline is falling behind.

Every number below comes from one worked example with made-up data: an Oracle ORDERS table of 480 million rows being replicated into Redshift. It is illustrative, not from a real system, and I flag it each time.

A matching count proves the pipeline didn’t lose or duplicate whole rows at one moment in time. It’s a useful first check, and I run it. But look at what it can’t see:

An update was lost or applied out of order

Counts drift, but only after enough deletes

A large text column was truncated in flight

An empty string became NULL (or the reverse)

Timestamps lost precision or shifted time zone

Five of those six defects leave the count untouched or only occasionally move it. If your exit criterion is “counts match,” you’ve certified the easiest thing to get right.

People compare GoldenGate and DMS on feature lists. I compare them on what happens when something goes wrong, because that’s where the weekends go. This is my rule of thumb, not a law. Check licensing and the current documentation for your versions before you decide.

Extract reads the redo, writes trail files

A task on a replication instance reads the source logs

Trail files absorb the backlog (size the disk)

Source logs must stay available until the task catches up

High-volume Oracle estates, strict ordering, long-lived replication

Whichever you choose, the target side looks the same, and that’s where most of this article lives.

I land every change as an append-only record with its operation, commit position and sequence. Then I apply only the latest change per key. Two reasons. First, retries and replays are harmless, because applying the same batch twice gives the same result. Second, Redshift doesn’t enforce primary keys. They’re informational, used by the planner, so the target will happily store duplicates and won’t tell you.

Deletes arrive as a change record, so the DELETE removes the old row and the INSERT skips it. Updates become delete-plus-insert, which suits a columnar store far better than row-by-row updates. In the worked example, 12 million changes a day split into 6.6 million inserts, 4.8 million updates and 0.6 million deletes (55%, 40% and 5%). Batching those is not optional.

Average lag is a comfortable lie. Here’s the arithmetic for the example. The table sees 12 million changes a day, about 139 a second on average and roughly 1,100 a second in the busiest hour (I assumed an 8x peak). Suppose the apply side can sustain 3,000 changes a second. That’s 2.7 times the peak. Healthy.

Now somebody runs a backfill that updates 40 million rows in an hour. That adds about 11,100 changes a second, for a total near 11,250 against capacity of 3,000. The surplus is 8,250 a second.

Using lag ≈ backlog ÷ apply rate as a rough estimate, a 5-minute target is breached after about 109 seconds, because the backlog passes 900,000 changes. By the end of the job the backlog is 29.7 million and lag peaks near 165 minutes. Draining it at the 2,861 a second of headroom takes another 173 minutes, so the pipeline is back to normal about 293 minutes after the job started.

A backfill that takes an hour at the source can cost you five hours of staleness downstream.

Two habits fix most of this. Alert when lag is rising for ten minutes, not when it crosses a line, so you hear about it early. And put source-side bulk jobs on a shared calendar, so the pipeline owner knows a surge is coming before the pager does. In DMS, watch the source and target latency metrics separately; they point to different bottlenecks (check the troubleshooting guide for your version).

The usual response to “counts aren’t enough” is to compare a random sample of rows. It feels rigorous. It isn’t, and the maths is short. If N is the table size, n the sample size and k the number of corrupted rows, the chance of catching at least one is about 1 − (1 − n/N)^k.

In the example, 480 million rows and 120 bad ones (0.000025% of the table). A 1-million-row sample finds at least one bad row 22% of the time. A 10-million-row sample finds one 92% of the time, and costs ten times as much. Checksums over the whole table find it every time, because every row is counted in some bucket.

The template I’d steal: each step has an action and a gate, and the gate is a number somebody can check. “Three clean reconciliation nights in a row” beats “looks good.” The T+7 row matters too. Keep the reverse path warm for a week, because mismatches that survive three clean nights tend to be the slow ones: month-end jobs, rare code paths, the table nobody remembered.

Counts are a smoke test. Land changes append-only and apply the latest per key. Watch the slope of lag and know your bulk jobs. Reconcile with bucketed checksums at a shared cut-off, and give every cutover step a gate that is a number.
