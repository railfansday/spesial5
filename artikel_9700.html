Terraform import does 1 thing: it ties a resource that already exists to an address in your Terraform state.

Use an import block. It has been in Terraform since 1.5 (June 2023), it shows up in terraform plan, and it goes through a pull request like any other change.

The fix is in the configuration: make the block match the real object until the plan shows only imports. Where an argument can never match, lifecycle { ignore_changes = [...] } tells Terraform to leave it alone.

One object in the console is often several resources in Terraform.

The S3 bucket is the classic case. Since version 4 of the AWS provider, a bucket's settings are separate resources:

Import the bucket alone and Terraform manages the bucket alone. The versioning setting stays unmanaged until you import aws_s3_bucket_versioning too (its ID is also the bucket name, for a bucket in your own account).

One bucket in the console, several resources in Terraform.

Unmanaged settings are where configuration drift hides.

Security groups have the same trap. Rules can live inline in aws_security_group or as separate rule resources, and the AWS docs warn against mixing the 2: "Doing so may cause rule conflicts, perpetual differences, and result in rules being overwritten."

Pick 1 style before you import. The AWS provider's docs call the separate aws_vpc_security_group_ingress_rule and aws_vpc_security_group_egress_rule resources the current best practice.

You imported the wrong object, or into the wrong address. Deleting the resource block alone is the wrong move: Terraform would plan to destroy the real object.

With an import block that has not been applied yet, there is nothing to undo. Delete the block.

The command line version is terraform state rm:

Delete the resource block and the import block in the same change. Leave the resource block and the next plan creates a second object. Leave the import block and the next plan imports the old one again.

HashiCorp recommends the removed block, for the same reason as with import: you get a preview. One exception: a removed block applies in every workspace that uses the configuration. If you imported into the wrong workspace, run terraform state rm in that workspace.

For a resource that is right but sits at the wrong address, use a moved block. It renames the address and touches nothing else.

The same file does opposite things on the 2 tools:

Terraform destroys the object. OpenTofu forgets it.

Always write destroy = false or destroy = true yourself.

Import blocks, for_each, identity and tofu plan -generate-config-out all work on OpenTofu, and tofu import takes the same arguments as the Terraform command.

A module that ships its own import blocks runs on Terraform 1.16 and later and fails on OpenTofu. Keep import blocks in the root module if you support both.

Moving between the 2 tools is its own project. Our Terraform to OpenTofu migration guide covers it.

An import is done when the plan shows only imports, and done properly when the next plan shows nothing.
