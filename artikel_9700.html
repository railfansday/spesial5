Mac mini as a server: 53 lessons learned while moving my AI jobs

Tanggal: 2026-11-22

Posted on Nov 22 • Originally published at marian.coach

Originally published at marian.coach. The full runbook with a check per step is in the public GitHub repo.

My Mac mini M6 with 32 GB arrived. I gave myself one day, with Claude Code doing the typing, to move all scheduled jobs off the MacBook.

By the evening I had logged 53 wrong assumptions, mine and Claude's. 33 of them apply to any Mac and are in the public repo, next to the runbook and the scripts. That list has grown to 37 since. The other 20 were about my own jobs. The 14 that hurt most are below.

The rule I ended the day with: cloud first, the Mac mini only for what the cloud can't run, and one job on one machine.

"My local notebook is freezing sometimes." I wrote that to Claude on 17 November, four days before the mini arrived.

I run a one-person business with scheduled AI jobs around it: a brief before each mentoring call, lead source traces, blog publishing, follow-up messages, SEO reports. The bigger picture is in how my AI executive assistant works. Until this week all of it ran on the MacBook I use for video calls.

The jobs run through a wrapper I call safe-run. Before a job starts, it checks if I'm on a call, if the laptop is on battery, if memory is low. If yes, the job waits and safe-run asks again 10 minutes later. Good for my calls, bad for the jobs. Some runs waited out their limit and were dropped.

Not all of that memory was the jobs. On day two I counted 24 open Claude sessions on the same laptop, and I can't split the swap between the two.

My Control Room dashboard showed it from the other side: in 25 days it recorded 495 runs that ended as "Mac asleep, offline or busy". On 17 November the overnight job that writes my outreach drafts crashed at 05:03 on a network timeout. The lid was closed.

Why a Mac mini AI server and not a Linux box? My jobs are launchd jobs, my browser profiles are macOS Chrome profiles, and my Claude Code skills expect the same paths as on the laptop. A second Mac meant zero rewrites.

Most Mac mini posts I read before buying start from the box: I Run 25 Automated Agents on a Mac Mini, or an M6 turned into an agent server that runs around the clock. They're right that a mini is cheap, quiet and fast. Where I disagree: they put the whole stack on it. A Mac at home is one power cut, one macOS restart or one Wi-Fi drop away from stopping all of it.

So I sorted the jobs before I moved one. A job runs where its data and its login live. Anything that only calls an API goes to the cloud.

Double sends are a state problem, not a machine problem. When the "already sent" ledger lives in a shared store with a key per message, a job can run on any machine, a restored backup or a cloned repo, and still send once. Mine still lives in gitignored files, so the senders are the last jobs to leave the box.

For a team the same sort works. The home box becomes an office Mac, a hosted Mac or a self-hosted runner. The jobs with no clean cloud home are the same two: logged-in browsers and the subscription CLI on local files.

Mentoring. Mac mini: intro-call briefs, session briefs and notes, the overnight session knowledge base, newsletter follow-ups, replies on syndicated posts, lead source traces. Cloud: the mentee evening digest and the newsletter send on Workers.

ELC community. Mac mini: logged-in browser jobs that send follow-ups, bounce reroute, reply watch, overnight outreach drafts, the work-email finder, the partner lead list, grant research. MacBook: manual sends and grant follow-ups.

ELC Conference. Mac mini: speaker invites from a logged-in browser.

Platform and SEO. Mac mini: Reddit and Quora answers, the Copilot citation pull, the login check for browser profiles, blog publishing, the fix queue, canaries for the senders. GitHub Actions: CRM sync to analytics, SEO reports, Bing stats, AI-crawler logs, a pipeline health check, the daily web brief. Workers: the reindex queue. Both Macs: the Chrome cleaner, the Claude login watch, the ledger mirror.

Personal ops. Mac mini: LinkedIn post drafts from yesterday's work, call follow-up drafts. GitHub Actions: the marketing board, daily and weekly. MacBook: meeting recordings, the memory jobs, the search index, the session snapshot.

I asked ChatGPT and Perplexity the same question in English, Czech and Polish: can I use Migration Assistant to set up a Mac mini server? Both said yes, in all three languages. Perplexity added in English that a clean setup "is often preferable". Neither mentioned scheduled jobs.

For a personal Mac, yes is the right answer. For a Mac that runs jobs, Migration Assistant copies the LaunchAgents and leaves their memory behind. Both Macs then send the same follow-up email to the same person.

Four rules, written before I touched the box.

My plists and scripts hard-code /Users/. The same short account name on both Macs means zero path edits.

I move jobs only with one script, move-job.sh. It stops the job on the laptop, copies its state, starts it on the mini. Then I check launchctl list on both Macs. A job on both, or on neither, is a failed move.

The send protection of my jobs is gitignored: 9.6 MB of state files, ledgers, "already sent" keys and kill switches. A fresh clone of the repos looks complete and writes again to people it already wrote to.

With ANTHROPIC_API_KEY in the environment, claude -p bills the API instead of the subscription, quietly. I found 6 jobs that loaded the key back from ~/.env after the wrapper removed it. The mini's ~/.env doesn't have the key at all.

Phase A takes 15 minutes at the mini with a keyboard. Phase B runs from the laptop over SSH, and Claude Code ran most of it for me. Each step is a command plus a check. The scripts and the full runbook are in the repo.

The server: the silver box between the speaker and the dock.

1. SSH key. Test that the name resolves first. My first ssh-copy-id hung with no error, because the name I typed didn't exist.

2. Secrets. Copy ~/.env without the Anthropic key:

3. Server settings. No sleep, restart after a power cut, wake on LAN:

4. Updates: download, don't install. In System Settings › General › Software Update › Automatic Updates, turn off "Install Security Responses and system files". With FileVault on, an unattended update restart stops all jobs.

5. Hardening. Firewall on with stealth mode, SSH with keys only, Spotlight off on the data volume. 10-root.sh in the repo does steps 3 to 5 with a check per line.

6. Toolchain. Command Line Tools, Homebrew, Node, Python with its certificates. Then make sure python3 is the one you installed:

7. Tailscale for access from anywhere, with no open ports. Sign in with a personal identity to a tailnet you own. Disable key expiry for the mini in the admin console, and put its 100.x IP in ~/.ssh/config.

8. GitHub and repos. gh auth login, then clone all repos to the same paths as on the laptop. Find them with no depth limit:

9. Claude Code login. Open Screen Sharing, run claude in a Terminal on the mini and /login there. Then test it with a LaunchAgent that asks Claude one question. That's the test that counts.

10. Remote Control (optional), to start a session on the mini from my phone. Trust the folder once in the GUI (claude, Yes, /exit), then run claude remote-control as a LaunchAgent with --capacity 2.

11. Chrome profiles. One profile per platform account, logged in fresh on the mini through each job's own --login command. Don't sign in to Chrome itself.

12. Move jobs in waves. Read-only jobs first, then browser jobs, then Claude Code jobs, senders last. Before each move, run the job's dry run on the mini with the environment its wrapper loads (set -a; . ~/.env; set +a). After each batch, check launchctl list on both Macs.

With FileVault on, a restart stops at the unlock screen and the jobs wait. On day one my mini restarted at about 14:15, cause unknown, and sat idle until I logged in at 14:20.

For planned restarts use sudo fdesetup authrestart, which comes back logged in. For the rest you choose: FileVault off with automatic login, or FileVault on and a watch on missing runs. I kept FileVault on.

To know it's alive I use my Control Room. It shows the last run of each job and which Mac ran it, and it flags "Ran on the wrong Mac". A login check opens each browser profile, and a watch warns me 10 days before a Claude login expires.

"all the 4 chrome windows are blank. no url opened." That was me at 15:49.

The fix: log in through each job's own --login command, and keep Chrome sync off in the job profiles.

claude auth status over SSH says "Not logged in", even after a login in the GUI. Over SSH the login Keychain is locked. A LaunchAgent runs in the logged-in GUI session, so its answer is the real one. The fix for SSH shells came on day two: the remote token, further down.

Check the result, not the summary. The toolchain script counted failures inside a subshell, so 14 failed npm installs still printed ALL PASS.

The same day, a git add across three repos with errors sent to /dev/null staged nothing and reported "nothing to commit". Now I check a push by asking git what is still unpushed: git rev-list --count @{u}..HEAD must say 0.

claude -p --chrome connects to the Chrome of my Claude account. With two Macs it found two browsers, couldn't ask which one, and stopped. Safe, nothing posted, but nothing done either. Each Mac now keeps its own Chrome device id in a local file, and the job picks that one or stops.

Just after midnight I asked Claude: "how many claude session do i have opended on his macbook vs mac mini?" The answer was 24 on the MacBook and 1 on the mini. 21 of them had been reopened together by my terminal's restore that afternoon.

I thought I was short on disk. I was short on memory. Moving the scheduled jobs fixed the nights. The days were still on the laptop, because an open Claude session is a job too.

The conversation stays on disk and claude --resume reopens it. So the cheap fix is to close what sits idle.

A session can also move to the mini: copy its conversation file over and resume it there. It carries the conversation, not your files, so push your work first. A local session can't move to the cloud.

There are two doors. From the Claude app or claude.ai/code I pick the mini as the environment, because Remote Control already runs there as a LaunchAgent. From the terminal, the plain form is one line that opens Claude on the mini in the folder I'm in:

Three things stay behind on the laptop: files you haven't pushed, your browser, and your screenshots and clipboard.

The plain form has a limit, and it took two fixes to get past it. The first is the token below. The second is the tmux setup after it, which is what I use now.

The terminal door hit the trap from above. Over SSH, claude -p answered "Not logged in · Please run /login", because SSH can't open the login Keychain. My scheduled jobs were fine: they run through launchd, and one of them had logged in at 18:19.

The quick fix is a long-lived token that only SSH shells use. Five steps, about three minutes. It gives you the model and nothing else: the mail, calendar and docs connectors and Artifacts stay missing, because their logins sit in the Keychain. For a quick question or a script over SSH, that's enough.

Two more traps on the way, both mine. I ran the pbpaste line while the clipboard still held that same line, so the token file contained the command. Then I pasted the one-time approval code as opposed to the token. The code goes into the terminal in step 1. The token is what comes out.

With the token in place I asked the next question: "when remote, is there any other disadvantage?" Claude tested a plain SSH session on the mini instead of guessing. The answer was longer than I hoped.

By the evening the biggest rows of the right column were fixed. A LaunchAgent now starts a tmux server with the desktop login on the mini. A session opened inside it inherits that login, so the Keychain opens. Tested the same day: the connectors and Artifacts loaded, and the session survived a dropped SSH connection.

My shortcut for a new session now opens it there by default. It warns me about uncommitted or unpushed changes in the folder, pulls on the mini when the copy there is clean, and reattaches to a session I left. A second shortcut keeps a session on the laptop. Both scripts and the LaunchAgent are in the repo.

I also tried the third place, a session in the cloud. It lost on three points: one GitHub repo per session, no local skills, and no local tool servers or hooks. So for jobs it's cloud first. For sessions the cloud isn't ready for how I work, and they run on the mini.

The split follows the same rule as the jobs: a session runs where its data and its login live.

Two machines means two copies of my Claude setup. On the morning of 22 November I asked Claude to update one skill on the mini too, and it turned out that nothing kept the two Macs in step. Each kind of install lives in a different place.

The drift after one day: 32 skills existed only on the laptop and 2 only on the mini. Both Macs had an uncommitted settings.json. The mini had one uncommitted edit that existed nowhere else.

Four manual steps per repo don't survive a busy week. So the same day I added one small sync job. It runs on both Macs at a 15-minute interval, for the config repo and the skills repo only:

If a rebase conflicts, the job undoes it, pushes nothing and alerts me. It doesn't guess. Plugins need no step, because Claude Code installs the enabled ones at its next start. The default model and effort setting travel the same way. Install something on either Mac and the other has it within about 15 minutes.

Two limits. The job is less than a day old, so I can't show its numbers yet. And it's for config and skills only. Job code doesn't travel this way: an automatic pull would put untested sender code on the mini within 15 minutes.

It's also an exception to "one job, one machine", on purpose: each Mac has to push its own changes. A job stays on one machine when it sends, posts or deploys. Guards and sync run on both.

256 GB works today. Chrome profiles, logs and node_modules grow, and a server with a full disk fails jobs in strange ways.

Wi-Fi was half a day of slow SSH, and the pre-boot unlock over SSH for FileVault needs Ethernet anyway.
