Selenium Explained: Browser Tests That Click Like a Real User

Tanggal: 2026-11-04

Posted on Nov 4 • Originally published at practicaldevblog.blogspot.com

Selenium is a tool for automating a real web browser. It opens Chrome, Firefox, or another browser, loads pages, clicks buttons, fills in forms, and checks what appears, exactly as a user would. That makes it the standard choice for end to end testing: tests that prove a whole web app works, from the login page to checkout, rather than testing one function in isolation.

The reason to drive a real browser is that many bugs only show up there. A button might look fine in code but be hidden behind another element on a small screen. A form might submit in a unit test but fail in the browser because a script loads late. Selenium catches those problems because it sees the page the way a user sees it, including layout, timing, and JavaScript behaviour.

Tests are usually written in Python, Java, C#, or JavaScript, using Selenium's WebDriver API. Here is a Python test that searches a site and checks the result. It uses an explicit wait, which is the single most important habit in Selenium testing.

The structure matters more than the search itself. The driver starts a real browser. driver.get loads the page. WebDriverWait then waits up to 10 seconds for the search box to appear, instead of assuming it is there instantly, which is how flaky tests are born. send_keys types into the box, Keys.RETURN presses Enter, and a second wait checks the new page title before the test declares success. The finally block guarantees driver.quit() runs even if a step fails, so a failed test does not leave a browser window open forever.

Locators are how Selenium finds elements, and choosing well saves pain later. Prefer a stable id or name when one exists, fall back to a clear CSS selector, and avoid long, brittle paths copied from browser tools that break the moment a designer rearranges a page. When a test fails, the first question should always be whether the locator still matches the page, not whether Selenium is broken.

Selenium trades speed for realism. Browser tests are slower and more fragile than unit tests: pages load at network speed, animations take time, and a small layout change can break a locator. Teams that write only browser tests end up with a slow, flaky suite. The healthy mix is a pyramid: many fast unit tests, fewer integration tests, and a small set of Selenium tests covering the journeys that matter most, like signup, login, and checkout.

If you are adding Selenium to a project, automate a single critical journey first, such as logging in and reaching the dashboard. Get that one test stable and running in your pipeline, then add the next journey. A small, trustworthy suite beats a large suite nobody believes.
