European businesses, particularly in the UK and Italy, face malware campaigns that exploit routine business correspondence. A recent Formbook (now also known as XLoader) campaign uses localized order and procurement lures to deliver an information stealer.

Manufacturing and technology companies are especially exposed because employees regularly handle purchase orders, supplier documents, and payment requests. A seemingly routine attachment can hide a JavaScript loader that ultimately deploys malware to steal browser-stored credentials.

The ANY.RUN team investigated the campaign, uncovering its infection chain, persistence methods, and links to other malware activity. These findings show how behavioral analysis and threat intelligence can help organizations strengthen their defenses.

The Formbook campaign relies on a familiar social engineering approach: making malicious attachments look like documents employees would normally receive as part of their work.

One of the analyzed archives, Nova narudžba 0148-712.zip, contains a JavaScript file with a Croatian/Bosnian title meaning “New Order”. Other related samples use themes involving price lists, procurement requests, quotations, and bank transfers.

The analyzed activity included submissions from the UK and Italy, alongside countries in the Balkans and South Caucasus. The language and themes of the lures indicate that attackers adapt their delivery materials to different markets rather than relying on a single generic document.

For EU-based organizations operating across multiple countries, this creates an additional detection challenge: security teams cannot assume that suspicious attachments will always use the company’s primary working language.

The archive was submitted to Interactive Sandbox multiple times starting October 7, 2026, and appeared as an email attachment on October 23. The investigation revealed a multi-stage infection chain involving obfuscated JavaScript, hidden PowerShell execution, encrypted payload delivery, and process injection.

The infection consists of four main stages.

The infection starts with Nova narudžba 0148-712.zip, which contains a JavaScript file with the same name.

Approximately 2 MB in size, the script is heavily obfuscated using obfuscator.io techniques. Most of its content consists of a Base64-encoded PowerShell payload, with additional string encryption and shuffled execution logic making static analysis more difficult.

The command includes: -ExecutionPolicy Bypass -NoProfile -WindowStyle Hidden -NonInteractive -NoLogo

These parameters hide the PowerShell window and bypass the default execution policy. The dropper also uses WMI to monitor the process and terminate it if it runs for more than 50 seconds.

For defenders, the combination of wscript.exe, hidden PowerShell execution, and randomly named scripts in temporary directories is worth investigating.

The dropped script acts as an AES loader, identified by the header PowerShell Modular AES Pipeline Loader.

It stores three Base64-encoded resources: the payload, encryption key, and initialization vector. After sanitizing and decoding them, the script uses AES-256-CBC to decrypt the next stage and executes it in memory through PowerShell’s ScriptBlock::Create() functionality.

The loader then clears its resource map and invokes garbage collection, reducing the artifacts available for disk-based analysis.

However, the infection is not completely fileless: the original JavaScript and intermediate PowerShell script remain useful sources of forensic evidence.

The decrypted PowerShell stage contains two components: a .NET injector named GHOST.dll and the final Formbook payload.

Protected with ConfuserEx, the injector uses process hollowing to execute Formbook inside the legitimate Windows process aspnet_compiler.exe.

A watchdog called Operate-Beacon checks every five seconds whether the process is running. If it is not, the loader reloads GHOST.dll and attempts injection again. ANY.RUN analysts observed 15 instances of aspnet_compiler.exe during the sandbox session.

Formbook subsequently moves into rekeywiz.exe, a legitimate Windows EFS-related utility. From there, it launches Firefox and creates a randomly named file in %TEMP%, consistent with the collection of browser databases before reading them.

The final payload is designed to steal browser-stored credentials and communicate with its command-and-control infrastructure.

Because the malware uses legitimate Windows processes as containers, defenders should examine parent processes, command-line arguments, execution context, and memory behavior rather than relying on process names alone.

The most useful detection strategy is to correlate these indicators rather than rely on a single filename or process.

For example, a PowerShell process is not inherently malicious. However, a hidden PowerShell instance launched by wscript.exe, executing a randomly named script from C:\Temp\, followed by repeated launches of aspnet_compiler.exe, provides a much stronger reason to investigate.

The same applies to persistence. A shortcut named SystemUpdate_ps_* masquerading as a system update service is considerably more suspicious when combined with the associated PowerShell execution pattern.
