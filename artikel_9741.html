this is my second progress update for the Decentralize AI Hackathon by HackerNoon and Nosana.

In my first article, I Built a Local AI Linux Assistant That Doesn't Rely on the Cloud, I introduced zkzkAgent: an AI agent that manages a Linux machine through plain language and runs entirely on my own hardware with Ollama.

That is still how it works by default. But running everything locally has a ceiling, and I kept hitting it.

To test the integration in real work, I switched to the 27B model on Nosana and gave zkzkAgent a task: create a new project called zkzk_ai, a calculator web app with a FastAPI backend and an HTML, CSS, and JavaScript frontend, and open it in VS Code.

The classifier sent the request to the planner (`NEEDS_PLANNING`). The planner wrote a 9-step plan, including the full content of every file, and then stopped and waited for me:

Once I approved the plan, the executor got to work. It made 10 tool calls, one at a time, across 10 graph iterations (with a maximum of 15).

Nothing complicated happens behind the scenes. The model running on Nosana picks a tool; that tool executes on my machine, and the result is sent back to the model.

Next, I asked: "Can you change the zkzk_ai Calculator to be zkzk?" The classifier sent this to the planner as well, which wrote a 7-step plan. After I approved it, the agent read static/index.html and then changed the name in three places: the page title and heading, the FastAPI app title, and the README. It did not touch the calculator logic.

I started the app with `uvicorn app:app`. The page loaded, and the calculator API answered:

Across both requests, every model call in the saved log, 18 in total, went to `inference.nosana.com` and returned `200 OK`. Every file write, command, and app launch happened locally.

I reviewed the code the agent wrote, and tested the backend directly:

- No eval. Expressions are parsed with Python's ast module, and only numbers, parentheses, and `+ - * / // % **` are allowed. When I sent __import__("os"), it was rejected with "Unsupported expression element: Call".

- Clear errors. Division by zero and complex results (such as (-1)**0.5) return a readable message instead of crashing.

- Input limits. Expressions are capped at 500 characters in both the browser and the API.

- Keyboard support. Enter evaluates, Backspace deletes, Esc clears and `^` types a power.

The code is on GitHub at [zkzkGamal/calculator], and the full run log is in the [zkzkAgent repo]

My first article was about an agent that doesn't rely on the cloud. This update doesn't change that. It adds a choice. Private or sensitive work stays on local Ollama, where nothing leaves the machine. Heavy planning can use a much larger model on Nosana's network instead of a centralized provider. In both modes, the tools, the files, and the final yes stay with me.

1. A real benchmark. Run the same five tasks on the local 2B model and on the 27B model on Nosana, and measure success rate, tool calls, time, tokens, and cost. Numbers instead of impressions.

2. Hybrid routing. Because the graph has separate nodes, each node can use its own model. The classifier and chat replies are short and could stay on a small local model, while the planner and executor use Nosana. Plain conversations would then never leave the machine.

3. Automatic fallback. If Nosana can't be reached, switch to local Ollama automatically, the same way the agent already turns Wi-Fi back on by itself.

4. Close the safety gaps. Enforce plan-level confirmations. Also put `run_command` behind a confirmation or an allow-list: today it can run any shell command, and with a remote model choosing the arguments, that matters more than before.

5. Fix the calculator bug with the agent doing the fix.
