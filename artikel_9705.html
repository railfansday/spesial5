Google picked a festival in Rio as the canonical for a rave in Buenos Aires

Tanggal: 2026-11-22

events.lat lists concerts, festivals and shows across Latin America in English, Spanish and Portuguese. It's a React SPA. At build time a script writes a static HTML "shell" for every public route (title, description, canonical, hreflang, JSON-LD, and a plain-HTML version of the page body), so crawlers get real content without running JavaScript. Any route without a shell falls back to the SPA's root index.html.

Under "Why pages aren't indexed", one row stood out:

Duplicate, Google chose different canonical than user: 1,640 pages.

About 97% of the examples were event pages, in all three languages. One of them was a rave in Buenos Aires that ran on 14 November. URL Inspection said Google had picked, as its canonical, the page of a musical in Rio de Janeiro. The two pages have no artist, city, country or date in common.

The shell builder only wrote shells for upcoming events:

The day after an event, its URL had no shell, so the host served the fallback: the homepage's HTML, with the homepage's title and . Every past event looked exactly like every other past event. Google clustered them and picked one page from the cluster to stand for the rest.

The numbers on the day I looked: 4,549 approved events in the past and 2,990 upcoming. Most of the event URLs Google knew about were already serving the homepage.

The same fallback was hiding in three more places:

Running events count as upcoming. One filter change:

Ended events get a shell of their own, marked noindex, follow. The page isn't worth ranking, but it isn't a duplicate of the homepage either. It has its own title, its own canonical, a line saying the event is over, and a list of what's coming up in the same city, so the links still pass somewhere useful:

The React side says the same thing. If the static HTML says noindex and the hydrated app says nothing, Google sees two versions of the page. EventDetail now sets noindex, follow for past events, matching the shell.

Small venues got the same treatment: a noindex, follow shell with the venue's name, its upcoming events (or "no upcoming events right now") and the rest of the city's calendar. And the threshold is now one exported constant used by the sitemap, the shell builder and the React page:

The build now writes 27,777 shells instead of 24,459: 4,415 ended events and 1,117 venues, each in three languages.

A smaller row, "Duplicate without user-selected canonical", had 74 pages. All ten examples were event IDs that no longer exist (deleted or rejected listings). They'd been serving the fallback too, with a 200 status. A fix that sets noindex on the "event not found" screen had gone live a day earlier, after Search Console's last data refresh. I loaded one in a browser to confirm, and left them for the next crawl.

"Validate fix" is running in Search Console as of 21 November. I don't know the result yet, and I'm not going to guess at one.
