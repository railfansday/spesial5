On 16 November I published an article about blocking the obvious ways a key reaches an AI coding agent. The first comment asked whether I had thought about putting blocked attempts on the conversation's timeline, with the agent's task and without the secret.

agentwhy already does that. The article gave it one sentence. So this is the start of a series: each week, one part of agentwhy, looked at closely. Part 1 is the view that answers that comment: what your AI and its helpers did, step by step.

All the screenshots are from the demo, a made-up project.

You asked Claude Code: "Find out why the AI chat stopped answering." It worked for six minutes. The report's first screen answers in three lines.

The helper's task matters most to me. In my own incident in September, the rule in AGENTS.md never reached the helper. The helper only had its task, and the task asked for the secret. Here you can see the task that was handed down, word for word.

The Step by step tab is the same conversation as a list, in the order it happened. Each stretch starts with what your AI wrote, then one row per step: what it read, what it ran, what it changed. Your AI's model sits above the list, as Claude Code recorded it: claude-opus-5-5.

The MCP tool. Your AI called search_issues on a Sentry MCP server. That server works outside the record, so agentwhy can't see which files it opened, and the row says so. It quotes the tool's own description, so you know what it was for.

The stopped attempt. "Tried to open customers.csv. A rule in your settings stopped it." In my setup a read refused by a deny rule fired no hook, so nothing in your hooks or logs would show it. It is still in the saved conversation, and that is where agentwhy reads it from.

It read assistant.ts, then tried .env. A rule stopped it. So the helper did go for the key, as its task asked, and the block held. Without this view you would only know that .env was not read. With it you know who tried, and why.

Two switches help on a long conversation: Every step or Only private, to hide the rows that touched nothing private. And every row with a private file has What happened, which opens that file's own story.

Claude Code saves every conversation as a file on your computer, and each helper's work in a file of its own. agentwhy reads those files, matches each helper's file to the task that started it, and puts them back in order. It runs on your computer, nothing leaves it, and any secret value is replaced before the page is built. It also works on conversations from before you installed it.

"Where it comes from" says agentwhy matches each helper's file to the task that started it. Here are two parts of that work, with the code. Every path below is in the public repository.

toolUseId is the id of the Agent call that started the helper. That is the whole join. A helper started another way, for example by a skill, has no toolUseId. In one session I found three of them. agentwhy reads the field as it is and never fills it in:

src/adapter/claude-code/events/delegation-index.ts

The core matches that callId to the Agent call with the same id. Where the ids do not pair one to one, it marks the link unresolved instead of choosing:

Why not by time? A helper can keep working after its call returns. In the session where I first measured the format, 6 of the 15 Agent calls returned at once, and the helper's report came later. A line's timestamp can also be earlier than the line before it. So agentwhy joins nothing by time. A link with no id is marked unresolved, and the delegation stays in the report.

In the demo, Helper 1 asked for .env by name, so the record names the file. A command does not have to. A loop, a glob or a script can print a file's lines without naming it. In one of my own test projects, a report said Only saw a name over a file that nl -ba had printed.

agentwhy runs on the computer that holds the file, so it can check the output against it. Once per run it hashes the lines of every text file in the project. A line is a file's own when it has at least 20 characters, three letters in a row, and no other file in the project holds it. Only a private file keeps its hashes:

Each hash is SHA-256 over a salt, the word text and the line. The salt is a new random UUID for every run:

The hashes stay in memory. No line, hash or count of a file reaches a page, the chat or a store.

Then each line of a call's output, as the model got it, is hashed the same way, after the line numbers of Read, cat -n, nl or a search's path:12: are stripped. Two of a file's lines in one output are a read of that file. So is its only line, where it has one:

The limits. Only the project's own private files count, not ~/.ssh. A file over 512 KB is skipped, and so is every file once a project passes 20,000 files or 32 MB of text. Only whole lines match: a line cut short, encoded, or reprinted by a script (python3 printing a CSV's rows as dicts) does not. One line from a file with several is not enough, and a file changed since no longer matches. So this is second evidence. It adds a read and never takes one away.

When I built it, I compared the reports before and after on 286 of my own conversations: 185 in five test projects, 101 in agentwhy's own repository. Seven changed, each a read the command reader had missed. Nothing else changed.

Run it in your project folder. It opens a page with your conversations from the last 7 days. Open one, then How it went, then Step by step. Or click through the demo first.
