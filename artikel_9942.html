Pointer Provenance in Rust vs C++

Tanggal: 2026-11-13

I’ve been exploring Rust, and one topic that got me intrigued is pointer provenance, particularly because it’s not easy to visualize.

To get a feel for vtables, what I wanted was to look at the actual memory, to see what it really looked like and prove that I could in fact call these functions through their respective function pointers. With provenance, I wanted to take it apart the same way, but it turns out it’s not so straightforward. This only got me more intrigued, so let’s see what we can find!

My first time hearing about provenance, I wondered, why hadn’t I heard about it before? It seems so crucial, yet a bit of an obscure concept.

The question is, how does it know that int* p doesn’t point to the same memory address where x lives (meaning that opaque(p) could end up modifying x)?

The compiler assumes p can’t equal &x because p wasn’t derived from x.

When I first heard about this, I thought it was a bit of a strange concept. What does it mean that something is derived from something?

I mean, if pointers were just numbers (memory addresses), p could theoretically happen to hold the same memory address as x’s allocation on the stack. Good thing they’re not just numbers!

This brings us to the core of provenance. That “derived from” relation is provenance: for every pointer, the compiler keeps track of which allocation it belongs to and may, therefore, touch.

I tried to find a way to print this mysterious provenance, but it turns out that it’s purely a compiler abstraction. It does not exist as an actual data field stored alongside the memory address. (There are exceptions though: feel free to look up the CHERI architecture to go down another rabbit hole).

So what can we do to inspect it? If the compiler knows about it then it must exist somewhere. If so, there must be a way to see it.

This is how I learned about LLVM IR (intermediate representation), which is essentially a low-level programming language that acts as a bridge between high-level languages (like Rust, C++, etc) and machine code.

What the compiler does is to conceptually construct a DAG (directed acyclic graph), to answer the question of where a pointer comes from and whether two pointers can touch the same memory.

If the root origins don’t match, LLVM can guarantee that writing through %0 will never alter the value stored at %2.

There is so much more to explore here that it’s hard not to get carried away because it’s truly fascinating. However, my original goal was to compare how C++ and Rust handle this, so let’s continue.

If we were to cast &x to an integer, then LLVM must assume that anyone could rebuild a pointer to x from that integer.

The result is that the compiler gives up the optimization:

That’s a pity if we only wanted to read the address and never intended to cast it back to a pointer. Wouldn’t it be nice if we could communicate this intent to the compiler?

This is exactly what Rust provides with its powerful provenance APIs.

p.addr() extracts the raw memory address integer while telling Rust’s abstract machine:

Still, we can benefit from using the more expressive API, and not relying on exposure semantics. It gives the compiler room to optimize in the future, and, by telling Miri explicitly what we mean, it can better help us catch bugs.

In lock-free data structures, we sometimes need to store status flags in the lower unused bits of a pointer. It’s a very cool trick, which left me with my eyes wide open for a minute when I first read about it. I talk more about it in this post. Essentially, due to alignment, the lower bits of pointers are “wasted” (always 0), so we can use them to store flags.

What we can do is work with an intermediate pointer value, which will have the flag bit set BUT that also inherits provenance from the original pointer. This is exactly the functionality that with_addr provides us. After we’re done, we can recreate our valid initial pointer.

The tagged value is stays a pointer rather than ‘usize’ because an integer is just a number and can’t carry provenance.

Keep in mind that tagged isn’t dereferenceable, given that p.addr() | 1 is misaligned for u32. Dereferencing it would be UB.

Actually, the reason that it runs is also interesting. What happens is similar to the C++ example. p as usize exposes the provenance of p, and since the reconstructed pointer points to the same allocation, provenance is recovered.

Provenance would be lost if we did some pointer arithmetic and landed in a different allocation.

To see what happens when provenance is not exposed, we can use ptr::without_provenance, which creates a bare address with no allocation behind it. (It’s useful for dangling or sentinel pointers, but it can’t be dereferenced).

As expected, Miri complains about a dangling pointer and tells us explicitly that it has no provenance.

Provenance, in short, is a hidden piece of information tracking “which allocation” a pointer originates from, which LLVM uses for optimizations.

In C++, uintptr_t casts force the optimizer to prepare for the worst case by disabling some optimizations.

In Rust, addr(), with_addr() and without_provenance() let you state your intent explicitly: you only want the number, or you are deriving a new pointer from an existing one. In principle, that gives the compiler room to optimize more aggressively. In our experiment, however, the Rust version is unoptimized too: x was still reloaded from the stack. Using more expressive APIs is still valuable though, as Miri can enforce the rules and catch bugs that stem from unintended usage.
