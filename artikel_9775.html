Most clusters I've worked on have at least one pod with an AWS access key or a GCP service-account JSON key sitting in a Kubernetes Secret. Someone minted it, someone copied it in, and nobody is sure when it last rotated.

Clouds providers have had a better answer for years. AWS has AssumeRoleWithWebIdentity and GCP has Workload Identity Federation. The workload presents a JWT from an issuer the cloud trusts and gets back credentials that expire in minutes. The catch is the setup.

Now multiply that by namespaces, clusters and accounts. I tried Terraform first. It's a poor fit here because the inputs (ServiceAccounts) are created by app teams at deploy time, not by the platform pipeline. And the drift I care about, like someone editing a trust policy in the console, happens outside any pipeline. The cluster already knows which workloads exist, so I made the cluster reconcile everything else.

Myceliam is a Kubernetes operator that makes the federated path the easy one.

Kubernetes trusts its own ServiceAccount tokens. IDPs (Identiy providers) Keycloak, Auth0, and SPIRE each issue JWTs they're willing to vouch for. Public clouds like AWS and GCP will happily accept a federated token — from an identity provider they've already been told to trust. Each of those three systems already knows how to trust something. None of them know about each other by default.

Myceliam is named after mycelium, the hidden underground fungal network that connects separate organisms and lets them trade nutrients. In the same way, Myceliam is a Kubernetes operator that weaves identity threads between clusters, identity providers and clouds. It watches namespace and ServiceAccount events and creates the matching resources in IdPs and cloud IAM on demand, so workloads can exchange short-lived credentials to access cloud resources.

The core idea is a fixed mapping from Kubernetes constructs to identity-provider and cloud constructs. Everything is derived from names, so the operator never needs a database:

No per-namespace container; one shared Resource Server per cloud, --

IAM OIDC provider per account, keyed by issuer URL

WLI provider -- in a shared pool

ClientIDList entry + one tagged trust-policy statement per role

workloadIdentityUser binding on each target SA

Myceliam operator supports SPIFFE, Keycloak and Auth0 for IdPs, AWS and GCP for cloud providers.

The user-facing interface is deliberately small: labels on a ServiceAccount, plus a namespaced CRD per cloud that lists which roles or service accounts the namespace may federate into.

A label alone is not enough. A single AutoidpAllowlist object (myceliam-system/default) lists the namespaces the operator may provision. If it doesn't exist, every namespace is allowed, so a first install works with zero config. Once it exists, only listed namespaces get new provisioning, and removing a namespace from it never blocks cleanup of what's already there. Who can write that one object, controlled with ordinary RBAC, is the real security boundary. Without it, anyone who can create a ServiceAccount could trigger provisioning in an external IdP and cloud account.

Trust, not authorization. The operator registers issuers and writes trust statements. It never attaches a permissions policy or grants an IAM role. If a role or GCP service account listed in a profile doesn't exist yet, the operator creates it with no permissions, as long as MYCELIAM_AUTO_CREATE_PRINCIPAL is true (the default). Auto-creation exists because AWS won't create a role with an empty trust policy, so pre-provisioning meant hand-writing exactly the statement the operator writes anyway. Teams that want to own role creation can set the flag to false, and a missing principal then fails that ServiceAccount's reconcile with a terminal error instead. GCP's default compute service accounts can't be created this way, so those must already exist. Either way, the operator's own credentials need permission to create roles and service accounts. Keeping the operator out of "what can this identity do" limits its blast radius to "who can assume what".

No per-SA role selection inside a profile. Every ServiceAccount that references a profile gets the same targets. If you need finer access, you split the profile. That keeps the CRD trivial to read in a code review.

An issuer in the middle, not just the cluster's own. Every Kubernetes cluster already runs an OIDC issuer for its ServiceAccount tokens, and you can register it directly with AWS and GCP. That works, but the cluster signs every namespace's tokens with one key set, and every cluster's issuer has to be registered in every target cloud account, which grows into a mesh. Putting a Keycloak realm per namespace, an Auth0 tenant or a SPIRE trust domain in between gives per-namespace signing keys (with Keycloak) and turns the mesh into hub and spoke: the clouds trust a handful of issuers instead of every cluster.

From there, the operator takes over — and keeps taking over, on a timer, not just once:

That reconcile loop is the part that matters most. The CRDs aren't a setup script you run once — they're the desired state, continuously enforced. Someone rotates a client secret by hand in the Keycloak console, or edits a trust policy directly in the AWS console? The next reconcile (default: every 300 seconds) puts it back. There's no drift to notice three weeks later during an audit.

The detail worth sitting with: Myceliam is only in steps one and two. It never proxies, mints, or even sees the workload's actual cloud credentials — once the trust is registered, the workload talks to the identity provider and to AWS directly, and asks for its own short-lived token at request time. The operator's job stops at making sure that handshake can happen.

The operator needs admin access to Keycloak or Auth0 and credentials in every cloud account. It would be ironic to solve that with a static key, but there's a real chicken-and-egg problem.

The operator is written in Go on controller-runtime, with one reconciler each for ServiceAccounts, Namespaces, the two AccessProfile CRDs, credential Secrets and the allowlist. Four pieces of plumbing ended up mattering more than I expected.

1. Retryable vs. terminal errors. Every call to Keycloak, Auth0, IAM or GCP can fail in one of two ways. A missing config or a malformed label is permanent: retrying won't fix it. A 503 or "client not created yet" is temporary. I defined two error types, operr.Permanent and operr.Temporary (which carries its own retry delay), and translate them into a ctrl.Result in one place:

2. Finalizers. Without a finalizer, a deleted ServiceAccount is gone before you can clean up its Keycloak client and trust statements. ServiceAccounts, Namespaces and both AccessProfile CRDs get myceliam.io/finalizer, and cleanup runs before it's removed.

3. Knowing what changed. If someone removes the aws-access-profile label, the operator has to remove that SA's trust statements. But a reconcile only sees the current object, not the previous one. So after each successful reconcile, the operator stores the last-applied state in an annotation. It's scoped to the four fields that matter, so unrelated label changes don't churn it:

4. Periodic resync. Drift on the IdP or cloud side produces no Kubernetes event. Every successful reconcile requeues itself after MYCELIAM_RECONCILE_INTERVAL_SECONDS (default 300), so a trust policy edited in the console or a secret rotated by hand in Keycloak gets put back within five minutes.

Keycloak and Auth0 model the world very differently, so I pushed the differences behind one interface. This is trimmed from the real one:

tenantID is a neutral stand-in for "whatever this IdP isolates a namespace with". The odd return value on EnsureAccessScope exists because of an AWS behavior covered below.

Each namespace gets a realm, and each ServiceAccount gets a client whose client_id is forced to the SA name. Keycloak always sets azp to the client_id, so every token's azp claim reliably names the ServiceAccount. I didn't need a custom mapper for that, and it turned out to be the most useful property in the whole system.

Cloud audiences come from client scopes. The operator creates one scope per (cloud, SA), named -, with an audience mapper, and attaches it as an optional scope. The name doesn't need the namespace in it, because a realm already is one namespace.

Auth0 has one tenant per deployment, assigns its own opaque client_id, and Resource Servers (APIs) aren't something you want one of per ServiceAccount. So the Auth0 provider uses one shared Resource Server per (cloud, cluster, namespace), and the per-SA Client Grants are what actually scope access.

That leaves a problem: nothing in an Auth0 token says which ServiceAccount it belongs to. The fix is a tenant-wide Action on the credentials-exchange trigger that copies values the operator stores in each Application's metadata into the token:

The operator manages the Action like any other resource. It creates it if missing, compares the deployed code to the embedded script on every reconcile, and re-deploys if they differ. The aws.amazon.com/tags block looks odd here, and the AWS section explains it.

For client-type: signedjwt, the workload authenticates with private_key_jwt (RFC 7523) instead of a shared secret. If a kubernetes.io/tls secret already exists (for example from cert-manager), the operator reads tls.crt. Otherwise it generates an RSA keypair and a self-signed cert. Either way it pushes the public key to the IdP, and an edited tls.crt is re-uploaded on the next reconcile.

Two details cost me time. First, Keycloak takes a JWKS, but Auth0's credentials endpoint takes a raw PEM and assigns its own kid (an RFC 7638 thumbprint). The interface therefore returns actualKid, and callers persist that rather than the value they computed. Second, I write client_id and kid to a separate -metadata secret so the TLS secret stays a pure kubernetes.io/tls secret that cert-manager is happy to own.

Registering the IdP is a get-or-create on the IAM OIDC provider, followed by adding whichever ClientIDList entries are missing. The interesting part is the role trust policy.

A role may already trust ec2.amazonaws.com, or another namespace's workload. The operator must touch only its own statement. I model just enough of the policy document to find statements by Sid, and I derive the Sid deterministically, because IAM only allows alphanumerics there and namespaces and SPIFFE IDs are full of hyphens and slashes:

upsertStatement replaces the matching Sid in place, or appends it, and returns false if nothing changed, so no write happens.

Bug I shipped: that "nothing changed" check used reflect.DeepEqual against the decoded existing policy. A JSON array decoded into any comes back as []any, but I was building conditions as []string. They never compared equal, so every reconcile rewrote every trust policy. The fix was to build the statement with []any throughout. It's an easy bug to miss because everything still works. It just isn't idempotent.

This one cost the most debugging time. When a token carries an azp claim, AssumeRoleWithWebIdentity checks the OIDC provider's ClientIDList against azp, not aud. Inside the trust policy, the :aud condition key also resolves to azp's value. I confirmed live that this happens even when aud is a single string. Get it wrong and you get a bare InvalidIdentityToken or AccessDenied with no hint, even when the signature, issuer and thumbprint are all correct.

Keycloak and Auth0 client-credentials tokens always carry azp. SPIRE JWT-SVIDs never do. So the operator writes an OR-match on :aud that accepts either shape. For Auth0 and SPIFFE it also adds a separate identity condition, because the namespace-shared audience doesn't prove which ServiceAccount is calling:

With no azp, AWS falls back to aud and refuses a token with more than one audience (Token audience contains more than one audience while authorized party is not present). GCP would accept one combined token, but AWS won't. A SPIFFE workload that needs both clouds therefore fetches two single-audience JWT-SVIDs. A Keycloak token could safely carry both audiences, because azp is always there, but all three example apps fetch one token per cloud so they work the same way.

A condition on :myceliam_service_account never matched, even though the claim was in the JWT with exactly the right value. :sub and :aud conditions on the same token worked. My best explanation is that AWS only exposes claims listed in the provider's discovery document (claims_supported), and a claim injected at runtime never appears there.

The workaround is AWS session tags. The Action writes the same values into the reserved https://aws.amazon.com/tags claim. The trust policy then matches aws:RequestTag/myceliam_service_account and grants sts:TagSession alongside sts:AssumeRoleWithWebIdentity. I verified it in both directions: a matching value succeeds, a mismatched one fails, and a Deny keyed on the tag really blocks calls. Two traps here:

Auth0's iss is https://{domain}/ with a trailing slash. The IAM OIDC provider URL must match exactly, and AWS doesn't normalize it.

My first version gave each Keycloak ServiceAccount its own AWS audience (aws--), a namespace-wide one for GCP, and a third convention for Auth0. Three schemes for one concept were hard to reason about and harder to explain. Audiences are now always --: shared by every SA in the namespace, and never shared across clouds or clusters, because both are part of the string. That only works because the audience is no longer what proves identity. On AWS, the per-SA check is azp folded into :aud for Keycloak, the session-tag condition for Auth0, and sub for SPIFFE. On GCP it's google.subject plus the per-principal binding.

Every SA adds a statement to each role it targets. A popular role eventually hits the trust-policy size quota (LimitExceeded: Cannot exceed quota for ACLSizePerRole). The operator doesn't prune stale statements yet. That's next on my list.

I call the IAM REST API directly rather than using the Go SDK, mainly to avoid Application Default Credentials. The operator already has its own short-lived GCP token and just uses it as a bearer token.

Each GCP project gets one shared Workload Identity Pool, and each namespace gets one provider per identity source inside it. Provider IDs must be 4–32 lowercase characters, and the cluster ID is part of the name, so truncation needs care:

If SPIRE already issues identities, there's no IdP object to create. The operator only registers the SPIRE issuer with AWS and GCP and uses sub, the full SPIFFE ID such as spiffe://example.org/ns/payments/sa/checkout, as the identity claim. It's the simplest path in the codebase and the best illustration of the operator's actual job: it doesn't issue identity, it makes existing identity legible to the clouds.

The operator is out of the picture once trust exists. It never proxies, mints or sees cloud credentials. The workload gets a token from its IdP and exchanges it directly. On AWS, no ambient credentials are needed for the STS call:

The repo has two small example apps, one OIDC and one SPIFFE, that do exactly this and list real S3 and GCS buckets. I used them as my end-to-end smoke test after every change.

This is early-stage software. Known gaps: no automatic pruning of stale trust-policy statements, no expiry-based rotation for operator-generated signed-JWT keypairs (rotation happens only when tls.crt changes), single-instance operation only, and SPIRE must already be installed. Cloud providers are still parallel packages rather than an interface like the IdP side. Tightening that is the prerequisite for adding Azure and OCI.
