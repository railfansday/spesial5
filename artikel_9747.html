Charge only when it is delivered: hold-then-capture balances in Laravel

Tanggal: 2026-11-18

If you sell something that may or may not be delivered, charging up front and refunding later works, but it is ugly. We run an SMS verification service, and a number that never receives its code used to leave two lines in the customer's history: a purchase and, minutes later, a refund. The money came back, but customers still saw "deductions" for things they never got and asked why they were charged.

So we switched to authorize, then capture: buying a number only puts the price on hold, and the charge happens when the code arrives. This post shows the pattern in Laravel with a ledger-based wallet. It is small, but there are a few traps.

What the customer can spend is balance - held_balance. Each order remembers its own hold:

The nullable held_amount matters: orders created before the change were charged up front, and they must keep the old refund behaviour. Never migrate money semantics in place.

All three lock the user row, so two parallel purchases can't both pass the balance check.

capture() goes through the same post() that writes every ledger entry, so it inherits the idempotency key check. That is the most important line in the whole feature (see below).

Every other debit, such as rentals or add-ons, must now check balance - held_balance instead of balance. Otherwise a customer with $1 can hold $0.70 for a number and still spend the full $1 elsewhere.

1. Parallel pollers. Our SMS poller can run twice for the same order. Both see "first code arrived" and both call capture(). Because the capture uses the order's purchase key (order:{uuid}), the second call finds the existing ledger entry and returns it before touching the balance. So the hold is released once and the customer is charged once. Without the idempotency key you would double-charge.

2. The catch must be broad. The supplier loop throws a business exception when no number is available, but a timeout or a bug throws something else. If you only release the hold on your own exception, an unexpected error leaves money frozen forever. Catch Throwable, release, rethrow.

3. Filtered messages are not codes. We keep SMS that fail validation (wrong app, no code) for the admin, but they must not trigger the capture. Only count delivered messages.

4. Moving an order between users. Our admins can move a number to another account. With holds, you move the hold (hold on the new owner first, so it can fail cleanly, then release on the old one), not a charge.

5. Show the hold. If the balance doesn't drop, customers try to buy more and hit "not enough balance". We show "$0.70 on hold" under the balance, and the API's get_balance returns balance (spendable) and on_hold.

Customers now see one deduction per code they received, and nothing at all for numbers that never got one. The ledger stays append-only and still adds up to the balance.

Disclosure: I work on receive-smss.net, a virtual number service for SMS verification, where this change shipped. The code above is simplified from our implementation.
