Why Base64 Breaks After Copy-Paste: Escaped \n, Line Wraps, Data URI Prefixes and Glued Chunks

Tanggal: 2026-11-14

Disclosure: I built the free Base64 Decoder on base64decodetool.com that I use for the checks in this post.

A Base64 string decodes fine in one service. Then someone copies it out of a log, a raw JSON body or a ticket, and it suddenly throws Invalid character or Incorrect padding. Sometimes it's worse: it decodes "successfully" into garbage. The string usually wasn't corrupted in transit. The copy-paste added or removed characters.

This post covers the four cases I see most and gives you one rule to check before you start guessing.

Every 4 Base64 characters carry 3 bytes (4 × 6 bits = 24 bits). After you remove whitespace and trailing =, a valid string has this many characters:

4n + 1 is never valid. One leftover character holds only 6 bits, which isn't enough for a byte. If you count 4n + 1, something was added or cut off.

The fix is to decode the JSON first (JSON.parse, json.loads, jq -r) and then decode the Base64. A real newline is harmless. The literal two characters \n are not.

This variant is nastier. Take a 69-byte illustrative sentence. Its Base64 has no padding (92 chars, a multiple of 4). Wrap it with an escaped Windows line ending, \r\n, and two stray letters, r and n, survive. 92 + 2 = 94 = 4n + 2, which is a valid length. The decoder pads it and returns 70 bytes. The text is correct up to illust, then turns into junk. My decoder doesn't throw here. It shows its amber notice instead: "Output contains replacement characters. Please select Hex or Binary if processing binary data." In a script, you'd get no warning at all. That's why you should compare the decoded size (or a hash) with what the sender reports.

1. The data: prefix. data:application/json;base64,eyJv... isn't Base64. In Python, the letters of the prefix count as data, so I got number of data characters (125) cannot be 1 more than a multiple of 4. Strip everything up to ;base64, first. My decoder does this automatically.

2. Glued chunks. Two separately encoded pieces joined together, such as SGk= + SGk= → SGk=SGk=, put an = in the middle. Both atob and Python reject it. Decode each chunk separately and join the bytes, not the strings.

3. Mixed alphabets. A Base64URL string (- and _) pasted into a strict standard decoder fails. My decoder maps - → + and _ → / on every input, whether or not URL-Safe Format is switched on. That's convenient, but it means it won't warn you that someone mixed the two alphabets.

Count the characters before you guess. 4n + 1 means something was added or removed. Unescape JSON before you decode, strip data: prefixes, decode glued chunks separately, and check the decoded size, because some corruption decodes without any error.
