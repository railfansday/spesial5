Conceptual recovery view. The lab stores accepted input and row results and derives the outcome; recovery-owner tracking is not implemented. Catalog data is fictional; the code and process-exit tests ran locally.

When a customer asks whether to upload a failed import again, the worker's health check cannot tell support what already changed. A retry count cannot answer that question either. The useful evidence is the accepted input, the committed work and the outcome derived from those records.

Here is a runnable catalog importer that makes those questions inspectable. The supplier and product data are fictional. The local implementation and failure tests were executed with Python 3.13.3 and SQLite 3.49.2; they are not a customer deployment or a distributed-system benchmark.

The lab uses one supplier's catalog in one disposable SQLite file. It deliberately keeps the catalog update and the completed-row result in the same database. There is no queue or external inventory API.

The ack field is a printed illustration of where acknowledgment would occur. It does not acknowledge a message to a real broker.

The imports table stores the caller's import ID, the original file bytes, their SHA-256 hash and the expected row count. Acceptance commits separately before processing begins, so an accepted import can exist with no completed rows.

The ID belongs to one exact delivery payload. Reuse it for a redelivery of those bytes. A corrected file needs a distinct ID; changing even whitespace under the existing ID is rejected by the code. The altered-input test changes a price from 1299 to 1300 cents, confirms a nonzero exit containing different bytes, and checks that prior records are unchanged.

Validation happens before acceptance. The payload must be a nonempty array; each row must have exactly sku, name and price_cents. Names and SKUs must contain non-whitespace text, prices must be nonnegative integers, and the file cannot contain duplicate SKUs. This makes row position a usable work identity within this immutable file. It is not a general identity for a product across future imports.

The stored bytes are immutable by application contract. This code does not prevent an administrator from directly altering the database.

Each row is identified by (import_id, row_number), enforced as the primary key of completed_rows. The worker starts BEGIN IMMEDIATE before checking whether that row is complete.

If a result already exists, it skips the catalog write. Otherwise, it upserts the product and inserts the completed-row record, including the resulting SKU, name and price, within that transaction. Commit makes both changes visible together. The exception handler rolls back before propagating an ordinary failure; the full code below preserves that handler and the replay check.

This implementation uses SQLite's single-writer behavior for coordination. SQLite's transaction documentation explains that BEGIN IMMEDIATE starts a write transaction immediately and can fail if another writer is active. The connection waits up to 15 seconds for a lock. That is bounded waiting, not unlimited recovery or a throughput claim.

In the duplicate-worker test, two fresh worker processes target the same import and local database. A third connection holds a write transaction while the test checks that both workers are still running. After releasing it, both workers complete. Audit triggers count exactly two catalog writes for the two input rows.

That observation is narrower than claiming the workers can run all their writes in parallel: SQLite serializes them. Longer contention can still fail.

The importer counts completed rows and compares that count with the accepted row count. It prints complete only when those counts agree. There is no independent success flag that can get ahead of row processing.

The captured catalog contains SUP-101, Steel bottle, at 1299 cents and SUP-202, Canvas bag, at 850 cents. Each has a completed-row result with the corresponding values. Support can inspect the records without relying on a process that may have disappeared:

The completed result describes what that import committed. A later import with a different ID can update the same SKU, so an older result is not proof of the catalog's current value. This lab does not solve ordering between different imports or prevent an older delivery under a different ID from overwriting newer data.

The tests launch real Python subprocesses and use os._exit at two explicit failure points. Each retry runs in a fresh process against the same temporary database. These are abrupt process exits, not operating-system crashes or power-loss tests.

Before the first row commits, the process exits with code 71. The accepted import remains, but the catalog and completed-row tables both contain zero rows. A fresh retry completes both rows. Support's next action follows from that saved state: resume the accepted import using the same ID and bytes.

After the first row commits, the process exits with code 72 before printing the acknowledgment. There is no stdout, but one catalog row and one completed result survive. The retry reaches two completed rows, and an audit trigger observes zero updates to the already committed row. Missing acknowledgment therefore does not mean no work committed.

Run the supplied suite to exercise these cases safely; it creates isolated temporary databases. The crash flags are test hooks, not operating instructions for valuable data.

The catalog write and result share one local transaction. A remote inventory update cannot join it. If a remote request succeeds and its response is lost, a missing local result does not establish whether repeating that request is safe. That boundary needs the provider's idempotency contract and a reconciliation process, with an owner for unresolved outcomes.

For broader background, Anjana Fernando's Practical Transaction Handling in Microservice Architecture, published November 30, 2020, discusses the move from local to distributed transactions. The local tests here do not validate that broader architecture.

This lab has not tested SQS, PostgreSQL, multiple hosts, network filesystems or machine power failure. synchronous=FULL requests SQLite's commit synchronization; it is not protection against every storage failure. Production ingestion, access controls, migrations and monitoring are omitted. No end-to-end exactly-once guarantee follows from these tests.

A recovery screen built on these records could show the accepted identity, which rows committed, and which remain. A conflicting payload should remain a conflict. An uncertain remote action should remain unresolved. Neither should become a green success badge merely because another worker started.

My guide to background jobs that survive a worker restart develops the broader restart-design questions. The complete local implementation and its tests follow here so this example can be inspected without an external repository.
