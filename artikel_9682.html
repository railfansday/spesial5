How I Made a 400-Page Storefront Load in Under a Second

Tanggal: 2026-11-12

I run a small e-commerce storefront — an online vape shop in Dubai with about 170 products, 37 categories, and 420 URLs in the sitemap. It is built with Next.js 16, Supabase, and Cloudinary, and it runs on the Vercel free plan, which means every deployment and every CPU second counts. Here is what actually moved the needle on speed, and what did not.

Before the change, a product page took 1.3–1.6 seconds just to show the product name, 2.1–2.3 seconds for the buy box, and 4–5.3 seconds total on a slow connection, at 364KB. The page was server-rendered on every visit: product data, reviews, and related products all fetched per request. On a free plan, that is both slow and expensive.

The single biggest win was generateStaticParams on the product and category pages. All 405 static pages now build in about 32 seconds, and a visit serves a pre-rendered page. Measured after the change: product name and buy box arrive with the first byte, TTFB 0.58–0.69s, total 0.79–0.91s, 246KB. Same content, same URLs — the work just moved from request time to build time.

Pre-rendering creates a second problem: when an admin edits a price, the stale page keeps serving. The fix was per-item cache tags — every loader tags exactly what it returns (product-, category-), and every admin save revalidates only the tags it touched, plus the page path. Changing one product's price refreshes that product's page and the category cards showing it, and nothing else.

One bug worth naming: the original code called revalidateTag after the return statement in three admin upsert functions, so it was dead code and admin edits never invalidated anything. The fix was moving the calls before the return. If your admin edits seem to "not take effect", check for code after a return before blaming the cache.

The checkout reserves stock before creating the order: a live read plus a conditional update on stock_qty (three retries per item), so two simultaneous orders cannot sell the same last unit. Over-ordering returns a 409 with a plain message. Cancelling or deleting an order restores exactly the reserved stock. When stock hits zero, the revalidation above flips the product page to "Out of Stock" on its own.

Product reviews used to load after the product. Loading them in parallel with the product (one Promise.all) cut a waterfall. New customer reviews are inserted with is_approved = false and only appear publicly after an admin approves them; the product's average rating is recomputed from approved reviews only. Nothing about this is clever — it is just doing the obvious thing in the right order.

The homepage is the slowest page on the site (426KB of HTML, 94 images) and the only real lever is cutting content — which the shop owner will not do, because the content is the SEO. The honest answer was to leave it alone and say so, rather than burn the free-plan budget on marginal gains. Not every slow page has a fix you are allowed to ship.

The live site is POD Shop, and the Juul range I used as the test case is at podshopdubai.com/category/juul. Same stack, same content — just faster, because the work happens at build time instead of on every visit.
