A support email lands: "Order NW-47790, the tent poles snapped on the first night, I paid $389 and I want every cent back today or I'm disputing the charge."

To act on that, your code needs answers to a handful of small questions. Is it a refund request? How urgent is it? Should a person handle it? What's the order number? How much money is involved? It's the same problem whether you're sorting a support inbox or building a custom chatbot that has to work out what each customer is asking for.

The usual move is to send the whole email to a chat model with a prompt that ends "respond in JSON", then validate whatever comes back. It works, but you're paying a model built to write essays to fill in five fields, and you're parsing its guess at a schema.

System One models are built for exactly this kind of job. In this tutorial we'll build a small support inbox pipeline with two of them: Jev from TypeSafe makes the decisions, and Clairic from Cloudflare reads the values. Plain TypeScript then turns their answers into an action. No prompt engineering for output formats, and no JSON repair.

The name comes from Daniel Kahneman's Thinking, Fast and Slow. System 1 is the fast, intuitive kind of thinking you use to read a face or a sign. System 2 is the slow, deliberate kind you use for long division.

A System One model is an AI model that understands natural language but doesn't generate text. You give it some input (the state) and a set of typed questions, and it gives back typed answers with probabilities. There's no free text to parse, because the model can only answer in the shape you asked for.

That's different from asking a chat model for structured output. SitePoint's guide to LLM structured output with JSON Schema shows how to constrain a chat model and validate its JSON with Zod. With a System One model, the type is the interface: a yes/no question comes back as a probability, a pick-one question comes back as one of your options, and a date comes back as a date.

Jev and Clairic are both System One models, but they do different jobs, and that's what makes them a good pair.

Jev can't hand you an order number, and Clairic has no way to pick from a list of options or answer yes or no. Give each one the job it's built for.

Every email went where it should. The whole run used 2,703 input tokens on Jev and 2,292 on Clairic, about US$0.0003 in total. At that rate, 10,000 support emails would cost roughly US$0.70.

The interesting part of the run wasn't the right answers. It was the two wrong ones.

"From last Monday." The run used 2 November 2026 as the reference date, which is a Monday. "Last Monday" means 26 October, but Clairic answered 2026-11-02, the reference date itself. Its confidence on that answer was 0.54, compared with 0.99 or higher on almost every other value in the run.

"A couple of weeks ago." Clairic turned this into 2026-10-19, which is a fair reading but still a guess. Its confidence was 0.43.

Neither date changed any action, because the rules only trust values at 0.9 or above. That's the habit to build: a value under your bar counts as unknown. A chat model returning JSON would have handed you "2026-11-02" with the same certainty as everything else.

One more catch: Clairic copied the order number as #NW-48213, hash included, because that's how the customer wrote it. Text values are spans of the input, so normalising them is your code's job. That's one line of code.

System One models handle the reading and the routing. They don't hold a conversation. Once an email is routed, something still has to write the reply, ask a follow-up question, or explain a returns policy in the customer's own words. That's where a chat model earns its cost.

The split that works is: System One models decide, code applies the rules, and a chat model only gets the cases where words matter.
