Stop Letting a Backup Job Starve Your Database: Practical cgroup v2 I/O Control on Linux

Tanggal: 2026-11-05

The backup window opens at 01:00. By 01:05 the database's p99 query latency has gone from 4 ms to 90 ms, and the on-call alert fires. The backup is not corrupt, not slow, and not even using much CPU. It is simply writing 400 MB/s to the same NVMe device the database lives on, and the database is now waiting in the block layer.

The usual first response is ionice -c3. It doesn't work, and it hasn't worked for years on most systems. The second response is a cgroup v2 io.max limit, which does work, but only if you understand what it does and does not throttle.

This is a practical tour of the io controller: what the three knobs actually do, how to wire them to systemd, how to prove the limit is being enforced, and the traps that make people conclude "cgroups don't work" when they do.

ionice sets an I/O priority on a process with ioprio_set(2). Whether that priority means anything depends entirely on the block scheduler:

CFQ, the scheduler that made ionice famous, was removed in Linux 5.0. If your disk is running mq-deadline or none, passing -c3 records a value and nothing reads it.

Even where BFQ is in use, ioprio is proportional, not a ceiling. A backup at idle priority will still consume every spare IOPS the database isn't using, and on a fast device "spare IOPS" is enough to ruin tail latency.

If io is missing from cgroup.controllers, the kernel was built without CONFIG_BLK_CGROUP and none of this applies. If it is present but not in cgroup.subtree_control, the controller is not delegated to children yet.

Also check the device, not the partition. systemd.resource-control(5) is explicit that these settings should reference "the originating, physical device", not a partition or loop device.

Resource control needs a boundary. Putting the limit on the backup service works, but a slice is better: everything the job spawns (restic, rclone, a shell pipeline) inherits the same budget, and you can raise the limit later without editing the service.

io.stat is a live per-device counter for the cgroup:

Read it before and after a run. wbytes divided by wall-clock seconds should land near your cap, not far above it. On a fast NVMe without a limit, a restic run will show write throughput in the hundreds of MB/s; with the cap it should flatten out.

Buffered writes lie to you. dd without oflag=direct or conv=fsync reports the speed of copying into page cache, which is memory speed, not disk speed. It will happily report 3 GB/s while the cgroup is capped at 100 MB/s, because the bytes have not reached the device yet. Always test with direct=1 or force writeback.

Cgroup writeback needs filesystem support. The kernel attributes writeback to a cgroup only on ext2, ext4, btrfs, f2fs, and xfs. On other filesystems, writeback I/O is charged to the root cgroup, so a limit on your backup slice will not catch data the page cache flushes later. Check findmnt -no FSTYPE /srv before trusting the numbers.

io.weight is inert more often than people think. It defaults to 100 and ranges from 1 to 10,000, but proportional control is provided by iocost or BFQ. On a stock system running none or mq-deadline, weights can be set and read back while changing nothing. Confirm the mechanism is live:

io.latency only compares siblings. It is work-conserving: when everyone meets their target, nothing is throttled. When one group misses, its peers with higher targets get queue-depth throttling and artificial delays. Set it on the groups that compete at the same level, not on a single child three levels down.

io.latency is blind without debug stats. The missed and total fields only appear when blkcg_debug_stats is enabled, and they are off by default. Without them, you are tuning a controller you cannot observe.

Network filesystems are out of scope. There is no block device to throttle. io.max on an NFS-backed backup directory does nothing.

%util on NVMe is not a saturation signal. It pins at 100% while the device still has headroom. Watch await and r_await from iostat -x 1, or io.pressure, which reports actual stall time.

A hard cap is the right answer when you know the budget. When you don't, invert the problem: tell the kernel what latency the database needs, and let it throttle whoever gets in the way.

Now when db.slice misses 25 ms, backup.slice is throttled until it recovers. When the database is idle, the backup runs at full speed. No static budget, no wasted capacity.

Two caveats: this needs CONFIG_BLK_CGROUP_IOLATENCY, and the target must be achievable. Setting 1 ms on a device that cannot deliver it means permanent throttling of everything else and no benefit to anyone. Measure first, then set the target slightly above the latency you see under normal load.

Most hosts want io.max on the known offenders (backups, container image pulls, log shipping) and io.latency on the workload that must stay responsive. Weights are the nicest model and the easiest to misconfigure.

max in every field means the limit is gone. That is the check to run after every change, in both directions: the file is the configuration, and it never lies about what the kernel is enforcing.

If a backup job is degrading your database, the fix is a budget, not a priority. Give the job a slice, give the slice a ceiling, and verify the ceiling in io.max — the rest is tuning.
