Ship it reversible: designing the undo layer an agent's irreversible actions need

Tanggal: 2026-11-14

The worst minute of operating an assistant was not a hallucination. It was a cheerful confirmation: "Done — I cancelled the appointment and sent the shop a note explaining why."

The appointment was gone. The note was in a stranger's inbox. Neither of those is a state I can put back. There is no ctrl+z for a message someone has already read, and no version of "cancel" that returns the slot the shop had already re-let.

I build an assistant that runs errands in the real world: forms, checkouts, bookings, cancellations, mail. Every design review I have with myself ends up in the same place. The interesting question is not can the agent do it. It is what does it cost to take it back, and who gets to find out.

We talk about "safe actions" as if safety lived in the API call. It does not. The same delete is a non-event on a draft and a catastrophe on the only copy of a tax document. Four things decide the class, and only one of them is in the code:

The classification takes ten minutes and changes the architecture. The agent stops treating "done" as one word.

Reversibility is not a boolean you find; it is something you manufacture. Five dials, in the order I reach for them.

1. Delay. Put the effect in a queue with a countdown instead of executing it. Forty seconds is enough for the person to read the confirmation line and say stop, and cheap enough that nothing else in the system notices. A delay is only honest if the countdown is visible and the item can still be withdrawn at second 39.

2. Snapshot. Before any destructive write, read the current value and store it with the effect record — not the new value, the old one. prior_state is the single field that turns most R-class mistakes into a non-event, and it is the field everybody forgets, because the happy path never reads it.

3. Stage. Split the action into a state that nobody minds and a promotion that everybody minds. A draft in the same mailbox the send would use; a preview URL that renders exactly the live page; a status='staged' row that a human or a second check promotes. Two-phase publish costs one extra state and one extra write, and it is the difference between "I posted the wrong thing" and "I staged the wrong thing".

4. Trash instead of delete. Delete sets deleted_at and hides the row; a nightly job removes it after thirty days. A tombstone is also a correct answer to "did this exist?" — which matters more than people expect when a later step needs to prove it acted on the right record.

5. Compensate. When none of the above applies, define the inverse explicitly and treat it as a first-class effect with its own record, its own approval and its own failure modes. A refund is not the absence of a charge.

Most real errands need two or three of these at once: a charge with a snapshot of the prior balance, behind a delay, with a refund path defined before the charge is allowed.

An "undo" button is a view over a record. If the record is thin, the button lies. Minimum shape:

Three of these fields do the real work. window_until makes the undo promise finite and therefore checkable. observed_by records the moment the effect stopped being private — the earliest point at which the inverse changes meaning. supersedes is the fence: an undo that arrives after the target has moved on is not an undo, it is a new decision.

Without status, an undo that failed looks identical to one that succeeded, and the next attempt is a guess.

This was the insight that changed how I set delays. The technical send is a write; the human event is delivery. Between those two is a variable-size gap I can use.

Practical rule: the hold window must end before any second party could plausibly observe the effect. For mail, that is a matter of seconds once it leaves your provider. For a booking, it is the moment the shop's calendar re-let the slot. For a public post, it is the first crawl or the first read. For a phone call, it is the first word spoken — which is why I treat outbound calls as X-class by default and require a person to be the one who places them.

A confirmation dialog is the cheapest possible reversibility, and the weakest: it moves the cost to the person's attention, once per action, forever. Downgrading the action removes the risk structurally. The table I keep, roughly:

Note the last row. When a site has no draft, the reversible substitute is a read-back: extract what will be submitted, compare it to what was intended, and only then press the button. It is not an undo, but it catches the majority of wrong-field errors before they become X-class.

This is where I see the most confident mistakes. An inverse is a new effect with its own consequences:

So compensation follows the same gate as any other C-class action: it needs its terms stated, a window, and — for anything a stranger will read — a drafted text that a human releases. An automated apology is how a small slip becomes a public incident.

The inverse is a tool call, so it inherits every tool-call problem: unknown outcomes, retries, duplicates. Three tests catch almost all of it.

Twice. Undo must be idempotent against its own record. status moves applied → undone once; the second call reads undone and returns it instead of running the inverse again. Without this, an undo that timed out and was retried re-books the slot that the first undo already released.

Late. After window_until, the inverse is refused and the refusal is reported, not silently downgraded. A promise you cannot keep is worse than a promise you never made; the person is planning around the sentence you printed.

After the world moved. Compare the target's current state to prior_state. If it differs in the fields the inverse assumes — the row was edited, the slot was re-let, the person replied — the undo is superseded, and the right output is a question, not an action. This is the same fence that stops a stale background job from writing, applied to the reverse direction.

I also test the dependency case, which is the one that hits hardest: effect A was undone while effect B was derived from it. A calendar invite derived from a cancelled booking, a receipt derived from a refunded charge. The rule I settled on is that derived effects carry the id of their cause, and undoing a cause marks its dependants orphaned for review rather than deleting them. An orphan list is a queue of questions; a silent cascade is a second incident.

Test 7 is the one that turns a demo into an operating system. Most undo buttons I have used are only tested for the happy path, so the interesting states — half-undone, compensation failed, orphaned dependants — are exactly the states nobody has ever seen.

Reversibility is a promise made in the interface, so it has to be legible before the decision:

And the agent should be able to say the uncomfortable sentence: "I already did the part that cannot be undone; here is what I can still do." That sentence is more useful than any success message, and it is the sentence an agent can only produce if the record told the truth about observed_by.

If the X-class undo rate is above zero, the fix is upstream: downgrade the action so it stops being X-class. Undo exists to cover the residual, not to make irreversible actions acceptable.

None of this makes an agent trustworthy. It makes its mistakes priced in advance — and it means the one action nobody can take back is the one the agent was never allowed to take quietly.
