Load Balancing Starts Before the Load Balancer: Routing Patterns for Distributed Systems

Tanggal: 2026-11-07

This is the third in my series on control plane architecture and design patterns. See the first article on a high-level overview of control planes here, and the second on the scaling component here.

I ended my last piece on scaling with a promise to come back to hot partitions, i.e., the situation where a single piece of your system is hit with disproportionate traffic no matter how well the rest of your infrastructure is provisioned. That problem lives squarely in load balancing and routing, which is what I want to dig into here.

The thing that surprised me most when I actually started building these systems is how little "load balancing" has to do with load balancers, once you get past the simplest cases. A load balancer is one tool for solving a routing problem. It's not the only one, and for a lot of distributed systems, it's not even the primary one.

For a basic web application, load balancing is close to what most people picture:

For stateless, interchangeable backends, this gets you most of the way there. Any healthy instance can serve any request, so the algorithm mostly just needs to avoid overloading any single one.

This is also where most teams' mental model of "load balancing" stops. It's worth pushing past that, because the moment your backend isn't stateless and interchangeable, this model stops being sufficient.

A distributed database doesn't have interchangeable backends. Each host owns specific partitions of data, and a request for a given key has to go to the host that actually holds it (or a replica of it). You can't round-robin your way out of that.  The routing decision is now coupled to where the data lives, which is a placement problem, not a traffic-distribution problem.

This is where load balancing stops being about the request path and starts being about the partitioning and placement strategy decided when data is written, long before any request shows up.

When a new table or dataset is created in a system like Cassandra, the control plane decides how its partitions get distributed and replicated across the fleet. Get that placement strategy wrong, and no amount of clever request routing fixes it later. You've already baked an imbalance into where the data lives.

Even a well-designed placement strategy runs into a specific failure mode: hot partitions. This happens when traffic to specific keys is wildly uneven, usually because of a poorly chosen partition key (a timestamp, a low-cardinality value, a celebrity user ID) that concentrates requests onto one partition regardless of how evenly the data was distributed.

The uncomfortable part is that this isn't something you can fully prevent through upfront design. Traffic patterns shift, applications evolve, and a key that was fine at launch can become a hotspot a year later. Detecting and correcting for it has to be an ongoing, automated function of the control plane, not a one-time decision.

Systems like DynamoDB build this kind of adaptive re-partitioning directly into their control plane, specifically so that a single misbehaving key doesn't require manual intervention every time it happens.

Databases are the clearest illustration of placement-time routing, but the same problem, and largely the same solutions, show up anywhere a system shards state across a fleet. Two examples worth knowing well, because they each stress the pattern in a different direction.

A distributed cache like Redis Cluster or Memcached with consistent hashing looks superficially like the database case: keys are hashed to determine which shard owns them, and requests get routed accordingly. But caches diverge from databases in one important way that reshapes the whole routing problem - cache misses are cheap enough to tolerate, but hot keys are far more common and far more punishing.

Because caches sit in front of a slower system of record, a single viral key (a trending post, a flash-sale product, a piece of session data for a suddenly-popular event) can spike orders of magnitude above normal traffic in seconds, not the gradual drift you'd see with a hot database partition. A few things follow from that:

The routing decision for a cache miss is still a placement problem, i.e., determination of which shard owns this key. The operational fix for a hot key, however, usually lives one layer up from the routing logic itself, in how aggressively you can avoid sending duplicate requests downstream in the first place.

Systems like Kafka consumer groups or Flink jobs route by partition, much like a sharded database. A message with a given key is deterministically assigned to a partition, and a specific consumer or task instance owns that partition for processing.

But the load balancing constraint here is different in a way that matters: ordering guarantees typically require that all messages for a given key are processed by the same partition, in order, which means you can't rebalance a hot partition by simply splitting it the way you might with a database.
