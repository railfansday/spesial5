From a security point of view, was fetching an unused dependency a potential attack vector? (like changing global state even without calling exported functions or using global data).

I don't know Rust enough to be sure but I don't think so. It only affect the package manager and not the compiler.

There is a risk in Cargo from unused dependencies - Cargo has a build graph based on the declared dependencies in Cargo.toml, and chooses what build steps to run based on that graph. One thing a crate can contain is a build script - which is code that's built and run on the build host at the time of compilation, and can do anything that code running as part of the build system can do.

In theory, an unused dependency can contain a build.rs that's got a security-relevant bug in it; that would then cause a security issue on the build host if you built the unused dependency. Removing it means that's not a problem :-)

First and most important: Safety is cultural. Rust's safety culture uses Rust's safety technology to deliver safety, but you can't just apply that technology and magically get safety, you need the culture. Secondly and maybe more understandably to people focused on technology, ALL of Rust follows the same rules and those rules achieve safety. What's different about Safe Rust is that the compiler can check everything you have done in Safe Rust follows the rules, so in Safe Rust following the rules isn't your problem, the compiler will check that. The "safe subset" technology can't work without a language where everybody else is following the safety rules all the time. Fully-qualified function call syntax is possible to use everywhere, again modulo unnameable types, but it looks quite ugly. While I agree that (for example) foo.into() is a bit ambiguous about what conversion we're performing, you can fix that by writing Bar::from(foo) if you prefer. Nobody in their right mind is going to write >::into(foo) or >::from(foo). (Those latter syntaxes exist to disambiguate the case where multiple traits define from() or into() methods or associated functions, or where Foo and Bar have inherent implementations of those methods or associated functions. But From and Into are well-known stdlib traits, so such a collision is unlikely in practice. It would be more plausible with more obscure traits, and fully qualified syntax is commonly used in macros because you can't know ahead of time that a collision is impossible.)

shadow_reuse lints cases where you re-use the value, for example maybe "width" on line 10 doesn't including padding but "width" on line 20 onwards adds 10 for padding. shadow_same lints cases where the shadow is just fiddling with the mutability or references, so maybe "goose" on line 10 is an actual Goose, but on line 20 onwards it's now just a mutable reference to the same goose. shadow_unrelated lints almost the opposite case from shadow_reuse, maybe "depth" on line 10 is an integer number of pixels while on line 20 onwards it's a 3D buffer. It might seem as though, since Rust has lints for so many misuses of shadowing, the whole idea of shadowing comes into disrepute, but in fact the argument for shadowing is that it is more readable - when done appropriately. Some codebases where shadowing is forbidden have to work around this. In languages like Rust with a good static type system this can encourage use of weaker, rubbish types and mutability when you'd be better off with immutable strong types and some shadowing. let delay : bool = /* somehow we discover a bool --- yes or no we want a delay here */ let delay : Duration = /* we make a (perhaps zero) Duration -- representing some amount of time */ let delay : MyHTMLType = /* some HTML about that delay */ If you forbid shadowing, you tempt somebody to decide booleans, durations and pointers to some HTML are all just basically integers, so we can say this is an integer and make it mutable then re-assign it, changing what it means repeatedly but sneaking past our "no shadowing" rule.
