ML Modules for Mere Mortals

Tanggal: 2026-11-14

I think everyone can agree code needs to be modular. Modularity lets us reason locally about our code no matter how big it grows. However, no one seems to agree on how code should be modular. There are a bunch of different approaches and each new language seems to bring their own spin on it.

Today we’re going to talk about a pretty old spin: ML Modules. ML here stands for Meta Language, as seen in SML and OCaml (and not machine learning). Despite SML first appearing in 1983, ML Modules have not caught on. OCaml is the sole production language you’ll find with an ML module system, and at the height of its popularity it’s niche.

This is a shame because ML modules have a lot to offer. We’re going to talk about what ML modules are and then touch a little on why ML modules are. Who better after all to explain modules, than the guy who doesn’t know what’s in a module ?…On second thought, don’t answer that.…I already wrote the blog post.

A little more unique is that ML modules will let us put not only function definitions in modules, but also type definitions:

Here we have a Set module with a Set type, which is a sorted Vec. Our module’s functions can refer to the type definitions much the same way they can refer to their module’s function definitions. Okay but that’s not that crazy, still well within the realm of Rust modules.

Not only can modules contain type definitions. Modules themselves have types. A module type is called a signature (so we don’t get it confused with “normal” types). The signature of our Set module is:

A module signature declares every definition of a module alongside its type. This might look similar to the way we define a trait in Rust. That’s because much like traits act as interfaces in Rust, signatures act as interfaces in ML Modules. Modules having signatures is the single most important thing to understand about ML Modules. All the complexity and expressiveness of modules results from them having signatures and the wonderful wacky things that enables.

Signatures resemble the way a C/C++ implementation file conforms to its header. Modules, unlike .cc files, aren’t in a 1:1 relationship with signatures. Our Set module can conform to any signature that it matches. A module matches a signature when it defines every declaration in the signature and they agree on type.

Matching a signature provides Encapsulation , hiding internal details of our module from our public API. Take a look at FullSetSig. Do callers of Set really need to know about index_of? Encapsulation advocates shout a resounding no: index_of is an implementation detail of Set.Set being a Vec and not integral to our Set API.

Ascribing a signature to a module lets us hide implementation details, but there’s a bit of a glaring hole here. Our signature no longer broadcasts that type Set is Vec. Within the Set module we’re free to use type Set as Vec, but everywhere outside the module type Set is now some unknown type. Because callers know nothing about our newly abstract Set type, all they can do is pass it to and from the methods provided by the Set module. As long as we keep our underlying Vec sorted within Set, we know no one else is able to mess with it. They simply don’t know enough about the type!

Our Set module is nearing perfection, but it still leaves a little to be desired: it only works for i32. Now we could of course write a new module SetU64, SetString, on and on everytime we need one, but c’mon there’s gotta be a better way. This isn’t Go.

Generics is the go-to solution for this problem. Heck we’ve even used it ourselves with Vec. ML Modules, however, have a more modular solution. You can parameterize a module by another a module.

Hopefully this has helped you see what’s cool about modules. Module’s power lies in their signatures. What would require a newtype wrapper or a visibility change in other languages can be accomplished by simply changing the signature a module is viewed at.

With abstract types, this allows for constructing webs of encapsulation where each piece knows precisely what it needs to about its neighbor and no more. Signatures act as this encapsulation boundary, freeing us to reason about our code modularly. As long as our module conforms to the expected signature we can contort and refactor it to our wildest whims and trust that it will continue to integrate into our system as expected. ML Modules are neat and I think they deserve more love and exploration in programming languages.
