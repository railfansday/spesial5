Sitemaps, Canonicals & OG Images From Your Nuxt Backend

Tanggal: 2026-11-15

Most SEO problems I inherit on Nuxt projects are not content problems. They are plumbing problems: a sitemap generated once at build time and never updated, canonical tags that keep every ?utm_ and ?sort= variant alive, and Open Graph images that return an HTML 404 page instead of a PNG. If your catalog, listings or case studies live in a database, those three outputs should come from the same database, at request time, with sane caching.

I run Loop Origin, a software studio, and as a Principal Software Engineer I have spent nine years shipping Laravel, Vue and Nuxt applications. I wrote this with help from AI tools and checked every command, header and code sample myself. This guide shows how I generate sitemaps, canonicals and OG images from the backend, with real HTTP output, a comparison of approaches and the failure modes I see in production.

Direct answer: Generate all three from your backend data at request time. Serve sitemap.xml from a Nitro server route backed by your API, set one normalised canonical URL per page with useHead, and render OG images through a cached image endpoint that returns image/png. Cache aggressively and invalidate when content changes.

A static sitemap.xml is fine for a ten-page brochure site. It breaks the moment content changes without a deploy:

The same is true of OG images rendered by a designer once per template. They go stale when the title changes, and nobody notices until a sales lead shares a link in Slack and the preview shows last year's headline.

Three things to copy: a real 200, an image or XML content type, and an explicit cache policy. The failure I find most often in audits is the opposite: an og:image URL that returns HTTP 404 with content-type: text/html, so every social share silently falls back to no image.

I default to custom Nitro routes when the data model is unusual (multi-tenant, per-locale, per-vendor) and to a module when the site is standard. The sitemap protocol limits each file to 50,000 URLs and 50 MB uncompressed, so anything larger needs a sitemap index either way.

A sitemap.xml index route lists /sitemap/1.xml, /sitemap/2.xml and so on. Keep lastmod honest: use the content's real update time, not now(). Escape & in any URL that carries query strings. And make sure every URL in the sitemap is the canonical version, returns 200 and is indexable.

Canonicals go wrong in three predictable ways: tracking parameters, sort and filter parameters, and trailing-slash or case variants. I normalise in one composable:

Rules I agree with the content team up front: utm_*, gclid, sort and view toggles never appear in a canonical; real pagination does; filtered category pages are canonical only when we intend them to rank. When a site moves or a URL scheme changes, the canonical rules and the redirect map have to change together, which I covered in the replatforming redirect map playbook.

A link preview needs an absolute og:image URL that returns a real image, ideally 1200×630. I render it on the server from the page's title and a brand template, then cache it at the CDN:

On the page: useSeoMeta({ ogImage: `https://www.yourstore.com/og/${slug}.png`, twitterCard: 'summary_large_image' }). Add a version or updated_at hash to the URL (/og/${slug}.png?v=1731650000) so a title change produces a fresh image instead of a cached old one. Social platforms cache previews on their side too, so the version parameter is what makes a re-share pick up the new image.

Use a module when your site is a standard content or catalog site; it handles chunking, indexes and defaults well. Write custom Nitro routes when you have multi-tenant domains, per-vendor catalogs or unusual URL rules the module cannot express cleanly.

Cache it for 10–60 minutes with stale-while-revalidate, and purge on publish if your CDN supports it. Crawlers do not need second-by-second freshness, and the cache protects your database during crawl spikes.

Sitemaps, canonicals and OG images are three views of the same data: which pages exist, which URL is the real one and how each page looks when shared. Generate them from the backend at request time, cache them deliberately and test them in CI, and the SEO layer stops being something you fix after every release.
