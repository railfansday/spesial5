Five Quiet AWS Limit Increases From 20 November Worth Reading Twice

Tanggal: 2026-11-23

Launch days get the attention. Limit increases get the production wins. AWS shipped a pile of them on 20 November, and a few remove problems I would normally design around. Here are the five I would read twice, with what the posts say and what they leave out.

General purpose buckets now support at least 11,000 GET/HEAD requests per second, up from 5,500. It applies automatically in all Regions at standard request pricing, with no application changes. AWS names ML training, analytics and data transfers as the target workloads.

What is not stated: whether 11,000 is per prefix or per bucket. The post still advises spreading requests across multiple prefixes, so I would keep prefix design as it is. Writes are not mentioned either.

The default stacks quota goes from 2,000 to 300,000, per account and Region, with no request needed and no charge. The post's example is a software provider with one stack per customer.

If you went multi-account early to dodge the old limit, this does not mean you should undo it. Account boundaries have other jobs. Not stated: whether nested stacks or StackSet instances count against it, and whether it can be raised further.

In provisioned mode, SQS FIFO event source mappings accept batch sizes up to 10,000, up from 10, with a batching window of up to 300 seconds. Ordering is kept within each message group. It is available in commercial Regions only.

Not stated: the payload size limit for a 10,000-message batch, and whether standard mode changes. Test your handler's timeout and partial-failure handling before raising the number. A batch that big fails differently.

Amazon Managed Service for Prometheus now supports up to 2 billion active series and 300,000 rules per workspace, and you can have multiple workspaces per account. Above that you file a limit increase. The previous limits and any price change are not stated.

Filterable metadata per vector rises from 2 KB to 40 KB at no extra cost. New vector buckets get it by default. Existing indexes need the UpdateIndexMode API to move to enhanced index mode. Not stated: whether the move is reversible, or any query latency effect. I would try it on a copy of an index first.

Search your own code for workarounds to these old limits: prefix sharding for read rate, batch loops around FIFO queues, metadata trimming for vectors. Some can go. Others are still the right design. Do you have one you can delete this week?
