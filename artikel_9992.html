At Antithesis, we love finding bugs in distributed systems. But Antithesis can also help eliminate certain classes of bugs by using a combination of AI and formal methods to prove the correctness of complex design choices.

In this post, we demonstrate the paradigm on two Raft implementations, production libraries from etcd and HashiCorp. Although theyâre implementing the same protocol, there are significant differences in the approaches the two use. We used AI, TLA+, and Antithesis to formally model the two libraries with trace validation. We iterated between model checking, Antithesis testing, and proof attempts, each of which exposed bugs in the code or gaps in the model. We patched bugs and refined the model until it was provable, and until every test run was conformant.

Our model handles several extensions to the core Raft algorithm including pre-votes, snapshots, leadership transfers, and, for etcd-raft only: read indexes for linearizability, async storage writes, and membership changes (where etcdâs implementation intentionally deviates from the Raft paper).

The final proofs establish core Raft safety properties such as Election Safety, Leader Completeness, and State-Machine Safety. In other words, our process established that once we applied the workarounds and fixes needed, the specific designs (scoped to the features we modeled) embodied in HashiCorp Raft and etcd-raft actually offer the same guarantees that the Raft paper does. Earlier this year, we wrote about how we keep finding bugs in every major Raft implementation we test with Antithesis. This was surprising, because the underlying Raft protocol has been extensively studied, formally specified, and rigorously proven correct (under a set of assumptions). In that post, we pointed out that many implementations subtly deviate from those assumptions, re-design the algorithm for performance, and/or extend the core Raft protocol with unverified extensions â thereby introducing bugs.

Since then, advances in AI have made automated theorem proving and formal verification of complex systems much more scalable, making it feasible to connect a specification to its implementation. So we set out to formally verify not just the core Raft protocol, but the specific designs implemented by production Raft libraries, incorporating custom data structures, different modes of concurrency, and various extensions such as pre-votes, leadership transfers, snapshots, and (in the case of etcd-raft) membership changes.

A key challenge in applying formal methods is to identify a level of abstraction that both allows us to reason mathematically about desired properties, and bridges the gap between specification and implementation. We are not yet at the point of reasoning directly at the level of assembly instructions or even programming language semantics in order to verify distributed safety properties in production systems.

Both Anthropic/Theoremâs OSS-Verify and Google DeepMindâs AlphaProof Code only model single-threaded assembly code; whereas distributed systems are concurrent.

The most widely used approach models the software as a state-transition system in a specification language such as TLA+, and checks invariants over these transitions for finite state spaces. TLA+ models can either be hand-written by experts, or these days, inferred directly from the code using AI. This approach has its own limitations, but is increasingly popular. The next challenge, then, is showing that the TLA+ model corresponds to the actual software that will run in production.

For our demonstration, we used Claude Fable 5.2 to automatically infer TLA+ models from the implementations of HashiCorp Raft and etcd-raft and then manually reviewed the safety properties declared in the specifications.

The etcd-raft repository has a TLA+ model crafted for trace validation that is now out of date, and is not designed for ease of proof. The Specular project produced models of etcd-raft and hashicorp-raft, but those models are designed for trace validation, not ease of proof, and the TLAPS leaderboard indicates that they remain unsolved as of 20 Nov 2026.

We had to manually provide guidance on which features to model or leave out, what scenarios to specify for model checking, and make one refinement to the auto-generated safety properties. While AI is generally bad at inferring properties, in this case we simply instructed the agent to express the core safety properties defined in the Raft paper.

We used the recently launched Antithesis plugin to automatically set up a test cluster, an input-generating workload designed to handle all the features captured in the model, and assertions that correspond to the modelâs safety properties. The software was then tested under fault injection while being fed random inputs, exercising various code paths and thread / message interleavings.

For this demonstration, we developed a lightweight trace validation kit that allowed the software running in Antithesis to emit structured log events that correspond to state transitions in the TLA+ specification. Any test execution that produced a trace that did not conform to some path in the model got flagged. A non-conformant trace could indicate incorrect instrumentation of the trace logging itself, or more seriously, a modeling error or a real bug in the system. We instructed our AI agent to diagnose which one of these it might be, using Antithesis as necessary, and continue iterating until the traces and the inferred model converged.

These instances, also synthesized by our AI agent, specify various bounds: clusters are usually three nodes, a single client value, at most a couple of terms of leader election, logs that are limited to a few entries, with only a handful of network messages in flight. These bounds sound tiny, but theyâre sufficient to create several interesting cases: competing elections, a deposed leader still replicating, log entries overwritten and re-replicated, crashes in the middle of an operation, etc. We also model checked various configurations of the Raft libraries, e.g. with pre-vote or snapshotting features enabled and disabled. These âsmallâ instances can reach a state space of over 1.6 million states, which TLC explores exhaustively. We also included some larger problems which were only checked via random simulation. If model checking triggered a safety violation, we attempted to reproduce it as an assertion failure locally or in Antithesis; if the software couldnât exhibit the behavior, the model had to be tightened.

Overall, our process was an iterative loop consisting of model checking (flagging invariant violations), trace validation (flagging deviations), model refinement (to fix design flaws or conformance), and software patching (to fix bugs).

In some ways, this approach is similar to and inspired by Specular. However, given their goal of finding bugs, Specularâs approach involved using AI to identify buggy scenarios before writing models, which meant that static analysis was doing a lot of the heavy lifting. In contrast, our models are intended to be more general and prove safety of the full design.

Along the way, we encountered bugs in both systems, including previously known open issues such as hashicorp/raft#695 and etcd-io/raft#551, as well as new ones such as hashicorp/raft#746 and etcd-io/raft#558. In our internal repository, we applied a total of 7 patches across the two implementations. In each case, our goal was to make the system and model pass both verification and validation.

We also encountered a few additional crash bugs, but those donât violate safety.

But bounded model checking only shows the absence of bugs in a small state space. The only way to get assurance for unbounded input sizes is via rigorous mathematical proof.

There are two good techniques for proving invariants correct for the whole specification: using a theorem prover integrated into TLA+ called TLAPS, or by translating the model into Veil, a library for the Lean proof assistant for modeling state-transition systems. We used both, delegating the task of proof construction to Claude Fable 5.2.

We used Veilâs official tla-to-veil LLM skill for the model translation, and the recommended approach of validating this via bounded equivalence checking, using TLC and Veilâs own model checker, on our previously stored instances.

Ideally, a TLAPS proof provides the best assurance, since it can attest to safety properties defined on the TLA+ model itself. However, we decided to translate TLA+ to Veil and attempt proofs in Lean. Why? As described in the previous section, our process was extremely iterative, involving several steps of model refinement. We wanted to use the proof engine as additional feedback in that process, feeding it any candidate specifications on which bounded model checking and trace validation both succeeded. We found Leanâs interactive tactic paradigm, predictable performance, and persistent kernel-checked proof terms to be key benefits in this iterative process.

On one occasion, a model of etcd-raftâs membership change as implemented could not be proven correct, revealing a complex bug whose trigger was beyond the state space that bounded model checking explores. In such situations, we could use the Antithesis plugin to attempt to synthesize a workload to reproduce the counter-example.

Antithesis also helped in the proof construction process. When working on challenging parts of the proof, Claude hypothesized several intermediate invariants which if true would lead to a straightforward proof strategy. The agent then used Antithesis to quickly check if those invariants held true in test runs, and discarded them if run-time assertions failed. Antithesis thus made the proof construction phase more efficient.

Once we converged on a state where the safety properties were fully provable in Lean and the model was passing trace validation with Antithesis, we froze the specification and asked agents to prove the same invariants on the TLA+ spec directly with TLAPS. This last step wasnât strictly necessary, but eliminated any shadow of doubt concerning the Lean proofs and the TLA+ spec.

End-to-end, the work on each library cost less than $1,200 in Claude Fable tokens and approximately 2000 Antithesis compute-hours.

Less, we should note, than the prepaid allowance in a single month of Antithesis Teams.

Note that our final proofs verify formal models of the implementation, not the code itself. However, we can gain confidence about the modelâs fidelity based on the trace validation performed with the extensive test coverage that Antithesis provides, including fault injection such as network partitions and node crashes. To strengthen assurance even further, our iterative process involved several steps of mutation testing, including: mutating the specification to check that the proofs fall through, mutating stored test logs to ensure that trace validation fails, and mutating the software itself to ensure that everything breaks.

The models still make several assumptions about the environment, which limits the reach of verification. For example, both Raft libraries provide pluggable interfaces for local persistent storage. In our test workloads, we use BoltDB for storage and the models assume that no single write (e.g., a log entry or tuple of raft state) is ever torn or corrupted, which BoltDB guarantees. A crash can still fall between two writes.

Our work also leaves out several library features which we have not modeled, such as lease-based reads for etcd-raft (because it depends on wall-clock timing), async heartbeats for hashicorp-raft (because it is known to be very very buggy; really), and membership changes for hashicorp-raft (because we were exhausted from patching bugs in the simpler core). Finally, we only verify safety properties and ignore liveness in this prototype. A comprehensive list of assumptions and limitations is provided in the associated artifactâs README.

Given our reputation as âa fuzzing companyâ, formal methods might seem like an odd direction for us to explore. But we see ourselves less as âa fuzzing companyâ and more as a correctness company. We need a wide range of different approaches if we want to build truly robust systems. Each technique compensates for the weaknesses of the others. Moreover, they amplify each otherâs strengths. The first property-based testing framework, QuickCheck, derived test inputs from a functionâs static type. Many of our customers use both testing and formal methods, so we want to make the two techniques work better together.

The biggest weakness of formal specification is that it proves the design correct, but doesnât guarantee that the code we implemented actually matches the design. Trace validation uses the strengths of tests to compensate for the core weakness of formal specification. Validation works best if our tests can reach wildly unusual system states, which aligns well with our core technology.

How formal specification can help testing is relatively less explored, but there are some opportunities here too. We often find that newcomers to property-based testing struggle to describe the properties for their system. But they can describe a high-level outline of what the system essentially does. With trace validation, we can potentially turn that outline into a property to test!

All that said, this is an early research project. We could easily map trace logs to spec behaviors because the code and spec were at roughly the same level of abstraction, with a close correlation between lines of Go and lines of TLA+. Most real-world specs, though, are two levels of abstraction above the code they model. This is because 1) TLA+ can do things impossible in a real system, like make truly arbitrary nondeterministic choices, and 2) the spec can simplify implementation details that donât affect the essential design. These features make specification more powerful, but also make trace validation harder.

Think of this as us demonstrating a medicine works on mice, but we havenât yet done a human trial. More work is needed, work which weâre now doing at Antithesis. Stay tuned to see where it ends up.

In formal specification (like with TLA+), we write highly abstract blueprints, or specifications, of systems and find bugs in those blueprints directly. Once weâve found and fixed all the bugs, we can be confident our real system isnât going to have certain design issues.

But how do we know that the code we write actually corresponds to the design we verified?
