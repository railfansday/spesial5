A faster Easter date function

Tanggal: 2026-11-11

This post is a fun little side quest to kickstart my journey optimising regional calendars.

Computing the date of Easter faster is not going to matter in any real application. Even in places where it might seem to matter, like high frequency trading applications, it is probably better to just use an in-memory lookup table for holiday dates...However, no "Fast Date" series would be complete without some mention of this classic problem.

The rules for Easter were broadly decided at the First Council of Nicaea, organised by Emperor Constantine in 325 AD, ultimately landing on the first Sunday after the first full moon, on or after March 21. Later, for operational efficiency, the church defined "full moon" according to a formula, which was eventually modified by Pope Gregory XIII in 1582 ("Gregorian Easter"), with the first Easter under the new rules applying in most Catholic countries the following year.The Church of England first observed the new date of Easter in 1753, but Eastern / Orthodox churches continue to follow the old rules.

This article is about the new "Gregorian" Easter, because it is much more complex and slow to compute. For more details on the underlying algorithm, you can see Gauss's Algorithm on Wikipedia (the first known self-contained function, which basically all later algorithms build on).

The accuracy range of around -11m â +16m years might seem a bit of overkill, but the reason I targeted this range is so that any date library that expresses dates via a signed or unsigned 32âbit "rata die", is covered by this function. This means that if you decide to not clamp the logic to years after 1582, at least it will return something resembling the correct rules, rather than garbage.

Note that this function contains more terms than traditional Easter functions, but bear in mind that the compiled assembly will be a lot smaller. So if you don't care about the speed, but want a tiny impact on binary size, that could be a reason to consider this function.

You'll notice that the very first thing we do is add a strange value SHIFT to the input value. This is done for two reasons:

For example, most Easter algorithms have a term like (5 + 8 * c) / 25, where c is the century (year / 100 + 1). The term 25 in the calculation of shift is responsible for aligning the century such that the constant 5 can be removed, resulting in c * 8 / 25, which is then approximated in the final algorithm with a single mul-shift: (u64) c * M25 >> 32.

Other terms in SHIFT: 19, 400, 30 are all doing similar things related to the 19-year-cycle, 400-year-cycle, and mod-30 steps.The term * 2 is different. Without this term, the range of coverage would be -5,403,600 â +22,363,835; which doesn't quite cover the range we wanted, which for signed 32-bit rata die, is Â±5.88m years. Including * 2 increases the value of shift by exactly 5,700,000, which is how many years it takes for the Easter pattern to repeat, and gets the range we are after.

Computing year % 19 is a staple of Easter algorithms.It's related to the Metonic cycle, where every 19 years there are nearly exactly 235 full moons.

We are going to compute these same things using a single multiplication.These steps seem unavoidable at first, but they can be eliminated. We'll begin by expanding the first one:

(11 * (year % 19) + ... ) MOD 30(11 * (year - year / 19 * 19) + ... ) MOD 30(11 * year - year / 19 * 209 + ... ) MOD 30(11 * year + year / 19 + ... ) MOD 30

The last step there might be the least obvious. It works because we can add any multiple of 30 to the multiplier and get the same result (a property of MOD), so add 30 Ã 7 = 210, which means we can remove the multiplication by 209 and just invert the sign.

This leaves us with only two terms related to year which can be computed efficiently in parallel, however using a 64âbit multiplier, we can actually merge these into one (fixed-point multiplication by 11 1/19):

u64 constexpr M19 = (1 << 32) / 19 + 1 + (11 << 32)((year * M19 >> 32) + ... ) MOD 30

This is the only 64âbit multiplication in the function, and a 32-bit compiler should have no trouble turning that back into the previous pair of multiplications.

The algebra above relies on MOD 30, which is different to % 30 in C for negative numbers.The value being computed does not go negative over our range, so the substitutions remain valid.

Now on to the other term: (year % 19) > 10. It is a well known trick to use the low bits from the mul-shift of division by 19 as a comparison cutoff, and the version used in my function is u32(b) > 0x90000000. The extra term in our multiplier (11 << 32) has no effect in the lower 32âbits, so this still works. Cassio Neri has written about things like this, if you want to read more you can start with this Overload Edition 154 .

So, this is just one multiplication plus the MOD 30, which is usually an additional two multiplications, but we'll eliminate those later in Trick #4.

So why not just subtract the result of % 7 like everybody else? Well, that would make the final line be: j - m + C (for some constant C). This does not fit the pattern of a single-operation LEA instruction on x86.

Instead, we adapt the fast-mod-7 code to use a fixed-point multiplier of 6 / 7 (rather than 1 / 7) before the right-shift-29, which means this line actually counts mod-7 backwards for us! This means the final line can be j + m + C, which fits LEA and saves... one cycle ð (depending on the compiler and CPU...).

This final bit, I'm not sure if it's been done before exactly like this.

Easter can only ever be in March or April (month 3 or 4), and luckily March is 31 days long, which means we can use % 32 to truncate dates there. A straightforward modulus would cause March 32 to overflow to April 0, a non-existent date, so we add the term v >> 7 which increments the date when it overflows (a lucky coincidence relying on April, month 4, being a power-of-2).

I have seen similar things done before using % 31, but I have not seen this with the clean bit-mask approach.

This article was prompted by Twitter/X user Dirk Loss replying to one of my posts with a link to a ChatGPT thread, where he used AI to compute Easter faster. See ChatGPT thread.

The AI actually did a pretty good job. It used learnings from my prior blog posts to apply various optimisations, but also came up with new twists on these ideas. It produced a function that is really fast, and that is accurate over the range 1498â14,544. The range is a fairly reasonable choice given that the modern rules for Easter took effect after 1582, and nobody really needs Easter further into the future.

In a serious case of "Not Invented Here" syndrome (on behalf of human kind), I had to see if I could beat the AI. I clearly did, otherwise there wouldn't be this blog post. The wider-range algorithm presented in this article has around 5-15% higher throughput across tested platforms, and similar latency (despite the wider range).

My algorithm was adapted from the one presented in Calendrical Calculations (Reingold and Dershowitz).I did not apply any learnings from the ChatGPT one, though we settled on several similar steps.

I suspect this function could be optimised more, as it still has the same overarching structure of existing algorithms going back a very long time.I tried for a little while to find a shortcut solution using the Python "Z3 Theorem Prover", which found an alternative which is a further 15-20% faster than my main one, however it's only accurate over a micro range [1894 .. 2199].
