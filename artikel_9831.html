Agents Are Not the Answer. Engineering Is.

Tanggal: 2026-11-16

How to build with rules, skills, hooks and subagents around a coding agent

For a while, I thought the problem was the model.

The agent would put a network call straight inside a screen component, and I would add a sentence to the next request: keep network calls out of the components. It would write a date-formatting helper when one already existed two folders away, and I would add another sentence. The requests got longer. The instructions file got longer. On the days the agent followed all of it, I took that as proof that the setup worked. On the days it followed none of it, I blamed the model.

It took me longer than I would like to admit to do the obvious thing, which was to stop writing and go look at what the tool was actually loading.

The rules I had written with the most care had never been read, not once. Their path patterns expected folder names that were different from the real ones. The instructions file stated a test count that was half the true number, and pointed to a document that didn't exist. In a folder above the project there was an old copy of that same file, loaded together with the new one and contradicting it. And a block I trusted completely had been letting everything through for weeks.

The model had been doing what it could with what I had put in front of it. I had been treating those files as notes to a colleague, when they were software: they had bugs, and I had never tested them.

As I write this, I don't have all the answers about how to make coding agents behave. Probably I never will. Section 9.5 lists what is still unproven, and it is not a short list. But I keep asking questions, and a few of them have turned out to be the right ones. Who decides that this piece comes into play? What happens when it fails? How would a person check?

Coding agents fail less from a lack of model capability than from a lack of engineering around the model. What the agent knows, what it can do and what stops it from making mistakes are all defined by a set of files: permanent instructions, rules per area, skills, subagents, hooks, permissions and memory. This text treats that set as software. It has an architecture, it has typical defects, and it can be tested.

The text is for anyone setting up or maintaining an environment of coding agents, in any tool. The examples use Claude Code's names, but the concepts hold for any tool that reads an instructions file such as AGENTS.md. Section 9 shows all of it applied to a real financial platform, with measured numbers. That is where the story in the prologue comes from.

A coding agent is a language model running in a loop: it reads the request, decides on an action (read a file, run a command, edit), receives the result, and decides on the next one. Everything it knows at that moment is in the context window: the system instructions, the configuration files that were loaded, the conversation, and the tool results. The model has no memory other than what is there and what it learned in training.

There is a useful image for this, attributed to Andrej Karpathy: the model is the processor and the context window is the RAM. Context engineering is deciding what occupies that memory at each step.

Intuition says that giving the model more information helps. It is a reasonable intuition. It is also wrong, or at least wrong past a certain point.

Anthropic describes the phenomenon as context rot: as the window fills up, the model gets worse at retrieving each individual piece of information. Attention is a budget. An important rule buried in a thousand lines of instructions has less effect than the same rule in a file of a hundred.

The practical consequence is the central principle of this text: look for the smallest set of high-signal tokens that produces the behavior you want. Every piece described from here on is a way of applying that principle.

The files that configure an agent have readers (the models). They have behavior (what the agents do because of them). They have bugs (a hook that doesn't fire, a path pattern that doesn't match). And they have debt (a number that stopped being true).

In other words, the practices that apply to product code apply to them as well: one responsibility per file, clear names, nothing duplicated, tests, review and maintenance.

This is the text loaded in every session, for every agent. It holds what is always true: what the project is, the vocabulary of the domain, the real commands, the security rules, the forbidden zones and the definition of done.

Because it enters every context, each line costs attention on every task. The rules for writing it:

A wrong fact in this file costs more than a missing one, because it teaches the model to act with confidence on something false.

Rules are the instructions file sliced by responsibility: one rule for the backend, another for the app, another for tests. A rule can declare which paths it applies to; in that case it is only loaded when a file from that area enters the conversation. A rule with no scope is always loaded, like the main file.

Rules are binding. Write "every new route has an entry in the permissions manifest", not "consider adding one". And name model files: pointing to a well-made file of 44 lines teaches more than describing what a clean route is.

A skill is a folder with an instructions file that has a name and a description. Of all the skills available, the model sees only those two things: name and description. When the task matches a description, it loads the body. This is called progressive disclosure. The knowledge exists, but it only takes up context when it is needed.

That is why the description is the most important part of a skill. It has to say what the skill covers and when to use it, in the words that show up in real requests. A vague description never fires.

Skills hold recipes (how to create a migration), formats (the body of a pull request), catalogs (code smells and their refactorings) and technology knowledge written from the project's real code. A skill can also be invoked by hand, like a command, and can be marked so the model never starts it on its own. That is useful for expensive flows.

A subagent is a role defined in a file: description, allowed tools, model and a system text. When it is called, it runs in a new, empty context window. It receives only the brief the calling agent wrote and the project's instructions files. When it finishes, it hands back a report. Everything it read along the way is thrown out.

The cost is real: the subagent knows nothing about the conversation, and what comes back is a summary. Detail is lost in both directions. Delegating only pays off when the work is large, independent, or needs fresh eyes.

Hooks are scripts the tool executes on events: before a tool call, after it, at the end of a turn. A hook that runs before the call can allow it, deny it or ask for confirmation. A hook that runs after can return text that enters the agent's context.

Hooks are the only piece that doesn't depend on the model obeying. They have two uses:

Rules for hooks: minimal dependencies, errors never silenced, denial messages that say what to do instead, fast execution, and tests with expected allow and deny cases.

Declarative lists of deny, ask and allow, by tool pattern and path pattern. They cover the simple case with no script: never read secret files, always ask before a commit. Whatever needs logic (block an existing migration, allow a new one) goes into a hook.

A directory where the agent writes down facts that should outlive the session: decisions made and the reasons for them, the preferences of whoever works with it, facts about the environment that aren't in the repository. A short index is loaded at the start of each session.

Memory is not a diary. Task state and summaries of finished work stay out, because they age fast and take up context forever.

The Model Context Protocol is an open standard for exposing external tools and data (ticket manager, database, documents) to the agent through a typed interface. It replaces hand-made integrations. Every connected server adds tool descriptions to the context, so the same discipline applies: connect what gets used.

There is a detail here that is easy to miss. Even when loading is guaranteed, obedience is not. A rule in the instructions file is always in the context, and the model can still fail to follow it in a long task. Only hooks and permissions guarantee the effect.

Out of this comes what I consider the most useful design rule in this text:

can be checked by a tool (types, lint, tests)

requires judgment and applies to one kind of task

requires focus, a different permission or fresh eyes

When an agent gets something wrong, the right question is which layer was missing. The fix goes into that layer. One more sentence in the next request fixes nothing.

The report has a fixed format. For a critic: verdict, blocking points, warnings and suggestions, each with file and line. For a builder: files changed, what was removed, commands run and their results, and what could not be done. The fixed format is what makes the flow auditable.

Before calling review, it checks the acceptance criteria in the code itself, runs the verification commands, compares the error counts against the baseline, and goes through the list of changed files looking for anything out of scope. When something fails, the work goes back to the responsible agent with the concrete problem. The limit is three rounds. After that the flow stops and reports.

Systems with several agents spend several times more tokens than a simple conversation. The same Anthropic text reports prototypes that created dozens of subagents for trivial questions.

Orchestration pays for itself on high-value tasks, with independent parts or parts that need separate review. For a one-line fix, it is waste.

The term comes from Kent Beck and was spread by Martin Fowler in Refactoring. A smell is a surface sign of a deeper structural problem. It isn't a bug: the code works. The cost shows up later, when every change gets more expensive and riskier.

The most used catalog groups smells into five families:

Long function, giant file, long parameter list, primitive obsession

Repeated if chain by type, forced inheritance

Duplicated code, a change that requires editing many files

One change becomes ten, and one gets forgotten

Dead code, abstraction for a future that never arrived, a comment that explains confusing code

Skipped layers, a function that lives off another module's data, long access chains

None of these causes is solved by asking the agent to "write clean code". Each one calls for a different piece.

Before writing: show what good looks like and what already exists.

Numeric limits work better than adjectives: a target of 40 lines per function, new files under 400, at most 4 parameters, at most 3 levels of nesting. The layering rule says where each kind of logic lives, which keeps the handler or the screen from accumulating everything.

Right after writing: deterministic feedback.

A hook that runs after each write analyzes the file and returns a list of problems to the agent, with the instruction to fix them or justify them in the report. Ideally this hook runs the project's linter. Where there is no linter, pattern searches cover part of the ground: too many parameters, deep nesting, an empty catch, commented-out code, too much state in one component. This check is approximate and has to be treated that way. It is a warning, not proof.

Before reporting, the builder runs a short self-check on its own diff. Did any function go over the limit? Did I write a block that already existed, and where did I look? Did I add a literal with business meaning? Did any handler or screen gain data access, an HTTP call or a formula? Did I leave anything dead?

In review: fresh eyes and bounded cleanup.

Every task leaves the area it touched cleaner than it found it.

The limit is what makes the rule workable: the cleanup stays inside the files and functions the task already touches, and it is smaller than the task itself. A cleanup bigger than the feature is another task. Without that limit, the agent turns a small fix into a refactoring nobody asked for and nobody can review.

Known security problems stay outside this rule. Fixing them as a side effect of another task mixes together changes that need their own review.

This is the part of the case I find most useful, and it is the part that looked worst at the time. There were six mistakes.

Hooks that didn't protect. This is the block from the prologue that let everything through. The original hooks called an interpreter that didn't exist on the machine. The error was silenced, the script exited with success, and everything was allowed. Migration protection did not exist for weeks, and nobody noticed. Lesson: minimal dependencies, errors never swallowed, tests for the hook.

Rules that never loaded. The path patterns expected folder names different from the real ones. The rules were there, written with care, and were not read a single time. Lesson: test the pattern against a real path.

Wrong facts in the instructions file. An outdated framework version, a test count at half the real number, a reference to a document that didn't exist. Lesson: measure and date.

A hook that blocked legitimate work. The pattern looked for the text of a forbidden command anywhere on the line, and it matched a file that merely mentioned the command. Lesson: analyze the structure of the command, not the loose text.

Conflicting instructions. When the checklist from section 6 was applied to the configuration itself, an old copy of the instructions file turned up in a folder above, loaded together with the current one and contradicting it. Lesson: list everything the tool loads, not just what is in the project folder.

Style rules in prose. The backend had no linter, so "no any, no debug logging, no fixed decimal places" went into the text and into a pattern-search hook. This is Lint Leakage, accepted knowingly as a provisional measure. The definitive fix is the linter.

Before this work, the repository had a configuration that looked like protection. Now it has one that has been tested.

This changes the conditions under which code gets written there. The audit in section 9.1 found components of 6 thousand lines because every new feature was copied from its nearest neighbor and nothing stood in the way. Today an agent working in that repository starts from the model files. It receives the map of what already exists before writing its first line. It hears about a function that passed the limit in time to fix it. And it cannot grow the files that were marked as never to grow.

The copying that produced the old code has been cut off at each of the four points from section 5.

Three things come next, in this order: the linter on the backend, CI blocking the merge, and the evaluations of the flow. With them, the same baselines that today say where the code stands will say, task after task, how far it has moved

Before creating any new piece, eight questions:

Which layer? Permanent fact, on-demand recipe, isolated role or guarantee?

Does something already cover this? Extend it or reference it.

What is the exact trigger? Test it against a real case.

What are the minimum tools? Who writes and who only reads?

What is the output? A fixed format, with evidence by file and line.

How does a person verify it? Command, baseline, diff.

What happens when it fails? A message that teaches the alternative; a limit on rounds.

What is the date of the measurement, and who maintains it?

There is a scene in Neon Genesis Evangelion that I kept coming back t

For most of the series, everyone treats the Evangelions as giant robots. They have pilots, hangars, launch rails and a maintenance crew. Then one of them tears off its own plating in the middle of a fight, and the head scientist, Ritsuko Akagi, says what the engineers had known all along. The plates were never armor. They are restraints, put there to hold back something that is alive, far stronger than the people who built it, and not fully understood by any of them.

I think this is the most accurate picture I have of what this text describes.

The Eva is not a robot. Nobody at NERV programmed it line by line. They found a way to work with it, and then built everything else around that fact: the plating, the cockpit, the cables, the command room. A language model is in the same position. The engineering in sections 2 to 8 is the plating and the command room.

The cable decides how the fight goes. An Eva runs on an external power cable. When the cable is cut, the internal battery lasts five minutes, and every plan made in the command room starts from that number. That is the context window from section 1. It is the scarce resource, and the design is done around it.

Synchronization is a request. The pilot doesn't steer with levers. The pilot thinks, and the Eva moves, as long as the two are in sync. Some days the sync is high and the machine does exactly what was intended. Some days it barely moves. And a few times it stops listening altogether and acts on its own. That is an instruction: followed most of the time, with no promise about the rest.

The restraints are the guarantee. What NERV could not afford to leave to synchronization, it bolted on. The plating doesn't depend on the pilot being calm or on the Eva agreeing. That is a hook. And the series shows what a restraint that fails looks like, which is the false guarantee from section 6: until the moment it breaks, it looks exactly the same as one that works.

Three computers, one decision. NERV's decisions go through the MAGI, three supercomputers that each hold a different side of the same mind and vote. They exist because a single opinion, however intelligent, inherits its own bias. That is the reviewer from section 2.4, who never saw the implementer's reasoning.

Taking the pilot out is the worst idea in the story. At one point the command decides the pilot is hesitating too much and switches to an autopilot, the Dummy Plug. The Eva finishes the job, and what it does cannot be undone, while the pilot sits inside screaming for it to stop. Section 8 is there for that reason: commit, push, migration and publishing stay with the person.

And when it works, everyone is in it. The operation I like most in the series is the one in which the electricity of the entire country is routed into a single rifle. There is a pilot who shoots and a pilot who holds the shield, engineers on the transformers, operators calling out numbers, a commander who has made the plan, and the three computers giving the odds. The first shot misses. The second one doesn't. It is orchestration, including the cost: you black out a country to stop an Angel, not to fix one line.

What I believe will outlast the tools is the question NERV's engineers had to answer for every part of that machine. Is this something we ask of the pilot, or is this something we bolt on?
