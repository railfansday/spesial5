The simplest way to explain it I think would be to say that Tailscale makes all your devices act like they’re on the same home network, no matter where they actually are.

Their site from 2020 is a bit clearer: https://web.archive.org/web/20201129111934/https://tailscale.com/

But basically it lets your various devices connect to each other, whereever they are, without having to deal with port forwarding, firewalls, dynamic DNS... so your phone or laptop can access self-hosted services on your Raspberry Pi (photos, Jellyfin, RSS, files, ...). It does this while keeping it all hidden from random people/attackers.

I don't use Tailscale, and instead just use plain Wireguard/mTLS, but Tailscale is easiest to set up and seems to be the most popular option for people that want to access their Raspberry Pi when away from home.

I primarily use it for a personal "private intranet"; I host services like Grafana and Forgejo on homelab machines inside my home, and then connect them to Tailscale so I can access them remotely through the tailnet without needing to put them on the public internet. As a bonus it also provides "funnel", a public reverse-proxy which works the same as serving to the tailnet, avoiding the need for a public IP to serve those services.

Unlike traditional VPNs, Tailscale does not tunnel traffic through its infrastructure per se - the control plane server governs access and routing, but traffic transits through establishing point-to-point WireGuard tunnels, with Tailscale operating relays which forward encrypted packets between machines when needed for e.g. NAT traversal. That said, you do give up some amount of self hosting - you can rent a cheap VPS and set up e.g. Headscale to get a decent subset of functionality (though I personally haven't tried this myself).

The best high-level overview of why Tailscale came to be, IMO, is https://tailscale.com/blog/two-internets-both-flakey

Here're some broad generalzations that may help you.

First, yes, most of what you find using search engines is poor quality, regurgitated marketing stuff. Sure, you can learn good things from those results, but you'll also learn poor practices at the same time. For instance, most marketed how-tos will tell you to download binary programs or Docker images, which might be OK for learning, but become security issues over time.

One good practice is to learn how to install software via source, or at least using a package manager that's updated often. Docker images are made when the creators feel like it, and often have dependencies baked in that are ancient and may have vulnerabilities. A proper packaging system that's updated often will use the same dependencies for all of your software and will be updated regularly, particularly when any of those dependencies have exploitable vulnerabilities.

Learn about and become comfortable with the Unix permissions model. It's actually quite good, and what some of these marketing people will tell you is wrong: if you use a separate, unprivileged user for each service you host, and one of those users gets compromised, and it can lead to a root escalation, then the issue is that your system isn't updated enough to not allow a root escalation. The number of people who want you to address the symptom and not the problem is huge, and they often advocate for, for instance, Docker or some other thing because it's popular, not because it actually makes sense.

Don't let feature creep win. I host dozens of Wordpress sites for friends and small businesses, and every time PHP gets updated, someone's site ends up not working because they got excited when setting up their site and install a dozen plugins, most which aren't necessary, but which aren't updated and cause their site to stop working with the latest PHP. I've gotten good at disabling plugins without logging in to WP. It's better to only install and use what you really want to use.

Related to that, I recommend installing, playing, getting everything working properly, making notes, then using those notes to reinstall from scratch so you know which steps are superfluous. Your first install might have twenty steps, but once you understand things, the second might have six. Clean is good.

Avoid passwords everywhere you can. Use ssh keys, only allow access to https login pages to certain IPs or IP ranges, if possible, make those links custom if you can, and so on. An OpenCloud login page that people (and bots) don't know is worlds better than a public one that bots will hit constantly.

For anything that does require passwords, don't reuse, don't use simple or basic passwords, and don't let anyone get away with thinking their weak password is "good enough" or that nobody will find the service to try too hard to log in. Assume everything will get tested, including every username, email address and password in every leak, ever.

Don't believe gatekeepers that tell you that you can't, that you shouldn't do certain things. I've taught people who are non-technical to self-host email. If non-technical people can do it, then why should gatekeepers who claim to be technically proficient be believed when they insist that email can't reasonably be self-hosted?

If you find yourself in communities of people who are condescending to you, or who are trying to tell you that a Raspberry Pi isn't a proper server, for instance, then find another community. This community is a good one :)

Oh - get good, durable storage for your Pi, and have fun!

For example, I have a static blog and whenever I want to see analytics (AWstats), which I access by starting a small webserver on localhost and then tunneling the port via ssh to my own box. Come to think of it, I haven't checked my analytics in years. But the point is, you can do this for any web interface to sensitive info or where you don't trust the security of the app (which should be every app, really).

Similarly, I run a private IRC server on which I chat to folks who have SSH access to my machine. This IRC server also listens on localhost only. I feel way better about this than when it would be available to anyone, even if it were locked down.

Finally, use a nftables or similar rule set where you block all ports and then selectively and explicitly allow only the services you intend to allow to be reachable from the outside. Then, if you accidentally misconfigure something to listen on external IPs, it's still not reachable.

A very non-concrete advice is simplicity.

When you self-host, you're responsible for security yourself (duh). And maintenance is gonna be a hobby. So scale accordingly: Choose software that doesn't aim to change from under your feet, because that'll make you put off maintenance (this is what some of us like to use the word "stable" to mean). Choose software that's easy to get back into and understand without having to be in the weeds every day. Choose software that'll at least break in obvious ways. Choose software where lots of things have to go wrong for things to break.

Reducing the access: Some only allow access to these ports: 22 for SSH (if you leave it on standard port, which you will see some people advise to change), 80 (normally never used except to ease SSL setup via Let's encrypt), and 443 (only for services that need to be public). Some people find the above even too open, and would reduce it further. Everything is behind tailscale (even SSH), and public services leverage Tailscale Funnel. No port is open on your machine, but a tunnel exist between your machine and tailscale infrastructure that expose your websites there. Reducing impact: The public websites can still be vulnerable to zero days (from tailscale funnel or not), so the idea is containing damage. Run your services in a containers is an easy way to limit impact to that service only if things go wrong (and not the whole server).

When configuring the grsec kernel, ensure to set up the socket limitation groups, GIDs which cannot open sockets (or flip it to require membership to open sockets "nosocks vs allowsocks")

Audit the system for setuid executables and, creating similar groups, limit access to them to certain users. If users cannot access a vulnerable SUID executable, they cannot exploit it.

Ensure to set sane limits.conf to avoid forkbombs.

Ring fence stuff with UIDs - one user, one service. That way a hacked service can leak its own stuff and not much more.

I assume your internet connection has enough bandwidth to sustain a small to moderate website. Self-hosting a publicly facing service is an order of magnitude more dangerous than self-hosting private services such as photo management applications or media servers because of the security implications. On the bright side, static pages can be hosted securely with relatively low effort compared to LAMP stack.

(a) Applying network segmentation is a good start. The RPi should not be able to communicate with other devices through router / firewall configuration. Maybe allow just one device based on IP or MAC address to access the RPi from the LAN.

(b) Then setup DNS records. I assume you own an FQDN. Use an ready-made or custom script to update the DNS records. I'm using dnscontrol alongside envsubst and to perform the changes but there are simpler solutions out there.

(c) Once the DNS is working and updating properly, use an application to issue SSL certificates. My favourite is acme.sh but there are quite a few polished alternatives, e.g. certbot, lego, etc.

(d) Now you're ready to setup a reverse proxy. Note that modern rev-proxies like Caddy can manage (c) on their own. I'm not using them, I'm familiar with nginx so I use that.

(e) Create a deployment user with minimum permissions and use that user to upload data via sftp or other secure protocol. If you want to setup a deployment pipeline via git, that's also possible through webhooks.

(f) Secure the system. I'm pretty sure that you can flat-out ban the big cloud CIDRs. That will save you from dumb scanners abusing your website. Since very few humans use these addresses for outgoing connections, I think it's a good strategy to block them straight-up. tl;dr: Minimize attack surface, by minimizing what runs as well as complexity. Make sure you know what you are doing and only add stuff if you know why.

By minimizing attack surface. The biggest mistake that people do is overengineering and thereby biting themselves. As others already pointed out, Docker is one example of increasing complexity that might bite you.

People give silly tips like port knocking, changing default ports, etc. that do nothing unless you have a serious and obvious security issue in first place. The chance you will have an issue increases with complexity, so try reducing it.

Use firewalls mostly as a way to prevent "I fucked up" situations. A firewall doesn't do anything for any open service. So in theory it should do nothing. Don't run anything non-local that shouldn't. You do that by having a firewall that blocks every port and then only add ports you understand and really want to be public.

Take care about the basic sane stuff, not about super theoretical things, because that often leads to being super protected against that one case, but not about everything else. In other words focus on building a wall before you worry about situations where one has it broken down already.

A great example of this is stuff like fail2ban, which is again something that does nothing and is more a way to potentially have fewer log messages. If you have a big hole it will be used regardless of it and if you don't it doesn't do more than what you'll reach by setting login attempts to 1 per connection (just keep in mind that a client might try multiple private keys on its own). If someone knows your password then it does nothing. If your password is guessable. Change it. If you think someone can bruteforce it, disable password authentication (preferred). Also I think newer versions of OpenSSH have a built-in equivalent of fail2ban.

On a related note: Don't add attack surface. Adding fail2ban and port knocking sound great, but like everything you run they can become an attack vector themselves. One might say that's not likely, but it's also not likely that someone gets in via SSH, not even if you allow a reasonable secure password, not even for root. Don't do that. Use SSH keys that are encrypted, but I think it's important to know what you are doing. If you fear that these attacks work then you are doing something wrong in first place.

So focus on reducing things. If you just have your raspberry pi at home and never want to connect from anywhere else, of course you can limit that. That's the thing where a firewall adds something.

A small thing that often is overlooked: SSH is essentially a VPN/secure tunnel on its own. Eg. you can use it to tunnel any service you want to your local system. With an SSH config you can do that every time you connect. For simple/self made setup that's a great way to make things accessible. Eg. if you have a DB running and want to run some local software against it without any need to open up a port. Just forward it via SSH. This is true for any kind of admin interface as well, or maybe if you have webmail, etc. Don't make it accessible via the internet and that whole attack vector is one less thing to worry about.

Usually for public websites the most vulnerable part is not any kind of authentication system, encryption, etc., but the web application itself. If you just want a blog you can get extremely secure by using a site generator. That reduces attack surface in terms of no node/PHP/Go/... vulnerability or self-written application code can hurt you. If you do put a web application there this will typically be your weakest point, but even there it's usually fairly unlikely to have an auth bypass and a lot more likely to have things like SQL injection or simply accidentally unauthenticated endpoints as well as misconfiguration of software - which again is a reason why you want to reduce the services you run to what you want/need.

In general doing the boring thing instead of that "big guide" is a good idea, as well as following official docs, because there is way too much scary stuff out there that will teach you how to make extremely insecure setups. Luckily many projects have some form of production guideline and most widely used software has sane defaults.

Regarding tailscale, etc.: As mentioned SSH can do most of that for you, but in addition wireguard isn't too hard to set up properly either. Overall being alone with a single server means you do not have to worry about a whole lot of management topics (eg. weak passwords, key handling, etc.).

Of course make sure your software is up to date, but I am sure you know that asking this question. If you can either make it automatic or if for some reason you cannot, then make it alert you about update if you are worried about things somehow going down. That can be a simple cron jobs and various operating systems have mechanisms to send emails that do that.
