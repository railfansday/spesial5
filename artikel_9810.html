Why your AI agent pushes as the wrong GitHub account (and a 3-minute fix)

Tanggal: 2026-11-20

You open a client project, ask Claude Code to fix a bug and open a pull request. Two minutes later the PR is up, from your personal GitHub account, with your personal email on every commit.

If you use more than one GitHub account on the same computer (work, personal, a client or two), you've probably hit some version of this:

I hit all three in the same week, so I dug into why it happens and built a small open-source fix. This post explains the problem, the pieces of git and the GitHub CLI that solve it, and the surprising gotchas along the way.

When Claude Code (or you) works in a repo, three different things decide which GitHub account is used, and they don't talk to each other:

The GitHub CLI has supported several logged-in accounts since version 2.40, but gh auth switch changes the active account globally. Switch to work in one terminal and every other terminal, including a Claude Code session you started an hour ago, is suddenly work too. Two agents in two repos can't each have their own account.

Each fixes one of the three identities. You need all three, and you need them to follow the folder you're in.

Put each account's projects in its own folder, for example ~/code/work and ~/code/personal, and make everything inside a folder use that folder's account. Git and the GitHub CLI already have every piece needed.

Git can load extra config only for repositories under a path:

Every repo under ~/code/work/ now commits as jane@acme.com. (Mind the trailing slash in gitdir/i:~/code/work/. Without it, the rule silently never matches.)

The empty helper = line clears any helpers defined earlier, such as your OS keychain, so only this one runs inside the folder. Tokens stay in gh's secure storage; nothing new is written to disk.

Your remotes stay exactly as they are. Bonus: includeIf is applied during git clone too, so cloning into the folder already uses the right key.

gh always prefers the GH_TOKEN environment variable over its active account. So instead of switching anything globally, a small claude shell function finds which account folder you're in and starts Claude Code with that account's token, for that process only:

Now gh pr create inside that Claude session runs as the folder's account, and a second session in another folder can use a different account at the same time.

I packaged all of this into claude-gh-accounts, a free, MIT-licensed installer for macOS, Linux and Windows (PowerShell and Command Prompt):

It installs anything missing (Git, GitHub CLI, Claude Code), suggests the GitHub accounts you're already logged in to, fills in your name and email from your GitHub profile, and optionally sets up an SSH key per account. Most answers are just Enter. Then:

Projects outside the account folders keep their usual settings. Re-running the installer remembers everything, so adding an account takes a few seconds.

Current limits, honestly: it's built for Claude Code in the terminal. In IDE extensions and the desktop app, git commits and pushes still use the right account, but Claude Code's own gh actions don't switch yet. Web and IDE support is next. It also covers github.com only, not GitHub Enterprise, for now.

If you juggle multiple GitHub accounts, I'd love to hear whether this fixes it for you, and what's missing. Ideas already on the list: a doctor command that shows which account a folder will use, and picking the account from the repo's owner instead of the folder.
