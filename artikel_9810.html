Why Model Context Protocol (MCP) Needs an Execution Firewall (And How We're Experimenting with One in Rust)

Tanggal: 2026-11-07

TL;DR: The Model Context Protocol (MCP) is solving one of the hardest developer problems in AI: giving models a standard way to find tools and context. But once an agent selects a tool, execution is usually direct: the agent calls the tool with standing API credentials. If an LLM hallucinates, misreads a number, or gets tricked by a prompt injection, nothing stands in between. We're experimenting with an inline zero-trust proxy written in Rust that treats agent tool calls as untrusted proposals rather than automatic commands. Here is what we've learned, what works locally, and where we're still looking for answers.

If you have spent any time connecting LLMs to databases, internal APIs, or file systems, you know the pain: every framework used to invent its own bespoke tool format.

Anthropic's Model Context Protocol (MCP) changes that for the better. It gives the industry an open, standard way for an assistant (like Claude Desktop or any custom agent loop) to ask an environment: "What tools do you have, and what schemas do they take?"

MCP acts like a clean, universal adapter catalog. It does this job really well, and we think it's winning that role for good reason.

MCP solves discovery and interface standardization. But it intentionally doesn't solve runtime safety policies.

In computer security, this is called ambient authority: whoever holds the connection holds the full permission of the master key.

This works fine for personal desktop productivity or harmless read operations (like reading local markdown files or querying a documentation site). But consider what happens when an autonomous agent is connected to real systems:

If an agent has direct execution rights, a single prompt error or edge-case reasoning failure immediately mutates your business state.

Over the last few months, we've been experimenting with a simple rule:

An agent should be allowed to propose an action, but it should never have the authority to execute it directly.

Rather than building another agent framework or replacing MCP, we built a small, standalone security proxy in Rust called the Trust Gateway, accompanied by an inspection CLI (trustctl).

Instead of the agent loop talking directly to the system with master credentials, the architecture puts an inline checkpoint between the agent and downstream executors:

In our test setup, the agent never touches raw API secrets or long-lived bearer tokens.

When the agent decides to invoke an API, it signs an action proposal envelope (canonicalized via RFC 8785). The gateway inspects the proposal. If valid, the gateway mints a short-lived, single-use grant (typically with a 30-second TTL) that is bound to the SHA-256 hash of the exact input arguments.

If the agent tries to reuse the grant, or tamper with the payload to change the destination account, the signature fails closed.

We wanted to ensure that evaluating safety doesn't add a slow, brittle database dependency in the hot path.

Using trustctl, an engineering team can pre-sign API capability bounds offline using standard Ed25519 keys:

Our core verification engine in Rust contains zero async code and zero network access. It is a deterministic state machine: it takes a proposal, verifies the cryptographic signature against the active policy bounds, and outputs an allow or reject decision in sub-millisecond time.

What happens when a tool's schema changes, or an agent calls an endpoint marked as destructive?

Rather than crashing or guessing, the gateway puts unverified or high-risk actions into an isolated ProbationStore (using SQLite with Write-Ahead Logging). In our demo environment, destructive actions require a two-human quorum signature before a grant is issued. The agent pauses its task loop and waits until the approval event appears in its audit stream.
