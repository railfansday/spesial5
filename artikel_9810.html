Another, possibly simpler, option to create an uninterruptible operation is to fork an auxiliary thread to do the resource acquisition. Since this thread is private, it is essentially immune to async exceptions.5 However, this will then still require some kind of communication protocol that allows the child thread to clean up when it realizes the parent is no longer interested; see also the discussion of Threads, below.

In some cases you may want to vary what the resource release function does, depending on whether or not the body terminated with an exception, and depending on the nature of that exception (see also discussion of generalBracket). For example, you may (or may not) opt for an abortive closure of a TLS connection after a timeout; or you may (or may not) opt to close a file handle without flushing the buffer. Such decisions are of course highly application specific; a timeout may simply mean that the main action should be terminated, but the resource should still be closed cleanly!

Threads are a microcosm of the three goals that we set up at the start of this blog post: we must avoid leaking threads, communication between threads can get stuck, and exceptions thrown in threads often need to be dealt with outside of those threads.

New threads run with an exception handler that silently swallows the asynchronous ThreadKilled, as well as synchronous BlockedIndefinitelyOnMVar and BlockedIndefinitelyOnSTM, which we will revisit shortly. Any other exception is handled by the uncaught exception handler, which by default simply prints it (though this can be changed).

In general it is good practice to ensure no exception is ever uncaught.6 In almost all cases you should therefore install an exception handler in the new thread; what this handler should do will be application specific, but we will consider one important class of problems in the next section.

In this blog post we focused mostly on principles, not the larger ecosystem. We cannot possibly give an exhaustive overview here, but there are a few packages that we should briefly discuss. Two I can unreservedly recommend: exceptions and async. The third, safe-exceptions, takes an opinionated stance on async exceptions which you may or may not want to adopt; here we will only point out some aspects to be aware of.

The exceptions package provides polymorphic versions of the standard exception handling functions through a stack of type classes: MonadThrow for monads in which we can throw exceptions, MonadCatch in which we can catch them, and finally MonadMask in which we have bracket available. Itâs mostly a straight-forward generalization of the functions in base, with the exception of generalBracket, which we discussed already.

As mentioned, safe-exceptions takes an opinionated stance on async exceptions, which is provided through a series of alternative implementations of standard base functions: catch, bracket, throwTo and others all behave subtly differently in safe-exceptions than they do elsewhere. As such, if you choose to use this package, my strong recommendation is to import the package qualified, so that use sites (Safe.catch) are clearly distinguished from the standard functions.

The use of safe-exceptions should be a deliberate choice: it is not a drop-in replacement. Refactoring existing code to import from Control.Exception.Safe instead of Control.Exception, without making additional changes, is unlikely to be correct.

The first important difference is that Safe.catch and related functions do not allow you to catch async exceptions at all. This means that you donât have to worry about catching async exceptions in handlers that catch âallâ exceptions, though you probably should not do that anyway. If you do try to catch an async exception, the code will compile just fine, but the handler will never run.

In the section on distinguishing sync and async exceptions, we discussed that the difference is about intent, not delivery mechanism. We implied, though did not spell it out, that this intent is stated statically, through the Exception instance. However, in the implementation of throwTo in safe-exceptions this intent is stated dynamically: throwTo will add an AsyncExceptionWrapper around the exception being thrown if toException does not already add the SomeAsyncException wrapper. This gives a catcher the ability to still see that it was âintended to be asynchronousâ, but it also means that even if that catcher is defined using standard catch, and it has a handler for that exact exception, it wonât be able to catch it anymore because the type match will fail.7

The behaviour of Safe.bracket is also subtly different from standard bracket. The most important difference is that it wraps the release callback in uninterruptibleMask_. This means that the release callback does not need to worry about async exceptions, but as we saw in the section on async exceptions during release, this may not always be safer: in the network example, uninterruptibleMask_ around an orderly closure could mean that the code will wait indefinitely for the network peer to respond, and cannot be timed out or interrupted with CTRL-C.

The other difference in bracket is what happens when the release callback was called because of an exception in the body: depending on the exact nature of the two exceptions (sync or async), exceptions thrown by the release may be silently swallowed, making it all the more important to be careful if youâre releasing multiple resources.

Writing code that does the right thing even when things go wrong can be quite difficult; this is inherent, not accidental, complexity. Asynchronous exceptions make this significantly more difficult still, but of course also come with a lot of benefits; for example, without asynchronous exceptions a general combinator such as timeout would not be possible. Exceptions also tend to be non-deterministic, so leaked resources, stuck code, or unhandled failures may not be noticed during testing. Nonetheless, with some good code hygiene many problems can be avoided; hopefully the guidelines in this blog post can assist.
