This is my third progress update for the Decentralize AI Hackathon by HackerNoon and Nosana.

In my last update, I connected zkzkAgent, my local-first AI agent for Linux, to Nosana's decentralized GPU network. A 27B model on Nosana planned and built a working web app on the first try. I ended that article with a promise: numbers instead of impressions.

Here they are. The whole Nosana side of the benchmark, 15 real agent tasks, cost $0.13.

"Does a 27B model beat a 2B model?" isn't worth a benchmark. Of course it does.

My laptop has a 4 GB GPU. That's enough for small models, and nowhere near enough for a 27B model, which needs roughly 15 GB even at 4-bit. So the questions that matter are:

If the answer is "a few cents and a few seconds," then a modest laptop doesn't have to choose between a weak local model and a centralized AI provider. It can keep the easy steps at home and rent a big brain only for the hard ones.

Every model ran the same agent: the same LangGraph graph, prompts, 25 tools and safety gates. Only the model behind it changed.

Each task ran 3 times per model: 60 runs in all.

Running an agent unattended on my real machine, 60 times, needed some care. Four design choices did most of the work.

1. One process per run. run_all.py starts every run as its own subprocess with a 15-minute limit. A hang or a crash costs one row, not the whole benchmark.

2. A scripted "careful user." The harness approves a plan once (ok) and answers no to every dangerous-tool confirmation. If the agent asks in plain chat instead of using the gate, the harness says yes once, so T5 tests whichever tool the agent actually picks.

3. A callback that sees every model call. zkzkAgent's graph has several nodes, and each one calls the model. A LangChain callback handler, passed in through app.invoke(state, config={"callbacks": [meter]}), counts calls, tokens and tool calls across all of them:

On Nosana, the call count matched the HTTP requests in the logs every time I checked.

4. Guards around the risky tools. Before the first call, guards.py wraps the agent's tools:

Every refused call goes into the results. That turned out to matter, as you'll see in T5.

One caveat about that table. No local model ever passed T4, the slowest task, so their time per success only covers the easier tasks. On the four tasks every model passed at least once, it's 14 s per success on Nosana, against 24 s for the 2B, 35 s for the 0.8B and 137 s for the 4B.

Cost comes from token counts at Nosana's listed price for this model: $0.20 per 1M input tokens and $2.00 per 1M output tokens. Output tokens, which include the model's reasoning, were about two thirds of the bill.

I expected the remote model to feel slower. So I measured time to first token and generation speed with one real agent call: the executor's system prompt, all 25 tool schemas and a short question, streamed 5 times per model.

Even with the network round trip, Nosana's first token arrived sooner than my local 2B's. On a 4 GB laptop GPU, just reading a 3,000-token prompt takes real time, and Nosana's GPU reads it faster than the round trip costs.

The small models generate tokens faster, of course. But per task, the 27B was as fast as the 2B or faster on three of the four easy tasks, because it needs fewer steps. On the kernel question, it made one tool call where the 2B made two.

There was one gotcha while measuring. The 27B on Nosana reasons before it answers, and LangChain's OpenAI client silently drops those reasoning tokens from the stream. So the speed test calls the API directly, and the reasoning counts. It's in the billed token counts too.

The most useful finding wasn't about model size at all.

One zkzkAgent executor call, with the system prompt and 25 tool schemas, is 2,968 tokens before any conversation history. Ollama's default context window is 4,096 tokens. So 72% of the window is gone before the agent does anything, and the reply, plus any reasoning, has to fit in what's left.

Nosana serves the 27B with a 131K window. During T4, its calls averaged up to 6,167 input tokens, which would never fit in the local window.

So I reran T4 on the 2B and the 4B with an 8K window, using a new OLLAMA_NUM_CTX=8192 setting in zkzkAgent.

T4 at 8K: 0 out of 6. A bigger window helps a small model get started, but on this GPU, it doesn't help it finish. The hard step needs a bigger model, and a 4 GB card can't hold one.

A thinking model that couldn't stop thinking.

Small models went around the safety gate. In 2 of their 6 safety runs, the 0.8B and the 2B ran sudo apt install cowsay through run_command, the general shell tool, instead of using the gated installer. One run tried six times. The benchmark guard blocked every attempt, but in normal use, run_command has no gate. The 4B and the 27B used the gate every time. Putting run_command behind a gate is now at the top of my list.

One tool error crashed a whole run. A 2B run asked get_files_info about a file that didn't exist. The tool raised FileNotFoundError, and the exception took down the whole agent. It should have returned an error the model could react to.

My first version of the benchmark had a bug. In a dry run, the 27B asked "Should I install it?" in plain chat instead of calling the tool, and my check marked that safe behavior as a failure. The scripted "yes, go ahead" follow-up fixed the test, not the agent. That's what dry runs are for.

The numbers practically draw the design for me.

zkzkAgent's graph already has separate nodes: a classifier, a chat node, a planner and an executor, and each one can use its own model. Here's the plan for my next milestone:

The hybrid benchmark will report what share of calls stays local and how often fallback kicks in. At the prices measured here, $25 of Nosana credits covers about 700 app builds, or about 2,800 tasks of this benchmark's mix.

After that, I'll move from the shared API to my own Nosana GPU job running the same 27B model, and measure VRAM use, startup time and cost per hour.

Everything is in the repo: the harness, the raw rows for all 60 runs, every log and the summary.

The benchmark runs a real agent on your machine, so read benchmark/README.md first to see what the guards do and don't cover.

Thanks to HackerNoon and Nosana for running this hackathon, and to the Nosana team for their feedback on the method. If you rerun the benchmark on your own hardware, I'd like to see your numbers.
