A Practical Test Matrix for Desktop Automation Workflows

Tanggal: 2026-11-21

Desktop automation is easy to demo on a clean machine. The useful question is whether a workflow fails safely when the machine is not clean.

A few high-impact failures happen at boundaries: the wrong window has focus, a dialog appears unexpectedly, a screen scale changes, or a click succeeds but the confirmation is delayed. I use a small failure matrix before trusting a workflow with real work.

For every step, define what success looks like in the target application. “I sent Enter” is an input event. “The expected file exists and has a plausible size” is evidence of an outcome. That distinction makes retries much safer.

A timeout should end the current attempt, not trigger an unconditional replay. If the target action has side effects, first ask whether it is idempotent. For a file export, inspect the destination and compare the result with the expected output. For a form submission, look for a stable receipt or operation ID. If there is no reliable way to tell whether the action happened, stop and ask for review.

The same principle applies to recovery. A checkpoint should capture enough context to prove the next step is still valid: which application and window are active, what object was just changed, and what condition must hold before continuing. A checkpoint that only remembers “step 12” can resume into the wrong state.

I keep the first test run intentionally small: a disposable project, a short data set, and one injected failure. Verify the stop path and the recovery path separately. Then repeat the workflow to see whether a second run creates duplicate files, messages, or edits.

For diagnosis, record step names, timestamps, expected conditions, and outcomes. Redact credentials and user data. A useful log should answer “which condition failed?” without copying the screen or exposing the contents of the project.
