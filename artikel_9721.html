Every Repo Has Its Own release.sh — Replace Them With One Command

Tanggal: 2026-11-22

The work is done. The tests pass. Now you only need to release it.

So you open package.json and change 1.4.0 to 1.5.0. You run npm install so the lock file follows. Then:

The build fails after the tag. Now you have a release commit and a tag for a version that does not exist, and you undo them by hand. Or git push is rejected, because a teammate pushed first. Or you forget the lock file, and the next person sees a dirty tree.

So you write a release.sh. Then the next repo is Python, so it gets its own release.sh. The Go one tags and does nothing else. The Rust one is half copied from the npm one. 😅

After a few years, every repo has its own way to ship, and you have to read the script each time to remember it.

shipo (Ship out of the box) is that script, written once, for every stack. You run one command:

And each repo says what is different about it in a small file, .shipo:

You don't start from zero. shipo init finds your stack and writes a first .shipo for it.

One flow for every repo. The differences live in .shipo.

This is the one idea the whole tool is built on. A release has two halves:

🛡️ Everything before publish is local. The checks run first and change nothing: the tools are there, the tree is clean, the tag is free, and the push will fast-forward. Then the version is written, committed, and tagged, and the build runs. If any of that fails, the commit and the tag are undone. Even after Ctrl-C.

📤 Publish leaves your machine. A pushed tag, a GitHub Release, a package on npm: those can't be taken back safely. So shipo doesn't try. It runs them one by one, and asks before each one that goes beyond git push:

If a publish step fails, nothing is undone. You fix the problem and run only that step again:

shipo check shows the plan before a release, and where a release stopped after one:

Undo what you can. Ask before what you can't.

shipo does not build, pack, or upload anything itself. It runs the tools you already use, in the right order:

Presets know where the version lives in each stack: package.json, pyproject.toml, Cargo.toml, composer.json, pubspec.yaml, pom.xml, *.csproj, or git tags for Go and Swift. Only the version text is rewritten, so your formatting and comments stay.

For anything else, you give a file and a pattern:

One more thing: commands run without a shell, the same way on macOS, Linux, and Windows. No &&, no pipes, no $VAR. If you need those, put them in a script and run the script. It is a small limit, and it means a .shipo works the same on every machine.

A Go CLI. The tag push starts your release workflow, so this is all:

A Docker app. The workflow builds the image, shipo waits for it, then deploys:

In a monorepo, each folder has its own .shipo and its own tags, like api/v1.2.3 and web/v1.2.3. shipo finds them all and asks which one to release.

Some projects ship a stable main and a next beside it. shipo adds the branch name to the version:

When next is ready, shipo final on next does the round trip: it switches to main, brings in the commit you tested, releases 1.3.0, brings the release back into next, and switches back.

It releases what was tested: the commit of the last -next tag, not whatever next holds now. Newer commits stay on next, out of the release.

The flow with the menu is for a person. But every part also runs on its own, with no prompt:

So an AI agent can release too, one step at a time. shipo skill claude user installs a skill for Claude Code (also Codex, Cursor, and Copilot). The skill tells the agent to read the project, write .shipo, run shipo check until it passes, show you the plan, and ask you before each publish step. It never runs the interactive flow, because that flow needs a person.

The agent writes the config and does the steps. You still say yes before anything leaves your machine.

And one honest note: shipo is young. The first commit is from November 2026, and most of it was written in a week. It releases itself with its own .shipo. If your release has a case it does not cover, open an issue.

It needs git. gh, logged in, is needed only for GitHub Releases and workflows.

If you have a release.sh in every repo, and each one is a little different, that is exactly what shipo is for.
