How to Add Idempotency Keys to a Node.js API with PostgreSQL

Tanggal: 2026-11-25

Stay up to date with AI tools, model releases, and developer workflows that matter.

A mobile app sends POST /orders. The server creates the order, but the response is lost when the phone switches from Wi-Fi to 4G. The app sees a timeout and retries. Now the customer has two orders, and your support team has a refund to process.

Retrying is the right thing for a client to do. The problem is that POST is not idempotent: RFC 9110 defines GET, PUT and DELETE as idempotent methods, but not POST or PATCH. Repeating a POST can repeat its side effects.

An idempotency key fixes this. The client generates a unique key for each logical operation and sends it with every attempt. The server does the work once, stores the response against the key, and returns the stored response for any retry. The IETF HTTPAPI working group is standardizing this pattern as the Idempotency-Key HTTP header field, and this tutorial follows its recommendations.

We'll build it with Node.js, Express 5 and PostgreSQL. By the end you'll have a table that stores keys, a function that safely claims a key under concurrent requests, an Express route that replays stored responses, and a client that retries without creating duplicates.

The tempting approach is to SELECT the key, and insert it if nothing comes back. Under concurrency that fails: two retries arriving a few milliseconds apart both see no row, and both do the work.

Instead, let the primary key decide. INSERT ... ON CONFLICT DO NOTHING either inserts the row or does nothing, atomically, even across many application processes. The UPDATE in the last step is also atomic. If two retries find the same expired lock, only one of them matches the locked_until < now() condition and gets the key. If the row disappears between the two queries, for example because it was released after a failure, the function reports in_progress and the client simply retries.

Set LOCK_SECONDS comfortably above the slowest time your operation takes. If the lock expires while the original request is still running, a retry can take over and run the work a second time.

Once a request owns the key, it creates the order and marks the key as completed. Both writes happen in one transaction, so there is no moment where the order exists but the key still says in_progress, or the other way round. releaseKey runs when the work fails. Deleting the claim lets the client retry with the same key instead of waiting for the lock to expire. It only deletes rows that are still in progress, so a completed response is never thrown away.

The route validates the body first. A request with invalid input never touches the key table, so the client can fix the input and resend with the same key. Error responses use the application/problem+json format from RFC 9457, which the idempotency draft also uses in its examples:

The server side only works if the client keeps the key stable. The most common client bug is generating a new key inside the retry loop, which turns every retry into a new operation. Generate the key once per logical action, before the first attempt:

The catch branch is the reason idempotency keys exist. After a timeout, the client can't know whether the order was created. With a stable key, retrying is safe either way: if the first attempt succeeded, the retry returns the stored order; if it didn't, the retry creates it. The random jitter spreads retries out, so many clients recovering from the same outage don't all hit the server at once.

In a browser or mobile app, store the key with the pending action, for example in the form state or a local queue. If the user taps "Place order" again after an error, reuse it. Only generate a new key when the user starts a genuinely new action.

Keys can't live forever, or the table grows without limit. The draft leaves the retention period to the server but says it should be published in the API documentation, so clients know how long a retry stays safe. Twenty-four hours covers most retry scenarios. A scheduled job can delete older rows in batches:

Run it every few minutes from cron or your job scheduler until it deletes zero rows. Deleting in batches keeps each transaction short, and the created_at index from Step 1 keeps the inner query fast. A retry that arrives after its key has expired is treated as a new request, which is why the retention period belongs in your documentation.

Idempotency keys don't replace other safeguards either. A unique constraint on a natural business key, such as one payment per invoice, still catches duplicates that arrive with different keys, for example when a user submits the same form from two tabs.

With one table, an atomic claim and a transaction that stores the response next to the work, POST endpoints become safe to retry. Clients get a simple rule: generate one key per action, reuse it on every retry. The server takes care of the rest, including the concurrent retries that a SELECT-then-INSERT approach misses.

The same pattern works for PATCH endpoints and for webhooks you send to other systems. Start with the endpoints where a duplicate costs real money or confuses a customer, and publish your key format and retention period in the API documentation so client developers know what to send.
