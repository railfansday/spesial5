Migrating from React Navigation to Expo Router: A Step-by-Step Guide (With a Cheat Sheet)

Tanggal: 2026-11-18

Expo Router is built on React Navigation, so most of what you know carries over. Migration is mostly moving screens into an app/ folder: each navigator becomes a _layout.tsx, each screen becomes a file, navigation.navigate('Name', params) becomes router.push('/path'), route.params becomes useLocalSearchParams(), and your linking config disappears because every route is a deep link automatically. The cheat sheet at the end maps every common API.

If your app was started a few years ago, it probably has an App.tsx with a NavigationContainer, a stack, a tab navigator and a linking config that nobody wants to touch. Expo Router replaces that config with your folder structure. Here's how to get there without breaking the app.

Expo Router renders its own navigation container, so your NavigationContainer in App.tsx goes away. Keep the old App.tsx open in another tab; you'll copy pieces from it.

The (tabs) group organizes files without appearing in URLs, which is why Home lives at /.

Screen options are the same React Navigation options you already use. A drawer works the same way with Drawer from expo-router/drawer (after installing the React Navigation drawer package).

Each screen file default-exports the component. You can keep your existing screen components where they are and re-export them, which keeps the diff small:

Then update each screen's navigation calls (next step). Moving the files physically into app/ can come later.

For more complex params, use the object form, which encodes values for you:

Params are now always strings, because they live in the URL. If you used to pass numbers, booleans or whole objects, parse numbers and booleans explicitly, and pass an ID instead of an object, then load the data on the screen. That second change is what makes every screen work from a deep link.

Going back and replacing: navigation.goBack() becomes router.back(), and navigation.replace(...) becomes router.replace(...).

Setting options from a screen: render a Stack.Screen inside the screen, or keep using useNavigation() and setOptions, which still works because Expo Router is built on React Navigation:

Focus effects: import useFocusEffect from expo-router instead of React Navigation.

The classic React Navigation pattern renders different screens depending on whether the user is signed in. In Expo Router, put each side in a group and guard it in one layout:

Recent Expo Router versions support protected routes with Stack.Protected and a guard prop; on older versions, a in the protected group's layout does the same job. Either way, deep links into protected screens respect the guard, which the old conditional-screens pattern didn't always handle cleanly.

This is the satisfying part. Your linking object with its screens mapping can be deleted: every file in app/ is a route, and with your scheme set, myapp://projects/42 opens the project screen with id: "42".

Search your codebase for code that built URLs by hand for notifications or emails and replace it with the new paths. Push notification handlers that called navigation.navigate should now call router.push with a path.

Moving from React Navigation to Expo Router is mostly a restructuring job: navigators become layouts, screens become files, navigation calls become paths and your linking config disappears. Do it one navigator at a time, pass IDs instead of objects and let typed routes catch the rest.

If you're starting a new app instead of migrating one, RapidNative generates React Native apps that already use Expo Router, which you can export as a standard Expo project.
