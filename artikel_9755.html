Debugging Electron Apps: A Practical Guide to Main, Renderer, and Production

Tanggal: 2026-11-10

Every Electron developer has lived this moment: the app works in dev, then ships to a user and misbehaves in a way you cannot reproduce. Stack Overflow answers fragment the debugging story across a dozen flags and launch args, and half of them are stale. This is the field guide I wish I'd had at version 1.0 — one reference for the main process, the renderer, utility processes, packaged builds, and the small set of tricks that turn "it works on my machine" into a reproducible bug.

An Electron app is not one program. It is a graph of OS processes that share a Chromium message loop. When something goes wrong, the first question is always: which process is broken? | Process | Runs | What it can do | How you debug it | |---|---|---|---| | Main | Node.js, single thread | filesystem, IPC orchestration, windows lifecycle | --inspect=5858, VS Code attach | | Renderer(s) | Chromium, one per BrowserWindow | DOM, web APIs, your UI code | DevTools, openDevTools() | | GPU process | Chromium compositor | drawing, WebGL | --disable-gpu to disable, chrome://gpu | | Utility process | Node.js child | utilityProcess.fork(), offloaded work | --inspect inherited or passed explicitly | | Utility (Node) child | child_process.fork / spawn | native addons, long jobs | stdio + --inspect |

The main process is just Node. Every Node debugging technique works, with one wrinkle: you launch it through the electron binary, not node.

Then open chrome://inspect in any Chromium browser, click Configure…, add localhost:5858, and you should see your main process appear. Click inspect and you get a full Node DevTools window with breakpoints, scope inspection, and an ES module-aware debugger.

outputCapture: "std" is the undocumented flag that makes console.log from main show up in the VS Code Debug Console. Without it, you are blind to stdout.

Renderer debugging is the closest thing to regular web work. The renderer is a Chromium tab.

Note: loading extensions from a hard-coded Chrome path works for local dev. For CI or a team, vendor the .crx into your repo and point loadExtension at the unpacked directory.

This is where the pain starts. Your dev script runs electron ., but the shipped app is an .exe / .app / .deb built by electron-builder or electron-forge.

The DevTools Protocol (CDP) is the same API Chrome exposes. Electron lets you turn it on with one flag.

Then open http://localhost:9222/json in any browser. You get a JSON list of every debuggable target — main process, each renderer, each service worker. Click the webSocketDebuggerUrl and you are in.

In DevTools (main or renderer), open the Performance tab, record for 5–10 seconds while reproducing the bug, and look for long yellow (scripting) tasks. For the main process specifically, the CPU profiler tab in the Node inspector gives a flamegraph.

When you suspect a leak: take a heap snapshot, do the suspect action, force GC, take a second snapshot. Switch the dropdown from Summary to Comparison and sort by Delta. Anything that grew and did not shrink back is a candidate leak. We covered the full leak-hunt workflow in the memory-management article; the key reminder is that Electron adds native retained memory (C++ side of BrowserWindow, WebContents, Tray) that V8 heap snapshots will not show up. Use process.getProcessMemoryInfo() and compare workingSetSize across the suspect action.
