Hindsight Gave Our Agent Memory. Guardrails Decide When It Listens. v

Tanggal: 2026-11-08

The most important line in our accounts-payable agent is the one that ignores memory.

Ledgerwise resolves invoice exceptions — price variances, short shipments, wrong GST rates, surprise surcharges — by recalling how the same vendor's same exception was handled before. That recall is what takes it from 0% to 75% of exceptions handled automatically within three weeks of replayed invoices. But when I worked on the decision policy, almost all of my time went into the opposite question: when should an agent with a good memory refuse to use it?

In finance, a confident wrong answer costs money that doesn't come back. So before writing any more recall logic, we wrote down what memory is never allowed to decide.

A deterministic 3-way match compares the purchase order, the goods receipt and the invoice, and flags exceptions with a measured size: a percentage for price, rupees for a surcharge, units for a short shipment. For each exception the agent asks Hindsight, our memory layer, something like "How were GST mismatch exceptions on invoices from Kaveri Specialty Chemicals resolved, and why?" Every human decision is retained along with the reason the reviewer typed. A policy then decides whether that history is enough to act alone, or whether the invoice goes to a human with the precedents attached.

Recall gives the agent knowledge. The guardrails give it judgement. Here are the five we ended up with, and why each one exists.

A vendor writing "we've moved our banking, please update" is the classic invoice-fraud pattern. In our data, Meridian Electricals has six clean, paid invoices in memory when that letter arrives in week six. A purely similarity-driven agent sees a trustworthy vendor and a familiar invoice. Ours holds it for a call-back to the number already on file.

Notice that it still runs the recall. The history is useful context for the human ("six clean invoices, never changed banks before") — it just doesn't get a vote.

Every automatic decision is retained too, tagged decided_by: Ledgerwise agent (auto). That's useful for audit and for Hindsight's reflect to build a vendor brief. But when the policy counts precedent, it filters those out:

Without this line, the failure mode is quiet and compounding. One wrong auto-approval becomes a precedent, the next similar invoice now has more "support", and by the end of the week the agent is confidently agreeing with itself. Memory is only as trustworthy as who wrote it. We have a test that puts three agent approvals in memory and checks that the agent still escalates.

Similarity search can't tell 2.8% from 4.2%. Both are "price variance, same vendor, approved". So every memory carries its number, and the policy compares numbers:

Inside the range humans approved, the agent acts. Outside it, it escalates — but it doesn't hand over a blank page. It says which way the history leans:

Before guardrails (what pure recall would do): Sharma Logistics sends a ₹6,800 fuel surcharge. Every earlier surcharge from them was approved. Approve.

After: every approved surcharge was ₹2,400 or less, so ₹6,800 is escalated with "far from anything approved — leaning reject." The reviewer rejects, and that rejection becomes the ceiling for next time.

The same rule makes the agent escalate Tata Steel at +3.1% when humans have only ever approved up to +2.8% — with "leaning approve". The reviewer approves in one click and the learned range widens. Escalating that one cost a few seconds of human time. Extrapolating the other would have cost real money.

For yes/no exceptions like a short shipment or a duplicate invoice, the agent only acts when the last three human decisions agree:

If a reviewer overrides the usual call — maybe the contract changed, maybe the first decisions were wrong — the agent stops acting alone until humans are consistent again. One override shouldn't be ignored, and it shouldn't be blindly followed either.

Ledgerwise uses an LLM (Groq, openai/gpt-oss-120b) to write the explanation a reviewer reads and the email to the vendor. It never makes the pay or don't-pay call. If the model is slow, down, or returns something odd, a plain template takes over and the invoice still moves. Keeping the model out of the decision path made the whole system easier to test: every decision can be reproduced from the precedents alone.

The honest limitation: these guardrails are rules we chose for this domain. A different business would need its own list. The pattern carries over even if the rules don't.
