Git Clone vs Fork: Stop Mixing Them Up

Your first open source contribution starts with a question: do I clone this repo or fork it?

Usually both. They do different jobs, and mixing them up is how people end up with broken remotes and pull requests that go nowhere.

You can’t push to a repo you don’t have write access to. Cloning someone else’s project gets the code onto your laptop, but your push will be rejected. A fork gives you a copy you can push to. A pull request is how you ask the original maintainers to pull your changes in.

Shortcut: with the GitHub CLI, gh repo fork owner/project --clone does the fork, the clone, and sets origin and upstream for you.

Once you fork, your copy is frozen at that moment. If the original moves on, you have to sync it, and there are three ways:

Sync before you start new work so your pull request doesn’t conflict with changes you didn’t know about.

Your own repo, or a team repo where you have write access

Contributing to a project you can’t push to

Just reading or running someone’s code locally

Forking is also how communities protect themselves. When Terraform’s license changed in 2023, the community forked its last open version into OpenTofu. When Redis changed licenses in 2024, the Linux Foundation backed Valkey. Both forks now have their own governance and keep their open licenses.

That connects to last week. A fork carries the original’s license with it. Your fork of an MIT project is still bound by the MIT notice, and a fork of a GPL project must stay GPL if you distribute it.

Further reading: GitHub Docs: “Fork a repo” and “Syncing a fork.”
