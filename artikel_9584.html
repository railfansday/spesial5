Note: A private disclosure is in flight, so the protocol and chain are withheld here. The bug pattern, the harness, and the fix are not.

Bridges are accounting machines with a public attack surface. Every message that arrives from the other chain is, from the contract's point of view, just a bag of fields that somebody typed. The only thing standing between that bag of fields and the treasury is a replay guard. If the guard is built out of the wrong bytes, it is not a guard at all — it is a suggestion.

I found one of those in a counterstake-style bridge. The short version: one foreign transfer of 400,000,000 base units was claimed three times, and the bridge paid 2,400,000,000. The extra 2,000,000,000 came out of tokens other users had locked in the agent. No private key was stolen, no cryptography was broken, no oracle was manipulated. The uniqueness key simply included fields the claimant controls.

This is the anatomy of that bug, the harness that proved it against the project's own execution engine, and the checklist I now run on every bridge I review.

A counterstake bridge moves value in one direction by locking it, and in the other direction by paying out against a foreign transaction. The payout path is the interesting one:

Step 3 is where money leaves. Which means step 2 must be idempotent: the same foreign transfer must be claimable exactly once, forever, no matter how many times it is submitted or what the submitter puts in the optional fields.

That is the entire security model of the payout path. Everything else — challenge periods, stakes, governance — is decoration on top of "one transfer, one payment".

The bridge is written in a declarative formula language: a state machine with init, messages and getters, where storage is a flat key-value map. There is no Solidity-style mapping, so replay protection is a storage convention: write a marker under a key derived from the claim, and bounce if the marker already exists.

Four of the seven inputs are attacker-controlled. The guard asks "have I seen this exact combination before?", when the only question that matters is "have I seen this transfer before?".

And there is no second index. I grepped every .oscript file in the repository for a transfer-keyed marker — var['tx_' || txid], var['transfer_' || txid], anything of that shape — and found none. The uniqueness marker is the only thing preventing a replay, and it is keyed on a hash the attacker can recompute at will.

Changing one byte of one optional field produces a different hash, a different marker, and a fresh claim record. That is it. That is the whole exploit.

The cost of an extra claim is the stake, and the stake comes back with the payout after the challenge window. So the marginal cost of claim N is opportunity cost and gas, and the marginal revenue is the full transfer amount. The bridge pays N × amount for one transfer of amount; the loss to the pool is (N − 1) × amount.

For the transaction I used: amount = 400,000,000, stake 400,000,000, payout per claim 800,000,000.

Note what the third line does: it changes txts by sixty seconds. The bridge does check that txts is not in the future and not absurdly old, but it never checks it against the actual foreign transaction, because it cannot — the value is attested, not proven. So the claimant picks any timestamp inside the accepted window and gets another claim.

Scale is bounded only by the agent's balance. Repeat claim N times, drain the pool, and the protocol is insolvent for every honest user still waiting to withdraw. This is why the impact lands as "direct theft of user funds" and not as a nuisance bug.

The useful part of this finding is not the bug. It is that I could demonstrate it against the project's own code, deterministically, in a few seconds, with no fork and no RPC.

The platform ships its formula evaluator as a library (evaluation.js in the core package). You can require it directly, feed it the agent's definition, send trigger messages, and read back the resulting state and outgoing payments. That turns "I think this is replayable" into a table of payments.

Two details make this credible to a triager:

Assert on the state, not just on the messages. The harness prints claim_num after each claim (1, 2, 3) and the num_ markers. Seeing three distinct markers for one txid is the bug, stated in the project's own data structures.

Two hardening measures are worth adding while you are in there: a per-transfer claim counter with a hard cap of one, and a global accounting invariant that total payouts for a given foreign txid never exceed its attested amount. The invariant is cheap and catches the next variant of this bug, not just this one.

This is not a bridge bug. It is a key design bug, and it shows up anywhere state is indexed by a hash that includes user input:

The audit question that finds all of them is the same: what is the smallest set of bytes that uniquely identifies this event, and is every byte in my key actually in that set?

If a byte in the key is attacker-controlled, the key is not an identity — it is a namespace the attacker can expand at will.

The report is with the maintainers now, with a reproduction anyone can run in under a minute. When the fix ships I will publish the full identifiers, the diff and the post-mortem. Until then, the pattern is the useful part — and if you maintain a bridge, the twenty minutes it takes to check your replay key is the cheapest insurance you will buy this year.
