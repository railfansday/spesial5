Normally, when the physical memory is running out, the OS can swap some memory being least likely to be accessed frequently into some reserved portions of the hard disk, and these portions are the Swap Space. Although the fastest M.2 SSD being as fast as more than 14GB/s with 15us latency, is still nowhere comparable to the fastest DDR5-8600 being as fast as more than 130GB/s with 70ns latency, the former is still comparable to the deprecated DDR3-1600.

However, every SSD has a hardware limit called Terabytes Written(TBW), and once its limit’s exceeded, some portions of the SSD will start to become permanently read-only or even totally inaccessible, until no more data can be written into any part of the SSD. As M.2 SSD is of no exception, Swap Space should only be used as the last resort rather than the poor man’s real memory. Otherwise, even for M.2 SSD with TBW as high as 5600, frequently using a large amount of Swap Space will still drastically shorten the actual life span of M.2 SSD. Considering its price, this isn’t economical at all.

Consider a PC with 24x2GB DDR5-8600 and an 8TB M.2 SSD with 5600TBW and 16GB Swap Space, if apps frequently borrow lots of memory from the future, that 16GB Swap Space can be frequently accessed with lots of TBW used. Let’s say it’s as crazy as having 8TB I/O on the Swap Space per day on average, after 5600 / 8 = 700 days, which is nearly 2 years, the TBW will be fully used and the M.2 SSD will start to have problems. Needless to say, the expected lifespan of M.2 SSD of this caliber should be as long as 10 years or even more, so using it this way is a waste of precious resources. Bear in mind that, because of wear leveling, it’s not just the NAND flash in the Swap Space that will suffer, but actually the entire M.2 SSD will be slowly damaged, and almost no M.2 SSD will partition a Swap Space on the hardware level.

Not only that, since the latency of that M.2 SSD is 15us, while that of those memory is 70ns, such a drastic difference on the latency will lead to thrashing when the Swap Space’s frequently accessed with large amounts of data. It’s because major page fault is a lot more expensive than a minor one, and frequent access of the Swap Space will lead to lots of major page faults in a short time. If they also involve large amounts of data, then many pages of virtual memory will have to be mapped frequently into the page table as well, with the fact that those pages need lots of time to be created. Besides, lots of major page fault in a short time can lead to frequent context switching, which can constantly interrupt the I/O of the entire OS or even the hardware itself in extreme cases, so thrashing should never be taken lightly. After all, not all major OS have counterparts of ZRAM or ZSWAP, so borrowing memory from the future can be very dangerous.

To avoid the Out Of Memory Error while allocating memory for every object, the following inequalities must be held:

M + S + D >= A >= A * (1 - F) * (1 - R) >= O * N * (1 - P)

S = the total amount of Swap Space from all M.2 SSD

D = the total amount of memory downloaded from the internet

F = the percentage of memory too fragmented to be allocated for creating any object

R = the percentage of memory allocation failed leading to resource starvation for the objects involved

O = the average amount of memory needed for object creation per object

N = the number of objects demanding memory allocation

P = the ratio of memory allocations for created objects being recycled in the object pool

There are 3 concepts not covered in this article yet – memory fragmentation, resource starvation and object pool:

Memory Fragmentation – It can be further divided into internal fragmentation and external fragmentation. Internal fragmentation will be a problem when there are lots of promises trying to asynchronously allocate memory for object creation, and this can be even more serious if those promises are also trying to borrow memory from the future. It’s because those promises themselves need to allocate small amounts of memory to be created, but if a memory page is 64KiB, lots of internal fragmentation will take place when many of those promises are created in a short time; External fragmentation can cause many objects that would’ve been created to fail to allocate enough contiguous memory, and this can eventually lead to many promises trying to create objects to be rejected instead. If many objects are created and destroyed in a short time, external fragmentation can quickly become very severe. Although both internal fragmentation and external fragmentation will be largely mitigated by the OS itself, and sometimes some Garbage-Collected languages can further help reducing internal fragmentation, both fragmentations will still be never trivial.

Resource Starvation – When memory allocation for object creation is performed asynchronously, it’s possible that some objects never managed to be created, causing the business logic needing those objects to be never run normally, ultimately causing other business logic having objects already created to throw exceptions as well. It’s especially the case when trying to borrow memory from the future, because the corresponding business logic doesn’t accept failure when first failing to create the objects needed, but rather gamble on the possibility that those objects can be created when they’re first needed. Such gambles are based on the anticipation that more physical memory will be added to the hardware on the fly, or more virtual memory will be downloaded from the internet, meaning that the whole architectural design’s the complete opposite of a fail-fast system, causing errors to be a lot harder to fix later on.

Object Pool – Let’s say you’ve a scrollable list having several hundred items, it’d be crazy to create every object for every item in the list right from the start, otherwise this can already cause the Out Of Memory error, or at least cause the list to take extremely long time to be loaded. Instead, all lightweight data of all items will be loaded into the memory in a lazy manner, but data like images will only be loaded while the corresponding items are currently displayed on the screen. Although frequent fast scrolling across lots of items will lead to frequent memory allocation and ultimately significant memory fragmentation, it’ll still better than loading several hundred images in the memory all at once.

Windows, MacOS and Linux are the 3 major OS in the PC market, but they handle the Out Of Memory error differently:

Windows – When Windows detects that the system’s about to be out of memory, it’ll first compress the least likely accessed memory pages to release some memory space, then it’ll start to use the reserved Swap Space if available memory is still tight, and finally rejects memory allocation requests from programs when there are still not enough memory. In very rare cases, where the memory demands of some programs cause the OS kernel to have insufficient memory in the non-paged area, the Windows might trigger BSOD to prevent permanently damaging the system itself.

MacOS – Similar to Windows, it’ll first compress the least likely accessed memory pages to release some memory space, as well as purging file caches and temporary data in memory, then it’ll start to use the Swap Space if available memory is still tight. But the difference is that, MacOS will keep extending the Swap Space until all SSD is used, only when they’re nearly full, restartable background services will be killed by Jetsam first, then users will have to manually kill some active apps if that’s still not enough. But if the thrashing’s too severe, it might cause a kernel panic instead.

Linux – Similar to MacOS, it’ll first recycle page caches to release some memory space, then it’ll start to use the reserved Swap Space if available memory is still tight. Users will either use ZRAM to compress the least likely accessed memory pages in the physical memory before using the Swap Space, or use ZSwap to compress those pages that’ll be in the SSD. If all these aren’t enough, the OS will call the OOM killer, which will assign oom_score to all apps consuming memory, and the ones with the highest scores will be forcibly killed by SIGKILL, but apps and services having root level access can set oom_score_adj to be -1000 to prevent themselves by being forcibly killed by the SIGKILL of the OOM killer.

The OOM killer in Linux deserves special attention here, because if many apps having severe memory leak set their corresponding oom_score_adj to be -1000, then the OS can still run out of memory even after the OOM killer kills all the other apps and services, which will cause the OS to have a kernel panic. Therefore, if some computer viruses managed to use privilege escalation to gain root level access, they can use their corresponding oom_score_adj to cause a kernel panic. While modern Linux won’t be so vulnerable to this attack vector, this vulnerability should still be taken seriously.

Sometimes it’s not the computer viruses that exploit this, but rather some legit apps borrowing memory from the future like crazy, by explicitly granting root access from users upon start, and using setuid to lower their access rights to its reasonable level after changing their corresponding oom_score_adj to -1000, the OOM killer will treat it as a normal user-level app that can’t be executed by SIGKILL. In contrast, some apps insisting on always synchronously allocate memory for object creations(thus being impossible to borrow memory from the future), might never touch their corresponding oom_score_adj, causing these apps not being the cause of OOM to be killed by the OOM killer instead.

With this much exploration on memory management, I can finally try to apply some wisdom there in real lives, and I’ll first talk about the essence of debt. When it comes to the raw pointers in C++, every new must be paired with exactly a single free, otherwise there will either be memory leak or double free; Similarly, for every debt involving a debtor and creditor, every borrowed debt must be repaid with the amount previously agreed upon, otherwise there will either be bad debt or risk of money laundering, usury, tax audit and frozen accounts, just like the risks caused by double free.

Viewing the essence of debt via promises, the creditor makes promises that the agreed amount will be disbursed to the debtor as a loan within the specified time interval, or the loan rejection logic previously agreed upon will be executed by the debtor; Similarly, the debtor makes promises that the borrowed amount will be repaid to the creditor within the specified time interval(the aspect of interests will be covered later), or the agreed logic of refusing to repay the debt will be executed by the creditor. Just as writing promises with only resolve but not reject is the anti-pattern of happy path coding(never handling any edge cases), making debt without exception handling is just asking for troubles.

Note that what people really need isn’t money itself, but rather the goods and services(including common goods and public services maintained by the government) that they can use money to buy from the market(or use tax to sustain the government). So disregarding the free-rider problem, when a debtor needs to borrow money from the creditor, it means that the debtor needs money to buy goods and services, but failed to produce goods and provide services with equivalent or higher market values. So the creditor will lend the loan only when he/she believes that the debtor is very likely to produce goods and provide services with market values higher than the loan amount before the loan expires.

When the creditor accumulates more and more bad debt due to the default of his/her debtors, the personal liquidity of that creditor will become smaller and smaller, eventually there will be so much bad debt that he/she won’t have any personal liquidity anymore, thus being unable to buy any needed goods and services. It’s like an app keep leaking more and more memory, until there are no more memory for that app to allocate for object creation, thus either throwing the Out Of Memory error or keep failing to run the needed business logic, eventually causing the app to cease functioning.

Before the adaptation of fiat money, money ultimately needs currently tangible entities as anchors, maybe they’re precious metal like gold, or maybe they’re a basket of daily necessities already on the market, but such anchors can never be anything in the future. On the other hand, fiat money doesn’t use any such concrete anchors, but rather use debt financing based on the national CPI and GDP to regulate the desired amount of M2, in order to avoid the problems caused by helicopter money, because now the central bank can use the policy rate to control the actual amount of M2.

Now that there’s debt involved, disregarding interest rates, those debt have to be eventually repaid, but the only way for the government to repay those debts is by tax and trade surplus in the future. However, when the scope is enlarged to the entire civilization, it’s the future tax of all governments in the world that keep repaying the debts necessary to keep fiat money working. The very fact that citizens are able to pay tax means that they’ve earned a lot more money than the tax they will pay, implying that they’ve produced goods and provided services of market value being much higher than the tax paid to the government. Therefore, the real anchors of fiat money are the goods and services that will be on the market in the future, forcing the civilization to keep producing more goods and providing more services than before, otherwise the debt will keep growing, until it’ll become so large that it’s impossible to repay anymore.

If physical memory corresponds to goods and services currently on the market, the Swap Space in the M.2 SSD corresponds to untapped natural resources pretending to the goods and services currently on the market, and the rest of the storage area in the M.2 SSD corresponds to obviously untapped natural resources, then the essence of fiat money becomes clear. In short, it’s just using asynchronous memory allocation to borrow memory from the future, based on the bet that more and more physical memory will be available on the fly, which is the same as the anticipation that the total amount of goods and services on the market will keep growing up in the future. In contrast, money using currently tangible entities as anchors strictly forbids asynchronous memory allocation, so it’s impossible for such money to borrow any goods and services from the future, meaning that any reckless object creation can lead to an instant OOM.

This can be easily illustrated by the 2008 financial crisis, ignoring the 50 trillion USD economic bubble vanished from the financial market, 19 trillion USD of global household wealth vaporized into thin air. On the other hand, how much worth of natural resources were destroyed? How much worth of goods were gone? How much worth of services were down? Probably nowhere near a trillion at most. This means that, even with a relatively conservative estimate, at least 18 trillion USD at that time were just promises of future goods and services, but never anything already materialized.

Nevertheless, fiat money does have its merits, provided that the central bank remain professional at all times. For instance, when the CPI increase rate is obviously too high or is noticeably higher than the GDP increase rate, if it’s because of having too much M2, then the policy rate can be increased to lower the CPI more than lowering the GDP, so that the excess M2 will first be collected by the commercial banks, then go back to the central bank. While the effects of such adjustments will be greatly diminished if the increase of CPI is due to lacking liquidity of goods and services, this shouldn’t occur so frequently. In fact, only the Russo-Ukrainian War and the 2026 Iran War have caused this recently.

Also, there might be some cases where some programs really need to borrow memory from the future, and I’ll use the following probably hypothetical example to show this. Let’s say you’ve a large server room having several server clusters, with each cluster having several servers as a single unit to run a unique app. In normal web traffic, a load balancer for each cluster will be enough, but when facing extremely large web traffic, if each customer request only needs a small data transfer object, while lots of memory needs to be allocated for creating objects to process them, synchronous memory allocation will either throw the Out Of Memory error, or have to deny some customer requests. Even with asynchronous memory allocation, if no memory’s borrowed from the future, some customers will still have to wait much longer than normal. Whereas if the app borrows memory from the future under this emergency, then immediately try to download memory from other server clusters, it’ll be possible that no customer have to wait for a very long time.

Recall that even M.2 SSD is still limited by its TBW, and if the Earth Ecosystem itself is the M.2 SSD of the civilization, then the rate of writing data shouldn’t be much higher than normal usage, otherwise the lifespan of the M.2 SSD will be a lot shorter than expected. However, if the M.2 SSD is mainly used as the Swap Space, then it’s almost certain that the rate of writing data will soon become ridiculously high, causing the M.2 SSD to degrade unusually quickly.
