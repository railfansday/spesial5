An LLM proxy setup solves a problem that becomes obvious the moment a team scales past a single developer hitting a single API. Provider dashboards show billing totals, aggregated over a billing cycle, but they do not surface token-level time-series data that engineers can actually act on. For a scenario like a paid-subscription chat frontend, where attributing costs to each client determines margin, aggregate billing data is nearly useless. Teams need to know which client, which request, and which model consumed what, broken down by tokens, latency, and cost.

The second pain point is operational security. Developers consistently report wanting upstream provider keys kept out of agents, test harnesses, and sandboxes. A single master key scattered across environments is both a security liability and a revocation nightmare -- when one environment is compromised, every integration sharing that key is exposed.

LiteLLM is the open-source proxy that addresses both problems directly: virtual API key issuance, unified per-request logging, and fallback routing across providers, all behind an OpenAI-compatible API surface.

By the end of this tutorial, readers will have a Dockerized LiteLLM proxy with virtual keys, request logging to a PostgreSQL database, multi-provider fallback between OpenAI and Anthropic, and an OWASP-aligned security checklist to harden the deployment.

Prerequisites: Docker and Docker Compose v2 (the docker compose plugin, not legacy docker-compose v1) installed, at least one upstream API key (OpenAI or Anthropic -- both are required for bidirectional fallback as configured), basic comfort with YAML and the terminal, and curl available on the host. For the Python fallback test later in this tutorial: Python 3.8+ and the openai package (pip install openai>=1.0.0).

The architecture is straightforward. Every LLM call flows through a single gateway:

The proxy intercepts every call, validates the virtual API key, attaches metadata (user, team, key ID), logs the full request and response cycle, and then decides which upstream model to hit based on the configured routing strategy. The client never communicates with the provider directly and never holds a provider key.

The LiteLLM image tag is pinned to main-v1.67.0. Confirm the tag exists before deployment: docker pull ghcr.io/berriai/litellm:main-v1.67.0-stable. For maximum reproducibility, pin to the image digest (@sha256:...) instead of the tag. Pinning matters for reproducibility and security auditing. The PostgreSQL service uses an Alpine-based image and includes a health check so the proxy does not start before the database is ready. The config YAML is bind-mounted read-only into the container. The DATABASE_URL is constructed in the Compose file's environment block so the database password is defined in only one place (POSTGRES_PASSWORD). The port binding is restricted to 127.0.0.1 so the proxy is not exposed on public interfaces; place a reverse proxy (nginx or Caddy) in front for external access with TLS.

Upstream keys live only in this file. They are never referenced in client code, never committed to version control, and never passed to agents or sandboxes. The master key authenticates administrative operations against the proxy's management API. All values must be set before the first run. On first run, LiteLLM automatically runs Prisma database migrations to create the required schema. This adds 30-60 seconds to the first startup compared to subsequent starts (the start_period: 60s in the health check accommodates this). If the litellm container exits immediately, check logs with docker compose logs litellm for migration errors before proceeding. Look for lines containing prisma or migration to confirm the schema was created successfully.

Use curl http://localhost:4000/health for a basic liveness check. For full readiness including model availability and database connectivity, use curl http://localhost:4000/health/readiness and confirm no error states are present. The readiness response includes the list of model names registered in the config, their provider status, and the database connectivity state. If any model fails to initialize (for example, due to a missing API key), it appears in the response with an error status. Confirming a clean readiness check before issuing virtual keys prevents debugging downstream failures that originate from misconfigured upstream credentials.

Virtual keys are the core isolation mechanism. Each client application, each agent, each staging environment receives its own key. That key can be restricted to specific models and capped at a maximum budget. If a sandbox key is compromised, revoking it has zero impact on production. If a single integration starts generating runaway costs, its budget cap halts spending automatically. Upstream provider credentials remain on the proxy server and are never exposed to consumers.

The success_callback: ["db"] and failure_callback: ["db"] directives in the config persist every request to the PostgreSQL database. This requires the database schema to be initialized (handled automatically by Prisma on first startup -- see the deployment section above). Each log entry captures the virtual key that made the call, the upstream model used, prompt and completion token counts, computed cost, response latency, and the HTTP status code. The failure callback logs failed requests (timeouts, 5xx errors, budget exceeded) with error details attached.

This is the data that provider dashboards do not surface as per-request rows queryable by key, model, and time range. Rather than a monthly billing total, engineers get per-request granularity keyed to their own virtual key identifiers, ready for time-series analysis.

LiteLLM also supports langfuse, prometheus, and custom webhook targets as callback destinations. These can be specified alongside or instead of "db" in the callback arrays.

Note: The virtual key is passed in a request header rather than as a URL query parameter to prevent it from being logged by reverse proxies, load balancers, and browser history. Verify the supported header name (X-Litellm-Key or equivalent) against your installed LiteLLM version's API reference.

The response is a JSON array of log entries, each containing the request ID, model, tokens, cost, and timestamp. Filtering by virtual key provides per-client cost attribution. Filtering by date range supports invoice generation and anomaly detection.

For teams that already run Langfuse, Prometheus, or Grafana, LiteLLM can forward callbacks to those systems. Adding "langfuse" to the success_callback array, along with the appropriate environment variables for the Langfuse API endpoint and keys, enables full trace-level observability with a UI. The LiteLLM documentation covers each integration's required configuration variables in detail.

The fallbacks key in the YAML config defines ordered fallback chains. When a primary model returns a 5xx error, times out (beyond the configured request_timeout), or raises a provider-level exception, LiteLLM automatically retries the request with the next model in the fallback list. The client sees no retry; the proxy handles it internally. The response includes metadata indicating which model actually served the request, but the client code does not need to implement any retry logic.

The num_retries: 2 setting means LiteLLM makes three total attempts on the primary model (the original request plus two retries) on retriable errors before triggering the fallback chain. The cooldown_period: 60 ensures that after repeated failures, the proxy backs off the failing provider for 60 seconds rather than immediately retrying against a provider that has explicitly refused requests. This prevents a single transient error from triggering an unnecessary provider switch while also respecting provider rate limits.

The openai Python SDK works unmodified because LiteLLM exposes an OpenAI-compatible API. The base_url points to the proxy, and the api_key is the virtual key. To verify fallback behavior, temporarily invalidate the upstream OpenAI key in the .env file and recreate the proxy container (docker compose up -d --force-recreate litellm) -- editing .env alone does not update a running container. All gpt-4o requests will then fail and fall back to claude-sonnet. The spend log entry for that request will show the fallback model as the one that served the response.

LiteLLM populates response.model with the actual serving model; if you find it returns the originally requested model name instead, verify the actual fallback model via the /spend/logs endpoint.

LiteLLM also supports a routing_strategy setting for load balancing across multiple deployments of the same model. For example, two separate OpenAI API keys for gpt-4o can be registered as separate entries in the model_list under the same model_name, and the proxy distributes requests between them. This is distinct from fallback routing, which switches to a different model or provider on failure. The two mechanisms can be combined: load balance across multiple deployments of the primary model, and fall back to a different provider if all deployments are unavailable.
