How to update one dynamic zone block in Strapi 5 (without deleting the others)

Tanggal: 2026-11-19

You have a Strapi 5 page built from a dynamic zone: a hero, a feature grid and a call to action. You want to change the hero's heading and nothing else. So you send an update with the hero block, and the feature grid and the call to action are gone.

That is how Strapi 5 writes lists. A dynamic zone, a repeatable component or a rich-text blocks field is replaced as a whole: the array you send becomes the new list, and anything you left out is deleted. The REST API works this way, and so does the update_ tool in Strapi's built-in MCP server. With one writer, that is a matter of sending the right array. With two writers, it is a race: each one sends a list built from its own read, the second write wins, and the first writer's block disappears with a 200 and no error.

People keep running into this. One GitHub issue reads, "found that I cannot update component". A docs issue is blunter: "Updating dynamic zones via REST API does not work." It does work. It just doesn't work the way most of us assume the first time.

Below are three routes, in order of how much control you have over the writer.

Disclosure up front: the third route uses writesafe, a plugin my company, IsoKron, built and maintains. It's free and MIT-licensed. Routes 1 and 2 need nothing but Strapi.

In Strapi v4 you could send a component's id and update that one row. The v4-to-v5 breaking changes document two things about that in Strapi 5:

The reporter of the issue above, on 5.32.0, got a 400 Invalid key id for sending id in a REST body at all. On 5.62.0 the server has moved on from the first point. A REST GET returns an id on every block, and if you read the draft (?status=draft) and send those ids back, the PUT returns 200 and updates the rows in place. Published ids still get a 400: "Some of the provided components in sections are not related to the entity".

None of which saves you. An id only decides whether Strapi updates a row or recreates it. The list is still replaced as a whole: a block you leave out is deleted, id or no id, and nothing in the request says which version you read.

Strapi's documented pattern for REST is still to leave ids out, so that is Route 1. I wouldn't build on undocumented id handling that changed between 5.32 and 5.62. The Document Service, which reads and writes the draft by default, accepts draft component ids by design; that is Route 2.

Strapi's recommended pattern for Content API clients is to omit component ids and send the complete list you want. Their docs put it in one line: "Include every component you want to keep."

This route is correct for one writer. It has no version check, so if an editor adds a testimonial block between your GET and your PUT, your PUT removes it. Nothing in the response tells you.

If the write happens in your own Strapi code (a controller, a cron job, a migration script), you can do what the REST docs say not to count on: load the draft with its component ids and update one entry in place. Strapi 5 ships an MCP server, which is how a growing number of pages now get edited: an agent connected at /mcp, sometimes while a person is in the admin panel. The built-in update_ tool behaves like REST. It replaces each list it is sent, it can't send component ids, and it has no version check.

We measured that during development on Strapi 5.62.0 with SQLite. An agent writing from a stale read while a colleague added a block deleted the colleague's block in 12 of 12 trials, for each of dynamic zones, repeatable components and blocks fields. None of 233 responses carried a conflict signal.

writesafe adds ws_* tools to that same /mcp endpoint through Strapi's plugin API (strapi.ai.mcp.registerTool), with the same admin tokens and permissions. Two of them do the work here.

ws_get returns the draft with a version token and a _key on every row of each top-level list. Over plain HTTP it's a JSON-RPC tools/call; the server is stateless, so no initialize is needed first:

Row ops (add, update, remove, move) apply to the current list inside the write transaction, under a row lock, not to the list as the agent last saw it. So a block a colleague added a minute ago survives, and the rows you didn't name keep their database ids. Row ops need no version, because a key is bound to the row's content: if someone changed the hero since your read, the call is refused with stale_row_key; if the hero is gone, row_not_found. Either way the agent reads again. It doesn't guess.

Sometimes you really do mean to replace the whole list. That's a set, and a set needs the version you read:

If the draft changed since that read, nothing is written. The reply is version_conflict with the current version, the current document and a retry hint telling the agent to re-apply only its own change.

In the same trials as above: with row ops, 0 of 36 colleague rows were lost and no ids were recreated. With a stale whole-list set, 36 of 36 writes were refused with version_conflict, and 36 of 36 landed after one re-read and retry. The table and conditions are in the reference.

To be plain about scope: this only applies to MCP tool calls. writesafe adds no REST routes and does not change what PUT /api/pages/:id does. Any HTTP client can make the calls above, not only an AI agent, but they go to /mcp, not /api. If your writers are REST clients, Routes 1 and 2 are your options.

By default (builtinUpdates: 'guard') the plugin also makes Strapi's built-in update_ refuse list and component writes and point the agent at ws_patch, so an agent can't take the old path by accident.

Then npm run build (the plugin adds a jobs page and a settings page to the admin) and restart. Create an admin token with Read and Update on your content type; tools/list on /mcp should now show the ws_* tools. Client setup for Claude Code, Cursor and others is in docs/clients.md.

None of this is a Strapi bug. Whole-list replacement is a reasonable contract for a REST API, and Strapi documents it. It just assumes one writer, and that assumption got quieter and less true once agents started editing content. If you only have one writer, send the full list and move on. If you have several, give each one a way to say which row it means and which version it read.

writesafe is on npm, in the Strapi Marketplace and on GitHub. If you hit a list edit the row ops don't cover, open an issue. The general idea behind it is written up in Send the change, not the object.
