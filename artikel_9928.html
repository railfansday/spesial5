Recall from our prior article, when we talked about macro hygiene, that Rust uses what’s known as “mixed-site hygiene”.Most items - other than local variables - are resolved from where the macro is invoked (functions, types, traits, etc.). For crate-local macros, you can be a little looser with this and require that the invoking code imports some items as needed to compile. But for crate-exported macros, it’s not a good idea to force the user to do this.Because of that, you should keep the following things in mind:You usually want to avoid using the crate keyword directly, because it may not refer to your crate.Since you’re in less control over the surrounding code for crate-exported macros, you should not assume anything about what has been imported at the invocation site.For declarative macros, there’s a special, always-present meta-variable called $crate, which resolves to the crate that your declarative macro is defined in. So it’s usually prudent to use that as a common reference point for any items needed by your macro’s expansion.// Example type - pretend we have a full type definition. pub struct MyCustomHashMap { /*...*/ } /// A declarative macro that produces a hash map. /// /// Note: Actually, the standard is attempting to add this! /// See: https://doc.rust-lang.org/stable/std/macro.hash_map.html #[macro_export] macro_rules! hash_map { ( $( $key:expr => $value:expr ),* $(,)? ) => {{ // Use our hashmap implementation from our crate. let mut map = $crate::MyCustomHashMap::new(); $( map.insert($key, $value); )* map }} } #[test] fn example() { let map = hash_map! { "key" => "value", }; assert_eq!(map.get("key"), Some(&"value")); } In the above example we demonstrate this with a MyCustomHashMap which our crate also exports.
