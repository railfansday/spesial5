My Mac Kept Freezing Because of 555 Idle MCP Servers

Tanggal: 2026-11-20

Posted on Nov 20 • Originally published at linkedin.com

My Mac kept freezing while I ran coding agents

It has 24 GB of RAM. Swap sat at 38.7 GB out of 39.9

Nothing heavy was open. Just a few agent sessions, or so I thought

My cleanup script flagged 287 processes. Most were two lines repeated about a hundred times each:

Both are MCP servers. I had started neither by hand

So I walked each process up to its parent and counted:

That makes 555 MCP server processes, about a third of everything running on my machine

Those memory numbers sit on the low side. Most of these processes had idled for days, so macOS had pushed them into swap. And ps leaves swap out

I blamed npx. It wraps each server in npm exec, and I assumed that wrapper swallowed the shutdown signal and left orphans behind

So I tested it. My script started a stand-in session and launched a server over stdio. Then it killed that session with SIGKILL to fake a crash

Both exited. Once a session dies, its server's stdin closes and any stdio server shuts down

Then I checked parents. All 555 servers had a live agent process above them. Those sessions were open and idle

One copy per session. Each stdio MCP server runs as a child of whichever session launched it. Ten sessions means ten copies of every server

Global config. I had four servers in the top-level mcpServers of ~/.claude.json. So every session in every project started all four. Most of those sessions made zero calls to Clarity or Colab

Sessions that stay open. Claude's desktop app keeps each sidebar session running, MCP children included. 78 of my 94 sessions were over a day old, and my oldest had run for 156 hours

And npx doubles the bill. Each npx server is two processes, and its wrapper eats about as much memory as the server itself

Red flag: those parent PIDs repeat over and over, and each one belongs to an agent

Prismor already sees each tool call my agents make, so it knows which MCP servers get used. I built three things on top of that

See it. prismor discover mcp now lists each server with its running copies, their memory and how many sessions called it in the last 7 days

On my Mac one screen showed it all. Three servers ran about 90 copies each, with zero calls all week. Prismor flags those

Both commands show their plan and ask before acting

Some servers I do call now and then. Prismor's MCP gateway can stop those after a quiet period (--idle-timeout). Agents still see their tools, and my next call starts the server again in about a quarter of a second

I leave it off for servers that hold state between calls, like one keeping a browser open

I tested each fix in an isolated rig: 10 stand-in sessions with 4 real MCP servers each, 3 of them never called

Then I ran it on my own Mac. 373 copies ended in 6 seconds

Swap dropped from 38.3 GB to 17.2 GB, and every open session kept running
