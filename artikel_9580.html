Dead-Letter Queues for Email Verification Webhooks

Tanggal: 2026-11-23

Email verification is often treated as a small REST API feature: create a token, send a message, and accept the callback. In production, the callback is a distributed-systems boundary. Providers retry, requests arrive out of order, and a valid message can become useless after its token expires.

A dead-letter queue gives the service somewhere explicit to put deliveries that cannot be completed safely. It also makes failures inspectable without turning every retry into another chance to activate an account incorrectly.

The webhook handler should not try to solve every problem synchronously. A provider may send a duplicate event, a downstream database can be briefly unavailable, or the message can refer to a verification token that has already expired. Treating all of those cases as HTTP 500 creates noisy retries. Treating all of them as HTTP 200 loses evidence.

The endpoint can acknowledge receipt after it durably records the event. Processing then happens from a queue or worker. This keeps the public API small and makes the failure policy visible in code.

Do not represent delivery with a single boolean such as processed. A small state machine is easier to query and safer to operate:

Store the provider event ID, event type, received timestamp, attempt count, next attempt time, and the last error. Keep the original payload in a restricted column or object store with a retention limit. Signature material and access tokens should be redacted before logs are emitted.

The provider event ID is the first idempotency key. If a sender does not provide one, derive a stable key from the verified event attributes, but document the collision tradeoff. A request ID alone is not enough because a retry normally has a new transport request ID.

It is also worth separating the delivery record from the verification result. A delivery can be completed while the token is rejected because it was expired. That is a business outcome, not necessarily a failed webhook.

The unique index turns duplicate delivery into a harmless conflict. The lease prevents a crashed worker from holding an event forever. Keep the lease shorter than the provider's retry horizon and renew it only if processing genuinely can take longer.

If completing the verification and recording an application event must be atomic, do both in one database transaction. For a separate message broker, use an outbox row in the same transaction, then publish the outbox record asynchronously. This is simpler to reason about than hoping two independent writes finish together.

The service should also define what happens when a verification link is used twice. A consumed token can produce a stable already_verified result. It should not be reactivated merely because a webhook was delivered again.

Retry policy belongs in the worker, not in the HTTP controller. Use bounded exponential backoff with jitter, and cap both the delay and the total attempts. For example, the delay can grow from seconds to minutes while a separate maximum age prevents an old event from being processed after its business meaning has gone stale.

This function only schedules work; it does not decide whether an error is retryable. Make that decision from typed errors or explicit result codes. A signature failure, malformed JSON, or expired token is terminal; a connection reset or lock timeout can be retried.

A Node.js worker should claim one event, process it with a timeout, and update the row in a finally path. If it dies, the lease expires and another worker can claim the event. Track lease recoveries because they can indicate a slow dependency or memory problem.

A dead-letter queue is an operational inbox, not a second normal queue. Give each record a reason code, payload fingerprint, first-seen time, and a link to the relevant request trace. A review tool can offer three actions: mark resolved, replay after a human decision, or discard after retention requirements are met.

When a test suite needs a throwaway email generator, make its mailbox lifecycle explicit in the fixture. A failed cleanup should not cause a worker to keep polling an inbox forever. Also, “tempail mail” is a common search typo, but it should remain plain text rather than becoming a misleading link.

The main design decision is not whether to add a queue. It is deciding which outcomes are safe to repeat and which must stop. Once that contract is explicit, a REST API, PostgreSQL transaction, and small Node.js worker can make email verification predictable even when providers behave unpredictably.
