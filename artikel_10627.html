A designer reports that a form’s error message overlaps its submit button. The developer opens the same page and sees no problem. Both are using the same code, but one has a narrow viewport, a translated interface, and an unusually long validation message.

A screenshot records what appeared on screen. A reproducible example also preserves the inputs, responses, permissions, and environment that produced it. That distinction matters when people review work at different times or join a project without knowing its undocumented conventions.

This article uses a workspace-invitation form as an example. The form accepts an email address and a role, submits a request, and displays either a confirmation or an error. The seven checks below turn its awkward states into something developers and designers can inspect together.

“The form looks broken” leaves too much for the next person to discover.

Include the browser, application revision, and relevant account permissions. Explain whether “360 pixels” means the browser’s layout viewport or the dimensions of an exported screenshot.

Avoid using real customer addresses in shared fixtures. A synthetic address such as member@example.test is sufficient to exercise the interface.

A form tested only with successful submissions is missing most of its interesting behavior.

Keep fixture values deterministic. Random addresses or constantly changing timestamps make visual comparisons harder to interpret.

Record expected outcomes alongside the data. A response containing a message does not establish where the interface should display it, whether focus should move, or which fields should remain editable.

Treat those as product decisions and test them explicitly.

Some failures can be reproduced by passing props to a component. Others depend on the request lifecycle.

Storybook args can describe inputs for isolated component states. An error-state story might supply a message, current field values, and a pending flag to a presentational form component.

However, passing pending: true does not prove that the real application enters or exits that state correctly.

For network-dependent behavior, use Mock Service Worker or your test runner’s request interception to supply a controlled response. Preserve the distinction between these two checks:

Avoid mocking the same endpoint in several overlapping layers. When a response is unexpected, the team should be able to identify which fixture produced it.

Also keep at least some integration coverage against the real API. A frontend mock that returns an outdated error shape can make the interface look reliable while hiding a broken contract.

Open the failing state at the recorded viewport. Inspect the error container, its parent layout, and the submit button.

Look for constraints such as fixed heights, absolute positioning, hidden overflow, and a flex or grid item that refuses to shrink.

Review the first baseline manually. A screenshot test can faithfully preserve a bug if the initial image is approved without inspection. Disabling animation for a snapshot also does not test the accessibility of motion itself.

The practical requirement for distributed contributors is a review process that carries its own context. Attach the exact fixture, preview location, reproduction command, and expected behavior to the issue or pull request.

Keep the open decision separate from the implemented behavior. This prevents reviewers from assuming that a visual change has already resolved a product question.

Name the person or team responsible for the component, and identify where design decisions are recorded. A stable fixture is useful only if someone maintains it as the component evolves.

A form that no longer overlaps can still be difficult to use.

Verify visible labels, keyboard navigation, focus visibility, and the relationship between errors and their fields. For field-level errors, consider aria-invalid and aria-describedby where appropriate.

The alert in the test example assumes a newly displayed form-level error. Do not add several competing live regions or announce every keystroke. Check the resulting experience with assistive technology.
