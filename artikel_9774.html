Build a Hyperliquid wallet tracker from the public info endpoint, in TypeScript

Tanggal: 2026-11-20

You have a Hyperliquid wallet address and you want to read it like a trader. What is open right now: which coin, long or short, how big, at what entry, how much unrealized profit or loss, at what leverage, and where is the liquidation price? And over the recent fills: how many, how much realized profit, and how often did a closing fill win?

You do not need an API key or a library for this. Hyperliquid exposes a public info endpoint, and perp state is public on chain. This post builds the tracker in TypeScript, calls the live endpoint twice, and runs the output on a small fixture so the numbers below are reproducible.

Disclosure: I am the founder of copy.top. We publish a free Hyperliquid wallet tracker page. The code below is a separate, minimal version written for this article. copy.top is independent and not affiliated with Hyperliquid.

The files are TypeScript and run on Node 22.6 or newer with type stripping (tested here on Node 24.7):

Imports between files need the .ts extension, and types use import type, which this mode requires. For plain JavaScript, rename to .mjs, delete the annotations and the import type lines.

Everything goes to one URL, POST https://api.hyperliquid.xyz/info, with a JSON body. No key, no sign-up. Two request types matter here:

Rate limits exist, so keep calls few. This tracker makes exactly two requests per run. If you poll, space the calls out and cache the answer.

I checked the field names below against real responses. In clearinghouseState, each entry of assetPositions has a position with coin, szi, entryPx, unrealizedPnl, liquidationPx, leverage and more. Numbers arrive as strings. szi is the signed size: negative means short. In userFills, each fill has coin, px, sz, side (A for sell, B for buy), time in milliseconds, dir (such as Open Short or Close Long), closedPnl and fee, plus ids I do not use.

AbortSignal.timeout(20_000) stops a hung request after 20 seconds instead of waiting forever. A non-200 answer throws.

Positions come from szi: skip zero, and read the sign for long or short. I treat liquidationPx as optional and print none if it is null.

For fills, a fill that closes something has a non-zero closedPnl. The summary counts those, counts the positive ones as wins, and sums closedPnl as given. I do not subtract fee from it, so I show fees on their own line.

With no argument it uses the fixture. With an address it calls the live endpoint.

Live use is node --experimental-strip-types run.ts 0xYOUR_ADDRESS.

Where do you find an address to try? Hyperliquid's own info endpoint has no leaderboard request (I tried {"type":"leaderboard"} and it was rejected). Hyperliquid does publish its leaderboard as a public JSON file at https://stats-data.hyperliquid.xyz/Mainnet/leaderboard, but it is about 39 MB, so I only read the start of it to get one address. I then made the two real calls above for that kind of wallet and trimmed the answers into a fixture. I dropped the ids and the address, kept the real strings for two positions and eight fills, and added one invented BTC long so the long case shows up. Live numbers move every second, so the output below comes from this fixture and not from the live wallet.

Check one line by hand. Of the seven closing fills, four have a positive closedPnl (147.01, 34.43, 32.35 and 17.32) and three are negative, so 4 of 7 is 57 percent. The realized total is the sum of all seven. In the HYPE row the liquidation price (103.36) is above the entry (76.73) because the position is short: the price has to rise to get there.

I also ran the same code against a live public wallet. It printed one open BTC short and 2000 fills, and the field names matched what is described above.

Past results do not predict future results. Nothing here is financial advice, and trading perps with leverage is risky: you can lose everything you put in.
