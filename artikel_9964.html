If you havenât read the earlier yk post, hereâs a very brief refresher. Given a lightly modified C interpreter6 as input, yk produces a VM with a meta-tracing JIT compiler as output7. yk doesnât aim to produce the fastest possible JIT compiling language implementation: rather, it aims to make the language implementation you know and love somewhat faster while retaining 100% compatibility. Put another way a âykifiedâ interpreter is a fork of the existing C version of the interpreter, with (hopefully!) a handful of adjustments.

As with any meta-tracing JIT compiler, yk identifies hot loops in the guest language (e.g. Lua or Python), and traces the interpreter (i.e. records what the C code is executing while it is interpreting the guest language). It then optimises those traces and converts them to machine code.

yk requires interpreters to tell it where potential loops in the guest language are via the YkLocation struct. Optionally â though if you want to get good performance, definitely necessary! â interpreter authors can add optimisation hints that embed knowledge about the language or its common idioms of use such as âat this point this seemingly dynamic value almost never changesâ. In general, working out where to put YkLocations is relatively easy, but working out where to put hints requires a much greater understanding of the interpreter, and careful measurement to understand which do and donât help.

The challenge I face when adapting an interpreter for yk is that I rarely know the interpreter well, if at all. Rather than trying to do everything at once, I have learnt to start off as simple as possible: I try and do the minimum changes that lead to some traces being recorded and compiled to machine code. Iâve also learnt to make sure that the languageâs test suite works from this very first step: keeping it working thereafter is not only much easier, but it lessens the number of times one attempts optimisations that are unsound.

For a simple interpreter, you might get a basic JIT compiler from an interpreter with fewer than 10LoC (Lines-of-Code) changed. For somewhat bigger interpreters, a few more changes tend to be necessary. Fortunately, it didnât take very long to work out what. 4 years ago, CPython added support for quickening under the heading of âspecialisationâ. The problem for yk is that sometimes a programâs opcodes can transition between specialised and unspecialised opcodes a large number of times, and the simple way Iâd added yk support meant that each transition implicitly threw away the associated trace and created a new one. My first port of call when optimising an interpreter is to tackle interpreter dispatch. When an interpreter is executing a program, it continually asks âwhat is the opcode of the current instruction? I was particularly lucky because the tier2 interpreter uses âexecutorsâ which are traces of (optimised) instructions. That means that we can attach a simple monotonically increasing integer code ID to a _PyExecutorObject and know that for a given code ID, an opcode at index I will always be the same.
