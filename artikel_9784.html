What happens when AI agents do not simply agree with one another, but solve independently, challenge assumptions, compare evidence, and make uncertainty visible? This is the engineering experiment behind Assembly.

Project status: Experimental; actively under development

Status snapshot used in this article: 17 November 2026

A large language model can give you a confident answer that is completely wrong. The difficult part is that, on the screen, a confident wrong answer can look almost identical to a confident correct one.

You can ask another model, repeat the question, or verify every claim yourself. But those steps are manual. They also do not guarantee that the second answer is independent of the first or that either answer has been checked against useful evidence.

That observation led me to build Assembly, an experimental multi-agent AI workspace. Instead of relying on one model response, Assembly explores a structured workflow: multiple agents attempt a problem independently, their answers are compared, disagreements can trigger research or debate, and a final response is assembled with the remaining uncertainty made explicit.

The important word here is explores. Assembly is an engineering experiment, not a proven method for making AI answers more accurate. Its orchestration, routing, consensus, and debate components have been implemented and tested offline, but live reliability and answer-quality improvements have not yet been established.

This article explains why I started the project, how its architecture works, what has been implemented, and what still needs to be tested.

Assembly is an attempt to make some of that process explicit.

The core idea is straightforward: let agents work independently before exposing them to one another's conclusions. Then compare their positions and evidence. When a meaningful disagreement remains, use another stage—such as research, debate, or an adversarial check—to investigate it. Finally, produce a synthesis that does not hide unresolved uncertainty.

This approach is related to research on self-consistency, model ensembles, and multi-agent debate. However, existing research also contains important caveats: self-correction without external feedback can be unreliable, and debate does not improve every task or every baseline. Assembly therefore treats the value of multi-agent orchestration as an open question.

Assembly is a time-bounded, bring-your-own-key (BYOK) AI workspace. A user supplies their own provider credentials, chooses a time budget, and submits a problem. The system then plans the work and selects a temporary team of agents from the configured model catalog.

The intended output is not merely a merged answer. Assembly is designed to retain structured information such as each agent's position, confidence, evidence, supporting or disagreeing agents, and remaining uncertainty.

The current time-budget options are 3, 5, 10, and 15 minutes. These limits are intended to keep a run bounded and to make the system account for available model capacity before work begins.

Assembly is not presented as a production-ready decision system. It should not be the sole basis for medical, legal, financial, security-critical, or emergency decisions.

Assembly uses a browser-based frontend and a Python backend, with the orchestration engine coordinating the AI workflow.

The frontend is a static-export Next.js application built with React and TypeScript, with Tailwind CSS for styling. It handles provider-key configuration, settings, time-budget selection, run controls, progress updates, and results.

The web workspace keeps user-side information—such as settings, usage, and run history—in browser storage. IndexedDB is the primary storage layer, with localStorage as a fallback. The application also uses a typed API client so that request and event payloads have a defined contract.

The backend is built with FastAPI. It exposes endpoints for the model catalog, preflight checks, provider-key testing, run execution, event streaming, and cancellation.

Validation is performed on the server as well as the client. For example, attachment validation on the server is authoritative; a client-side check is not treated as a security boundary.

This is the core of Assembly. It handles planning, capacity checks, temporary team formation, model routing, independent solving, consensus scoring, debate, adversarial checks, and synthesis.

Provider adapters sit behind a common interface. A family-aware router selects configured models for different roles while considering available keys and quota information.

Provider and model identifiers, family classifications, role information, and quota metadata are maintained in a central models.yaml catalog rather than being duplicated throughout the application.

Adapters have been written for several providers, including Gemini, Groq, OpenRouter, and Hugging Face. Cerebras was considered during early development but was unusable on one test account. Mock and replay providers are also available so that the default test suite can run without making live provider calls.

Why route by model family rather than provider? Two different providers may expose the same underlying model. Treating those as independent perspectives could create a misleading impression of diversity. Family-aware routing is intended to reduce that risk, although genuine independence between model families has not yet been measured.

When a run needs external information, the research module can search and fetch bounded static-page content. Tavily is the primary search service. The fallback path may use Wikipedia, arXiv, Semantic Scholar, or DuckDuckGo.

Retrieved content is sanitized and treated as untrusted evidence before it is included in a prompt. A citation manager deduplicates sources so that the final answer can include the sources actually used.

Run progress is delivered to the browser using Server-Sent Events (SSE). The frontend can display agent activity, consensus changes, disagreements, and the final response. Cancellation is handled through a separate API endpoint.

SSE replaced an earlier WebSocket-based prototype because the run-progress flow is primarily one-way: the backend sends updates to the browser, while cancellation can be handled separately.

The run is bounded by its time budget. It may also end because of cancellation, provider failure, or other stopping conditions. The design aims to avoid debate rounds that add no value: a round should resolve a disagreement, add evidence, correct an error, or materially change the assessment. If the deadline arrives while agreement is weak, the remaining uncertainty should be reported rather than concealed.

A key part of the workflow is the adversarial check. When agents appear to agree too early, one agent can be asked to assume that the consensus is wrong and search for the strongest counterargument. This is a design mechanism, not proof that premature agreement will always be detected.

The current stack is deliberately practical for a small, local-first project:

SQLite is used for local and planned desktop execution, where a database server would add unnecessary setup. The hosted backend is designed not to persist run questions, answers, or provider keys in a server database. Earlier plans involving PostgreSQL and Redis were dropped from the current demo scope.

The desktop direction is a Windows application using Tauri with the Python backend bundled as a local sidecar. Tauri provides a lightweight desktop shell, but the sidecar, installer, and credential-store integration still require work.

Assembly uses a bring-your-own-key model because free-tier quotas are generally tied to individual provider accounts. Instead of relying on one shared operator key, users configure their own provider credentials.

That design avoids a shared project credential, but it makes key handling especially important. The current implementation has limitations that should be understood before using real keys.

In the hosted web experience, provider keys are stored in the browser's IndexedDB, with localStorage as a fallback. They are stored as readable values: they are not encrypted at rest and are not protected by an operating-system credential vault. JavaScript running on the same origin could potentially read them, including injected JavaScript in an XSS incident.

The browser sends keys to the backend over HTTPS for preflight, key-test, and run requests. Under the documented request behaviour, preflight and run requests send all saved provider keys regardless of which models are selected; run requests can also send a saved Tavily key. A key-test request sends only the key being tested.

The backend is designed to use keys transiently and not write them to a database or disk. Request handling avoids logging raw request bodies, and a masking filter is used to scrub key-like values. However, hosting providers may maintain their own network or operational logs outside the application's control.

The desktop version is intended to use the Windows credential store. A Windows Credential Manager adapter exists in the repository, but the current settings flow still uses the WebView browser vault. OS credential-store use is therefore only partially implemented; it is not yet the primary save path.

Search results, fetched pages, and uploaded files are untrusted inputs. They may contain indirect prompt-injection instructions intended to manipulate a model. Assembly applies structural mitigations: retrieved text is sanitized and marked as untrusted evidence; attachment content is escaped, size-limited, and marked untrusted; fetching is bounded; and attachment bodies are not intended to appear in logs, events, database rows, or error text.

These measures reduce exposure but do not eliminate prompt injection. The project has not yet completed a systematic adversarial evaluation of injection robustness. A malicious claim could also be repeated or amplified as it passes from one agent to another.

Assembly starts with a modest premise: one model response does not provide an independent check. A structured group of agents might make disagreements, evidence gaps, and uncertainty easier to inspect.

The project turns that premise into a working engineering pipeline: planning, family-aware model selection, independent solving, consensus scoring, debate, adversarial checking, and synthesis. It combines a Next.js frontend, a FastAPI backend, multiple provider adapters, and a BYOK approach designed around user-supplied model access.

There is meaningful implementation work in place, and the offline test suite covers important parts of the system. But the central hypothesis remains untested. Live operational reliability has not been established, comparative benchmark results do not yet exist, and the hosted execution and Windows desktop paths still need completion.

That is why I want to keep the project's limitations visible. If multi-agent orchestration helps, the benchmark should show where and by how much. If it does not, that is worth reporting too.
