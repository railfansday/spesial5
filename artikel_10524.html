Every integration that moves something out of your system has the same weak point, and it is

not the happy path. It is the second attempt.

Your code posts a document to a provider. The connection drops before the response arrives. You now hold no job id, no confirmation and no idea whether anything left the building. The timeout told you about your network. It told you nothing about theirs.

So you retry, and you either send the thing twice or you never send it at all. Pick one, because

without help from the API you cannot have both.

The first instinct is a client-side guard. Hash the payload, keep a table of what you have already

That works until the duplicate attempt comes from a different process, a different container, or a

queue worker that started after a deploy. Your table is local state defending against a distributed

The second instinct is to ask the provider whether the job exists. That means listing recent jobs

and matching on something, usually the recipient and a timestamp window. It is a search, and

searches have false positives. Two legitimate sends to the same recipient a minute apart look exactly like one send and one retry.

The third instinct is to make the operation naturally idempotent. That works beautifully for a database upsert and fails completely for anything that leaves your control. A document that has been transmitted cannot be un-transmitted by a second call.

An idempotency key, generated by the caller, attached to the request, and honoured by the

The contract is simple. The caller invents a unique string per logical operation. Every attempt

carries the same string. The first request to arrive does the work and records the result against that key. Every later request carrying that string gets the recorded result back instead of doing the work again.

The important part is where the state lives. It is on the server, which is the only place that knows

whether the job exists. Your retry loop stops needing to be clever. It just needs to reuse the key.

Stripe popularised this pattern and the reason it spread is that the alternative is unbounded.

Without it, every caller writes their own deduplication, badly, and the failure only shows up under load.

Document and messaging APIs are where it matters most, because the side effect is visible to

someone outside your company. Fax for Agents is a current example of the pattern taken

seriously. It requires an Idempotency-Key on every mutating call, so a retry hands back the

same job instead of creating a second one.

Idempotency solves the duplicate. It does not solve the other half, which is that you still do not know what happened.

Most integrations model this as a boolean. Sent, or not sent. That is wrong, and you discover it

the first time a transmission half completes.

A useful state machine for a send has more room in it. Fax for Agents publishes six states:

queued, active, partial, failed, unknown and delivered. Two of those are the interesting ones.

unknown means the provider has not said. Not failed, not delivered. The correct response to

unknown is to wait. A retry loop that treats unknown as failure needs rewriting, because that is

how you produce duplicates even with idempotency in place.
