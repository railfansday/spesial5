Most slow-query investigations start in the wrong place: a CPU alert fires, someone opens the plan cache, and whatever is running right now gets tuned. That finds the loudest query, not necessarily the costliest one, and it says nothing about what changed.

Query Store supplies the missing piece: historical visibility. It records query text, execution plans, and runtime statistics over time intervals. Because this information is persisted in the user database, it survives SQL Server restarts. Execution plans then help explain why a particular query is slow.

An Index Seek is not always better than an Index Scan. SQL Server chooses an access method based on estimated cost, cardinality, available indexes, and the amount of data required. However, certain patterns deserve investigation.

Before creating an index, evaluate existing indexes, write overhead, storage consumption, and whether the proposed index would actually improve the workload.

For example, comparing an integer column with a string parameter can introduce an implicit conversion and prevent an efficient index access path in some circumstances. Similarly, spills to tempdb can indicate that an operator received an insufficient memory grant. These warnings help identify where further investigation is needed.

The objective is not simply to make one execution faster. It is to restore predictable performance across the workload.

Even with Query Store enabled, several issues can affect the accuracy of your investigation.

1. Query Store stops collecting information

A full Query Store can transition into read-only mode.

Check sys.database_query_store_options regularly, especially actual_state_desc, desired_state_desc, and readonly_reason.

2. Ad hoc workloads inflate storage consumption

Applications that generate many unparameterized queries can create large numbers of distinct query entries. Use an appropriate capture mode and investigate parameterization opportunities.

A reasonable average duration can hide occasional executions that take several seconds. Examine maximum duration, standard deviation, execution counts, and individual runtime intervals before deciding that a plan is healthy.

4. Time zones create misleading correlations

Query Store timestamps are stored in UTC. Convert timestamps appropriately before comparing them with application logs, deployment records, or monitoring dashboards.

5. Historical statistics are not necessarily actual execution plans

Query Store provides valuable plan history and aggregated runtime statistics, but it should not be mistaken for a complete historical record of actual execution plans with actual row counts. Use actual execution plans and appropriate runtime diagnostics when deeper investigation is necessary.

The examples in this article target different SQL Server versions.

Always verify the feature's availability and configuration requirements for your SQL Server edition and deployment environment.

Diagnosing slow SQL queries requires more than identifying expensive operators in an execution plan. The most effective approach combines historical workload information with detailed execution-plan analysis.

The tooling is not the hardest part of SQL Server performance troubleshooting. What separates a ten-minute diagnosis from a three-day investigation is having the historical evidence to understand what changed. Query Store provides that evidence. Execution plans help explain it. Together, they give database engineers a repeatable approach to diagnosing and resolving SQL Server performance problems.
