Code review shouldn't catch import rules: a React Native architecture ESLint enforces

Tanggal: 2026-11-16

Posted on Nov 16 • Originally published at praveensingh.co.in

Short answer: Bareship writes its architecture down as lint errors instead of a wiki page. ESLint checks that imports go one way through five layers and that features never import each other, and dependency-cruiser checks the whole graph again in CI. Other rules each came from a real bug: hard-coded text, left/right styles that don't mirror in right-to-left languages, and calls the React Compiler caches. Every error message says how to fix it and links the decision behind it, so a teammate or an AI agent can fix the code without asking anyone.

This is Part 3 of Building Bareship. Part 2 covered the offline queue and ended with a promise: an architecture the linter enforces.

Every React Native project starts with folders and good intentions. Someone draws the layers on a whiteboard, everyone agrees, and it holds for a few weeks. Then a settings screen borrows a hook from the feed because it's quicker, a string skips translation because it's "temporary", and the person who knew the rules is on leave. Code review is supposed to catch this, but reviewers are looking at whether the feature works, not at import paths.

So in Bareship the rules are errors. They show up in the editor while you type, block the commit, and fail CI.

The rule that matters most is the one in the middle row: a feature never imports another feature. If the settings screen needs the feed's data, that's a sign the shared part belongs lower down, in entities or shared. Then you can delete or rewrite the feed without touching settings, which is also how pnpm strip-examples can remove the whole demo with one command.

eslint-plugin-boundaries enforces this in the editor. The whole policy is generated from one list, so the order of the layers is written down exactly once:

Two more import rules sit on top. app may use a feature only through its index.ts, its public API, and never reach into its files. And nobody imports a folder's index.ts barrel inside the layers: barrels caused require cycles and loaded more than a screen needed. Removing them touched 29 files, and the Android release bundle went from 3,831 to 3,824 KB.

dependency-cruiser checks the same layer rules a second time, over the whole graph at once. It also catches what a per-file linter can't see: import cycles across many files, and app code that imports a dev dependency, such as a test or mock tool that should never ship in the app.

On top of these, the 15 React Compiler rules from eslint-plugin-react-hooks are all errors, not warnings.

Most of the table needs no plugin. ESLint's built-in no-restricted-syntax takes an AST selector and a message, which is enough for a lot of house rules:

If you only take one idea from this post, take this one: when a bug comes from a pattern, a ten-line lint rule stops the whole class of bug, in every file, for every future developer.

Look at the messages again. None of them just says "not allowed". Each one says what to do instead, and most name the decision record that explains why: docs/decisions/0005, ADR 0017, AGENTS.md › Styling.

That matters for people: a new teammate fixes the code from the message, without asking anyone or opening a wiki. It matters even more for AI coding agents. I built much of Bareship with Claude Code, and an agent reads a lint error far more reliably than it remembers a paragraph of guidelines. AGENTS.md has one line about these rules: "Fix the import, never disable the rule." When the agent broke a rule, the fix went into the linter or its message, not into a comment on a pull request. The next agent, or the next person, then gets the right answer from the tool.

The first week with rules like these feels strict. A quick fix you'd normally push needs a moment's thought about where the code belongs. After that, nobody has to remember the rules, and review is about the feature again.

The rules also have to cover your own tools. The formatRelative rule arrived in 0.2, but the feature generator kept writing a list screen that called it. So in 0.4.0, pnpm gen feature produced code its own linter rejected. Nothing ran the generators end to end, so nobody noticed until I tried one while writing a post. 0.4.1 fixed the template and added scripts/ci/check-generators.sh, which runs every generator on a scratch copy and checks the result for types, lint, formatting, boundaries and tests.

And sometimes a rule is wrong for your app. Then you change it in one place, in eslint.config.mjs, and write down why in a decision record next to the others. That's the point: a rule you disagree with is a conversation about one line of config, not about whose turn it is to be strict in review.
