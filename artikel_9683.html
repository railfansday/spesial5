Come far leggere a Claude Code i check di GitNest e proporre un nuovo tentativo che approvi tu in osFoundry

Tanggal: 2026-11-12

Alla fine di questa guida puoi chiedere a Claude Code "il change set di checkout è verde?" e ricevere una risposta letta da osFoundry, non indovinata dai tuoi test locali. Claude Code elenca i check sul commit composto del change set, ti dice quale è fallito e, se sembra instabile (flaky), richiede un nuovo tentativo solo per quel check. Il retry non parte quando lo chiede Claude Code. Arriva in osFoundry come scheda "Retry GitNest check" con la versione del change set e il commit esatto, e viene eseguito solo quando fai clic su Approve retry.

La CLI di osFoundry stampa la stessa riga con osfoundry agent connect claude --print. In Claude Code esegui /mcp, scegli osfoundry e poi Authenticate. Il browser apre osFoundry e scegli un workspace. Da lì gli strumenti compaiono come mcp__osfoundry__….

Un check mai eseguito non si può né leggere né ritentare. In GitNest apri la pagina delle impostazioni del repository. Qui contano due pannelli:

In GitNest, la sezione Project del repository dice "Connected agents in this project can use approved GitNest read tools when their connection owner still has repository access." Solo il proprietario del repository vede il selettore. Scegli un progetto e osFoundry conferma "Repository project updated".

Poi apri l'icona della chiave → Connected, seleziona la connessione di Claude Code e, sotto Projects, aggiungila a quel progetto.

Esempio: Aggiunta della connessione di Claude Code al progetto che contiene il repository

Sotto Tools, nello stesso pannello, "All supported tools are on by default." Quelli usati in questa guida compaiono come list gitnest work, list gitnest checks, list gitnest saved results, read gitnest work e propose gitnest check rerun. Per lasciare a Claude Code la sola lettura dei check, togli la spunta a propose gitnest check rerun e fai clic su Save tools.

I nomi di strumenti e argomenti sono quelli che il server di osFoundry restituisce da tools/list. Repository, change set, ID, nomi dei check e risposte sono contenuti di esempio.

Claude Code chiede conferma prima della chiamata propose perché lo strumento è annotato con destructiveHint: true. È la sua richiesta di permesso, separata dall'approvazione in osFoundry.

Prima di approvare, guarda il change set. Nella sua pagina di revisione in GitNest, il pannello dei check sta sopra le schede e riassume il commit composto in una riga, qui "Checks did not pass: e2e", con ogni check e il suo stato sotto. Un change set non ancora composto non mostra alcun pannello, e un commit senza check mostra "No checks have run against this commit" invece di una spunta.

La campanella mostra " proposes retrying a GitNest check". In icona della chiave → Connected → la tua connessione → Needs your approval, la scheda riporta:

Esempio: Una proposta Retry GitNest check sotto Needs your approval

"Review change set before approving" apre la stessa pagina di revisione. Se il commit sulla scheda è quello che hai controllato, fai clic su Approve retry. Il check e2e torna in coda per quel commit e il tuo runner lo prende in carico. Poi avvisa Claude Code, che richiama list_gitnest_checks.

Il retry indica un commit, non un branch. propose_gitnest_check_rerun richiede expected_change_set_version e expected_composition_oid, quindi la scheda dice sempre quale commit composto Claude Code ha visto fallire. Se qualcuno ricompone il change set mentre la scheda è in attesa, il commit che approveresti non è più quello sulla scheda. osFoundry ricontrolla versione, commit e stato del check al clic, e una scheda non aggiornata non viene eseguita. Il pannello mostra allora "Could not decide this proposal. Its access may have changed." Chiedi a Claude Code di rileggere i check e di proporre sul nuovo commit.

Si può ritentare solo un check concluso. La descrizione dello strumento dice "retry one finished check", e lo stato del check fa parte del ricontrollo. Un check già di nuovo in coda o in esecuzione, perché qualcun altro l'ha ritentato o il change set è stato ricomposto, non viene messo in coda una seconda volta.

Un check per proposta. check_name è una sola stringa di massimo 200 caratteri. Ritentare l'intera suite richiede una scheda per check, ognuna decisa da te. Così il retry di un e2e instabile non rilancia di nascosto una scansione di sicurezza che preferisci lasciare fallita.

In questo percorso niente gira sulle macchine di osFoundry né modifica il codice. I check girano sui runner che hai registrato. Approvare un retry rimette in coda un check, e basta. Non ricompone, non fa merge e non pubblica. Il merge aspetta comunque che ogni check obbligatorio passi sul commit.

Le letture restano essenziali. list_gitnest_checks restituisce uno stato limitato solo per il commit composto attuale. list_gitnest_saved_results e read_gitnest_work escludono i binding locali e le credenziali, quindi Claude Code può dirti che un test è fallito, ma non vede mai il token del runner né il percorso del tuo checkout locale.

Per provarlo, registra un runner su una macchina libera, fai push di un change set con un check che sai essere instabile e chiedi a Claude Code se è verde. La pagina di GitNest mostra le schermate di repository, change set e check, e la pagina Connected descrive il pannello di approvazione.
