The two-account test: one check to run on your Supabase app before launch

Tanggal: 2026-11-14

This post was drafted with AI assistance. It comes from Try the Door, which sells kits for builders shipping apps made with AI tools. The whole check is below, free; one paragraph at the end names the kits.

If you built your app with Cursor, Lovable, Bolt or Replit on Supabase, run this before launch: can one signed-in user read another user's rows?

It hides for a simple reason. While you build, you are signed in as yourself. Every query returns your data, and that looks right. But "I can see my rows" and "only I can see my rows" are two different claims, and the happy path only tests the first.

Run this only on an app you own or are authorized to test.

In your own app, make two accounts, A and B. A second browser or a private window keeps both signed in.

Sign in as A and create something real: a note, an order, a profile field. An empty result also comes back when A owns nothing, so an empty result alone proves nothing.

Two common causes: row-level security (RLS) is off on the table, or a policy says, in effect, "any signed-in user can read". Both look fine when you only ever test as yourself.

Firestore rules do the same scoping job, and the same two-account test applies.
