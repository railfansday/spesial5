Why Stripe sends your webhook twice (and how to process it once)

Tanggal: 2026-11-22

Posted on Nov 22 • Originally published at hamichi.dev

Stripe will send you the same event twice. Your endpoint timed out. You returned a 5xx. The process died after the work but before the 200.

In live mode, Stripe retries for up to three days, with exponential backoff. In a sandbox, it retries three times over a few hours. Stripe does not promise a single delivery, or a tidy order. The second POST is not a bug in Stripe. It is the contract.

The unique key for a delivery is event.id. Store it atomically before you grant anything. The second delivery should return 200 and do nothing.

A flag you read and then write is not enough. Two requests can both think they are first. A unique constraint, or a SET key NX lease, is what stops a double license.

Return 200 for a duplicate. A 500 makes Stripe retry a delivery you already handled.

Deduping only on event.id is necessary, and not sufficient. Creating a subscription can produce customer.subscription.created, invoice.created, invoice.paid, and charge.created. A Checkout payment can arrive as checkout.session.completed and later as checkout.session.async_payment_succeeded. Those are different Event objects. Key fulfillment by the Checkout Session id, or by the invoice or subscription you actually fulfill.

Stripe does not guarantee event order. Snapshot events record created in seconds. Two distinct events can share a timestamp. If you apply whichever update has the later created, a tie is a guess. Re-fetch the Checkout Session or the subscription and trust the live object. Acknowledge stale and tied events so Stripe stops retrying.

Return a 2xx quickly enough to avoid a timeout, but only after the claim is stored. Slow work, such as sending the email, can happen after that, as long as a retry cannot grant twice.

Save this as sent-twice.test.ts next to a package.json that contains { "type": "module" }. It needs Node 22 or later.

The first test is a retry of the same Event. The second is two Event objects for one Session. Both end in a single grant and a 200.

Insert the event id first, then fulfill. If the process dies after the event claim and before the session insert, Stripe's retry will see a duplicate event id and skip the grant. A safer pattern is to treat the event claim as a short lease (processing, then complete), and always let the session unique key be the thing that makes the license exist only once. Your database still does the remembering.

If you want this already wired up, the Hamichi Webhook Kit verifies the signature, records event.id, and keys fulfillment so a second Event object for the same Checkout Session does not grant twice. Express, Next.js, and NestJS examples are included.
