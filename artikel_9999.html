Next, we will focus on processing application-specific DirectPlay packets. DirectPlay messages are received via the Receive method of the IDirectPlay4AÂ interface. This method can return the DPERR_NOMESSAGES error codeÂ (0x887700BE),Â which is often handled by programs using DirectPlay. TheÂ HandleSysMessage function partially processes system messages, these messages are designed to manage game session events. The structure of each system message is defined in the DirectPlay headers, unlike user messages, which are defined by the application.

The function handling user messages was located by tracing back the call to the ReceiveÂ method. A minimalist DirectPlay-based server was written to send a specifically crafted message to the client. First, an instance of a DirectPlay object must be retrieved using the CoCreateInstance6Â API.

Next, the program selects the IPX network service provider using the EnumConnectionÂ andÂ InitializeConnectionmethods. The IPXwrapper DLLs must be placed in the server's execution directory. The server then creates a session via the Openmethod [1]. The first parameter is a session descriptor specifying the maximum number of allowed players, the game name, and the guidApplication. This unique identifier must match the game ID for Star Wars Racer: {C95FB584-FA31-11D2-909D00AA00A322AD}. A player is created using the CreatePlayer method. An event object is created and will be signaled whenever a message intended for this player is received. The core message processing is handled inside the ReceiveLoopÂ function [3].

This function waits for a message from the DirectPlay object using the WaitForMultipleObjects7Â API [1]. The message is retrieved via the Receivemethod, which returns the sender's identifier. The application must handle two types of messages: system messages, where the sender ID is DPID_SYSMSG , and custom messages specific to Star Wars Episode I: Racer.

System messages always begin with a DWORD indicating the message type, with the remaining fields defined according to that type. The server application must handle the DPSYS_CREATEPLAYERORGROUP system message. When a player connects, the server saves their ID to send the payload later. Initially, the server responds with a proprietary type 0x20Â message containing the list of active players in the game session.

Exploitation is triggered when the target player sends a type 0x22Â message. This message is sent by the client after connecting and again contains the player's name.

The exploit works by responding with a type 0x21 message that overwrites a handler in the network_handlers_tableÂ array. Setting the index to 0x01737B26 targets the addressÂ 0x004E9DE4Â , which corresponds to the handler for message 0x33. The handler is replaced with 0xEC7BC8, which corresponds to the receive buffer address.

A second type 0x33 message containing shellcode is sent, causing the program to execute the code received in the packet.
