CVE-2026-123903 Patch Assurance: Proving Fixed Builds Survived Rollback

Tanggal: 2026-11-24

Patching vCenter is often described as a single maintenance event. For CVE-2026-123903, the more accurate description is a chain of evidence. The organization must prove that every relevant appliance reached the listed fixed build, that the new build remained in place, and that a later restore or clone did not bring an older image back into service.

Broadcom identifies a VMware Directory Service authentication bypass in vCenter with a maximum CVSSv3 base score of 9.8. A network-reachable actor may bypass authentication and gain unauthorized access. The advisory lists no workaround.

The response matrix is branch-specific. VMware Cloud Foundation and vSphere Foundation vCenter 9.1.x.x is fixed in 9.1.2. The 9.0.x.x line is fixed in 9.0.2.0300. Standalone vCenter 8.0 is fixed in 8.0 U3m. Cloud Foundation 5.x is fixed in 5.2.5.

VMware vCenter 7.0 is directed to Broadcom Support for extended-support customers. Telco Cloud Platform and Telco Cloud Infrastructure use KB463501. A generic statement such as "vCenter was updated" does not establish that any of these branch requirements were met.

Collect the running version from the management interface and, where the vendor process supports it, from the underlying appliance record. Store the result with the asset identifier, collection time, collector, and product branch.

A screenshot or exported configuration has more value when it includes the instance identity and version in the same record. Text from a change ticket alone can show intent but not the final state.

An appliance restored from a snapshot, backup, or cloned template may return to an earlier build. Check restore and recovery records after an upgrade. Confirm the version again when a vCenter instance is recovered for disaster recovery, moved between environments, or replaced from a template.

A backup can contain an older build, and a recovery operation can change the state without appearing in the original patch report.

Broadcom says the advisories' patches are cumulative. A later cumulative build may contain earlier fixes, and a system recently updated for the prior VMSA may already include the current 8.0 fix. The only reliable conclusion comes from comparing the running build with the matrix.

Cloud Foundation and Telco Cloud products can involve multiple components. Patch the component that the matrix identifies, and follow the product-specific guidance for the surrounding platform. Do not assume that an ESX update alone resolves a vCenter CVE.

Record the current build, the target build, backup status, maintenance access, integration dependencies, and the rollback decision point. Confirm that the maintenance team can reach the management interface after the change and that the approved recovery procedure is available.

The advisory does not require a particular rollback method. The organization should use the vendor-approved process for its product version and document the result.

After the upgrade, confirm the build, service health, administrative access, and the management integrations used by the operations team. Review logs for unexpected restarts, configuration changes, and access attempts during the window.

If the build is correct but service health is poor, the asset is patched and still not operational. Track those states separately. If service health is good but the build is wrong, the vulnerability task remains open.

A patch manager can mark a ticket complete while an appliance has drifted. A second reviewer should sample the population, compare the observed version with the expected branch, and check restored or cloned systems specifically.

The sampling record should include exceptions. A vCenter 7.0 asset waiting for Broadcom Support is an exception with an owner and a next step. A Telco Cloud asset waiting for KB463501 coordination is another. An unexplained unknown version should not be accepted as complete.

Patch assurance comes from local build records. The external count can inform reporting about the management-plane footprint, but it cannot close an asset record.

Keep the pre-change build, target version, maintenance approval, post-change version, owner, exception status, and later drift check. This package answers the questions that matter after a critical advisory: what was changed, where, when, and how the organization verified it.
