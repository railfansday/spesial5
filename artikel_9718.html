Benchmarking AWS Amplify, Lambda, Web Functions, and ECS for Next.js

Tanggal: 2026-11-22

"Should this run on Amplify, Lambda or ECS?" is usually answered with a feature list. I wanted numbers. So I took one Next.js app, deployed it to four AWS runtimes in the same account and Region, including the new Lambda Web Functions, and measured the things that decide the choice in practice: latency under load, cold starts, CPU speed, real limits, and the monthly bill at four traffic levels.

Lambda and ECS run the exact same container image, and the Web Function runs the same files from a .zip. Amplify Hosting builds the same Git commit. Every command, script, and result is in a public repository, with deploy and cleanup steps:

Every response reports which runtime served it, the CPU architecture, and whether it was the first request of that process (a cold start):

Everything runs in eu-central-1. Lambda and Fargate use arm64 (Graviton) and roughly the same size: Lambda with 1024 MB of memory, and a Fargate task with 0.5 vCPU and 1 GB. A Web Function environment has a fixed size of 2 arm64 vCPUs and 2 GB, which you can't change, and Amplify chooses its own compute.

While the setup is running, the only fixed cost is the ECS part: the load balancer, one Fargate task and four public IPv4 addresses, about $1.90 per day. Lambda, Amplify and DynamoDB cost close to nothing at test traffic. Run the cleanup script when you are done.

The app is a normal Next.js app router project. The only special setting is the standalone output, which produces a small self-contained server.js for the container. Amplify builds the app its own way, so the setting is applied only in the Docker build:

--provenance=false keeps a plain single-platform image. By default, buildx adds an attestation manifest and pushes an image index, which Lambda may refuse to use. The script tags each image with the Git commit, so an immutable tag always matches one commit.

The next image scanned with zero findings. The compressed image is 88 MB in ECR (233 MB unpacked).

The DynamoDB table is on-demand with one item. Each runtime gets its own IAM role with exactly one permission, dynamodb:GetItem on this table.

A public Function URL now needs both permissions: lambda:InvokeFunctionUrl, and lambda:InvokeFunction limited to calls that come through the URL. I removed the second one to check, and the URL answered with 403 and a helpful message:

A Function URL is free and needs no API Gateway. For production, you would usually put CloudFront in front of it for a custom domain, caching and AWS WAF.

The documented default is 1,000 concurrent executions, but my account had 10. Ten concurrent requests at about 100 ms each is roughly 100 requests per second, and anything above returns 429 Too Many Requests. I requested an increase in Service Quotas (quota code L-B99A9384).

The increase to 1,000 was approved automatically after 2 hours and 20 minutes. Lambda's fast endpoints need far less concurrency than you might expect: at about 40 ms per request, 50 requests per second keep only 2 to 3 environments busy. The CPU endpoint at 50 requests per second peaked at 57 concurrent executions, well over the original limit.

Lambda Web Functions are a new kind of Lambda function for HTTP traffic. Your code is a normal web server that listens on a port, Lambda gives it an HTTPS endpoint, and each execution environment serves many requests at the same time, like a container. It still scales to zero when there is no traffic.

The Next.js standalone server reads HOSTNAME and PORT instead, so the entry file maps one to the other:

To keep the comparison fair, I didn't rebuild the app. The deploy script copies /app out of the same linux/arm64 container image, adds index.js, and deploys that folder:

--include-hidden-files is easy to miss: the Next.js build lives in .next, and without the flag the command leaves hidden folders out of the package. deploy creates the S3 bucket, the function, the first revision and a public endpoint, and waits until the endpoint is active. My first deploy took under a minute.

A revision is an immutable snapshot of code and configuration. Changing an environment variable means a new revision, and an endpoint can route traffic to one revision or split it between two, which gives you canary deployments without CodeDeploy.

The pricing model is different from classic Lambda. In eu-central-1 you pay $0.30 per million requests, $0.000035 per vCPU-second of CPU time that your code actually uses, and $0.0000046 per GB-second of memory for the whole life of each environment. A request that waits for DynamoDB uses almost no CPU, so it costs very little. But an environment that stays alive costs memory time even between requests: one environment kept alive for a month is about $24 in memory alone.

A Fargate task in a private subnet needs a NAT gateway or VPC endpoints to pull its image, and either costs more than the task itself. For this test, the tasks run in public subnets with a public IP, and the security groups do the protecting:

Two roles, two jobs: the execution role lets ECS pull the image and write logs, and the task role is what your code runs as. The DynamoDB permission goes on the task role only.

Two settings save time on every deploy. The target group health check uses /api/health every 10 seconds with a healthy threshold of 2, so a new task gets traffic in about 20 seconds. The deregistration delay is 10 seconds instead of the default 300, so an old task stops quickly.

One bug from my script is worth sharing: --output text separates a list of subnet IDs with tabs, not spaces. My script turned spaces into commas, so the service request got one "subnet ID" with tabs inside and failed with Subnet ID must match subnet-[0-9a-f]+. Pipe the list through tr '\t' ' '.

Amplify Hosting connects to GitHub with its own GitHub App. It does not use an AWS CodeConnections connection, even if you already have one for CodeBuild or CodePipeline. So the first step is in the console: Create new app, GitHub, choose the repository and the main branch. Amplify detects Next.js and uses the amplify.yml from the repository.

This is the biggest surprise for anyone coming from Lambda or ECS. Amplify passes environment variables to the build, not to the server-side code at runtime. The fix is to write the variables your server code needs into .env.production during the build:

The || true is there because my first build failed without it. Before the variables were set, grep found nothing and exited with code 1, and Amplify stopped the build with "Command failed with exit code 1".

Two more rules: variable names can't start with AWS_, so the app reads APP_REGION instead of AWS_REGION, and secrets should not go into .env.production this way, because they end up in the build artifact.

The server-side code needs AWS credentials to call DynamoDB. Amplify calls this a compute role: an IAM role that amplify.amazonaws.com can assume.

Without a compute role, the page renders but the DynamoDB call fails with a credentials error.

The first response from Amplify answered a question the console doesn't:

AWS_LAMBDA_FUNCTION_MEMORY_SIZE is set, so the server code runs on Lambda with 1024 MB, on x64, managed by Amplify. You can't choose the memory size or arm64, and it doesn't count against your account's Lambda concurrency quota.

At 10 requests per second (p50 / p95 / p99 in milliseconds, 1,200 requests each):

On light requests, ECS is the fastest, Lambda and the Web Function are close behind with almost the same medians, and Amplify is about 1.5 times slower than Lambda. ECS wins here because nothing sits between the load balancer and a warm Node.js process.

The CPU row is the surprise. One Fargate task with 0.5 vCPU could not keep up with 10 CPU-heavy requests per second: each request needs about 80 to 150 ms of CPU, so the work arrived faster than half a vCPU could do it. Requests queued, the ALB health checks timed out, and ECS replaced the "unhealthy" task in the middle of the test. 8% of requests failed and the median rose to 1.9 seconds. Lambda, the Web Function and Amplify handled the same load without errors, because they add execution environments as the load grows.

The lesson is not that ECS is slow. A fixed-size service needs auto scaling and headroom, and a health check that shares the CPU with the work it checks can turn an overload into a restart.

At 200 requests per second (p50 / p95 / p99 in milliseconds, 24,000 requests each):

Lambda, the Web Function and Amplify barely noticed the twentyfold increase: their medians moved by a few milliseconds and no request failed. For the Web Function, I ran the 200 requests per second test twice, because AWS says the first load test on a new Web Function scales conservatively, and the table shows the second run. The two runs were within a few milliseconds of each other. Lambda scaled to 234 concurrent executions in the first seconds of the test, then settled between 50 and 90, with zero throttles.

The single ECS task reached 100% CPU and failed. At 50 requests per second the same task used about 65% CPU on the page endpoint, so one 0.5 vCPU task handles roughly 70 page requests per second before it falls over. For real traffic, you would run at least two tasks with target tracking auto scaling at 50 to 60% CPU.

The 50 requests per second results look like the 10 requests per second ones for Lambda, ECS and Amplify, so I left them in the repository instead of adding another table.

One more number explains why Lambda looks so fast: its billed duration (the CloudWatch Duration metric) was 9 to 16 ms at the median for the light endpoints. Most of the 40 ms that the client sees is the network and the Function URL, not your code.

The CPU endpoint does the same 50,000 hashes everywhere:

Lambda gives CPU in proportion to memory: one full vCPU at 1,769 MB. At 1024 MB you get a bit more than half a vCPU, and you pay for the milliseconds you use. A Web Function environment always has 2 vCPUs, and you pay only for the CPU time you use. Node.js runs JavaScript on one thread, so a single request can use only one of them, but that one is a full vCPU. Fargate gives you exactly the vCPU you reserve, all the time, whether you use it or not.

Lambda, 10 forced cold starts (the script changes an environment variable before each request):

Amplify, one request after 20 minutes without traffic, 3 times: 1.94 s, 2.00 s and 0.33 s, compared with about 0.16 s for a warm request. All three were served by a new process, so the third one probably landed on an environment that Amplify had already prepared. You can't see or control this, so plan for about 2 seconds on the first request after a quiet period.

Web Function, 5 forced cold starts (each run creates a new revision, which starts new environments):

ECS has no cold start while a task is running, which is what you pay the fixed monthly price for. Scaling out is a different story: in the ECS events, a replacement task registered with the load balancer about 25 seconds after it started, and then needed two 10-second health checks before it got traffic. A new Lambda environment was ready in about one second.

I asked each runtime to wait longer and longer, and to return larger and larger responses:

If your app has report downloads, file exports or slow third-party calls, these limits decide more than any latency number. Classic Lambda can go beyond 6 MB with response streaming, but that needs code changes. With Web Functions, you get it without changes.

Prices are on-demand prices in eu-central-1 from the AWS Price List API, in November 2026, without free tiers:

Web Functions publish their own usage in CloudWatch (EnvironmentCPUTime, EnvironmentActiveTime and ExecutedRequests in the AWS/Lambda/Web namespace), so I could calculate the real bill for my load tests instead of estimating it:

71% of the bill was memory. At 200 requests per second, Lambda ran up to 55 environments, and none of them served more than 2 requests at the same time (the EnvironmentConcurrentRequests maximum). That was the case in both 200 requests per second runs. AWS documents that a new Web Function starts with a conservative per-environment concurrency limit and raises it as it learns, but I didn't see that happen in about 25 minutes of testing. About 30% of the memory time came after the test, while the environments waited about 5 minutes before Lambda removed them.

The same request mix on classic Lambda would cost about $0.15, or $1.04 per million requests. So in my test, Web Functions cost about four times as much. If the per-environment concurrency grows over time, as AWS describes, this gap will shrink, so treat it as the cost of a new function under a load test, not a final verdict.

For the monthly bill, I used the measured durations: 20 ms of Lambda billed time per request (the 9 to 16 ms median, rounded up), and 5 KB per response. Amplify doesn't publish its billed compute time per request; its CloudWatch Latency metric averaged about 100 ms, which includes the CDN, so I show 100 ms as the upper bound and 30 ms as a likely lower bound. ECS uses the measured capacity of about 50 requests per second per task with headroom. For the Web Function, I used 27 ms of CPU per request, at least one environment alive all month (requests arrive more often than every 5 minutes at these levels), and the measured 0.24 environments per request per second at steady load.

The script is in the repository (bench/cost.py), so you can run it with your own durations and response sizes.

The same build runs on classic Lambda, Web Functions and ECS, so this is not a one-way decision. The Web Function in this article is the same /app folder as the container image, plus a 5-line index.js. Starting on Lambda and moving when your traffic or your limits change is a reasonable path.

The script deletes the Amplify app, the ECS service, cluster, load balancer and target group, the Lambda function, the Web Function and its code versions in the shared awscli-lambdaweb-* bucket, the security groups, the ECR repository, the DynamoDB table, the log groups and the IAM roles. Everything it created has the tag project=runtime-benchmark, so you can check in Tag Editor that nothing is left.

The feature lists told me that ECS is "more powerful", Lambda is "serverless" and Amplify is "easy". The measurements told a more useful story. The always-on container was the fastest per request and the first to fail, because one task is a fixed amount of CPU. The three serverless options were a little slower per request but did not care whether traffic was 10 or 200 requests per second. The newest one, Lambda Web Functions, removes most of classic Lambda's limits and was the fastest on CPU, but its memory billing made it the most expensive serverless option in my test. And the limits that matter most for real apps, request timeout and response size, differ by an order of magnitude between them.

If you only take one thing from this article: measure your own app on the runtime you plan to use, before you choose. The repository makes that a few commands, and the cleanup script removes everything when you are done.
