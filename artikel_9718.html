I Built an AI OS That Evolves on Demand: Device and Host Boundaries

A small keyboard and screen can make an AI agent feel like a separate appliance. The permissions behind that screen still belong to software running somewhere else. Deciding what crosses that boundary is part of building the device.

S1-ADV connects a M5Stack Cardputer ADV to an OpenClaw agent on a computer or server. The handheld also has local tools, including notes, a calculator, a focus timer and games. The useful engineering question is how those two worlds remain understandable when one physical interface reaches both.

The ESP32-S3 runs the embedded firmware: keyboard input, display, recording and playback, local applications and device updates. It does not run the language model. A Node.js bridge converts the handheld’s HTTP and WebSocket interaction into the gateway protocol used by the OpenClaw host.

The host supplies the configured model and speech services. Development tools can also live there, but a chat connection and permission to build firmware are separate choices. The project’s basic installation does not create a universal service that can safely implement any requested feature without review.

This division is more useful than calling the whole system an “AI device” and leaving the execution location implicit. If text replies work but speech does not, there is a speech configuration to inspect. If a local calculator works without the bridge, that is local firmware doing its job.

The public security model puts gateway credentials and the gateway’s persistent device identity on the bridge host. The handheld uses its bridge token. The gateway stays on loopback; remote handhelds reach the bridge over verified HTTPS/WSS.

The architecture also calls for one device identity per bridge instance, with separate private storage for independent devices. That makes the identity boundary an explicit deployment responsibility. Copying one provisioned installation to several devices is not equivalent to configuring independent clients.

These are documented boundaries, not a claim that the project has completed an independent security audit. It has not. The repository describes a bounded maintainer review and remaining trust assumptions. A demonstration video is not evidence that those assumptions have been exhaustively tested.

The bridge architecture maps allowed topics to agent sessions. The device can request history, send text or audio, and receive streamed events through that configured interface. This is a reason to keep the set of allowed destinations deliberate instead of presenting every host conversation to every handheld.

Permissions should be judged by what the chosen agent can actually do. The README recommends starting with a restricted chat agent and enabling firmware-building rights only when deliberately needed. A small screen does not make a powerful host action smaller.

The film explores a loop from a feature idea through source changes, a build, an offered update, installation and testing on the Cardputer. It is tempting to collapse that into “the gadget evolves.” Keeping the stages visible makes the experiment easier to assess.

The device applies firmware; the host provides the development environment and update assets. Site-specific automation and integration permissions are additional configuration. A compiled binary still needs the right target, a delivery path and a physical test. Each step answers a different question.

There is also an open reproducibility limit: the public README says public builds have not yet been tested on a freshly provisioned physical device. The recorded, configured device demonstrates the maintainer’s setup. It does not establish that every new installation will succeed.

Private firmware builds can embed Wi-Fi settings and device tokens. The security guide explicitly excludes provisioned binaries, environment files, private bridge configuration, recordings and conversation logs from public issue attachments. The public repository is the place for source and maintained setup instructions, not a copy of someone’s working personal environment.

For this project, the honest starting point is Cardputer ADV, an initial USB setup, a configured host and text interaction before optional voice. Other Cardputer variants are untested. That is a narrower description than a universal pocket assistant, and a more useful one for someone deciding whether to reproduce it.

The full demonstration film shows the actual device and the broader development workflow. The source and documentation let readers inspect the boundaries behind it. S1-ADV began with OmniBot by Naz Louis and contributors; those origins and dependency notices remain in the project’s credits.
