Critical security vulnerability affects OpenSSH on Alpine Linux systems

Tanggal: 2026-11-08

Version 10.6p2 of OpenSSH has been released with a workaround for a critical vulnerability that affects Linux systems that use musl libc with PAM disabled, such as Alpine Linux. OpenSSH developer Damien Miller said:

If you operate a Linux system that uses musl libc without PAM (Alpine Linux is one example) then stop reading and set PasswordAuthentication=no or disable SSH for these systems IMMEDIATELY.

This vulnerability does not exist on non-Linux systems, Linux/glibc systems and Linux systems that use PAM for password authentication.

We consider the root cause of this bug to be outside OpenSSH itself, but we're in a good position to deliver a mitigation quickly.

The Alpine Linux project has announced that it will be backporting the OpenSSH fix "all the way back to Alpine 3.16", which was released in May 2022.

There are certain scenarios that public key authentication protects against that password authentication doesn't. You have to decide for yourself whether those are relevant for you. Password authentication requires the user to transmit the password in a form that the server can decrypt. The server will know the cleartext password (even though it was encrypted in transit) and must know that to be able to verify it. (Even though in the server's user database it's stored in a hashed + salted form.) This means that if someone manages to successfully impersonate the server (e.g. via a compromise of the private key of the server, maybe because a system backup was available on a public S3 bucket, for example), they will obtain all the cleartext passwords from password authentication. With public key encryption this is not possible, even if the server is compromised it will not be able to learn the secret key. Now granted, that DOESN'T mean that password authentication is completely broken or something - it's NOT an automatic red flag to me - but we should acknowledge that it has some real drawbacks compared to e.g. public key authentication.

Just off the top of my head, major problems include: a) Can't log into the system locally (be it text console or GUI environment) using a public+private key b) Restricts what systems you can log in _from_ -- any such systems need access to a copy of your private key c) In practice, most SSH keys are passphrase-less, used for *convenience* [1] rather than "passwords bad". As a single keypair is typcially used to allow access into many unrelated systems, a key compromise becomes far worse than if a single password was cracked or compromised. (a) is more generalized as "ssh public key authentication is completely incompatible with every other authentication mechanism you already need to use" [1] "this way I don't need to remember/type in system-specific passwords" (often combined with passwordless sudo and a culture encouraging 'curl | sh' )
