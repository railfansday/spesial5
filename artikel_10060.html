11 nanoseconds per word: Ridiculously Over-Optimizing Anagrams

Tanggal: 2026-11-06

A friend recently pointed out a new Word Ladder game variant: Find a path of mutations from a start word to an end word, where mutations can be single letter changes, single letter deletions or additions, or anagramming the word. It annoyed me (the paths involving anagrams can be wickedly hard to spot), so, naturally, I wrote a solver for it. And when the solver took over a second to run, I of course had to optimize it. Along the way, I found a fun trick for anagram indexing—fitting a collision-free prime-product identifier for every word in the dictionary into a single 64-bit integer—that I hadn't seen before (though the history of computing is long and Knuth probably noticed it in 1965).

For completeness, I should note that what I was interested in was finding all anagrams in a dictionary---if you just want to find anagrams of a specific word you can probably get away with a much simpler hash table design! We'll use all of the anagrams in the next post talking about solving the whole word ladder.

In 173 nanoseconds you could execute roughly 4400 instructions on my Macbook Pro M1. Who has time to wait for that??

When optimizing, one of the first places to be suspicious is allocations, and this one has them in droves. Every word results in either the allocation of a Vec or an append to a Vec, which sometimes needs an allocation. Much better, but we can do better yet. The time to sort that string and create a new string allocation is non-trivial and we're doing 178k of them. That's going to be another big chunk of nanoseconds.

Let's try a letter count vector instead, and pack it tightly into an integer. With only 26 characters, if we assume that no word has more than 15 repetitions of the same character, we could use 4 bits per character for 26 x 4=104 bits. That fits comfortably in a u128, and while that's not tiny, it's at least a nice fixed size 16 byte thing we can use as a fast hash table key.

Storing the letter count as a u128 is also a little slower than necessary, because it'll be split across two 64 bit registers and requires the compiler to carry that addition across them and do twice as much work for equality testing. But if we tried lettercounting in 64 bits, we would only be able to store 2 bits, and many words have more than 3 of the same letter ("MISSISSIPPI", for example, already has 4 S's).

Instead, we'll use an approach based on Gödel numbering: we'll create a small table associating one distinct prime number with each letter, and identify each word by the product of the letter-primes. This guarantees a unique identifier for each mix of letters. Naively, one might assign "a -> 2, b -> 3, c -> 5" and so on. But this is a practical blog post, and we'd like to fit the result in 64 bits; if we use the naive assignment, we overflow at the 365th word in our dictionary, "ABORTIVENESSES". And that's only 14 characters long, we have 3157 15-character words as well! If we let it wrap, we'll have just implemented a hash function, and there's no guarantee that two words won't accidentally collide, so then we'd need to add some machinery to check that...

So here's the trick: Find an optimized assignment of primes to letters in the alphabet such that none of the words in our Scrabble dictionary overflow a 64 bit number. I started out thinking about the standard English letter frequency (ETAOINSHRDLU, etc.), but that turns out to be a little wrong: We don't care much about words like "the", we care about words like "WRONGHEADEDNESS". So instead, we need to go based on the patterns found in the 3157 15-character words. In particular, while "E" remains assigned to 2, the common "T" is assigned 29, and we use 3 for "I". Our friend "J" is assigned 101, since the longest word with two or more J's in it is only 12 characters long: JEJUNENESSES. Looking at that, those E's and N's and S's better have low values, and they do: 2, 19, 17. We could handle 15 N's in a row in 64 bits still.

To solve this, I had a small program start with the letter-frequency ordering (which does a lot better than alphabetical but isn't good enough), loop finding the first word that overflowed and switch out some of its primes for lower valued primes. This is looking pretty good. The only last optimization I have to add is to address some branch mispredictions in that rest != 0 loop. We can instead just treat all words as if they're 16 characters long and ignore the 0's at the end by mapping them to 1 in our primes table (i.e., they have no effect on the product). Using a fixed length of 16 also permits more auto-vectorization by our friendly compiler. To support that, we also separate the computation of the prime product from the insertion into the hash table, allowing more ILP from our now-vectorized multiplication loop.

Result: 2.3 ms -> 1.96ms (10.9ns/word, 15x faster than baseline)

We're finally pretty close to what I think a single core on my machine can get without explicit vectorization. That 1.96ms is about 1.23ns per byte, which could theoretically be about 3.2 x 8 x 1.23 = 31 instructions (but realistically fewer), which doesn't leave a ton of room for optimization---though I could be wrong! There's some space in there for an even faster hash table implementation but I'd rather stick with common, off-the-shelf things there.
