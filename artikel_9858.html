Five memory leaks that kill Flutter apps on older phones

Tanggal: 2026-11-10

A memory leak happens when your app holds on to objects it no longer needs, so the Dart garbage collector can't free them.

On a modern phone with 8 GB of RAM, a leak can hide for a while. On an older phone with 2 or 3 GB, it's a different story: the operating system kills your app in the background, or it crashes while someone is using it. Your crash reports fill up with devices you never tested on.

The most common Flutter leaks have one thing in common: something outlives its screen.

AnimationController, TextEditingController and ScrollController all hold resources. If you create one in a State, you dispose it in that State.

Rule of thumb: if it was created in initState, it gets cleaned up in dispose.

A periodic timer or a stream subscription keeps running after the user leaves the screen, and keeps the State alive with it.

cancel(), not just setting the variable to null.

Never store a BuildContext in a long-lived variable or a singleton:

If you hold on to the context of a screen after the user has navigated away, that entire screen and all of its widgets stay in memory. Pass context into the method that needs it, use it, and let it go. For app-wide navigation, use a navigator key or your router instead.

Open Flutter DevTools and watch the Memory tab while you navigate in and out of a screen a few times. Memory should go up and come back down. A graph that only ever climbs is a leak.

Test on the oldest, cheapest device you can get. Leaks that never show on a flagship show up there within minutes.
