What is Exchange Online? A guide to the Microsoft 365 email service behind Outlook, from mail flow and security to why its outages reach so many users

When Outlook stops sending mail, the program on the screen is often not the part that failed. The problem can sit one layer down, in a service most people never open or log into directly. That service is Exchange Online, and it holds the mailboxes Outlook displays.

What is Exchange Online? It is Microsoft $MSFT's cloud-hosted messaging platform, part of the Microsoft 365 suite. It stores and delivers email, and it also keeps calendars, contacts and tasks. Microsoft hosts and operates it. It is the hosted counterpart of Exchange Server, the product organizations run on their own servers.

That split between app and service explains why a single fault can look so widespread. Outlook for Windows, Outlook for Mac, Outlook on the web and the Outlook mobile apps can all connect to the same back end. When that back end has a fault, every one of those clients can misbehave at the same moment. A user may restart a laptop, reinstall an app or switch phones and find the same problem waiting.

The reach goes beyond the inbox. Companies, schools and public bodies of every size keep their mailboxes in this one service. Other Microsoft 365 tools draw on it as well. Teams, for example, pulls its calendar data from the user's Exchange mailbox. A problem in Exchange Online can therefore surface in places that do not look like email at all.

Knowing how the service works helps people read symptoms more accurately. Someone who can still read old messages but cannot send new ones may be looking at a local copy of the mailbox. That copy is not a live connection. An administrator who knows where Microsoft posts incidents can confirm a wider issue before spending hours on a single machine.

The 10 slides that follow cover the service piece by piece. They explain what the service is and how it differs from Outlook. They show why its outages spread and how to check Microsoft 365 service health. They also cover how mail reaches the service, how it filters spam and malware and which mailbox types it supports. The final slides look at compliance tools, hybrid setups with Exchange Server and the protocols and programming interfaces clients use to connect.

The service handles four kinds of data. Email is the most visible, but the same mailbox also holds a person's calendar appointments and meeting invitations. It keeps personal contacts, along with the tasks and to-do items a user creates. All four live in one mailbox, so they follow the user to any device that signs in.

Exchange Online is the hosted counterpart of Exchange Server. Exchange Server is software that organizations install and run on their own hardware. With the online version, Microsoft runs the servers in its own data centers instead. The customer manages users and settings, while Microsoft handles the hardware, the operating systems and the software updates underneath.

Each subscribing organization gets its own tenant. A tenant is the customer's private space inside Microsoft's cloud, holding its users, mailboxes, domains and policies. Exchange Online shares that tenant with other Microsoft 365 services, including Teams, SharePoint Online and OneDrive. Those services draw on the same user accounts. That shared foundation makes Exchange Online more than a stand-alone mail server.

Microsoft sells access per user through subscriptions. Many Microsoft 365 business and enterprise plans include Exchange Online as part of a wider bundle. Organizations that only need hosted mail can also license it on its own through Exchange Online Plan 1 or Plan 2.

Everyday users reach Exchange Online through an email app, most often a version of Outlook. That app reads and writes the data held in the mailbox. Administrators see more of the service. They manage mailboxes and settings through the browser-based Exchange admin center and the Microsoft 365 admin center.

Customers do not patch or upgrade Exchange Online themselves. New features and fixes reach each tenant as Microsoft deploys them across its service.

Outlook is the email program people open on their screens. Exchange Online is the Microsoft $MSFT 365 service that stores their mailboxes and delivers their messages. One is the client, and the other is the server it talks to.

The split is easy to miss because the two are sold and used together. A worker at a company on Microsoft 365 rarely sees the name Exchange Online anywhere. They see an Outlook icon, an inbox and a calendar. The stored mail, the folders, the meeting invitations and the contact list all sit on Microsoft's servers, not inside the app.

Outlook comes in several forms that can connect to Exchange Online. There are desktop apps for Windows and Mac, a browser version and mobile apps for iOS and Android. Each is a separate piece of software with its own interface and its own update schedule. All of them draw on the same mailbox.

That shared mailbox is why a message read on a phone shows as read on a laptop. A meeting accepted in the browser appears on the desktop calendar too. A folder created in one app shows up in the others. The apps do not keep a master copy of their own. They display what the server holds.

Neither side is tied exclusively to the other. Outlook can add accounts from other providers, including Gmail and other IMAP services. Exchange Online, in turn, accepts connections from mail apps that are not Outlook.

Outlook.com adds another source of confusion. It is Microsoft's free consumer email service. A business mailbox in Exchange Online is a separate, paid offering. Organizations buy it through Microsoft 365 plans or as a standalone Exchange Online subscription.

The server side is where a fault can reach every device together. Each Outlook app depends on the same mailbox, so trouble there shows up in all of them. A user who switches from a laptop to a phone meets the same error. To that user, it looks like Outlook has broken.

The reverse case looks different. A problem confined to one copy of Outlook, such as a damaged desktop profile or an outdated mobile app, usually affects only that device. If Outlook on the web still works while the desktop app does not, the mailbox itself is likely reachable.

An Exchange Online outage spreads widely because one shared service holds mailboxes for a large number of organizations. Several other Microsoft $MSFT 365 tools also draw on those mailboxes. A single back-end fault can stall email, calendars and scheduling for many workplaces at the same moment.

Each of those organizations keeps its mail in Microsoft's hosted platform rather than on servers of its own. That concentration is the first reason a problem travels so far.

When a shared piece of the service misbehaves, the effect is not confined to one employer's server room. It can reach customers in many sectors at once. An office worker, a teacher and a council employee may all find their inboxes unreachable together.

The second reason is that Exchange Online sits underneath more than email. The mailbox is also where a user's calendar, contacts and tasks live.

Microsoft Teams reads calendar data from that same mailbox. The meetings list inside Teams depends on the back end that serves Outlook. A person who switches from Outlook to Teams to check an afternoon meeting can run into the same gap in both apps.

The service is built to survive the loss of individual machines. Exchange mailbox databases are copied across several servers using database availability groups. Exchange Online inherits that design from Exchange Server.

If one server fails, another copy of the database can take over. That replication reduces the chance that a single broken server takes mailboxes offline.

Replication has limits. It guards against the failure of a single server, not against faults in the shared systems that every mailbox server depends on.

Authentication is one of those shared systems. Users sign in to Microsoft 365 through Microsoft Entra ID, Microsoft's identity service. Outlook cannot open a mailbox until that sign-in succeeds, no matter how many healthy database copies exist.

Networking is another shared layer. It sits between the user and every copy of the database. Extra replicas behind it do not help if the path to them is broken.

A bad configuration change is a third category. A setting pushed across shared infrastructure reaches every server it touches, including the ones holding duplicate copies. Redundant databases offer no protection against a mistake applied to all of them.

That is why the breadth of an incident says more about which layer failed than about any one machine. A problem limited to one mailbox usually stays local. A problem that hits mail, calendars and sign-in across many organizations at once traces back to a component they all share.

The most direct way to confirm an Exchange Online problem is the service health dashboard in the Microsoft $MSFT 365 admin center. Microsoft posts incidents there. That helps show whether a fault sits in the cloud service or closer to the user.

The dashboard sits inside an administration console. That makes it a tool for IT staff rather than for most employees. A worker who suspects an outage usually needs an administrator to check it.

Symptoms can narrow the question before anyone opens the dashboard. Every Outlook version, from the Windows desktop app to the mobile apps, reads from the same mailbox in Exchange Online. Comparing two of them is a simple test a user can run without admin access.

If mail fails in the desktop app but works in Outlook on the web, the problem more likely sits on that one computer. A failure that shows up in both at once shifts suspicion toward the service.

The same test reaches beyond Microsoft's own apps. Exchange Online also accepts connections over IMAP and POP, where an organization has enabled them. A third-party mail app linked to the same mailbox can serve as one more point of comparison.

Outlook desktop in cached mode complicates that test. It keeps a local copy of the mailbox. Messages that had already arrived can still open during a back-end failure. That makes reading old mail a weak sign that the service is healthy. A better check is whether a new message leaves the outbox and whether fresh mail arrives.

When no incident is posted, administrators can look closer to home. The Exchange admin center and Exchange Online PowerShell let them review their own organization's mail settings.

Several of those settings can stop mail without any fault at Microsoft. Connectors and mail flow rules, also called transport rules, control how messages move between Exchange Online and outside systems. A connector or rule set up incorrectly can disrupt mail for a whole organization while the service runs normally.

Protocol settings are worth a look as well. Admins can enable or disable each connection protocol on a per-mailbox basis. A protocol switched off for one person can explain why a single app fails for that user and nobody else.

Email sent to a Microsoft $MSFT 365 organization finds its way there through the domain's MX records, which point to Microsoft's servers. Once a message arrives, connectors and mail flow rules decide how it moves between Exchange Online and outside systems.

An MX, or mail exchanger, record is an entry in the domain name system. It tells every sending mail server on the internet where to deliver mail for a given domain. For a domain set up in Microsoft 365, that record typically names a host ending in mail.protection.outlook.com.

The domain has to be added to the Microsoft 365 tenant and verified first. The domain owner proves control by publishing a DNS record that Microsoft checks before the domain goes live.

The MX record lives with the domain's DNS host, not inside Microsoft 365. Each record carries a time-to-live setting. That setting controls how long other servers keep using a cached answer. A switch of mail providers therefore does not take effect everywhere at the same moment.

Connectors handle the less direct routes. An inbound connector accepts mail from a specific partner or service. An outbound connector sends mail through a chosen path instead of straight to the internet. Organizations use them to pass mail through a third-party filtering service, to exchange mail with a business partner or to link Exchange Online to an on-premises server. A connector can also require Transport Layer Security, the standard that encrypts mail in transit, on its route.

Mail flow rules, also called transport rules, act on messages as they pass through the service. Each rule pairs conditions with actions and can include exceptions. One rule might add a legal disclaimer to outgoing mail. Another might block certain attachment types, redirect messages to a reviewer or apply encryption. Admins build these rules in the Exchange admin center or with Exchange Online PowerShell.

These layers matter when mail stops arriving. A misconfigured connector or an overly broad rule can block or reroute mail for a whole organization while Exchange Online itself runs normally. The message trace tool in the Exchange admin center shows the path a specific message took and where it stalled.

SMTP, the protocol mail servers use to hand messages to one another, also tolerates short delays. A sending server that cannot reach its destination generally queues the message and retries for a limited time. Mail held up by a temporary fault often arrives late rather than vanishing.

Exchange Online Protection is the filtering service built into Exchange Online. It scans incoming and outgoing mail for spam and malware. Microsoft $MSFT Defender for Office 365 is a separate security layer that sits on top of it for organizations that license it.

Every organization with Exchange Online mailboxes gets Exchange Online Protection, usually shortened to EOP. It works at the edge of the service, before a message reaches an inbox. Microsoft also sells EOP as a standalone service for companies that still host mailboxes on their own Exchange servers.

EOP checks mail in stages. Connection filtering looks at the reputation of the sending server. Anti-malware scanning inspects attachments for known malicious code. Anti-spam filtering then gives each message a verdict, such as spam, high-confidence spam or phishing.

Those verdicts decide where a message ends up. By default, ordinary spam goes to the recipient's Junk Email folder. Messages judged more dangerous, such as malware or high-confidence phishing, are held in quarantine. Admins control who can review and release quarantined items.

Filtering also covers outbound mail. EOP watches for accounts that suddenly send spam, a common sign of a compromised mailbox. An outbound spam policy can block such a user from sending. That protects the reputation of Microsoft's mail servers and of the organization's own domain.

Sender authentication belongs to the same layer. EOP evaluates SPF, DKIM and DMARC results to judge whether a message really came from the domain it claims. Spoof intelligence adds a check for senders pretending to be someone at the recipient's own organization.

Microsoft Defender for Office 365 targets threats that basic filtering can miss. It comes in Plan 1 and Plan 2. Plan 1 adds Safe Attachments, which opens files in a sandbox before delivery. It also adds Safe Links, which checks a URL at the moment a user clicks it. Plan 1 brings stronger protection against impersonation as well.

Plan 2 includes everything in Plan 1 and adds tools for security teams. These include Threat Explorer, automated investigation and response, and attack simulation training. Microsoft 365 E5 includes Plan 2.

Admins manage these policies in the Microsoft Defender portal. Microsoft offers preset Standard and Strict protection policies as starting points. Organizations can also build custom policies of their own.

The filtering layer is worth checking when someone reports missing mail. A message that never appears may have been quarantined or routed to junk rather than lost to a service fault. Reviewing quarantine and running a message trace can separate a filtering decision from a wider problem.

Exchange Online offers several kinds of mailboxes and groups, each built for a different job. User mailboxes belong to individual people. Shared mailboxes, room and equipment mailboxes, distribution lists and Microsoft $MSFT 365 Groups serve teams, spaces and shared resources.

A user mailbox is the standard account tied to one licensed person. It holds that person's email, calendar, contacts and tasks. It is the mailbox Outlook opens by default when that person signs in.

A shared mailbox gives a team a common address, such as a support or sales inbox. Several people can read and reply from it without sharing a password. Nobody signs in to a shared mailbox directly. Admins grant permissions to individual users rather than handing out credentials.

Three permissions do most of the work. Full Access lets a person open the shared mailbox and read its contents. Send As makes a reply appear to come from the shared address itself. Send on Behalf shows both names, so recipients can see who answered for the team.

Shared mailboxes do not require a license of their own in most cases. Microsoft requires one when a shared mailbox needs litigation hold or more storage than the unlicensed allowance.

Room mailboxes represent physical spaces such as conference rooms. Equipment mailboxes cover items that are not tied to a location, such as projectors or company cars. Together they are known as resource mailboxes. People book them by adding the room or item to a meeting invitation. The resource can accept or decline automatically, based on whether its calendar is free.

Admins can set booking rules for each resource. These include how far ahead someone can reserve it, how long a meeting may run and whether a delegate must approve requests.

Distribution lists, also called distribution groups, work differently. They store no mail of their own. A message sent to the list's address is copied into each member's mailbox. Dynamic distribution groups build their membership automatically from attributes such as department or office location.

Microsoft 365 Groups go further than a distribution list. Each group gets a shared inbox and calendar in Exchange Online, plus a SharePoint site for files. Every team in Microsoft Teams is backed by a Microsoft 365 Group.

Admins create and manage all of these in the Exchange admin center, a browser-based console. Exchange Online PowerShell handles the same tasks from the command line and suits bulk changes. The New-Mailbox cmdlet can create shared, room or equipment mailboxes. Set-CalendarProcessing controls how resource mailboxes respond to booking requests.

Exchange Online includes built-in compliance tools that decide how long email is kept and how it can be searched later. Retention policies, litigation hold, archive mailboxes and eDiscovery all work on the same mailboxes people open every day in Outlook.

Retention policies set the rules for how long content stays in a mailbox and what happens when that period ends. An organization can keep messages for a set period, delete them once they reach a certain age, or keep them and then delete them. A single policy can cover every mailbox in a tenant. It can also target specific users or groups.

Microsoft $MSFT 365 retention policies are configured in Microsoft Purview, the company's compliance portal. Older Exchange retention tags belong to a feature called messaging records management. They apply rules to individual folders or messages and can still be managed through Exchange Online PowerShell.

Litigation hold preserves everything in a mailbox, including items a user deletes or edits. Organizations apply it when they expect a lawsuit, an audit or an internal investigation. Deleted items and the original versions of edited items are kept in the Recoverable Items folder. Most of that folder is hidden from the normal mailbox view. Its contents stay available to searches. The user can keep working in Outlook while the hold is in place.

Archive mailboxes give each user a second storage area for older mail. The archive appears as a separate folder tree in Outlook and Outlook on the web. Archive policies can move messages there automatically once they pass a set age. This keeps the primary mailbox smaller without deleting anything.

eDiscovery tools let authorized staff search across many mailboxes at once. Searches can filter by keyword, sender, recipient and date range. They can reach archive mailboxes and items preserved under hold. Results can be exported for review by legal or compliance teams.

The features available depend on the license. Mailbox storage allowances differ between Exchange Online Plan 1 and Exchange Online Plan 2. Plan 2 includes litigation hold. Plan 1 customers can add it, along with expanded archive storage, through the Exchange Online Archiving add-on.

These tools control what is kept and what can be found. They do not restore access during a service disruption. Archive mailboxes and held items are stored inside Exchange Online itself, not in a separate system. They depend on the same service as the primary mailbox.

Exchange Online and Exchange Server are the same messaging platform delivered in two ways. Microsoft $MSFT hosts and operates Exchange Online as part of Microsoft 365. Exchange Server is licensed software an organization installs on its own hardware. A hybrid deployment connects the two.

The practical difference is who carries the operational load. With Exchange Server, the organization supplies the hardware and installs the software on Windows Server. It also applies Microsoft's cumulative and security updates itself. Its own staff handle backups, capacity planning and recovery when a server fails.

Exchange Online moves that work to Microsoft. The company runs the servers, applies updates and manages the underlying infrastructure. Customers still configure mailboxes, policies and mail flow, but they no longer maintain the machines underneath.

That split also changes what an outage touches. Users whose mailboxes sit on the organization's own Exchange Server can usually keep opening them when the hosted service has a problem. Users with Exchange Online mailboxes cannot count on that. Mail passing between the two environments can still be delayed.

A hybrid deployment runs both environments side by side. Organizations choose it for two reasons. Some use it as a bridge during a gradual migration, moving mailboxes to the cloud in stages rather than all at once. Others keep certain mailboxes on their own servers indefinitely and place the rest in Exchange Online.

Microsoft provides the Hybrid Configuration Wizard to set up the connection between the environments. Once it is configured, users in both locations can share one email domain and one address book. They can also see each other's calendar free/busy information. Meeting scheduling therefore works across the divide.

Mailbox moves in a hybrid setup are handled in migration batches. A user's mailbox moves to the cloud, and Outlook reconnects to the new location. The person's email address stays the same.

Hybrid also adds moving parts. Mail between the two environments travels over connectors, and the on-premises servers still need patching. An organization in hybrid mode depends on both its own infrastructure and Microsoft's.

Mail apps reach Exchange Online through a handful of protocols, chiefly MAPI over HTTP, Exchange ActiveSync, IMAP, POP and SMTP. Software that reads or changes mailbox data in code uses Microsoft $MSFT Graph, the current programming interface for the service.

MAPI over HTTP is the connection the classic Outlook desktop client for Windows uses to talk to Exchange Online. It carries mail, calendar items, contacts and other mailbox data inside standard web traffic. That design lets the desktop client work over an ordinary internet connection, with no dedicated network link to Microsoft.

Exchange ActiveSync is a synchronization protocol built for phones and tablets. Mobile mail apps use it to keep email, calendars and contacts in step with the mailbox on the server. The built-in mail apps on many phones rely on it when a user adds an Exchange account.

IMAP and POP are open internet standards that Microsoft does not own. IMAP keeps messages on the server and mirrors folders across devices. POP is designed to download messages to a single device. Neither protocol carries calendars or contacts. Apps that read mail over IMAP or POP use SMTP to send it.

Admins can switch each of these protocols on or off for individual mailboxes. In Exchange Online PowerShell, the Set-CASMailbox cmdlet controls those settings. The Exchange admin center offers the same choices for a single mailbox. Turning off POP and IMAP for accounts that do not need them reduces the number of ways a mailbox can be reached.

Microsoft Graph is one API that spans data across Microsoft 365, reached through the graph.microsoft.com endpoint. For Exchange Online, it exposes mail, calendar events and contacts to developers. The same interface also reaches data in other services, such as Teams and OneDrive. An app can work with a user's mailbox and files through one set of calls.

Exchange Web Services, or EWS, is the older interface that applications have used to work with Exchange data. Microsoft has announced plans to retire EWS in Exchange Online. The announcement concerns the cloud service specifically. Microsoft points developers to Microsoft Graph as the replacement. Tools that still depend on EWS will need to move before the retirement takes effect.
