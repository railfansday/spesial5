Akamai _abck: the cookie that rewrites itself on every response

Tanggal: 2026-11-10

This post is about three things that break Akamai automation in practice: treating _abck as a one-time token, discarding bm_sz and ak_bmsc because _abck looks like the important one, and ignoring solution.headers because no other solver returns any.

Scope: everything below is for QA automation on properties you are authorised to test.

If you only keep one, keep _abck — but understand that on its own it is half a conversation.

This is where Akamai differs from every other solver integration I maintain. Its solve result includes solution.headers — browser headers to reuse in subsequent requests — and the field is explicitly documented as possibly null.

When it is present, replay it. When it is null, fall back to solution.useragent and keep your own header set consistent with it: same Accept-Language, same sec-ch-ua family, same header order. A UA that says Chrome 131 with a sec-ch-ua for Chrome 108 is exactly the sort of mismatch the sensor data is built to catch.

Some Akamai-protected applications only validate the session after a specific XHR or POST — the price lookup, the search call, the cart estimate. Until that request happens inside the session, _abck stays at ~-1~ no matter how clean the browser is.
