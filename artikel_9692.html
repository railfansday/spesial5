SubtitleGenerator renders burned-in captions in the browser. You select a local video, generate a transcript, edit the captions, and export an MP4 with the captions rendered into its frames. The video rendering runs locally in the browser.

In one session, a user received their transcript and then made seven unsuccessful attempts to export a video with burned-in captions. We observed no further events from that session.

The failure UI appended the same generic advice to the error message every time:

Your project is safe. Try again or use a current desktop Chrome browser.

When I went to find out why the exports failed, I couldn't. Our analytics sent a single hard-coded error category for every export failure, so the specific error code was thrown away at the moment of capture. There was no export table in the database, no error reporting on the export path, and the local export history only recorded successes. Other exports succeeded during the same period, so the evidence did not point to a service-wide failure.

So this article is not a root-cause story for that one session. That cause is unrecoverable. It is about the two things I could fix:

If you render, encode or package anything heavy in the browser (WebCodecs, OPFS, canvas, workers), the same two problems are probably waiting in your code.

Before letting anyone press export, the app checked this:

It checks that the APIs exist. It does not check that they work for this file at this size. VideoEncoder can exist and still refuse the codec, resolution or bitrate you need. VideoDecoder can exist and still be unable to decode the user's source.

The real capability checks did exist (can this profile be encoded, can this source be decoded, is there enough quota), but they ran after an export attempt had started. Some of them could reject the attempt before rendering began, and output verification only ran after the file was produced. Either way, the user had to spend an attempt to find out, and the UI then offered the same generic retry advice.

The fix was a small preflight that runs when the export dialog opens, before an export attempt starts. It asks four questions, in this order:

The design decision that matters most is what happens when a probe itself breaks. A probe is new code running against browser APIs that behave differently across versions and devices. If a probe throws, I can't tell whether the browser is unsupported or my probe is wrong. Blocking the user in that case would turn a bug in my checking code into a new way to stop people from exporting.

So every probe is wrapped, and a throw means "unknown", which lets the export continue:

The kernel returns a negative result for unsupported encoding, unsupported decoding, insufficient storage, or a false font result. The dialog blocks the capability failures but leaves storage shortfalls retryable, because the user can fix those.

The encode probe uses mediabunny's canEncodeVideo with the codec, resolved dimensions and bitrate of the free export profile. The decode probe opens the user's file and asks the primary video track whether it can decode.

The storage check was not new. It came from an earlier failure: during testing, a 30-minute export at 8 Mbps on a 16 GB machine ran almost to the end and then failed with QuotaExceededError when the file was finalized in OPFS. Everything before that point was wasted work.

The 1.15 ratio is a safety margin for muxing overhead, not a guarantee. An estimate is not a reservation, and other tabs can use storage between the check and the render. If estimate() itself throws, the check is skipped. When I built the dialog preflight, I reused this guard instead of writing a second one.

Because low storage is fixable, it doesn't disable the export button. Once the export starts, the same check runs again, and if it still fails, the message says how much space is needed and how much is available.

The second problem was the message. "Try again" is a promise. If a capability check rejects the requested AVC profile, immediately repeating the same attempt is unlikely to help.

The export already threw typed errors. The fix was to decide, per code, what the user should do next:

This is a policy, not a diagnosis. For three error codes, the policy removes the immediate retry action and recommends a current desktop Chrome or Edge browser. That is a suggestion, not a guarantee that another browser will succeed. The mapping also can't prove that every render-failed is temporary, so unknown errors still default to a retry.

When the preflight returns a definite "unsupported", the dialog shows a similar redirect before an export attempt starts: "This browser can't export a burned-in video. Open in a current desktop Chrome or Edge to export. Your subtitles are safe — keep editing here."

Export-failure events now also carry a six-value export_failure_kind field alongside the generic category. When an event is captured, we can see which kind of error it was, although render-failed still groups several possible causes.

The preflight kernel was written against a failing test first. Its unit tests cover the decision rules by injecting probe results:

The font case tests the kernel's rule, not the real adapter. In the app, the font adapter returns true when collection succeeds and throws when it fails, and a throw is allowed.

End-to-end tests use an injection hook, available only in test mode, that forces the encode probe to report "unsupported" or to throw. That covers both sides of fail-open in a real browser: the blocked state with its redirect copy, and the throwing probe that must not block. At a 390px viewport width, another test injects an insufficient-storage error and checks the shortfall message, a visible retry button and an enabled export button. It doesn't run a second attempt.

One gap I should name: I haven't found a test that directly asserts the eight-second timeout. The timeout is implemented, but it isn't covered the way the other branches are.

What the tests can't show is everything the probes don't cover. In a later Android investigation, export failed immediately with render-failed. On the tested phone (a Xiaomi 13 Ultra on Chrome 151), FontFaceSet.load rejected font requests that included the next/font fallback backed by local(). Loading only the primary family for export fixed that failure.

Our font preflight only collects the font resources. It doesn't run the font loading that happens later in the export path. I don't have a record of what the preflight returned on that phone, so I won't claim it passed and then failed. The point is narrower: that failure was in a step the preflight doesn't exercise. A preflight is a sample of the pipeline, not a dry run of it.

What is still unsolved: the cause of those seven failures is gone for good. Some older devices still fail at runtime in places no preflight covers yet. And a passing preflight can still end in a failed export, which is why the error mapping matters as much as the checks.

The export code described here runs in SubtitleGenerator. The lesson isn't specific to captions, though: check what you can before the expensive step, and don't ask people to retry something you already expect to fail.
