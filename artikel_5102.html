Bitcoin Lightning developers patch bug that could make completed payments disappear

Tanggal: 2026-11-17

A software flaw could cause nodes to lose track of settled payment updates after restarting, threatening the integrity of Lightning channel records.

Bitcoin Lightning developers patched a software vulnerability that could cause nodes to lose track of settled payments after a restart, potentially disrupting the accounting records that secure payment channels.

The flaw affected LND, a widely used implementation of Bitcoin's Lightning Network, which enables users to send Bitcoin through payment channels without recording every transaction directly on the blockchain.

Developers released v0.21.8-beta and v0.20.8-beta on Nov. 11 to address the issue, which stemmed from an error in how the software saved and restored channel updates.

The vulnerability could cause a node to reconstruct incomplete payment records after restarting, even when the original information remained stored on its disk.

That failure threatened the consistency of Lightning channels, where participants rely on accurate records to determine which payments have settled and what each party is owed.

According to LND maintainer Olaoluwa Osuntokun, known as Roasbeef, the problem involved a counter that tracked acknowledged updates from a connected Lightning peer.

The software stored the number of entries using a 16-bit unsigned integer, which can represent values only up to 65,535.

Once the list reached 65,536 entries, the counter reset to zero, even though LND continued writing the updates to storage.

Upon restarting, the node could interpret that zero as an empty list and omit a previously settled hashed timelock contract (HTLC), a conditional payment mechanism that helps secure transactions across Lightning channels.

At 65,536 log entries, LND's old stored count could wrap to zero. The released patch adds write guards and checks older records on load.

Oversized lists are rejected before commitment progress or revocation, and before serialization writes record bytes.

The updated reader validates entries and count. It can recover qualifying complete lists; malformed trailing data is rejected.

The fix prevents new oversized logs and conditionally recovers complete older records.

The vulnerability became more concerning after developers identified a potential way for connected peers to push the affected update list toward its limit.

In the GitHub discussion, LND collaborator ziggie1984 explained that a peer could repeatedly send transaction fee updates and commitment signatures while withholding a required revocation message.

That behavior allowed the list of pending acknowledgments to grow without being cleared.

The developer reproduced the behavior in a unit test, generating 201 stored updates after 200 rounds of messages.

Crucially, the accumulated entries survived reconnects, suggesting that repeatedly disconnecting and reconnecting would not necessarily prevent the list from eventually reaching the overflow threshold.

The potential weakness matters because Lightning depends on both parties maintaining consistent payment-channel states. Losing track of a settled update could undermine the records used to reconcile channel obligations.

However, the project's disclosures do not identify any confirmed exploitation or financial losses associated with the flaw.

To address the problem, developers introduced checks that prevent oversized update lists from advancing the channel state or being written to storage.

They also modified how LND reads existing records, allowing nodes to recover complete update lists saved by older versions when the underlying data passes validation.

The fix was merged into LND's main development branch on Nov. 5 before being included in both November releases.
