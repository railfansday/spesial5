Type inference and narrowing with reverse arrows

Tanggal: 2026-11-19

November 10, 2026 by José Valim, Guillaume Duboc in Internals

This article explains how Elixir implements type inference and type narrowing using reverse arrows: a small set of composable ideas, rather than special cases hardcoded into the type checker.

Thanks to this work, the upcoming Elixir v1.21 passes all tests in the If-T: Type Narrowing Benchmark by Guo et al.. This means v1.21 can find even more sure bugs in existing Elixir programs and, once type signatures are introduced, narrowing will give us more precise types and fewer false positives.

The type system was made possible thanks to a partnership between CNRS and Remote. The development work is currently sponsored by Fresha, Supermethod and Dashbit.

Elixir performs type inference by refining the dynamic type. This is quite different from how inference and gradual typing are implemented in most type systems, so let’s break it down.

In many gradual languages, the dynamic type, often known as any, is a “black box” and can be used in any context. For example, imagine this Elixir function, where x starts with type dynamic(), as there is no type signature:

The program above uses x both as a number (more precisely, as integer() or float() in x * 2) and as a bitstring in byte_size(x). In some gradual type systems, the type checker will accept the program above, even though it will crash at runtime, because the dynamic type can be used in any context.

However, in Elixir, the dynamic() type can be refined, and the above will report the following typing violation:

As you can see in the error message, Elixir infers that the type of x after x * 2 is a dynamic(float() or integer()). This means that x can be given to any function that accepts at least one of float() or integer(). However, because byte_size(x) expects a bitstring, we have a typing violation.

This is possible because dynamic() in Elixir actually means dynamic(term()), where term() is the top type. Then, as a variable is used throughout the code, its dynamic type is refined by intersecting its type with the arguments of the functions the code invokes. In other words, we go through the following steps:

x is given to x * 2. The left operand of * expects integer() or float(), which we then intersect with term(), and therefore x gains the type dynamic(integer() or float())

x is given to byte_size(x), which expects a bitstring. The intersection of integer() or float() with bitstring() is empty, which will lead to a typing violation

This time, we pass x to the remainder function, rem, which expects all of its inputs to be integers. This means that, at the end of this function, Elixir will correctly infer that x can only be an integer, because x was refined from dynamic(term()) to dynamic(integer() or float()) and then only to dynamic(integer()). The inferred type for using_x_as_integer is a function, commonly written using the arrow notation: dynamic(integer()) -> :ok.

The best part is that all dynamic types in Elixir are refined and therefore the type system is always doing its best to find bugs, even in the presence of dynamism. And the refinement itself is often quite precise, thanks to reverse arrows, which we will explore next.

An arrow is the type of a function: integer() -> boolean() is an arrow that says “given an integer, this function returns a boolean”. The type on the left of the arrow is its domain (what it accepts) and the type on the right is its codomain (what it returns). Every function has arrows, whether they come from a type signature you wrote or are inferred by Elixir from the function’s clauses.

With this in mind, and remembering that rem only works on integers (its type is integer(), integer() -> integer()), what do you believe is the inferred type of x in the function below?

You may think x is dynamic(integer() or float()), because that’s the domain of negate. However, x will once again be inferred to be dynamic(integer()), because Elixir propagates types through the arrows in reverse: it starts from what the outermost call expects and walks inwards, from results to arguments, until it reaches the variables. Let’s break it down.

We start type checking the function and we find rem(negate(x), 2). rem has a single arrow, integer(), integer() -> integer(), so we know that negate(x) must return an integer() for this to type check

Now we type check negate(x). negate has two arrows: integer() -> integer() and float() -> float(). Since its result must be an integer, we can discard the float() -> float() arrow, as it never returns an integer. The only remaining arrow is integer() -> integer(), so the argument of negate must be integer()

Now we type check x itself. x starts with the type dynamic(term()). We then intersect it with integer(), resulting in dynamic(integer())

In other words, inference goes in two directions. Going forward, from arguments to results, arrows tell us what each call returns. Going in reverse, from results to arguments, arrows tell us what each argument must have been for the call to produce the expected result. As we give precise type signatures to our programs using multiple arrows, the type system will use these same arrows to infer precise types. As we will learn next, Elixir uses this technique to infer types from guards and to perform type narrowing (also known as occurrence typing).

If multiple arrows could return true, we would then simply union their domains.

To narrow x, we need to reverse the arrows of is_integer(x). In Elixir v1.20, we only did so for the expression given directly to if or case. Here, the expression given to if is the variable y. All v1.20 knew about y is that it was a boolean(). Inside the do-branch, y is true, but by then the connection between y and is_integer(x) had been lost at the assignment, so there were no arrows to reverse.

This would be quite harmful once we add type signatures, because it means trivial refactoring techniques, such as extracting an expression into a variable, could lead to false positives.

Elixir v1.21 solves this by keeping track of the expression each variable was assigned to. Now, when y is narrowed to true, we know y came from is_integer(x), so we continue propagating true in reverse through the arrows of is_integer, narrowing x to integer(). Elixir’s approach to type inference and narrowing is built on a few ideas that compose well. Dynamic types are refined as variables are used, multiple arrows give precise types to functions, and propagating types through those arrows in reverse lets us infer and narrow types across conditionals, patterns, and assignments, all without hardcoding knowledge about specific functions.

In Elixir v1.21, we use these techniques to find sure bugs in existing Elixir programs, without requiring any changes to your code. The same mechanisms will apply once type signatures are introduced: the more precise the signatures, the more precise the narrowing and the fewer false positives.
