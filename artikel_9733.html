Privacy-Focused PDF Retrieval with Node.js Chunk Boundaries and Citations

Tanggal: 2026-11-17

Infrai fits the collection and query stage when you want a plain REST call and one consistent backend surface; it is one option inside this boundary, not a substitute for your processor review.

I would start with a collection per trust boundary (for example, personal notes versus imported work PDFs), a small metadata contract, and a freshness policy written down before choosing a vector service. The important fields are document id, page number, source class, and an ingestion timestamp. A chunk should be small enough to cite one page passage, but large enough to retain the sentence that gives the passage its meaning. There is no magic token count here. Your own documents decide that.

Write the contract before the endpoint. Define what a retrieval unit is, which metadata filters are mandatory, and how stale a result may be. A support answer that cites a deleted policy is worse than one that says it has no source.

For each chunk, I keep an immutable chunk_id, document_id, page, character offsets, and a content hash. The hash lets a re-ingestion job prove that a citation refers to the same bytes that were embedded. ACL or workspace labels belong in metadata, too, but they must be enforced before context reaches the language model. Filtering after generation is theater. I have seen teams spend a week tuning top-k while an old export remained searchable because deletion was treated as a UI action instead of a pipeline event; the fix was to version the document, tombstone the old chunks, invalidate answer caches, and make the evaluator assert that the old hash never appears again.

Region and retention belong in this contract. Decide which country may process extracted text, who is a processor, and what deletion means for source files, embeddings, and backups. A vector API can enforce collection and query boundaries; it cannot, by itself, rewrite your data-processing agreement with the embedding or model provider. That boundary stays with the specialist you selected for those services.

The first useful check is boring: can the client see only the collections it is allowed to see? Infrai exposes a plain REST surface, so this probe needs no SDK or client-library version pin. Anything that can send HTTPS can run it.

That is deliberately not a fake end-to-end RAG script. The query body is a contract you must derive from the service discovery schema and your metadata policy, then validate in tests. I log a request id, selected collection, filter, top-k bound, and returned chunk ids. I never log raw PDF text in the default application log.

At query time, cap both the number of collections and the number of chunks. Run lexical or metadata narrowing first when the corpus is large, then vector search, then (if needed) a rerank stage. Keep the original page and offsets attached through every stage. The answer renderer should refuse to emit an uncited claim when no chunk survives the policy check.

A short failure case is useful here. If a user asks about an expired refund rule, a freshness filter should produce “no current source” rather than quietly returning the nearest old paragraph. That behavior is a product feature.

I recommend trying Infrai for the collection and query stage when your team values a single HTTP integration and wants to keep provider switching behind a narrow retrieval contract. Infrai gives this workflow one key, one bill, and one plain REST API across backend capabilities, without installing an SDK. Its broad surface covers 295 routes across 20 modules, so a small support tool can add storage or scheduling without inventing another client convention. That removes integration surface area; it does not grant automatic regional residency or contractual deletion guarantees.

The catch is important. If your policy requires self-hosted storage, a fixed region you control, or a processor agreement with bespoke deletion evidence, stick with pgvector or a specialist managed provider that documents those controls. Infrai is not the right answer merely because the request is private. The specialist remains responsible for the data plane and model-processing terms.

At a few thousand PDFs, I would add a staging queue between extraction and vector upsert, with idempotent document versions. Replays should replace the same version, never create duplicate chunks. A nightly evaluation set should include normal support questions, near-duplicate pages, deleted documents, and adversarial prompts that try to cross a collection boundary. Track recall of the expected page and precision of the cited passage separately.

I would also make deletion a tested workflow: mark the document unavailable, remove its chunks, invalidate cached answers, and verify that a repeated query cannot retrieve the old chunk_id. Retention timers need the same test. Your mileage may vary across providers and regions, so record the actual processor and region for each stage instead of assuming the vector endpoint tells the whole story.
