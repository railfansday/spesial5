The IMPACT Framework: Six Rules for Better AI-Generated Designs

Tanggal: 2026-11-05

James Shehan, designer and writer at Prompt Like a Designer.

James Shehan, designer and writer at Prompt Like a Designer.

Ask an image model for "a clean modern landing page hero for a SaaS app" and you'll get something that looks fine. Soft lavender gradient. A floating dashboard tilted 8 degrees. Three feature icons in rounded squares. A violet "Get started free" button. You've seen it a thousand times, because you literally have: it's the average of every SaaS hero the model was trained on.

I've been a designer for more than 30 years. For the last few I've been watching developers fight this output, and the fix isn't a better model or a magic keyword. It's the same thing I'd tell a junior designer on day one: stop describing feelings and start specifying decisions.

So I turned the rules I actually use into constraints a model can follow, wrote a small function that assembles them into a prompt, and tested it against vague prompts on the same model. Everything below is copy-paste: the constraint blocks, a system prompt, Python and JavaScript builders, a lint checklist, and the exact prompts behind each example.

1. Vague adjectives resolve to the statistical mean. "Clean," "modern," "professional," and "premium" don't point to a visual. They point to a cloud of millions of images that were tagged or captioned with those words. When the model has nowhere specific to land, it lands in the middle of that cloud. The middle of everything looks like nothing in particular. That's the generic look.

Think of it like an underspecified function call. If you pass render(style="modern"), every unset parameter falls back to a default, and the defaults are whatever was most common in training. A designer's job is mostly setting those parameters on purpose.

2. The model's resting state is "add more." Unconstrained, image models reach for gradients, drop shadows, glow, texture overlays, decorative icons, stock people, and full-saturation color. Each of those feels like it's adding value one at a time. Put together they're noise. Restraint is never the default. You have to ask for it, every time, by name.

So the fix has two parts: replace adjectives with measurable facts (ratios, hex codes, positions, counts), and always ship an exclusion list.

I group the rules under six letters, IMPACT. Every layout problem I've diagnosed in three decades falls under one of them. Each block below is written in prompt language, so you can paste it straight into a prompt and edit the values.

"Make the headline bigger" is a vibe. A ratio is a spec. Name what reads first, second, third, and what must stay quiet.

A 3:1 ratio works for most screens. Posters can go 4:1 or more. Below roughly 2:1, the model tends to make everything the same "medium-important" size, which is the main reason generated layouts feel flat.

Models and beginners both under-space. Open space reads as confidence. Ask for it as a number, and differentiate spacing inside a group from spacing between groups (that's proximity, and it's how readers know what belongs together).

Listing colors isn't enough. "Navy, coral, gray" lets the model spread all three everywhere. Assign each color a job, roughly 60/30/10: anchor (background and big areas), support (text and structure), accent (the one thing you want found). Three colors is the ceiling. Only the accent is saturated.

Almost-aligned is worse than unaligned. People can't name it, but they feel it as sloppiness. Pick one rule and say it. Left-aligned usually carries more authority than centering everything.

For a two-part layout: asymmetric: text block flush left in the left half, product screenshot in the right half.

Contrast is the difference that makes the important thing findable: size, weight, color, space. One strong contrast decision does more than five weak ones. The test I use is the squint test. Blur the image. If the dominant element disappears, contrast is broken.

(For real UI, still check WCAG: 4.5:1 for body text, 3:1 for large text. The model won't do it for you.)

Two typefaces maximum. One family in two weights is often better. Image models render named fonts poorly, so for image generation describe the character of the type; for HTML or code output, name actual fonts.

For code output: Headlines in Inter 700, body in Inter 400 at 16px minimum, headline ≈ 3x body. Reliable free pairs: Playfair Display + Inter, Merriweather + Open Sans, Lora + Lato.

Not a letter, but non-negotiable. Pick the four to eight that fit the medium.

A quick translation table I run on every brief:

single flat background, generous whitespace, two colors max, no ornament

name an era: Swiss International Style, contemporary Scandinavian minimal

restrained palette, left-aligned, one accent, no decoration

fewer elements, more whitespace, quieter color (asking for "luxury" gets gold gradients)

heavy weight, large size jump, one dominant element

name the mechanism: larger, higher contrast, or the only saturated element

If you're wiring an LLM in front of an image model (or asking an LLM to write HTML/CSS), put this in the system prompt. It turns any user brief into an IMPACT-constrained prompt.

Hand-writing that block every time is error-prone, and the constraints are really data. So I made them data. This is a single file, standard library only. An optional graphic field lets you name the one strong visual idea, and an explicit "No other shapes" stops the model adding a second. It also enforces two rules (three colors, two typefaces) by raising, so a bad spec fails fast instead of producing a muddy image.

Because the spec is a plain object, you can store brand presets in JSON, version them in git, and diff them in code review. Changing the accent color for a campaign becomes a one-line PR instead of a re-write of a paragraph of adjectives.

Generation isn't the end. I run every result through the same six lenses, and the failure tells me which line of the spec to change. Fix structure (I, M, A) before surface (P, C, T).

When something fails, don't rewrite the whole prompt. Change the one parameter (raise hierarchy_ratio, tighten exclusions, narrow the accent's job) and regenerate. That's what makes this debuggable instead of a slot machine.

The "before" isn't bad. That's the point. It's competent and indistinguishable: gradient wash, tilted dashboard, floating stat cards, a feature row nobody asked for, and copy the model made up. The "after" has one headline at a clear 3:1 ratio, one accent color used exactly once (the button), a flush-left text block, and the exact words I specified. It looks like a decision was made.

"Professional" got neon, a blue-to-magenta gradient on the title, four icon bullets, a stock crowd photo, a neon sign, and invented dates and venue. Seven competing focal points. The IMPACT version has one: the title at roughly 4x the details, one orange circle as the only saturated element, and the venue line exactly as written. You can read it from across a room, which is the only job a poster has.

The "before" is the conference post you scrolled past this morning: dark navy, a blue-to-purple gradient on the title, a stage photo in a tilted frame, four icon features, a gradient ticket button, and a name, dates, and venue the model made up. Every element is shouting, so nothing is. The constrained version uses the optional graphic parameter to allow exactly one bold element: oversized terracotta brackets that bleed off the edge and tuck behind a heavy condensed headline. It's louder than the "before" in the one place that matters and silent everywhere else. One accent color, flush-left text, the exact words I wrote, and it still reads at thumbnail size.

Note the restraint isn't "make it plain." A minimal prompt with no focal graphic gave me a correct but bland card. Constraints remove the noise; you still have to specify the one strong idea.

To be straight about limits: image models still misspell text sometimes, so check every string. They also drift on exact hex values, so treat the palette as a strong steer and correct in post if brand color matters. And over-constraining has a cost. If you pin every element's position you get stiff, mechanical layouts. Pin the structure (what dominates, where the main blocks live, what's excluded) and leave a decision or two to the model.

But the core finding has held across every model I've tried. The gap between generic and designed output is mostly not the model. It's the number of decisions you made before you hit enter. Turn those decisions into parameters and you can make them once, reuse them, and review them like any other code.
