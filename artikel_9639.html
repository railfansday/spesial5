What Is Web Cache Deception and How Can Attackers Exploit It?

Tanggal: 2026-11-11

Web cache deception (WCD) is when an attacker tricks the cache into storing a private, dynamic response by taking advantage of the differences in how the cache and the origin server each interpret a URL. The victim is lured into requesting an ambiguous URL; the cache mistakes their sensitive response for a cacheable static file and stores it; the attacker then requests the same URL and reads the victim’s cached data. It could either be by clicking a link or through phishing emails.

A cache sits between client and origin server. On a cache miss it forwards the request to the origin, stores the response per its rules, then serves it; on a cache hit it serves the stored copy directly.Cache key— the parts of the request (usually URL path + query string, sometimes headers/content type) used to decide if a stored response matches an incoming request. In the PortSwigger lab, I targeted a URL that served a private, user-specific page,“https:// 0a260049032f207080a25840006d006a.web-security-academy.net/my-account”, using Burp Suite, I logged in as a user to access my API key.

Using Burp, I sent the my-account request to the Repeater — this is where the vulnerability lives, I appended “x.css” to the a dynamic, private page’s URL and sent the request, The first response came back as a cache miss.

On the second response, after delivering the payload from the exploit server to the client website I got a cache hit containing the client’s API key, meaning the private page had been cached. Here’s what happened: the first request was for a private, dynamic page that should never be cached. But with x.css appended, the origin server ignored the suffix, still resolved the path to /account, and served the private page anyway. The cache, however, only looked at the URL ending — saw .css — and stored the response as if it were a static file.

I logged in as Wiener, then repeated the attack to obtain Carlos’s API key — this is exactly what a real attacker would do: send the ambiguous URL to Carlos, perhaps via a phishing email. When Carlos clicks the link and logs in, his private API key gets cached. The attacker then simply revisits that same URL and reads Carlos’s cached data.Preventing web cache deception

Conclusion: Web cache deception isn’t a flaw in the cache or the origin server alone — it’s what happens when the two disagree about what a URL means.
