Buku Bon: building a voice-first ledger skeleton for Indonesia with Kiro (Kiroween 2026)

Tanggal: 2026-11-19

This post is written as part of the **Kiroween 2026 hackathon* (Skeleton Crew category).*

In Indonesia, a lot of money is tracked on paper or not at all. The warung (corner shop) owner remembers who bought rice on credit this week. The ojol (ride-hailing) driver guesses at night whether today's orders covered fuel. Nobody wants to type numbers into an app with one hand while serving a customer or waiting at a red light.

That is Buku Bon: a voice-first ledger skeleton, and two very different apps built on it.

The Skeleton Crew challenge asks for a template that is lean but flexible enough for two distinct apps. My rule was strict: an app is only a config file.

A config declares the intents, their keywords and sign, and a summary view. This is the whole "debt" model of the warung app:

No framework, no build step, no runtime dependencies. Data stays in the browser, the app works offline through a service worker, installs as a PWA, and exports CSV. If the browser has no speech recognition, typing the same sentence works.

Speech recognizers return a mess of words and digits. The parser has to understand all of these as the same kind of thing:

It uses three accumulators (millions, thousands, the current group) and is checked by a property-based test: for random n, parseAmount(say(n)) === n, where say() speaks the number in Indonesian words. That one property found more edge cases than a page of unit tests would have.

Everything Kiro reads lives in /.kiro at the repo root.

Three steering files are always included: product.md (who the users are, speak first / type second, confirm before saving, Indonesian copy and rupiah), tech.md (plain ES modules, a pure DOM-free parser, Web Speech id-ID with typed fallback) and structure.md (the app-is-a-config contract).

The single most useful line was: "extend the skeleton generically instead of special-casing an app."

When I asked Kiro to add "Pak Budi lunas" (settle a whole debt) and a driver's daily target, it did not write if (app === 'warung'). It added two generic intent flags to the skeleton — settle and meta — and switched them on only in each app's config.js. That is exactly the design I wanted, and I didn't have to ask for it in the prompt; the steering did that.

The spec in .kiro/specs/voice-ledger-skeleton/ has EARS-style requirements, a design with the parser algorithm and correctness properties, and tasks.md. Working from tasks instead of vibe prompts made each Kiro turn small and checkable. Kiro also kept the spec honest: while implementing it added R7 (offline), R8 (settle balance) and R9 (daily target metadata) and ticked the tasks it finished.

After the first turn, a headless smoke test showed the weekly chart drew no bar for today and the mic emoji rendered as an empty box. Kiro fixed both, but the re-test still showed every bar at the same tiny height.

I described the symptom and asked for the root cause in one line. Kiro's answer:

Percentage height on .bar collapsed to min-height because .day-bar flex column had no explicit height, making the percentage relative to nothing.

It fixed the CSS in the skeleton (keeping it generic) and re-ran the tests. Asking for the root cause, not just a fix, is a habit I'm keeping.

The repo has two agent hooks in .kiro/hooks/: run parser tests on save and keep the skeleton generic (flag words like warung, ojol or utang inside skeleton/ and move them into config hooks). Hooks fire in the Kiro IDE; I worked in the CLI, so I ran the same loop by hand — asking Kiro to run npm test after every task and to do the generic-skeleton check. That check caught a leftover "tidak punya utang" ("has no debt") string in skeleton/app.js, and Kiro moved it into a settleEmpty hook in the warung config.

The first scaffold (parser, store, voice wrapper, both configs and tests) and the first drafts of the .kiro files were prepared earlier in the submission period with help from an AI assistant; Kiro CLI sessions then built tasks 10–14 on top. No third-party frameworks or starter kits are used.

A third app (a market stall or an arisan savings group) — which should be one new config.js — plus voice read-back of balances and WhatsApp-friendly reminders for customers who owe.

If you build something for small businesses in your own language, I'd love to hear how you handle spoken numbers.
