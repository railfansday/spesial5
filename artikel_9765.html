Stopping Duplicate Executions in External Webhooks: A Practical Guide to Redis Distributed Locks

Tanggal: 2026-11-09

A few weeks after launching an API endpoint designed to ingest webhooks from a payment processor, our on-call rotation received an urgent ticket from customer support: "A user appears to have been charged twice within three seconds for a single checkout session."

A deep dive into our application logs quickly surfaced the underlying cause.

Under elevated load—triggered by brief JVM/Python garbage collection pauses or database connection pool contention—our webhook consumer endpoint exhibited an edge-case latency spike of just a few hundred milliseconds. The payment provider's delivery gateway marked this request as an unacknowledged timeout. Per standard delivery SLA and webhook reliability protocols, their automated retry policy kicked in immediately, resending the identical JSON payload via TCP/HTTP retries.

These concurrent requests arrived at our API server fleet almost simultaneously. Even though our backend service performed standard pre-validation queries (the classic SELECT ... WHERE event_id = ? check before an INSERT), standard read-committed transaction isolation levels and concurrency interleaving allowed both worker threads to observe that the transaction record "did not exist yet." Both threads proceeded to execute business logic, process payment records, and commit duplicate rows.

This classic race condition cannot be reliably prevented at the application layer using optimistic queries alone. It demands strict, atomic mutual exclusion at the data store level before entering the critical section.
