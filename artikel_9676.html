Why Is It Always an .md File?

Tanggal: 2026-11-24

Posted on Nov 24 • Originally published at jeelvankhede.hashnode.dev

Most of what I hand to an AI agent these days is a Markdown file.

Most of what it hands back is one too. The plan before the code. The summary after it. The instructions that tell it how a repo works. Somewhere along the way, .md became the default extension of working with AI. Even this article started life as one.

I kept noticing it for a while before I started asking about it.

The question I could not shake was a different one:

The first asks about the model. The second asks about everyone else.

JSON was there. HTML was there. YAML, plain text and Word documents were all there first. Any of them could have become the format we hand to agents. None of them did.

There was no announcement. No committee. No moment where the industry agreed that AI would run on Markdown.

For years, Markdown was the README. The file you skimmed for the install command and closed. Then chat assistants started answering in it, with headings, bullets and code fences in every reply. Then the instruction files arrived. Claude Code reads a CLAUDE.md. OpenAI's coding agents read an AGENTS.md. Skills ship as a SKILL.md. Different companies, different tools, and every one of them landed on the same extension.

When that many teams land on the same thing without coordinating, something is pulling them there.

The interesting part is figuring out what.

The answer I would have reached for is that models simply read Markdown best. It is lighter than HTML and more structured than plain text. It sounds like exactly the kind of thing a model would prefer.

It is a tidy answer. It does not hold up.

In 2024, researchers at Microsoft and MIT gave GPT models the same prompts in four formats: plain text, Markdown, JSON and YAML. On one benchmark, GPT-3.5 scored 59.7 with JSON and 50.0 with Markdown. A GPT-4 model flipped the result and did better with Markdown.

The best format moved with the model and the task. There was no single winner.

To be fair, those were GPT-3.5 and GPT-4, and I have not seen the same test run on today's models. But the larger model was already the less fussy one. If that holds, the format matters even less to the model now.

So the reason sits somewhere else. On our side of the screen.

Markdown is from 2004. John Gruber built it so people could write for the web in plain text, without typing HTML tags.

Stack Overflow answers are written in it.

So are Reddit comments.For close to two decades, that is where engineers explained things to each other.

Then, in June 2020, OpenAI unveiled GPT-3.

A month later, Connor Leahy, Sid Black and Leo Gao founded EleutherAI, a Discord server for people who wanted to replicate GPT-3 in the open. Leahy later said it began as "something of a joke". IEEE Spectrum called the group "mostly self-taught hackers".

A joke that needed a lot of reading material.

To train a model, they needed text, and more varied text than whatever a web crawl happened to scoop up. So they built their own dataset and published it on the last day of 2020: the Pile, 825 GiB of English text from 22 sources. It trained their GPT-Neo models, and parts of it went into Microsoft's Megatron-Turing NLG and Meta's OPT.

Two of those 22 sources were GitHub, where a repository introduces itself with a README, and Stack Exchange, where answers are written in Markdown. Together they came to about 127 GiB, roughly 15% of the whole. Not all of that is Markdown. Much of the GitHub share is code.

The part that matters most is that the list exists at all. Many labs do not publish exactly what their models read. Even researchers studying Llama and OPT have had to work from stand-in datasets. EleutherAI wrote every source down.

I cannot see inside the closed training sets. Nobody outside those labs can. But the one set I can open puts the places where engineers write Markdown right there in the mix.

So when a model answers in Markdown, I read it as the house style of the people it most likely read.

AI did not adopt Markdown. It inherited it.

That explains why the model writes it. It does not explain why I keep accepting it.

An instruction file for an agent has two readers. The model follows it. I write it, edit it, review it, and have to trust that it says what I think it says.

Most formats are built for one of those readers. JSON and YAML are comfortable for the machine and tiring for me. A Word document is comfortable for me and has to be converted before the tool can use it.

Markdown works for both, even when nothing renders it.

That was Gruber's design goal from the start: a Markdown document should be publishable as-is, as plain text. Two decades later, that goal matters in a place he never designed for. Not every answer an agent gives lands in a chat window that renders it. Some of it lands in a terminal, or in a raw file in an editor.

And because Markdown is plain text, it behaves like code. It sits in the repo next to the code it describes. A change to it shows up as a diff. It goes through the same review. When an agent starts behaving differently, the history tells me which line of its instructions changed.

It has limits, and I do not want to pretend otherwise.

Diagrams are where I feel it most. Markdown has no syntax of its own for them. The common answer is Mermaid, a diagram written as text inside a code fence, and GitHub has rendered it natively since February 2022. Not every platform does. The same block is a clean diagram in one place and a wall of code in another.

Not all the platforms where I publish articles support diagrams, and I have run into that a couple of times, enough to make a rule for myself. Every diagram drawn as plain box text inside a code fence, forty characters wide, like the one above. It is the one shape that renders the same way everywhere I publish.

It works. Boxes and spaces, aligned by hand.

Part of the reason is that Markdown never got a single standard. Gruber shipped a syntax page and a script, and left the edge cases open. When a group tried to standardise it in 2014, Gruber objected to them using the name, and the effort became CommonMark. So every platform speaks a slightly different dialect.

Even so, every time I weigh it against the alternatives, it holds. Diagrams suffer. Almost everything else works.

I started with a question about a file extension. It turned out to be a question about who has to read the file.

JSON is written for parsers. HTML is written for browsers. Markdown was written for people, and people are where the models learned to write.

Not because it is the best format for the model.

Because it is the one format where the model and I can read the same thing, without a tool standing in between.
