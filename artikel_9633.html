Your AI Is Generating PRs, Not ROI

AI coding tools are generating more pull requests than ever, but more PRs don't equal ROI unless that code ships, holds up in production and reduces work downstream.

Ask any engineering leader if their team uses AI to write code, and you'll get a yes before you finish the question. Ask them what that AI is worth, and watch the yes turn into a pause.

That pause is the actual state of the industry right now. Not "should we adopt AI." That question is over. The question nobody has a good answer to is simpler and more uncomfortable: can you prove it worked?

We talk to a lot of engineering leaders whose teams have already bought the AI. Vendors, internal agents, standardized copilots, all of it. And when we ask how they know it's paying off, we hear some version of the same three things, over and over, from companies that have nothing else in common.

Here's the accepted story: AI writes code faster, so engineering gets faster, so the org gets more done. It's clean. It's also wrong, or at least wrong enough to be dangerous.

Speed of code generation isn't the same thing as speed of value delivery. We've heard this described, almost word for word, by leaders at very different companies: their AI tooling is optimized for the speed of the coding loop, and that optimization is flooding review queues with pull requests that don't address the problems actually costing them money. One technology leader we spoke with put a number on it: their organization still allocates 30 to 40 percent of R&D to legacy sustenance. An AI that makes commits faster doesn't touch that number. It might make it worse, because now there's more code to sustain.

More code, faster, is a vanity metric. It looks like progress on a dashboard. It is not the same thing as fewer defects, fewer escalations, less tech debt, or a codebase anyone actually trusts. If your only instrumented signal is "how fast did we ship the diff," you've measured the part of the SDLC that was never the bottleneck.

The more sophisticated a team gets with AI, the worse this problem gets, not better. We talked with a leader at an enterprise planning-software company who had built dozens of finance agents and an internal factory that turns specs directly into agents. Real infrastructure, real investment. And their honest assessment was that they have no standardized way to measure how their engineers actually use these tools, and now they're dealing with agent sprawl: agents triggering each other, versioning headaches, token spend nobody forecasted, and a growing need to gate daisy-chained agents just to protect the budget and the systems underneath them. This team caps R&D spend as a percentage of revenue and wants AI to bring that number down every year. Nobody can currently tell them if it is.

That's not a failure of ambition. It's a failure of measurement discipline arriving after the infrastructure, instead of before it.

We heard the same shape of problem from a team running a home-grown AI development process, stitched together across a project tracker, a code host, an LLM, and a browser-automation tool for execution. It works, in the sense that a demo works. But their own words to me were that the current evaluation criteria are largely subjective, and what they actually want is a clean, quantifiable way to tell the business whether the tooling is worth what it costs. A demo is not a metric. A vibe is not ROI.

There's a second version of this problem that shows up earlier in the buying process. Teams benchmark every new AI purchase against the general-purpose AI they already pay for. We've had conversations where the honest pushback was some version of: our senior engineers already get most of what they need from existing docs and the chat assistant they use every day, so why would we pay for something else? That's a fair question, and it's one every vendor in this category, including us, has to answer with evidence, not adjectives.

None of this is a story about bad tools. Cursor-style coding assistants, general chat assistants, internal agent factories: they're all doing exactly what they were built to do, which is help someone write code faster. The gap isn't in the tool. It's in the fact that "wrote code faster" was never the metric that mattered, and almost nobody instrumented the metric that does.

If speed of code generation is the wrong number, what's the right one? It's the same handful of things it's always been, just harder to see once agents are shipping code faster than anyone can review it by hand: defects that never reach production. Tickets that never escalate to L3. Tech debt that shrinks instead of compounding. Time to root cause. Time to trust a change before it ships.

Those aren't vibes. They're measurable — but only by something that holds your code, your production behavior, and what your customers actually report in one model instead of three disconnected tools. That's the argument for an engineering world model: not more code, but a traceable line from every change to its consequence, and the judgment to tell you which one you're looking at. Code simulations exist for the same reason: catching the defect before it merges is worth more than shipping the diff a day earlier. Agentic debugging is worth more than agentic writing, because writing was never the expensive part of the SDLC. Understanding what you wrote always was.

The teams we talked with weren't wrong to adopt AI. They were wrong about which loop to speed up. Every engineering org we know is currently running an experiment on itself, at scale, with no control group and no instrumentation. Fix the instrumentation before you fix the model. The PRs were never the point.
