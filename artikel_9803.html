Shopify deletes API-created webhook subscriptions after 8 failures. An n8n safety net, no Code node

Tanggal: 2026-11-16

Picture a shop that keeps taking orders all weekend while your n8n container sits in a restart loop. Every delivery fails. Shopify retries 8 times over 4 hours, and "after 8 consecutive failures, the subscription is automatically deleted if it was configured using the Admin API." On Monday n8n is healthy again, and silent. Nothing ran, so nothing failed, so no error workflow fired.

That rule applies to shop-specific subscriptions, the ones created with webhookSubscriptionCreate: the usual route when there is no app project (no shopify.app.toml, no CLI). App-specific ones are treated differently (next section).

Both were run on n8n 2.46.6 against a mock GraphQL endpoint and PostgreSQL 16, not a live shop. API version: 2026-10, the latest stable at the time of writing.

Shopify's own advice: "Choose app-specific subscriptions unless your topics, delivery URIs, or filters need to vary between shops." Per its subscription docs, failing app-specific subscriptions "will not be deleted by Shopify"; failing shop-specific ones "will be deleted".

That block goes in shopify.app.toml and ships with shopify app deploy (syntax from Shopify's docs; not deployed in the test run).

My default: use it whenever there is an app project and one URL serves every shop. The watchdog below is then pointless, since webhookSubscriptions "returns only shop-scoped subscriptions, not app-scoped subscriptions configured in TOML files".

Stay with the API when the URL differs per shop or there is no app project. The reconciliation job is worth having either way: deliveries can still be missed.

From the webhooks overview, the HTTPS delivery page and ignoring duplicates:

Keep the webhooks and add one cheap poll an hour as a safety net.

POST it to https://YOUR_SHOP.myshopify.com/admin/api/2026-10/graphql.json (callbackUrl is deprecated, use uri). Use the production URL: n8n registers it when the workflow is published.

Tokens changed in 2026. New custom apps can't be created in the admin any more (existing ones keep working); they come from the Dev Dashboard. A token from the client credentials grant lives 86,399 seconds, about a day, and only works for apps your organization owns.

A static header credential would break after a day, so the workflows fetch a token first: an HTTP Request node posts to /admin/oauth/access_token with a Custom Auth credential, then the GraphQL node's Headers option sends X-Shopify-Access-Token. The credential's JSON makes the request a form, as Shopify requires, and keeps the secret out of the workflow:

Without the Content-Type header, n8n 2.46.6 sent the same body as JSON; with it, the mock received the three fields form-encoded. With a non-expiring token (older admin-created app), drop the token node and use a Header Auth credential.

The HMAC key is the app's client secret, kept in a Crypto credential.

The expressions used in the IF and GraphQL nodes:

Two Schedule Triggers, so a failure in one branch can't stop the other.

Shopify's docs say to fetch objects updated "since the last time the job ran", so the run state is stored in a sync_state table, read and written by Postgres nodes. The first node computes the lower bound and this run's start, once:

Every page of a run uses the same filter, because the GraphQL node reads since from that node (a $now-based expression had drifted by a second between pages):

One Postgres node upserts the whole page in a single statement, then an Edit Fields node puts the GraphQL response back (Postgres returns its own result, not the page), and an IF on hasNextPage loops back into the GraphQL node. On the last page the IF's false output runs Save sync point.

Why one chain. The obvious design splits each page into a per-order upsert branch and a "Another page?" branch feeding Save, but with n8n's v1 execution order the branches leaving a node run top to bottom by canvas position, so moving nodes around could run Save despite a failed upsert. Here Save sync point has a single input, the IF's false output, and the IF only receives an item after Upsert page succeeded, wherever the nodes sit. One statement per page is also atomic, and an empty page still emits an item (jsonb_to_recordset on [] inserts nothing), so the checkpoint moves.

Don't use max(updated_at) of your orders table as the checkpoint: the webhook path writes there too, and one live delivery after an outage would move it past the hole.

If nodes.length is 0, the CreateOrdersUpdated mutation runs and the alert includes its userErrors, so you can tell "re-created" from "tried and failed". The first test run created the subscription and alerted; the second did nothing.

The watchdog runs on the instance it watches, so it can't notice that instance dying. Poll /healthz from an external monitor, and make sure someone reads the emergency developer mailbox.

The receiver runs the same INSERT ... ON CONFLICT (gid) DO UPDATE ... WHERE shopify_orders.updated_at <= EXCLUDED.updated_at with a VALUES ($1, ... $7) list, fed by an array expression ({{ [ $json.id, $json.name, ... ] }}) rather than a comma-separated string, so a comma in a value can't shift columns. The WHERE guard refuses older data when two executions for the same order finish out of order.

Expected: 200 for a valid signature, 401 for another secret, a changed body or a missing header.
