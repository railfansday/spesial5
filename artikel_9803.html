How I Built a Chrome Extension That Turns 40 Tabs Into One

Tanggal: 2026-11-19

Chrome's native tab groups did not solve my problem. Neither did the memory saver. My problem was simpler and dumber: I keep forty tabs open because I am afraid of losing them, and forty tabs cost me about two gigabytes of RAM and all of my attention.

So I built an extension that does one thing: it takes every tab in the current window, writes the URLs into local storage, closes the tabs, and shows them back as one scrollable column. One click in, one click out. It is 136,138 bytes across 69 files, uses four permissions, and makes zero network requests.

This post is the engineering part: the ordering that keeps you from losing data, the normalization layer, the undocumented field I had to support, and the MV3 service-worker traps that cost me a weekend.

I set the budget before writing the code, because a tab manager that itself eats memory is a joke:

none, no host permissions, no remote code

That last one matters more than it looks. With no bundler there is no shared module graph, and that single fact causes the first real bug.

The popup does the whole operation. Naive version reads the tabs and closes them; that version loses data whenever anything in between fails. The working version is this:

Write before close. If storage.append rejects (quota, serialization, a corrupted key), the tabs stay open and the popup shows an error. Losing the list is recoverable; losing the tabs is not.

Open the manager before closing. If chrome.tabs.remove runs first and the manager fails to open, the user is staring at an empty window with no idea where their tabs went. Opening first means the destination exists before the sources disappear.

Never trust t.url to be a string. chrome:// pages, chrome-extension:// pages, and about:blank return empty URLs or URLs that cannot be reopened. Filtering happens once, in isRestorable, and the same predicate runs on every input path — see the next section.

Every list of tabs in this extension comes from a different place: the live browser, an imported JSON file, an old storage format, a snapshot created by a service worker. Four writers, four chances to store null, a duplicate, or a chrome://newtab.

So collapsing the same window twice adds nothing instead of doubling the list.

Yandex Browser is Chromium, and MV3 extensions load in it unchanged. But it has a feature Chrome does not: tab groups as separate "spaces", and each tab object carries a numeric spaceId.

This field is not in Chrome's extension API documentation. chrome.tabs.query in Chrome returns undefined; in Yandex it returns the space number. If you ignore it, two things break: collapsing pulls tabs out of other spaces the user did not touch, and restoring drops every tab into whichever space happens to be active.

If it is null, the extension behaves exactly like it does in Chrome — whole window, no grouping. Restoring inverts the logic: group the saved entries by spaceId, then for each group find any live tab in that space, activate it (which switches the window to that space), and create the tabs after a short pause:

The 350 ms pause is not superstition. Without it, chrome.tabs.create lands in the space that was active before the switch completed, and the user gets a pile of tabs in the wrong place.

The daily backup runs from chrome.alarms, which means the writer is the service worker. Three things bit me.

No imports. With no bundler, background.js cannot import storage.js. The service worker therefore contains a second copy of createSnapshot. That is real duplication, and it has already drifted once (the worker version does not update the stats key). If I were starting over I would either add a five-line build step or put the storage module in a separate file loaded via importScripts.

Alarms have a minimum. periodInMinutes: 1440 is fine, but the first run has to be delayInMinutes, and the alarm must be recreated on both onInstalled and onStartup. Chrome clears alarms when the worker is discarded; it does not clear them across browser restarts, but users do uninstall/reinstall.

lastError is not optional. Creating a context menu item with an existing id throws, and because the callback is async the error surfaces as "Unchecked runtime.lastError" in the console — harmless until a reviewer sees it:

chrome.storage.local is 5 MB by default (10 MB on current Chrome), and a tab entry is roughly 200 bytes. That is twenty thousand tabs — until someone saves a snapshot of a window with 400 tabs, five times. Then set rejects.

That last row is the honest part. The engineering is the easy half. A tab manager competes with a dozen free clones and with Chrome's own vertical tabs, so discoverability is a different problem entirely — and it is not solved by a smaller bundle. What did move the needle was localization: 53 locales cost about 4 KB of icons' worth of download and they roughly doubled installs per release in non-English markets.

The extension is Tabs in One on the Chrome Web Store — free, no account, no telemetry. The source for the parts quoted here is in the package if you want to diff it against your own implementation.
