One model gateway across clouds: LiteLLM on Cloud Run and Azure with zero API keys

Tanggal: 2026-11-15

As of November 2026. All identifiers in this post are examples.

We built a proof of concept with two AI agents: one on Google Cloud, in Agent Runtime, and one on Azure, in Microsoft Foundry. Each agent has its own identity in Microsoft Entra Agent ID and stores no secret.

Agents call models. This post covers how ours reach them: a model gateway that runs in both clouds, serves Gemini and Azure OpenAI from either side, and holds no API key for any of it.

During a demo we switched off the gateway in one cloud. The agent's next answer came through the other one, and we barely noticed the switch.

An agent can call a model directly. With two agents that is fine. With fifty it gets uncomfortable:

A model gateway fixes the three at once. Agents talk to one endpoint, and the rules and the usage records live there. We used LiteLLM because it speaks to both Vertex AI and Azure OpenAI behind one OpenAI-compatible API.

The catch is that a gateway usually introduces two new kinds of secret: the keys it holds for the model providers, and the keys it hands out to its callers. We wanted neither.

Each gateway is connected to both model families. The one on Azure can call Gemini, and the one on Google Cloud can call Azure OpenAI. An agent uses the gateway of its own cloud and gets the same catalogue either way.

LiteLLM normally gives each caller a virtual key. That is one more secret per agent, which is exactly what we wanted to avoid.

Each agent already has an identity in Microsoft Entra Agent ID and can get a token for any audience it has a role on. So the gateway is one more audience, a2a-llm-gateway, with one role, LLM.Invoke. The agent sends its own Entra token as the bearer.

The allow-list comes from the inventory file we use to onboard agents:

The onboarding pipeline assigns the LLM.Invoke role in Entra and creates the team in LiteLLM with those models. An agent that asks for a model outside its list is refused before any provider is called.

This is the part that makes the design hold together. Every link from the gateway outwards uses the identity of the workload.

From Google Cloud to Gemini. The Cloud Run service account has the Vertex AI role. Nothing to configure.

From Google Cloud to Azure OpenAI. LiteLLM asks Google for an OIDC token and presents it to Entra, where a federated credential on an app registration accepts it. In the model entry it is one line:

From Azure to Azure OpenAI. The Container App's managed identity.

From Azure to Gemini. This is the reverse federation. The managed identity's token is exchanged at a Google workload identity pool, which lets it act as the same service account the Cloud Run side uses. Google's client libraries do the exchange when they find this credential file:

A small sidecar keeps the Azure token in that file fresh. The pool accepts only that one managed identity as a subject.

To the database. Both gateways reach Cloud SQL through the Cloud SQL Auth Proxy, as a sidecar, with IAM database authentication:

The database user is the service account. There is no password in the connection string.

Once every agent in a cloud depends on that cloud's gateway, the gateway is a single point of failure for all of them. So one thing has to be guaranteed: an agent keeps getting answers when the gateway of its own cloud is unavailable.

There is also a rule worth stating: a refusal is not an outage. A 401, a 403 or a 429 means the gateway is working and said no. Moving to the other cloud must never be a way around that answer.

In our test, with the Azure gateway switched off, the Azure agent's next answer came through the Google Cloud gateway. Nobody touched anything, and the switch was barely noticeable.

Between an agent and a model there is no API key to rotate.
