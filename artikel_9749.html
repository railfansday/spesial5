ODF vs. Managed Block Storage on IBM Cloud: How I Model the Tradeoff for Stateful Workloads

The old myth that "containers are only for stateless workloads" died years ago. Today, production Kubernetes environments routinely host mission-critical stateful workloads, from transactional databases and Kafka clusters to AI/ML feature stores and virtual machines.

When teams move stateful applications into production on Red Hat OpenShift on IBM Cloud, they quickly encounter a fundamental storage architecture decision: Should they use cloud-managed block volumes, or deploy in-cluster software-defined storage with OpenShift Data Foundation (ODF)?

Treating storage like an afterthought works fine until a database pod restarts on a new node and sits in CrashLoopBackOff while you explain to leadership what an attach-detach timeout is. As the product manager working on container storage at IBM Cloud, I walk engineering teams through this choice every week. Both storage architectures are mature, production-proven options, but they optimize for fundamentally different operational priorities.

To make the right choice, you first have to understand where the storage intelligence lives in each model.

IBM Cloud Block Storage operates outside your Kubernetes compute nodes. When a stateful pod requests a PersistentVolumeClaim (PVC), the IBM Cloud Container Storage Interface (CSI) driver calls the VPC storage API to provision a dedicated, NVMe-backed volume on the cloud storage fabric and attaches it directly to the host hypervisor.

OpenShift Data Foundation (ODF) takes the opposite approach. Powered by open-source Ceph, Rook, and NooBaa, ODF aggregates the physical NVMe drives attached to your bare-metal worker nodes into a single, unified, software-defined storage pool managed by Kubernetes operators.

The most immediate technical differentiator between these two storage models comes down to access modes and application architecture.

For standard database engines running in high availability (such as a PostgreSQL or MySQL StatefulSet with a primary and read-replicas), each replica manages its own dedicated storage volume. Replica synchronization happens at the application database layer rather than the storage layer.

For these workloads, IBM Cloud Block Storage using the ibmc-vpc-block-10iops-tier or dynamic Storage Defined Performance (SDP) profile is exceptional. You get guaranteed IOPS, volume snapshots, and online capacity expansion without running storage daemons on your nodes.

Traditional cloud-managed block volumes are exposed as single-attached ReadWriteOnce (RWO) storage through Kubernetes, making them unsuitable for workloads that require simultaneous multi-node access. If your workload requires concurrent writes from multiple pods (such as shared data ingestion pipelines, machine learning training sets, or CMS asset pools), ODF provides native POSIX-compliant CephFS with ReadWriteMany (RWX) access across all nodes.

Even more critical is Red Hat OpenShift Virtualization. When running virtual machines on OpenShift alongside containers, migrating running VMs across physical hosts without downtime (the cloud-native equivalent of VMware vMotion) requires shared-access storage.

Standard cloud block storage cannot support live migration because the hypervisor on the destination node cannot attach a volume that is still locked to the source node. OpenShift Virtualization addresses this by consuming Ceph RBD in raw block mode (volumeMode: Block) rather than as a mounted filesystem. ODF provides validated storage classes like ocs-storagecluster-ceph-rbd-virtualization with shared access patterns. Destination nodes mount the disk image before migration begins, transferring memory states with zero guest downtime.

Engineering is always a study in tradeoffs. ODF is powerful, but deploying it blindly for every workload is a major architectural mistake.

ODF requires bare-metal worker nodes with local NVMe drives. The absolute architectural minimum is 3 worker nodes, with 6 nodes recommended for production clusters so you can drain a node for maintenance without degrading replication.

If you are running a small cluster with 3 Virtual Server Instances (VSIs) hosting a few microservices and a lightweight cache, spinning up 3 or 6 bare-metal nodes just to run Ceph makes zero financial sense. Managed VPC Block allows you to run small, flexible VSI instances and attach 20 GB or 100 GB volumes on demand.

Because ODF uses a default replica factor of 3 for high availability, 30 TB of raw NVMe storage yields roughly 10 TB of usable application capacity. Additionally, Ceph OSDs, Monitors, and Metadata Servers run as pods inside your cluster, consuming worker node memory and CPU cycles.

In Ceph, you must actively govern capacity. When an ODF cluster reaches ~80% capacity (nearfull), Ceph begins throttling write operations to prevent disk starvation. At ~85% capacity (full), Ceph blocks new writes entirely to protect cluster consistency. (Ceph is fantastic, but when it hits 85% full and starts refusing writes to protect data integrity, it will definitely get your team's undivided attention.)

With managed VPC Block, each volume is completely isolated. If volume A fills up, volume B is unaffected, and you can resize any attached volume online with a single pvc spec update.

ODF embeds a full distributed storage system inside your cluster. Even though IBM Cloud automates deployment and day-2 operator lifecycle management on ROKS, platform teams must still understand cluster storage health, data rebalancing behavior during node maintenance, and proactive capacity planning.

On generic cloud setups or DIY Kubernetes, operating Ceph is notoriously complex. Cluster operators often spend days configuring CRUSH maps, tuning OSD placement, and managing daemon recovery during node upgrades.

This is where the platform architecture matters. On competing hyperscaler Kubernetes platforms (such as AKS, EKS, or GKE), ODF is not generally available as a native managed platform add-on. On ROSA and ARO, customers must manually install and maintain ODF operators.

On Red Hat OpenShift on IBM Cloud (ROKS), ODF is delivered as a fully managed IBM Cloud add-on. IBM SREs handle operator deployment, daemon lifecycle, health monitoring, and version patching, allowing platform teams to consume Ceph storage classes directly via standard Kubernetes manifests without operating the underlying storage infrastructure.

Choose IBM Cloud Block Storage when you want lightweight, pay-as-you-go, isolated block volumes for databases running on flexible virtual server instances with zero storage daemon overhead.

Choose OpenShift Data Foundation when you run bare-metal OpenShift clusters that demand high-throughput local NVMe performance, multi-modal storage consolidation (block + file + object), or live migration for OpenShift Virtualization VMs.
