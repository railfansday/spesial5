The simplest way to explain it I think would be to say that Tailscale makes all your devices act like they’re on the same home network, no matter where they actually are.

Their site from 2020 is a bit clearer: https://web.archive.org/web/20201129111934/https://tailscale.com/

But basically it lets your various devices connect to each other, whereever they are, without having to deal with port forwarding, firewalls, dynamic DNS... so your phone or laptop can access self-hosted services on your Raspberry Pi (photos, Jellyfin, RSS, files, ...). It does this while keeping it all hidden from random people/attackers.

I don't use Tailscale, and instead just use plain Wireguard/mTLS, but Tailscale is easiest to set up and seems to be the most popular option for people that want to access their Raspberry Pi when away from home.

I avoid exposing my services to the public internet since I am the only user. They are available only via WireGuard. I use plan WireGuard, but solutions like Tailscale or NetBird are fine if you need something else to deal with configuration for you.

On top of that, I still do HTTPs everywhere (using the ACME DNS-01 challenge so I get proper certificates from Let's Encrypt without exposing anything on the public Internet).

Authentication is mostly based on passkeys (I use PocketID for single-sing-on) and I only use SSH keys (backed by secure enclaves whenever possible).

I run my services in NixOS. For my threat model it's okay to run everything on the same machine but to get more workload segregation you could separate the various services across several VMs/micro-VMs.

How much you need to care about security is entirely dependent on what you host. I would for example greatly invested in security if I self-hosted a public facing file storage or an email server.

I would in general care much less if as you describe I would be hosting a static website on a Raspberry Pi. The risk just isn't that big. It can't cost you a lot of money since it's your own hardware. The worst thing that could happen is that a stranger gains complete control over your Raspberry Pi. They could possibly probe your local network (but not if you put the Rasberry Pi on a subnet), display other information on your website or put your Rasberry Pi to work on something benefitting them (as part of a botnet or crypto mining for example).

I personally wouldn't consider any of those possibilities as great risks. And as a bonus, setting up logging to detect if any of these were happening could be a fun side project.

I assume your internet connection has enough bandwidth to sustain a small to moderate website. Self-hosting a publicly facing service is an order of magnitude more dangerous than self-hosting private services such as photo management applications or media servers because of the security implications. On the bright side, static pages can be hosted securely with relatively low effort compared to LAMP stack.

(a) Applying network segmentation is a good start. The RPi should not be able to communicate with other devices through router / firewall configuration. Maybe allow just one device based on IP or MAC address to access the RPi from the LAN.

(b) Then setup DNS records. I assume you own an FQDN. Use an ready-made or custom script to update the DNS records. I'm using dnscontrol alongside envsubst and to perform the changes but there are simpler solutions out there.

(c) Once the DNS is working and updating properly, use an application to issue SSL certificates. My favourite is acme.sh but there are quite a few polished alternatives, e.g. certbot, lego, etc.

(d) Now you're ready to setup a reverse proxy. Note that modern rev-proxies like Caddy can manage (c) on their own. I'm not using them, I'm familiar with nginx so I use that.

(e) Create a deployment user with minimum permissions and use that user to upload data via sftp or other secure protocol. If you want to setup a deployment pipeline via git, that's also possible through webhooks.

(f) Secure the system. I'm pretty sure that you can flat-out ban the big cloud CIDRs. That will save you from dumb scanners abusing your website. Since very few humans use these addresses for outgoing connections, I think it's a good strategy to block them straight-up. You can setup a cron script to download CIDRs and update your firewall "block" tables.

f.1 Make sure you setup some sort of monitoring, so that you can quickly measure things like resources and even incoming requests (e.g. response latency, No of incoming requests, etc). Since you're going to self-host you'll have log access which means full visitors info.

f.2 You might want to explore the possibility of setting a "chroot"

f.3 Alerting: pushover is a good "host -> mobile" alternative, another is to setup the SMTPd in a way that the system can send you emails with status reports, etc. to your personal email.

(g) Backup everything locally (e.g. another NAS) or remotely (backblaze is fairly cheap), or both.
