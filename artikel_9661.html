GitHub Actions Importer: what it converts and what it leaves for you

Tanggal: 2026-11-15

Posted on Nov 15 • Originally published at latchkey.dev

GitHub Actions Importer is a GitHub CLI extension, gh actions-importer, that runs in Docker and converts pipelines from Azure DevOps, Bamboo, Bitbucket Pipelines, CircleCI, GitLab, Jenkins and Travis CI into GitHub Actions workflows. Its audit, forecast, dry-run and migrate commands inventory a CI server, estimate Actions usage, convert one pipeline to local files and open a pull request, while secrets, runners and unknown plugins or orbs remain manual.

The five subcommands in the order to run them, with what each reads and writes. Only migrate opens a pull request.

You have more pipelines than you want to convert by hand, and you want to know which ones will convert cleanly before you promise a date. That is the job the Importer does best: it reads the CI server, converts every pipeline it can, and writes a report that sorts them by how much is left to do.

It is not a finished migration. GitHub's documentation sets the goal at 80% conversion per workflow and says every converted workflow should be inspected before it runs production work. This page covers each command, the files they write, the per-platform manual work, and the mapping details that change behavior.

The Importer is a container image plus a gh extension that drives it, so it needs Docker running and the GitHub CLI installed. It does not have to run on the CI server; it talks to it over the API.

configure prompts for a GitHub personal access token (classic) with the repo and workflow scopes, which migrate uses to open pull requests, plus the URL and token for your CI system, and writes them to .env.local. update pulls the latest image. The extension itself last tagged a release, v1.3.6, in October 2023; the converter ships in the image, so run update before each session.

All seven platforms support all four planning and conversion commands. What differs is the subcommand and the flag that identifies one pipeline for dry-run and migrate.

From each platform's "Migrating from ... with GitHub Actions Importer" page on docs.github.com, read 2026-11-12. For GitLab and CircleCI, audit needs an organization account; dry-run and migrate also work with a user account.

audit fetches every project on the server, converts each one and writes audit_summary.md beside the converted files. Pipelines land in four buckets: successful (everything converted), partially successful (the structure converted, some items did not), unsupported, and failed, which usually means the original was invalid or the token could not read it. Build steps are counted as known, unknown or unsupported, and a Manual tasks section lists the secrets and self-hosted runner labels you have to create. workflow_usage.csv lists the actions, secrets and runners each pipeline uses, which is the list a security review wants.

forecast reads completed runs, the previous seven days by default, and reports job count, execution time, queue time and concurrent jobs. Execution time is your minutes estimate and concurrent jobs is your runner count. On Jenkins it needs the paginated-builds plugin installed first.

Each platform guide on docs.github.com publishes a supported-syntax table and a list of constructs you must migrate manually. The manual lists are short and worth reading before the audit, because they predict most of the Manual steps section in every pull request.

dry-run converts one pipeline and writes the workflow to disk. This is where you shape the output before anything reaches a repository. Custom transformers are Ruby files passed with --custom-transformers: runner maps a source label to an Actions label, env rewrites or removes a variable or points it at a secret, and transform replaces an unknown build step, such as a Jenkins shared library call, with steps you define.

Map runners first. The documentation states that a label the Importer cannot map becomes ubuntu-latest, and runner :default changes that fallback.

migrate runs the same conversion and opens a pull request against --target-url. Its description carries a Manual steps section, usually the secrets to create. Merge only after the first run on a branch is green.

Read the environment variable mappings before you trust a converted condition. The Importer maps Jenkins BUILD_NUMBER to github.run_id, a large unique id, not the per-workflow counter github.run_number, so image tags change shape. It maps GitLab CI_COMMIT_BRANCH and CircleCI CIRCLE_BRANCH to github.ref, which is refs/heads/main, so a comparison against main silently goes false. GitHub's sample list-features output also shows actions/cache and reusable-workflows disabled; check yours and turn them on with --enable-features if your target supports them.
