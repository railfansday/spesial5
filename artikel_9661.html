Ask a general purpose AI assistant for a YARA-L brute force rule. You will get something that looks correct. Paste it into the Google SecOps Rules Editor. It fails on line five, because LOGIN is not a valid UDM event type. The correct value is USER_LOGIN.

Fix that. The next error is a port compared to the string "443". Fix that. The compiler complains that an outcome variable uses an event field without an aggregate.

The worst case is the rule that compiles cleanly and never fires. Your Okta parser writes FAIL for a failed login. The rule checks for BLOCK. Nothing errors. Nothing alerts. You find out during an incident review.

I write detection content for a living. I got tired of fixing the same five mistakes in every AI generated rule. So I built yara-l-skill, an open source Agent Skill that teaches coding agents to write, review, tune and convert YARA-L 2.0 rules

An Agent Skill is a folder with a file of instructions, plus any reference docs and scripts the agent needs. The agent loads it when the task matches the skills description. You install it once. Every YARA-L request picks it up automatically.

The same folder works in Claude Code, Claude.ai, GitHub Copilot, OpenAI Codex, Gemini CLI, Cursor and any other client that reads the SKILL.md format.

The skill also tells the agent to state which source constructs have no clean YARA-L equivalent. Silently dropping a filter during conversion is how you end up with a noisy rule nobody trusts.

The skill ships lint_rule.py, a Python 3 script with no dependencies. The agent runs it on every rule before it answers, and you can run it yourself in CI.

It checks section order, event type values against the UDM enum, integer fields compared to strings, event variables that never join to a match placeholder, unaggregated outcome fields, absence conditions without match, leading .* in regex, and missing meta keys.

A clean lint result does not mean the rule compiles. The linter catches the common mistakes before you paste. The SecOps compiler is still the final word.

Parser fixtures: the gap the linter cannot close

Valid syntax and a rule that fires are two separate problems. The linter solves the first one. Fixtures address the second.

A fixture is a JSON file with three things: a sanitized raw log, the UDM event a specific parser produced from it, and the rule that should or should not fire on it. They live in folders by log type:

The checker also rejects fixtures that contain public IPs, real email domains, or real GUIDs, so nobody leaks tenant data in a pull request. When the agent writes a rule for a log source that has fixtures, it reads them first to learn which fields that parser actually fills.
