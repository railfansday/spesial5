Writing a DSL for high performance parallel programming in OxCaml

Tanggal: 2026-11-14

Using ASCII waveforms to test hardware designs

The following is part of a series of posts about 2026 summer intern projects—for more, see “What the interns have wrought, special jumbo 2026 edition”

We have a lot of performance-critical SIMD code (single-instruction, multiple-data) running on CPUs across the firm. These are highly parallel programs where you run the same computation across arrays of data, in our case for options pricing or for low-latency risk checks. Because OCaml hasn’t historically exposed SIMD instructions, these programs often involve an inner loop written in fairly esoteric C. Writing these loops requires implementers to think carefully about hardware, and doing performance tuning, such as modifying unroll factors or vector widths, can require major changes to the code. Moreover, these programs are constrained to a specific instruction set. If we were to target a different architecture or a newer processor, we’d have to rewrite the program.

For his summer internship, Sai Konkimalla built a compiler for a domain specific language (DSL) that makes SIMD more ergonomic and widely accessible. The compiler takes advantage of OxCaml features that were only very recently added to the language, such as runtime metaprogramming, to enable users to write a kernel just once as a regular-ish OxCaml function, then compile and run it on multiple architectures.

To help solve the problem of SIMD code being rather difficult to write and maintain, our DSL uses the SPMD, or “single program, multiple data” programming model. As opposed to SIMD intrinsics, SPMD is higher level and not tied to a specific instruction set. We might normally think of higher-level languages as slower, but with SPMD, a higher level of abstraction lets the compiler make better decisions about how to optimally use the underlying hardware. This ability can lead to significantly faster code.

Like CUDA, we don’t write the kernel as a loop. Instead, the developer writes a function that computes a single entry of the output slice, and the SPMD compiler generates code to loop over the output slice and compute the value at each index.

You may wonder why we loop over the output and not the inputs. Looping over the output is easier to model because each iteration writes to exactly one location, so iterations can be easily vectorized, reordered, or parallelized. If we were to loop over the inputs, different iterations could write to the same output entry. The compiler would then have to reason about whether the writes could be re-ordered. By guaranteeing that each output entry is written exactly once, we can avoid this complexity.

One wrinkle with Sai’s project is that we wanted to execute the SPMD compiler at runtime. Runtime compilation (often called just-in-time or JIT compilation) is when the compiler generates code while the program is running. This gives us two main advantages: we don’t have to worry about building for all potential target architectures at compile time, and we can use data obtained at runtime for optimizations.

That latter point is especially important for generating high-performance code. When executing at runtime, the compiler has more data that it can use to optimize the code than it would when executing ahead-of-time. For example, our compiler can use runtime data to compile away branch instructions, which can slow down execution by consuming CPU resources.

To implement our JIT compiler, we used runtime metaprogramming, a feature that lets us generate, compile, and evaluate OxCaml code at runtime by using the OxCaml compiler as a library. As far as we know, Sai’s project was the first real program at Jane Street to use it. (He discovered some bugs in its implementation and helped report/reproduce them for the OxCaml team.)

The plain if_ can’t do that, because the condition is a bool# uniform and therefore it must be the same value for all lanes.

select and if_var are similar in that they both take in a condition of type bool# varying. Where the two constructs differ is in how the branches are evaluated. With if_var, the compiler can decide whether to execute the branch that is not chosen by the condition, whereas with select, both branches are always evaluated. Further, if if_var executes an untaken branch, any potential side effects, such as raising exceptions, will not be observable. So select true 1 (1/0) will raise an exception, but {if,if_var} true 1 (1/0) will not.

Usually, a high-performance JIT compiler would target a low-level language such as assembly or LLVM IR, which necessitates thinking quite hard about complicated details such as registers, pointers, and so on. Luckily, we didn’t have to do this, since we could use metaprogramming to emit OxCaml code. This also lets us rely on optimizations in the OxCaml compiler, saving us from having to implement them ourselves.

OxCaml’s metaprogramming features let us explicitly generate OxCaml code at runtime using quotes and splices. A quotation represents an OxCaml expression that is created at runtime and will be evaluated at a later time. For example, <[if Random.bool () then 42 else 5]> represents an unevaluated expression of type int, so the quotation itself has type <[int]> expr. Once this expression is evaluated, its result will be an int.

At this point, Sai needed to validate that his JIT implementation was both fast and correct. One strategy he used was to compare the JIT against a reference implementation. We had previously implemented an interpreter that took the front-end representation and directly executed it. While extremely slow, we could be fairly confident that the interpreter would have the correct behavior, so could be used to verify that the JIT was also correct.

Sai wrote four example programs, including an implementation of Newton’s square root algorithm and a kernel adapted from some production code, in plain OxCaml, C with AVX2 intrinsics, C with AVX512 intrinsics, and as an SPMD kernel (which could be either executed by the interpreter or JIT compiled). Each combination was benchmarked on inputs of various sizes.

Sai also worked on an extensive test suite for all of the different language features and edge-cases. This suite included a test that generated random inputs with Quickcheck generators, then ran those inputs on the four example programs. Their outputs were cross-checked and compared bit by bit. He also wrote tests confirming that the code didn’t allocate on the heap.

The benchmarks found that the JIT was much faster than the interpreter. However, the JIT was about the same speed (or slightly slower) than the manual OxCaml code and significantly slower than the C implementations. This wasn’t that surprising, since we hadn’t implemented any real optimizations or tuning in the compiler. Naturally, this needed to change if we wanted to catch up to the C implementations.

Sai then started looking at adding optimizations to the compiler. With the current compilation pipeline, this would have been slightly painful. Our front end representation was not designed to be easily analyzed or optimized. While that wouldn’t have necessarily stopped us from doing analysis, it’s often a better idea to add an intermediate representation (IR) that is more amenable to optimization. Sai implemented an IR based on A-normal form (ANF), a format where each intermediate value gets its own variable. Sai designed this IR with a key design principle in mind: Generating the final OxCaml code from the IR should be a trivial process. Any interesting compilation logic should end up explicitly represented in the IR.

Like with the previous backend implementation, Sai put in a lot of work to validate the correctness of the new compilation path. He added the new backend to the existing cross-validation logic across the test suite, then added expect tests that printed the IR and the emitted OxCaml for various examples, which helped us confirm that the behavior was exactly as expected.

Once we were confident that the new IR-based path was correct, Sai deleted the previous backend.

With the current implementation, the IR backend generates essentially the same code as the first JIT, so the two perform about the same.

However, optimizations are now significantly easier to add. We’re currently working on adding vectorization and constant hoisting to the compiler. Preliminary benchmarks have found that these changes result in code that is on-par with our C AVX2 implementation.

We’re also working on adding scheduling. Scheduling lets users customize how the kernel loops over the code with a sophisticated set of transformations like “split this loop into 8 piece chunks, vectorize these chunks, then unroll by 4”. Intelligent scheduling is important for getting the maximum possible performance out of the kernel. Eventually these schedules could also be auto-generated and benchmarked, so that the compiler can find the optimal one for your kernel.
