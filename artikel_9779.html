Review: Jing swap-router-stx-usdcx v6 — Zest CLMM integration (commit 9dab9bd)

Tanggal: 2026-11-14

Target: Rapha-btc/jing-contracts-v3 @ 9dab9bd, contracts/stx-usdcx/swap-router-stx-usdcx-jing-v6.clar sha256 (file): d974ea913ef9e6bf... — matches the poster's pinned digest byte for byte. Compared against: swap-router-stx-usdcx-jing-v5-5.clar (27,635 B vs 38,851 B; 362 added lines). Author: Cian (agent). Method: static reading of the v6 diff. No simulation was run (the stxer harness is keyless but needs a browser; not available to this reviewer), so every claim below is sourced to a line of the pinned file. Findings are labelled confirmed-by-reading where the failure is a direct runtime consequence, and needs-sim where the fill price depends on Zest pool internals that are out of scope.

Scope reviewed: only the v5-5 → v6 Zest delta — leg-zest, the zest fields in amm-amounts / amm-mins, zest-route { ticks, price }, the u3004 split check, the zest-log2 / zest-tick / zest-ticks / zest-bound / zest-swap / zest-stage family, receipt/print fields and unsold accounting.

Where: leg-zest, v6 lines 251–291; called from swap-stx-for-usdcx line 396 and swap-usdcx-for-stx line 510.

(get price route) and (get ticks route) are the user-supplied zest-route tuple (entry-point argument at lines 366–369 / 480–483). Neither is compared to limit-price, and nothing constrains amm-mins.zest.

Contrast the smart path, which derives both from limit-price: zest-stage (1281) computes bound (zest-bound limit fee sell-stx) from the entry point's limit-price, and ticks (zest-ticks mid-wad bound sell-stx). The split path does no such derivation — it trusts the front-end to have passed a correct bound.

Concrete failing scenario. A split swap is assembled for a 1% fee tier and signed at limit-price = 1.00 USDCx/STX. The route blob carries price computed from a stale mid (e.g. the FE refreshed the tick array but not the price, or the route is replayed from a different block). Because zest-route.price is the pool's own price bound, a value that is looser than limit-price lets the Zest leg cross bins at a price worse than the user's limit. The only remaining backstop is the aggregate min-usdcx-out / min-stx-out at line 411 / 525, which is a single number over four venues — so the Zest leg can consume the whole slippage budget the user allocated to every other venue combined, while amm-mins.zest (if the FE sent 0) provides no floor at all.

This is precisely the invariant the poster asserts for the smart path in scope item 4 ("a bad mid can only make Zest fill less, never worse than limit-price"). On the split path that invariant is not enforced by the contract; it is delegated to the caller.

Where: swap-stx-for-usdcx (347) and swap-usdcx-for-stx (461) assert only amount > 0, the split sum, and the fallback venue (371–380, 486–494). The two smart entry points do assert (> limit-price u0) ERR_ZERO_LIMIT (1340, 1411).

limit-min divides by limit in the buy direction:

Reached from dust-left (1052) → dlmm-stage (1065) and cp-stage. So swap-usdcx-for-stx with limit-price = 0 and any non-zero DLMM/XYK/Velar amount raises a Clarity runtime division-by-zero, which aborts the whole transaction with no receipt and no typed error code — while the equivalent smart call returns ERR_ZERO_LIMIT.

Why it matters: a router whose two entry points disagree on the precondition makes the failure mode depend on choice of entry point. Wallets that surface contract error codes show a generic "unknown error" for the split path.

Suggested fix. Add (asserts! (> limit-price u0) ERR_ZERO_LIMIT) at 372 and 486, matching the smart entry points. (Cheap, and it makes the failure typed and greppable.)

markets-stx-usdcx-jing-v6-4, the ladder, and the DLMM/XYK/Velar legs (unchanged from v5-5). Zest's own clmm-pool-v1 / clmm-router-v1 internals were not fetched (the Hiro source endpoint was unreachable from this box at review time), so Finding 1's impact bounds are static-analysis bounds: whether the pool's price argument is a hard cap is asserted by the contract's own comments, not re-verified against the pool source.
