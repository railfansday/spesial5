WordPress Heartbeat API: The Hidden Requests That Can Slow Down Your Website

Tanggal: 2026-11-21

When troubleshooting a slow WordPress website, most developers start by checking plugins, themes, caching, and database queries.

But have you ever considered that WordPress itself might be generating repeated background requests?

That's exactly what I discovered while investigating a client's website.

In my previous article{:target="_blank"}, I shared how a client's WordPress website had numerous plugins installed and was experiencing performance problems.

During my investigation, I contacted the hosting provider's support team and asked them to examine the server logs.

They reported a massive number of requests associated with something called the WordPress Heartbeat API.

At the time, I wasn't familiar with Heartbeat or how it worked.

What I discovered was an important WordPress feature that many developers use indirectly without realizing it.

In this article, I'll explain what the WordPress Heartbeat API is, how it works, when it can affect performance, and how to investigate and control it safely.

The WordPress Heartbeat API is a built-in feature introduced in WordPress 3.6.

It allows communication between the user's browser and the WordPress server at regular intervals without requiring a full page reload.

Heartbeat uses a configurable interval that varies depending on the WordPress context and activity.

A commonly used default interval is around 15 seconds, although actual behavior can differ between screens and configurations.

Heartbeat can also slow its polling when browser activity changes.

This means it isn't necessarily sending requests at a fixed rate under every condition.

A single Heartbeat request usually isn't a problem.

The concern arises when many requests are generated or when processing them becomes expensive.

Each request may require PHP processing and could trigger additional plugin callbacks.

On a server with limited resources, excessive or expensive requests can contribute to performance problems.

An administrator might have several WordPress dashboard tabs open.

If Heartbeat is active in multiple tabs, each may generate periodic requests.

Some plugins extend Heartbeat with their own functionality.

Poorly optimized callbacks can increase the amount of processing performed during a Heartbeat request.

On hosting environments with constrained CPU or PHP worker capacity, background requests can compete with other requests for resources.

However, Heartbeat requests alone don't prove the cause of a performance issue.

You don't necessarily need a performance plugin to inspect Heartbeat activity.

Your browser's developer tools are a useful starting point.

Log in to your WordPress dashboard and open a page where Heartbeat is active, such as the post editor.

Leave the page open long enough to observe whether requests repeat.

If you see that action, you've identified a Heartbeat request.

You can also inspect the request's timing and response.

Remember that the total request duration isn't the same as PHP execution time, and a slow request doesn't necessarily mean Heartbeat itself is inefficient.

Browser DevTools show requests from your own browser session.

Server logs can help reveal request patterns across the website.

Once you've confirmed that Heartbeat activity deserves investigation, you can consider adjusting its behavior.

However, I wouldn't recommend disabling it globally as a first step.

Heartbeat supports useful functionality, and changing it can affect the editing experience.

After changing Heartbeat settings, return to the browser's Network tab.

Check whether the frequency of Heartbeat requests has changed as expected.

Then test important WordPress functionality.

Ideally, compare measurements before and after the change under similar conditions.

If you have access to server monitoring, look at PHP worker utilization, CPU activity, and request volume.

A reduction in Heartbeat requests doesn't automatically prove that the website became faster.

The objective is to determine whether the change improved the original problem without introducing new issues.

When the hosting provider first mentioned WordPress Heartbeat, I didn't know much about it.

I had worked with WordPress for years, but this particular feature wasn't something I had previously needed to investigate in detail.

The experience reminded me of three important lessons.

Looking at the website's frontend doesn't always reveal what is happening on the server.

Logs and resource metrics can provide valuable evidence.

Plugins can be useful, but adding one without understanding the problem can make the setup more complicated.

Sometimes WordPress already provides the hooks and tools needed to investigate or adjust a feature.

What matters is the ability to investigate unfamiliar behavior, understand the underlying system, and evaluate possible solutions.

In my case, a real client problem motivated me to learn about a WordPress feature I hadn't previously explored.

And that knowledge became useful beyond the original project.

One final point worth mentioning is that Heartbeat and WP-Cron are different mechanisms.

Both are worth understanding when troubleshooting WordPress performance, but they should not be confused.

In my next article, I'll explore WP-Cron in more detail, including how it works, why scheduled tasks sometimes fail or run late, and when using a real server cron job can be useful.

The WordPress Heartbeat API is not a bug or an unnecessary feature.

It provides useful functionality that helps WordPress deliver a better editing and administration experience.

However, like any server-side activity, it can contribute to performance problems under certain conditions.

The key is understanding how it works, measuring its impact, and making changes only when the evidence supports them.

My experience with a client's website taught me that troubleshooting isn't always about finding a new tool.

Sometimes it's about discovering a feature you didn't know existed.

Before disabling Heartbeat or installing another optimization plugin, investigate the requests and understand what's actually happening.
