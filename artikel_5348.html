10 AI cybersecurity terms explained, from breakout time to deepfakes

Tanggal: 2026-11-18

10 AI cybersecurity terms, from breakout time and agentic AI to deepfakes and prompt injection, defined in plain language with how each attack or risk works

Artificial intelligence sits on both sides of the security problem. Attackers use it as a tool to write convincing messages and imitate real voices. Defenders also have to protect it as a target. A model that reads email, writes code or answers customers can be manipulated like any other system.

That double role has produced a working vocabulary that matters well beyond security teams. A finance employee asked to approve a payment on a video call needs it. So does a manager deciding whether staff can use a chatbot, and a board reviewing an incident report. Without shared definitions, a warning about prompt injection or shadow AI can sound like jargon. In practice, each term points to a specific risk and a specific response.

Some of these AI cybersecurity terms are new. Agentic AI, prompt injection and data poisoning describe problems that arise from how machine learning models are built, trained and connected to other software. Others come from older security ideas. Breakout time measures how quickly an intruder spreads from one compromised machine to the rest of a network. CrowdStrike $CRWD popularized that metric in its annual threat reports. Red teaming comes from traditional security testing, and shadow AI echoes the older term shadow IT.

Organizations trying to manage these risks also have a formal reference point. The U.S. National Institute of Standards and Technology published its AI Risk Management Framework 1.0 in January 2023. The framework is voluntary. It offers a shared structure for thinking about AI risk rather than a set of legal requirements.

The 10 terms below are a selection, not a complete glossary. Each slide defines one term in plain language and explains how the attack or practice works. Several of the terms sit close together. Prompt injection, jailbreaking and adversarial examples all involve manipulating what a model receives. Each one exploits a different weakness, though. Prompt injection overrides an application's instructions, and jailbreaking pushes a model past its own safety rules. Adversarial examples use small, deliberate changes to an input to make a model misclassify it. Reading the definitions side by side makes those distinctions easier to keep straight.

Breakout time is the time an attacker needs to move from the first compromised machine to other systems on the same network. It measures how long defenders have to spot and contain an intrusion before it spreads beyond its starting point.

CrowdStrike $CRWD, the U.S. cybersecurity company, popularized the metric in its annual threat reports. The term describes attacker behavior, not a single tool or exploit. It applies whether the first foothold came from a phishing email, a stolen password or an unpatched server.

The step that breakout time tracks is known as lateral movement. After gaining access to one laptop or server, an intruder typically looks for credentials, maps the network and searches for more valuable targets. Those targets often include domain controllers, which manage user accounts across a Windows network. File servers, databases and backup systems are common targets too. MITRE ATT&CK, the public knowledge base of attacker techniques maintained by the nonprofit MITRE, lists lateral movement as a tactic of its own.

Attackers often move sideways with legitimate tools already present on the network. Remote Desktop Protocol, PowerShell and administrator accounts can all serve that purpose. Security teams call this approach "living off the land." It can make malicious activity look like routine IT work. That makes early detection harder.

Breakout time differs from dwell time. Dwell time counts how long an attacker stays inside a network before being discovered. Breakout time covers only the first stretch, from initial access to the jump onto a second system.

The distinction matters for defense. An intrusion caught on a single machine can often be handled by isolating that device and resetting the stolen credentials. Once an attacker reaches many systems, the cleanup becomes a much larger investigation. Ransomware operators, for example, often spread across a network before encrypting files. That lets them lock as many systems as possible at once.

Defenders work against the clock on two fronts: faster detection and slower spread. Endpoint detection and response software watches individual devices for suspicious behavior and can cut a machine off from the network. Network segmentation and multifactor authentication make each sideways step harder. Both measures slow the attacker down.

Agentic AI refers to AI systems that pursue a goal by planning a sequence of steps, using software tools and taking actions with limited human input. That autonomy is the source of both their usefulness and their security risk.

A standard chatbot works in a simple loop. A person types a prompt, the model writes a reply, and the exchange ends there. Any action that follows is taken by the human who read the answer.

An AI agent closes that gap. Given a task such as booking travel, sorting an inbox or fixing a software bug, it breaks the goal into smaller steps. It then decides which tools to call, reads the results and adjusts its plan before moving on. Those tools can include a web browser, an email account, a file system, a calendar, a code repository or a company's internal software.

The security question follows directly from that access. An agent that can send email can send the wrong email. An agent that can edit files can delete or leak them. An agent that can write and run code can introduce changes no one reviewed.

Two broad failure modes concern security teams. The first is hijacking, where an attacker steers the agent toward a goal of their own. That can happen through malicious content the agent encounters while working. The second is misdirection, where no attacker is involved. The agent misreads its instructions or chains together steps that produce a harmful result. In both cases, the damage depends on whatever permissions the agent holds.

Agents act on behalf of a person or an organization. To do that, they typically carry real credentials, such as login sessions, API keys and access tokens. If an agent is compromised, those credentials are exposed along with it.

One defense draws on an older idea: the principle of least privilege. Jerome Saltzer and Michael Schroeder described it in their 1975 paper "The Protection of Information in Computer Systems." It holds that every program and user should have only the access needed to do the job.

Applied to agents, that means narrow permissions scoped to a specific task. An agent that summarizes documents does not need the ability to send email. An agent that drafts code does not need permission to push that code into a live production system.

Other safeguards include requiring human approval before high-impact actions such as payments, deletions or outbound messages. Teams can also log every tool call. That record lets them reconstruct what an agent did and in what order. Keeping an agent's access separate from the wider corporate network limits how far a single error or compromise can spread.

A deepfake is an image, video or audio clip that artificial intelligence has generated or altered. In most cases, the result makes a real person appear to say or do something they never said or did. Deepfakes matter in security because they exploit the trust people place in seeing and hearing someone directly.

The word combines "deep learning," the branch of machine learning built on layered neural networks, with "fake." It entered wide use in late 2017. That year, a Reddit $RDDT user posting under the name "deepfakes" shared videos in which celebrities' faces had been swapped onto other people's bodies.

Several techniques sit under the label. Face swapping replaces one person's face with another's across a video. Lip-sync manipulation alters mouth movements to match new audio. Face reenactment transfers one person's expressions and head movements onto someone else's face. Some images contain no real person at all and show an entirely synthetic face.

Much of the early work relied on generative adversarial networks, or GANs. Ian Goodfellow and colleagues introduced the method in 2014. A GAN pits two neural networks against each other. One generates fake samples, and the other tries to tell them apart from real ones. Each round of that contest pushes the generator toward more convincing output. Newer image and video tools also use diffusion models. These start from random noise and remove it step by step until an image emerges.

For attackers, the main appeal is impersonation. A fabricated video of a senior executive can be used to pressure staff into sharing passwords or granting system access. Deepfakes can also target identity verification. Banks and online services often ask new customers to take a selfie or short video and match it to a photo ID. A synthetic face can be used to try to pass those checks. So can a manipulated video fed directly into the camera stream.

Defenses fall into three broad categories. Detection tools look for visual inconsistencies such as unnatural lighting, blurred edges around the face or mismatched reflections. Each flaw a detector learns to spot is also a flaw that developers of generation tools can work to remove.

Provenance standards take a different approach. The Coalition for Content Provenance and Authenticity is an industry group whose members include Adobe $ADBE and Microsoft $MSFT. It has developed a technical standard that attaches signed metadata to a file. That metadata records where a piece of media came from and how it was edited.

The third defense relies on process rather than technology. Companies can require that any unusual request made over video be confirmed through a separate, known channel before anyone acts on it.

Prompt injection is an attack that hides instructions inside text a large language model reads. The model then follows the attacker's instructions instead of the ones its user or developer intended.

The weakness comes from how these models handle input. A language model receives everything as one stream of text. The developer's setup instructions, the user's request and any outside content all arrive in the same form. The model has no reliable built-in way to tell a trusted command from a sentence that only looks like one.

The name echoes SQL injection, an older attack on databases. In that attack, someone slips database commands into a form field meant for ordinary data. Prompt injection works on the same principle of mixing data with commands. The difference is that a language model reads plain human language. That leaves no fixed syntax for a filter to catch.

The attack comes in two forms. Direct prompt injection happens when a user types the malicious instructions into the chat window. A user might tell a customer service bot to disregard its earlier instructions and reveal its configuration, for example.

Indirect prompt injection is harder to spot. The instructions are buried in content the model processes on someone's behalf, such as a web page, an email or a shared document. A person asks an assistant to summarize a page. Hidden text on that page tells the model to do something else. The user may never see the planted words. They can sit in white text on a white background, in comments or in metadata.

The stakes depend on what the model can reach. A model that only produces text can be pushed into giving false or misleading answers. A model allowed to call other tools could be steered into sending private data to an attacker or taking actions the user never requested.

OWASP, the nonprofit Open Worldwide Application Security Project, lists prompt injection first in its Top 10 for large language model applications. Common defenses include restricting what the model can access, treating its output as untrusted and requiring a person to approve sensitive actions. None of these measures fully removes the risk.

Data poisoning is an attack in which someone corrupts the data used to train or fine-tune an AI model. The finished model then behaves wrongly. The damage is built into the model itself and does not depend on what a user types later.

The attack works because a machine learning model learns its behavior from examples. If an attacker can slip altered or mislabeled examples into that collection, the model absorbs those patterns along with the legitimate ones. The bad records can be hard for engineers to find among a very large number of normal ones.

Poisoning produces two broad kinds of harm. The first is degraded accuracy. In this case the attacker wants the model to become less reliable overall — a spam filter that lets more junk through, or a fraud model that misses more fraud. The second is a hidden backdoor. A backdoored model works normally almost all the time. It switches behavior when it sees a specific trigger chosen by the attacker. That trigger might be a particular phrase, a small pattern in an image or an unusual string of characters.

Backdoors are the harder problem to catch. A backdoored model can perform well on standard accuracy tests. Those tests are unlikely to contain the attacker's trigger. The flaw stays dormant until someone who knows the trigger uses it.

One simple technique is label flipping. The attacker changes the labels on some training examples, for instance by marking malicious files as safe. Other methods leave the labels correct and alter the content in subtle ways instead. That makes the tampering harder to spot during review.

Timing separates data poisoning from attacks on a model that is already running. Poisoning happens before or during training. The attacker shapes what the model learns, rather than tricking a finished model later.

The training data supply chain is where that exposure begins. Many models learn from large datasets scraped from the public web, bought from third-party vendors or drawn from open-source collections. Each of those sources is a point where someone outside the organization could insert content. Fine-tuning carries the same exposure on a smaller scale. A company that adapts a model with customer records, support tickets or user feedback is trusting that data too.

Defenses focus on knowing where data came from and checking it before use. Teams track data provenance and restrict who can modify training sets. They filter for outliers and duplicates, and they test models against known trigger patterns. None of these steps guarantees a clean model. Fixing a poisoned model can require retraining it on verified data.

Jailbreaking is the practice of crafting prompts that get an AI model to ignore its built-in safety rules. The goal is to make a chatbot produce content its developer trained it to refuse, such as instructions for causing harm.

The term comes from an older practice. People jailbroke iPhones and other locked devices to remove manufacturer restrictions and install software the maker had not approved. With AI models, the restrictions being removed are behavioral rather than technical. Nothing in the model's code is changed. The attacker works entirely through the conversation.

Those restrictions come from how a model is built. Developers train large language models to decline certain requests. A common technique is reinforcement learning from human feedback, in which human ratings of responses are used to steer the model's behavior. That training shapes tendencies rather than enforcing fixed rules. A carefully worded prompt can sometimes push the model outside the behavior it was taught.

Jailbreak prompts take several familiar forms. One approach asks the model to play a character who has no rules. An early example aimed at ChatGPT circulated online as DAN, short for Do Anything Now. Other approaches wrap a forbidden request inside fiction, a hypothetical scenario or a claimed research purpose. Some split a request into harmless-looking pieces spread across a long conversation.

Jailbreaking and prompt injection are related, but they aim at different targets. A jailbreak goes after the model's own safety restrictions — the limits its developer trained into it. Prompt injection goes after the instructions an application gives the model. Those instructions might tell a customer service bot to discuss only its company's products. A single attack can involve both, but the weakness being exploited is different.

The distinction shapes who handles the defense. Resisting jailbreaks falls largely to model developers. They retrain their models and add filters that screen what goes in and what comes out. Guarding against injection falls more heavily on the companies building applications on top of those models.

For businesses, the risk is that a deployed chatbot can be talked into producing harmful, offensive or dangerous output under the company's name. A model that refuses a request in one phrasing may comply when the same request is reworded. Model updates can also change that behavior. A safeguard that held against one version of a model is not guaranteed to hold against the next.

Adversarial examples are inputs that have been changed in small, deliberate ways so that a machine learning model misclassifies them. Because the attack targets a model that is already in use, the technique is also known as an evasion attack.

The classic case involves an image. An attacker adjusts pixel values by amounts too small for a human to notice. A person looking at the altered picture sees the same object as before. The model assigns it a different label, sometimes with high confidence.

The weakness comes from how models learn. An image classifier does not recognize objects the way people do. It learns statistical patterns across many numerical features. Those patterns can respond sharply to changes that carry no meaning for a human eye. An attacker who understands that sensitivity can push an input across the boundary the model uses to separate one category from another.

Attacks are often described by how much the attacker knows. In a white-box attack, the attacker can see the model's internal structure and parameters. That access lets the attacker calculate which changes will have the most effect. In a black-box attack, the attacker can only submit inputs and observe outputs. That attacker must probe the model repeatedly to find a change that works. An adversarial example crafted against one model can sometimes fool a different model trained for the same task. Researchers call this property transferability.

Images are the textbook example, but the idea applies wherever a model makes a decision about an input. A malware file can be modified so that a machine learning detector scores it as harmless while the code still runs. Spam and phishing messages can be reworded to get past filters that rely on learned patterns. Audio can be altered so that a speech recognition system transcribes something other than what a listener hears.

Timing separates evasion from data poisoning. Poisoning corrupts a model while it is being trained. Evasion leaves the model untouched and manipulates the inputs it receives after deployment.

Defenses exist, but none is complete. One common approach, adversarial training, adds manipulated examples to the training data. The model then learns to classify those altered inputs correctly. Other measures screen incoming data for signs of tampering before the model sees it. A model's accuracy on ordinary test data does not show how it performs against an attacker deliberately searching for its blind spots.

Shadow AI is the use of AI tools by employees without approval from their company's IT or security team. The main risk is that confidential information, such as customer records, source code or contract terms, gets pasted into an outside service the company does not control.

The term borrows from shadow IT. That older phrase covers any software, cloud service or device that staff adopt on their own, outside official channels. A team that stored work files in a personal cloud account or tracked projects in an unvetted app was practicing shadow IT. Shadow AI applies the same idea to chatbots, writing assistants, coding helpers, transcription services and image generators.

The typical case is ordinary. An employee who wants a quick summary of a long report or a cleaner draft of an email may open a free chatbot in a browser tab. The issue is what goes into the prompt. Once text is submitted, it leaves the company's network. From that point it is handled under the provider's terms, not the employer's.

Those terms vary. Some consumer AI services retain conversations and may use them to improve their models unless a user opts out. Business and enterprise tiers from the same providers often come with different data-handling commitments. An employee signed in with a personal account may not know which set of rules applies.

Unapproved tools can cause problems on the way back in, too. Code written by an unvetted assistant may contain security flaws. A chatbot's answer may contain factual errors that end up in documents sent to customers. Browser extensions that add AI features can request broad permissions to read web pages, documents or email.

Companies typically respond with a mix of controls. Some block specific AI websites on corporate networks. Others license enterprise versions of AI tools with contractual data protections, giving employees a sanctioned alternative. Acceptable-use policies can spell out which categories of information may never be entered into an AI service. Data loss prevention software scans outbound traffic for sensitive patterns such as account numbers. It can be configured to cover AI prompts as well.

AI red teaming is the practice of deliberately attacking an AI system to find its weaknesses before real attackers do. Testers act as adversaries. They probe a model or an AI-powered product for ways it can be misused, tricked or pushed into causing harm.

The practice borrows its name and approach from traditional security red teaming. In that older discipline, a red team plays the attacker and tries to break into an organization's networks, buildings or processes. A blue team defends. The exercise shows where defenses fail under realistic pressure rather than on paper.

AI red teaming applies the same adversarial mindset to a different kind of target. A conventional red team might look for an unpatched server or a weak password. An AI red team looks for prompts, inputs and sequences of actions that make a model behave in ways its builders did not intend.

The scope is broad. Testers typically attempt jailbreaks and prompt injection against the system. They also hunt for harmful outputs. These include instructions that could help someone cause physical harm and responses that leak private information. Answers that reflect bias against particular groups count as failures too.

One feature sets AI testing apart from much of traditional security work. Language models produce probabilistic outputs. The same prompt can return different answers on different attempts. A single failed attack does not prove a system is safe. Testers often repeat and vary their attempts to gauge how reliably a weakness can be triggered.

Red teaming can target a model on its own or the full application built around it. An AI assistant connected to email, documents or company databases has more ways to fail than a model answering questions in isolation. Testing the whole system shows what an attacker could reach in practice.

The findings feed back into fixes. Developers may retrain or adjust a model, add filters on inputs and outputs, or narrow the permissions an AI tool holds. Models and the applications around them are updated over time. For that reason, red teaming is usually treated as a recurring exercise rather than a one-time check.

Voice cloning uses AI to copy a person's voice from recorded audio samples. Vishing is voice phishing — a scam carried out over a phone call. The pairing lets a caller sound like a specific relative, manager or colleague.

A cloning model learns the pitch, accent, rhythm and tone of a voice from existing recordings. It can then produce new speech in that voice. Some tools work from typed text. Others convert the scammer's own speech into the target voice as they talk. The source audio can come from anywhere a person's voice is public, such as social media videos, podcasts, conference talks or a voicemail greeting.

Vishing is older than AI cloning. The word joins "voice" and "phishing." The classic version relies on a caller posing as a bank, a government agency or a tech support desk. Scammers often pair it with caller ID spoofing, which makes a call appear to come from a trusted number. Cloning adds something the older scam lacked: a voice the target already knows.

At home, a common script is a family emergency. A call arrives in what sounds like a child's or grandchild's voice. The caller describes an arrest, an accident or a trip gone wrong. Then the caller asks for money quickly and asks the listener to keep it quiet. That pattern predates AI and is known as the grandparent scam.

At work, the impersonated voice usually belongs to someone with authority. A call that appears to come from a manager or finance chief may ask an employee to approve a wire transfer. It may also ask them to change a supplier's bank details or share login credentials. A call to an IT help desk that imitates an employee may seek a password reset or a new device enrolled for multifactor authentication.

Each version leans on the same levers: urgency, authority and secrecy. The aim is to rush the target past the checks they would normally apply. Requests for payment in forms that are hard to reverse, such as wire transfers, gift cards or cryptocurrency, are a common feature.

The defenses rely on verifying the request through a separate channel rather than judging the voice. Hanging up and calling back on a number already on file gets around a spoofed caller ID. Some families agree in advance on a code word that only a real relative would know. Companies can require a second approver for payments and a call-back step before any change to bank details. A familiar voice on its own is not proof of who is on the line.
