Docker patches Java4Shell and the NGINX HTTP/2 with Docker Hardened Images

Tanggal: 2026-11-21

OpenJDK and Oracle disclosed Java4Shell (CVE-2026-114938) on November 17, and NGINX released fixes for two HTTP/2 flaws the next day. Docker began publishing fixed images for both in the Docker Hardened Images (DHI) catalog starting that same day.

What we know about Java4Shell is that it’s a memory-corruption bug in the Java runtime that can let an attacker with no credentials run code inside a Java application. Many container images contain a Java runtime, including application images that bundle their own, so it affects teams well beyond the ones that write Java.

Docker Hardened Images are the trusted foundation your applications should run on, because a flaw in the runtime inside an image is fixed only when that image is rebuilt, and Docker rebuilds its hardened images as soon as upstream fixes become available. Fixed images for the Amazon Corretto, SapMachine and Azul Zulu runtimes and for NGINX are in the catalog today, with Eclipse Temurin following as soon as Adoptium completes its fixed builds.

To decode Base64 quickly, the HotSpot JVM uses a hand-written routine built on AVX-512 instructions. That routine miscalculates a length when the input ends in unexpected padding and writes up to 62 bytes past the end of a buffer on the Java heap. Calif, the researchers who found it, turned that into heap disclosure and remote code execution.

They demonstrated code execution before authentication against default installations of Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate, and after authentication against Kafka, Solr, Elasticsearch, Gerrit and Spinnaker. They note there is no universal exploit: each application needs its own, and they have not published those. As of November 18 there are no public reports of exploitation in the wild.

Oracle rates the issue 8.1 (High) under CVSS 3.1. The researchers rate it 9.2 (Critical) under CVSS 4.0. CISA has issued an alert urging immediate patching.

To check a host’s CPU, run this on the host or Kubernetes node. Hardened runtime images have no shell, so it will not run inside the container.

grep -m1 ‘^flags’ /proc/cpuinfo | tr ‘ ‘ ‘\n’ | grep -E ‘^(avx512f|avx512bw|avx512vbmi|bmi2)$’

The host is affected if all four flags are printed.

Two other ways to check, for when a shell on the node is hard to get.

Ask the JVM. This works in hardened images:

docker run –rm –entrypoint java -XX:+PrintFlagsFinal -version | grep -w UseAVX

UseAVX = 3 means the JVM is using AVX-512 on that host. Treat the host as affected until the full check says otherwise. A value of 0 to 2 means AVX-512 is not in use. On ARM64 nothing is printed. The answer applies only to the host the command ran on.

Ask Kubernetes. kubectl get nodes -L kubernetes.io/arch,node.kubernetes.io/instance-type shows the architecture and instance type of every node. If you run Node Feature Discovery, nodes with the instruction set carry the label feature.node.kubernetes.io/cpu-cpuid.AVX512VBMI=true.

Check build runners and CI workers as well. They run Java, and they talk to the network.

Application images that bundle Java, such as Keycloak, Jenkins, Kafka, Elasticsearch and Solr

They follow the bundled runtime, which for many of them is Temurin, and they are rebuilt once the runtime they use is fixed. Until then, set the flag yourself.

Set the mitigation flag yourself on every JVM that is still waiting for a fixed runtime, and check what each image already sets before you do. Treat the flag as a stopgap, because a JVM is protected only if the flag reaches it when it starts, and a deployment setting or a start script can override it or drop it. A fixed runtime is the only thing that closes the issue, so move to the fixed image as soon as it is published.

The CPU check and the mitigation flag in the steps below apply to any image that runs a HotSpot-based OpenJDK build. The version strings in this post come from Docker Hardened Images, so for an image from another source, confirm the fixed build in that source’s advisory.

The fixed build can only come from whoever builds your image, because the Java runtime and the system packages your application runs on come from the image underneath it. That dependency is why a hardened image is a necessary step toward a trusted software supply chain. With Docker Hardened Images, tracking each vendor’s fix and rebuilding on it is work Docker does for you. The images are minimal and secure by default, and they are built to serve as a trusted and verifiable upstream for your builds. You can move a service onto one by following the migration guide.

A container often runs more than one JVM, for example when a build tool forks a JVM for tests, an application server starts helper processes or a CI agent starts a JVM for every build step. Five rules follow from that table. We tested each on DHI images.

JAVA_OPTS only works where a script reads it. With JAVA_OPTS=”-XX:-UseBASE64Intrinsics” set and a plain java command, the intrinsic stays on. No warning is printed.

A flag on the command line stops at that process. We started a JVM with the flag on its command line and had it start a second JVM. The child ran with the intrinsic on. With JAVA_TOOL_OPTIONS or JDK_JAVA_OPTIONS in the environment, the child ran with it off. A child started with a cleared environment gets nothing, whichever variable you use.

Check what the image already sets before you set anything. In Docker and Kubernetes, your value replaces the image’s value. It is not appended.

docker inspect –format ‘{{range .Config.Env}}{{println .}}{{end}}’ \  | grep -E ‘^(JAVA_TOOL_OPTIONS|JDK_JAVA_OPTIONS)=’

Our FIPS images use these variables to configure the FIPS provider. dhi.io/eclipse-temurin:21-fips sets both. When we replaced its JDK_JAVA_OPTIONS with only the flag, the JVM started normally, but the org.bouncycastle.fips.approved_only property was gone. Nothing warned us. If the command prints a value, copy it and add the flag at the end:

env:  – name: JDK_JAVA_OPTIONS    value: “ -XX:-UseBASE64Intrinsics”

Not every FIPS image uses the same variables, so run the check for each image.

Keep JAVA_TOOL_OPTIONS away from Java 8. Java 8 is not affected and does not know the flag:

Picked up JAVA_TOOL_OPTIONS: -XX:-UseBASE64IntrinsicsUnrecognized VM option ‘UseBASE64Intrinsics’Error: Could not create the Java Virtual Machine.

Adding -XX:+IgnoreUnrecognizedVMOptions to the variable does not help on Java 8. Where Java 8 shares an environment with a newer Java, either scope the variable to the containers that need it or use JDK_JAVA_OPTIONS, which Java 8 ignores. Java 11 accepts the flag, so it is harmless there.

Verify the process, not the environment. Running java -XX:+PrintFlagsFinal -version inside a container starts a new JVM. It tells you what the environment gives a new JVM, not what the JVM already serving traffic was started with. For the running process, use the startup log line. JDK_JAVA_OPTIONS prints one too, starting with NOTE: Picked up. In an image that includes the JDK you can also ask the process directly:

jcmd VM.flags | tr ‘ ‘ ‘\n’ | grep UseBASE64Intrinsics

The answer must be -XX:-UseBASE64Intrinsics. If the flag reached the JVM through an environment variable, it will not show in the process’s command line, so ps is not a reliable check.

Some applications discard these variables on purpose. Elasticsearch’s start script, for example, ignores JAVA_TOOL_OPTIONS and expects ES_JAVA_OPTS. Check your application’s documentation.

The day after Java4Shell, NGINX released fixes for two memory errors in the way it handles HTTP/2 connections, tracked as CVE-2026-123007 and CVE-2026-123633. A crafted request can crash a worker process, and where an attacker gets past the operating system’s memory protections it can run code inside that worker. Both flaws need HTTP/2 to be enabled on the server, and the same releases fix other NGINX issues that do not depend on HTTP/2, so update either way.

The Docker Hardened Images for NGINX were rebuilt on NGINX 1.30.7 and 1.31.9 and published on November 18, the same day as the upstream release. To patch, pull the image again and redeploy, and move any tag pinned to an older exact version to a fixed one. nginx -v prints the version, and the fixed ones are 1.30.7 and 1.31.9. The notes on pull policy, mirrors and your own images in the section above apply to NGINX images in the same way.

The vulnerable code is in the Java runtime inside the image, and if you are using DHI, shipping the fix becomes our job. Whether that code can be reached in your deployment depends on things an image cannot see: the CPU it is scheduled onto, the options you start it with, the processes it starts, and the traffic you send it.

It was only four weeks ago that the news was PHP2Shell and the eMudhra certificate compromise. Calif, the security research team that found Java4Shell and helped find PHP2Shell, says it used AI to find this flaw in about an hour and that the whole effort cost less than $200 in tokens. When a flaw like this can be found and weaponized at that price, it is reasonable to expect more of them.

If you lead a team or answer for how your organization builds and ships software, the questions after a week like this one are whether you were exposed and how quickly you can prove you were not. It is imperative to have a trusted foundation in place before the next flaw appears, and Docker Hardened Images is that foundation to adopt. This week Docker began publishing fixed Java and NGINX images to the catalog within a day of each disclosure, with the images still waiting listed in the status table above. Each image ships with a signed SBOM and SLSA Build Level 3 provenance, so you have a record of what it contains and how it was built.

The Docker Hardened Images catalog is free and open source under Apache 2.0, and moving one of your services onto a hardened image typically means changing one line in its Dockerfile. If you are not building on Docker Hardened Images yet, start today.
