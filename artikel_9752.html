Can a Plain Table Hijack Your AI Agent? Defending Against Indirect Prompt Injection in Tool Outputs

Tanggal: 2026-11-20

Tuần này trên Dev.to có bài "Can a plain table hijack an AI agent?" khiến mình giật mình: chỉ cần một bảng CSV, một trang HTML hay một issue trên GitHub có chứa vài dòng chữ kiểu "Ignore previous instructions...", là agent của bạn có thể quay ra gửi file .env cho người lạ. Đây không phải lý thuyết. Mình từng review một agent nội bộ đọc file Excel do khách hàng upload, và chỉ với một ô có nội dung khéo léo, nó đã gọi tool send_email với dữ liệu của khách khác. Bài này chia sẻ cách mình hiểu và phòng chống indirect prompt injection, loại tấn công mà phần lớn team Việt Nam đang build agent đều chưa để ý tới.

Với LLM, mọi thứ trong context đều là token. Model không có khái niệm "đây là data, đây là lệnh" ở mức kiến trúc. Khi agent gọi tool read_csv() rồi nhét kết quả vào prompt, nội dung đó đứng ngang hàng với system prompt của bạn.

Direct prompt injection là khi user tự gõ lệnh độc. Indirect thì nguy hiểm hơn nhiều: kẻ tấn công không cần tương tác với agent. Họ chỉ cần cài payload vào nơi agent sẽ đọc: một ô trong spreadsheet, alt text của ảnh, comment HTML, README của repo, hay một dòng trong kết quả search.

Với các model đời mới, tỉ lệ bị lừa đã giảm đáng kể, nhưng không bao giờ là 0. Và chỉ cần trúng 1 lần trong 1000 request là đủ để bạn lên báo.

Kỹ thuật đầu tiên là làm cho model nhìn thấy rõ đâu là dữ liệu không đáng tin. Microsoft gọi nhóm kỹ thuật này là spotlighting, gồm delimiting (bọc bằng tag), datamarking (chèn ký tự đánh dấu) và encoding (base64). Lưu ý quan trọng: regex filter chỉ để log và cảnh báo, không phải hàng rào bảo vệ. Attacker có thể viết payload bằng tiếng Việt, tiếng Nhật, hoặc diễn đạt vòng vo. Spotlighting giảm đáng kể tỉ lệ thành công, nhưng vẫn là biện pháp "xác suất". Lớp bảo vệ thật sự phải nằm ở tầng code.

Nguyên tắc mình áp dụng: model có thể bị lừa, nhưng code thì không. Mọi tool call phải đi qua một policy gate viết bằng code thuần, và gate này biết context hiện tại đã bị "nhiễm" dữ liệu không tin cậy hay chưa.

Điểm mấu chốt: khi agent đã đọc bất kỳ dữ liệu nào từ bên ngoài (user_upload, web_fetch, github_issue), mọi hành động có side effect đều cần người xác nhận. Nghe phiền, nhưng trong thực tế phần lớn tác vụ "đọc file rồi tóm tắt" không cần side effect, nên user hiếm khi bị hỏi.

Nếu muốn đi xa hơn, hãy xem pattern Dual LLM của Simon Willison hoặc paper CaMeL (Google DeepMind, 2025): một LLM "privileged" chỉ lập kế hoạch và không bao giờ nhìn thấy dữ liệu thô, còn một LLM "quarantined" xử lý dữ liệu nhưng không có quyền gọi tool. Giá trị trả về được truyền qua biến tham chiếu ($VAR1), nên payload không bao giờ chạm tới planner.

Indirect prompt injection là lỗ hổng mang tính kiến trúc của LLM. Chưa có model nào "miễn nhiễm", và có lẽ sẽ còn lâu mới có. Thay vì hy vọng model đủ thông minh, hãy thiết kế hệ thống với giả định model sẽ bị lừa.

Nếu chỉ làm được một việc trong tuần này, hãy làm mục 2. Một cái if session.tainted đơn giản có thể là thứ duy nhất đứng giữa một file CSV vô hại và sự cố rò rỉ dữ liệu khách hàng.
