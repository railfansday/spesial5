One of the biggest improvements to Go's tooling has been the introduction of new ways to run third-party tools. We now have three options — go install, go run, and go tool — each suited to slightly different use cases.

The first option is to install the tool on your local machine using the go install command. You can run this command from anywhere on your machine, and it will download the necessary source code for the tool and create an executable binary in your GOBIN directory. So long as your GOBIN directory is on your system path, you can then run the tool whenever you need it.

Using go install tends to be a good option for general-purpose tools that happen to be written in Go, where you don't need to pin a specific version for use within a project or necessarily keep up with the latest release. Personally, I tend to use it for installing tools like hey, which I often use for things outside of Go development.

In late 2022 the Go team released govulncheck, which checks your codebase against the Go vulnerability database to find known vulnerabilities in any standard library packages or third-party dependencies that you're using.

Unlike many other vulnerability scanners, it only flags vulnerabilities that actually affect you... meaning that a vulnerability in a part of a package that your code doesn't use won't be flagged.

It's an excellent tool, and I recommend running it routinely before you deploy a new version of your application to production.

It's also worth mentioning the shadow tool, which identifies instances of variable shadowing in your code.

Before compiling your application, it's sensible to run go mod verify to check that the dependencies in your module cache haven't been modified since they were downloaded.

I normally run go mod verify immediately before running go build, as part of an automated build process in a CI workflow or Makefile task. This helps to make sure that builds are reproducible, and you're not using an accidentally modified dependency during compilation.

It's important to note that the go build tool caches build output in the build cache. This cached output will be reused again in future builds where appropriate, which can significantly speed up the overall build time.

Using the build cache comes with one important caveat — it does not detect changes to C libraries imported with cgo. So if your code imports a C library via cgo and you've made changes to it since the last build, you'll need to use the -a flag which forces all packages to be rebuilt. If you ever want detailed output explaining precisely what go build is doing behind the scenes, you can use the -v flag to print package names as they are being compiled, or the -x flag to print the detailed commands that are being run. You'll probably want to use these in conjunction with the -a flag, because otherwise you might not see much output as Go reuses packages from the build cache rather than recompiling them.

Finally, if you run go build on a non-main package, it will be compiled in a temporary location and again, the result will be stored in the build cache. No executable binary will be produced.

Go also supports profile-guided optimization (PGO), which allows the compiler to use information gathered from profiling your application to make better decisions when compiling your code.

Normally, when compiling your code, the compiler has to make educated guesses about which functions are likely to be called frequently, which code paths are more common, and where it should make optimizations. PGO allows you to provide a CPU profile from a representative run of your application so that the compiler can make better-informed decisions.

For example, it may use this information to more aggressively inline frequently called functions, or optimize common code paths.

The good news is that using PGO is relatively straightforward. First you need to generate a CPU profile using one of the techniques described in the previous section. Alternatively, you can rename your profile to default.pgo and place it in the directory containing your main package. Go will automatically detect this file and use it when building your application, so you don't need to specify the -pgo flag explicitly.

In practice, the recommended workflow is to collect a representative profile from your production application, use that profile when building your next release, and periodically collect new profiles as your application evolves.

For more information, see the official PGO documentation and the Go blog post introducing PGO.

Sometimes profiling isn't enough to understand what's happening in your application. For example, a CPU profile can show you which functions are consuming the most CPU time, but it won't necessarily help you understand why a goroutine is blocked, why your application isn't making progress, or why a request is taking so long.

For these situations, Go has a built-in execution tracer, which has been improved significantly in recent Go versions. It records runtime events such as goroutine scheduling, system calls, garbage collection, and other activity over a period of time. You can then use the go tool trace command to visualize and explore what happened.
