OpenRun v1.0 - declarative deployments for internal tools on Docker or Kubernetes

Tanggal: 2026-11-20

After over three years of development, over 2000 commits, 170 releases and with multiple customers running OpenRun in production, I am happy to do the 1.0 release for OpenRun.

OpenRun is an open source self-hosted GitOps platform for deploying web apps and internal tools declaratively. Deploy on a single node with Docker/Podman, or deploy apps onto a Kubernetes cluster. OpenRun adds the authentication, authorization and auditing features required by teams. Code based internal tools get the deployment and auth features which are usually available in low code platforms.

I started the OpenRun project (called Clace initially) in April 2023 - feels like an eternity ago. I have been working on OpenRun as a part time project, doing consulting on the side.

OpenRun is built to make it easy for teams to declaratively deploy internal tools. OpenRun also aims to make it easy to set up OIDC/SAML based authentication, with RBAC policies to control which apps are available to which teams and roles.

Go: OpenRun is implemented in Go. The fast compile cycle and excellent runtime performance of Go make developing in Go fun. The difficulty of adding dynamic behavior was the one challenge in Go, especially compared to something like the dynamic class loading available in the JVM. Out of process loading using go-plugin was the solution used to get dynamic loading behavior. There is an additional performance overhead of an RPC call but there are advantages in terms of ease of use and stability.

Starlark as the config language for declaring apps and defining app handler functions. The familiarity of Python which Starlark provides makes it very easy to get started with for end users.

Hypermedia (using HTMX) based UI is used for the built-in actions UI and for the optional Console app. Hypermedia apps work well for the types of apps being built with OpenRun. Fewer frontend dependencies, no separate frontend build pipeline and avoiding the NPM ecosystem have been some benefits of building Hypermedia based apps.

SQLite and Postgres: For single node deployment, SQLite is used for metadata. For Kubernetes deployment, Postgres is used for metadata. No ORM is used. This was a bit more work to develop initially but allowed for complete control over the queries used for each database.

Declarative deployments: Initially, the plan was to use the Kubernetes libraries for three way merge (between new config, previous config and current state), but implementing it in OpenRun itself turned out to be simpler and easier to maintain. The implementation is custom built for what OpenRun needs, so it does not have the complexity of a general purpose library.

In terms of user adoption, it would have been better to start with Containerized apps, since those work with existing user applications, without requiring any OpenRun specific development.

Starlark Apps: OpenRun did go somewhat overboard with Starlark support, with features like allowing database app development from Starlark. Containerized apps would have been better since they work with the complete language ecosystem. The Hypermedia support could have been limited to what is required for a backend for frontend pattern (although hypermedia apps do not need much of a frontend). Internal apps like the Console are built with Starlark, so the work done to support this was still useful.

Container Management: Single node deployment with Docker/Podman and multi-node with Kubernetes are the two supported modes. A multi-node deployment, with each node having a Docker/Podman installation, was considered but not done since that would have introduced too many complexities in terms of container and volume management.

There are many products which make deployments easier. OpenRun differs in that it provides a declarative solution and is targeted at teams deploying internal tools.

With recent improvements in AI, internal tools which would have required weeks of development work can now be built much faster using AI agents. Higher level abstractions for deploying internal tools securely are necessary now, since the tools themselves are easier to build.

Agents are at a point where they can handle the deployment workflow themselves. Letting agents directly do production deployments might be fine for testing and personal workflows, but that approach is not suited for team environments. A declarative approach is better if you want to set up multiple deployment environments and restore an environment from scratch.

Agents are pretty good at writing the YAML boilerplate required for Kubernetes deployments. Internal tools generally require OIDC/SAML authentication, RBAC and audit logs. Kubernetes alone does not make enabling such access policies easy. OpenRun provides a higher level app deployment abstraction. This helps reduce the overhead of maintaining the deployment configuration. Using Kubernetes directly, multiple systems like CI builder, ArgoCD, auth proxy, Internal Developer Platform (IDP) etc. have to be configured to get the functionality OpenRun provides.

The core config format, CLI commands and API are stable and will maintain backward compatibility across the 1.x releases. The plan is to ensure that existing deployments should work without issues when doing upgrades across 1.x, as new features are added and issues fixed.

Date based versioning is being used for the 1.x releases. All fixes go on the main branch and releases use the 1.YYMM.D[D]V version format, where V is the version number on that day, zero-indexed. So v1.2611.130 means the first release on 13 Nov 2026.
