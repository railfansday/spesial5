Why Microsoft keeps going down: 7 common causes of cloud outages, explained

Tanggal: 2026-11-12

Free daily briefing on global business news.

Common causes of cloud outages, from bad configuration changes to DNS and sign-in failures, explain why Microsoft services like Azure and Microsoft 365 sometimes go down

When Outlook stops loading or Teams calls drop for many users at once, the cause is rarely a server room going dark. Many large cloud failures start smaller than that. One setting, one piece of code or one shared component breaks. Then the cloud's own automation can copy the problem across a global system faster than any person can step in.

That speed is the trade-off at the heart of modern cloud computing. Microsoft $MSFT runs Azure, its cloud platform, alongside Microsoft 365 and Teams, the online services that handle email, documents and meetings for many organizations. These products are separate brands, but they sit on shared infrastructure. They share data centers, networks, deployment systems and a common sign-in service. A fault in one of those layers can surface in many products at the same moment. To a user, it looks as if all of Microsoft has gone down.

The same design that makes the cloud efficient also makes its failures visible. A company that once ran its own email server might have suffered an outage that only its staff noticed. When that company moves to a large cloud provider, it shares the provider's strengths and its weak points with many other customers on the same platform. A single problem can reach businesses, schools, hospitals and government agencies across several continents at once.

The causes of cloud outages tend to fall into a handful of recurring categories. Some are human, such as a mistyped configuration value or a software update with a hidden bug. Others involve technical plumbing, such as the Domain Name System that directs traffic or the identity service that checks who is allowed in. Some are physical, such as power, cooling and network hardware. A few come from outside, including floods of hostile traffic designed to knock services offline.

The seven slides that follow walk through a selection of these common failure types. They are not a ranking, and they do not explain any specific incident. Each one describes how a particular kind of failure works, why it can spread and what cloud providers do to contain it.

For businesses that depend on Microsoft's cloud, these patterns matter in practical terms. Knowing where failures start helps IT teams read status updates, plan backup options and ask sharper questions about resilience before the next disruption arrives.

A single incorrect setting, pushed automatically to thousands of servers, can break a cloud service before engineers notice anything is wrong. Faulty configuration changes are among the most commonly cited causes of large cloud outages. They can happen without anyone writing a line of new code.

Configuration is the set of instructions that tells software how to behave. It covers details such as which servers accept traffic, how much capacity a service may use, which network paths data should follow and which security rules apply. Changing a configuration value does not alter the program itself. It alters the conditions the program runs under.

At the scale of Azure or Microsoft $MSFT 365, nobody edits those settings by hand on each machine. Providers use automated configuration management systems that write a change once and distribute it across fleets of servers in many regions. That automation keeps settings consistent from one machine to the next. It also means a mistake travels as fast as a correct update.

The errors themselves are often small. A single wrong number can be enough. So can a missing entry in a list of allowed addresses, a limit set too low or a rule applied to the wrong group of machines. A setting that looks harmless on its own can also conflict with another setting elsewhere in the system.

Providers try to catch these problems before they spread. Common safeguards include automated validation that checks a change against expected formats and rules. Peer review by a second engineer adds another check. Many systems also keep a record of the last known good configuration.

Rollback is the standard recovery tool. If a change causes failures, engineers revert to the previous settings and push that version out instead. In principle, reverting a setting is quicker than writing and shipping a code fix.

Rollback has limits, though. A bad change can disrupt the management tools, network access or permissions that engineers need to undo it. Servers that crashed may have to restart and reload before service returns. As a result, a configuration error that takes seconds to deploy can take much longer to reverse.

New code can break a cloud service when it carries a defect that testing did not catch. Cloud providers ship software updates constantly. A single flawed release can slow down or take offline the email, meeting and file storage tools that businesses depend on every day.

Software in a large cloud platform is never finished. Engineers release fixes, security patches and new features on a rolling basis, often across many parts of the system in the same week. Each release carries risk. Code that passed every check in a test environment can still behave differently once it meets real customers.

The gap between testing and reality is the core problem. Test environments are smaller and quieter than production. They rarely reproduce the full volume of traffic or the variety of customer setups in a global service. They also miss many of the odd combinations of old and new software that build up over time. A memory leak that takes days to grow can slip through. So can a race condition that appears only when thousands of requests arrive at once.

Providers limit the damage with staged rollouts. A change goes first to a small share of customers or servers. Engineers watch error rates, response times and crash reports before sending it further. If something looks wrong, the release stops before it reaches everyone.

A canary release is one version of this approach. The name comes from the caged canaries that miners once carried to detect dangerous gas. The first small group of servers plays the same role and signals trouble early. Feature flags add another safeguard. They let engineers ship code with a new function switched off. The function can then be turned on gradually, or shut off again without a fresh deployment.

These methods reduce risk, but they do not remove it. Some defects stay hidden until a release reaches full scale. Others are triggered by a rare event, such as a date change or an unusual request, long after the rollout looks complete. Monitoring can also miss a problem when the early symptoms are subtle.

A bad release that gets through is usually undone by redeploying the last version that worked. Finding the culprit comes first. A large platform may have several releases moving through it at once. Each one is a suspect until engineers rule it out. Code that changes how stored data is structured adds another obstacle. The older version may not be able to read data the new one has already rewritten. In that case, shipping a corrected update can be faster than going back.

A Domain Name System failure can make a Microsoft $MSFT service vanish for users even when every server behind it is running normally. The servers have not crashed. The system that tells computers where to find those servers has stopped giving answers.

DNS works like a phone book for the internet. People type names such as outlook.com, but computers connect using numeric IP addresses. Before a laptop or phone can open a mailbox, it has to ask DNS which address belongs to that name. The connection can begin only after a reply comes back.

That lookup passes through several layers. A device usually sends its question to a recursive resolver. An internet provider, an employer or a public DNS service typically runs that resolver. The resolver then works through the DNS hierarchy until it reaches the authoritative name servers for the domain. Those authoritative servers hold the official records for the name.

Problems can start at any point in that chain. Authoritative servers can become overloaded or unreachable. A record can be edited incorrectly, pointing a name at the wrong address or removing it altogether. A resolver can fail and leave everyone who relies on it unable to look anything up.

From the user's side, the result looks like a complete outage. A browser reports that the site cannot be found. Desktop apps such as Outlook or Teams retry and eventually show a connection error. Nothing in the message tells the user that the mail and chat servers are still working.

Caching makes DNS failures uneven and slow to clear. Resolvers store answers for a set period called the time to live, or TTL. The domain owner chooses that period. A user whose resolver still holds a valid cached answer may keep working while someone relying on a different resolver is cut off.

The same mechanism works against recovery. If a bad record has been cached, the corrected version reaches users only as the old entries expire. Engineers may restore the right records quickly, yet the service comes back in waves rather than all at once. That lag explains why complaints can continue after a fix is in place.

DNS also matters to Microsoft's business customers directly. Microsoft offers Azure DNS, a service that hosts DNS records for customers' own domains. Businesses that use it rely on that service to point visitors to their websites and apps. Short TTL values let an organization redirect traffic faster during trouble. The tradeoff is a higher volume of lookups, which adds load on the name servers answering them.

When Microsoft $MSFT Entra ID cannot confirm who a user is, Outlook, Teams, SharePoint and the Azure portal can all look broken at the same moment. The apps themselves may be running normally. People cannot get past the sign-in step to reach them.

Entra ID is Microsoft's cloud identity service. It was previously called Azure Active Directory, and many IT administrators still use the older name or its abbreviation, Azure AD. The service checks credentials, applies security rules and decides which accounts can open which resources across Microsoft 365 and Azure.

The system works by issuing tokens. After a user signs in, Entra ID gives the app a digitally signed token that vouches for the person's identity and permissions. The app accepts that token instead of asking for a password again. The exchange follows industry standards, including OAuth 2.0 and OpenID Connect.

Single sign-on extends the same arrangement across products. One successful login can unlock email, chat, file storage and the third-party business apps a company has connected to Entra ID.

That convenience creates a single front door. If the identity service slows down or rejects valid requests, every product behind it inherits the problem. For a person at a desk, mail, chat and files all seem to fail together.

Security checks add more steps that can fail. Multifactor authentication may ask for a code or an approval in the Microsoft Authenticator app. Conditional Access policies can weigh a device's compliance status, location or sign-in risk before granting entry. Each check depends on another system answering on time.

Timing shapes how an identity problem appears. Tokens expire after a set period and must be renewed. Someone already signed in may keep working for a while. A colleague opening a laptop fresh may be turned away. That uneven pattern can make an identity fault hard to diagnose at first.

Mistakes inside a customer's own tenant can produce a similar lockout. A badly scoped Conditional Access rule can block an organization's whole workforce, including the administrators who need to fix it. Microsoft recommends that organizations keep emergency access accounts for this situation. These are often called break-glass accounts, and they sit outside normal sign-in policies.

Physical faults inside a data center can take servers offline even when every line of software works. A power interruption, a cooling breakdown or a failed piece of network equipment can each cause it. Cloud providers build layers of backup to absorb these faults, but each layer has limits.

Power is the first point of exposure. A large data center draws electricity from the utility grid. A sudden drop or surge on that feed can cut power to whole rows of server racks.

Facilities bridge that gap with uninterruptible power supplies. These run on batteries for the short window it takes backup generators to start. The generators usually run on diesel and can carry the site until grid power returns.

The handoff between those systems is a weak spot. A transfer switch can fail. A generator can fail to start, or batteries can run down before backup power takes over. In each case, servers lose power abruptly. Machines that shut down without warning can take time to restart. Some come back with failed components or data that needs checking.

Cooling is a second vulnerability. Servers produce heat constantly. Data centers remove it with chillers, air handlers and, in some facilities, liquid cooling. When cooling capacity drops, temperatures in the server halls climb quickly.

Server hardware is designed to slow itself down or switch off before heat damages it. That protects the equipment. It also removes computing capacity from the service running on it. Hot weather adds strain. Cooling systems must work harder when the outside air is warmer.

Ordinary hardware also wears out. Hard drives, memory modules, power supplies and network switches fail routinely across any large fleet of machines. Most of these failures stay invisible to users. Software moves the work to healthy machines.

A failed core network switch or storage cluster is a different matter. It can cut off many servers at once.

Microsoft $MSFT limits the reach of these problems through geography. Azure divides its infrastructure into regions, and many regions contain availability zones. Each zone is a physically separate location with its own power, cooling and networking. A service spread across several zones can keep running if one zone goes dark.

That protection depends on how a workload is set up. Applications deployed in a single zone or a single region have no fallback when that location fails. Failing over to another region also takes time. Data written moments before a fault may not have copied across yet.

Network problems can cut users off from Microsoft $MSFT services that are still working normally. A faulty routing change, an overloaded link or a distributed denial-of-service (DDoS) attack can each stop traffic from reaching its destination. The application stays healthy in its data center, while customers see timeouts and error pages.

The internet is a patchwork of separate networks, each run by a different company or institution. They share directions using the Border Gateway Protocol, or BGP. Through BGP, each network announces which blocks of IP addresses it can deliver traffic to. Its neighbors then pass that information along to their own neighbors.

That arrangement depends on trust. A network might announce routes it should not, or withdraw routes it still needs. Traffic can then be sent down the wrong path or dropped entirely. A large provider's address ranges can effectively disappear from parts of the internet when this happens. The servers behind those addresses keep running, but packets no longer find a way to them.

Large cloud providers also run their own private wide area networks, which link data centers across countries and continents. Routing inside that backbone follows the same logic. A mistake in how traffic is steered between regions can cut off services in one location from the users and systems that depend on them.

Congestion is a quieter version of the same problem. Every network link has a fixed capacity. When demand exceeds it, routers start dropping packets and response times climb. A fiber cut or a sudden shift of traffic onto fewer paths can push the remaining links past their limits. Users then see slow page loads, choppy Teams calls and failed file uploads rather than a clean shutdown.

DDoS attacks create congestion on purpose. An attacker directs traffic from many machines at once — often a botnet of compromised computers, home routers and internet-connected cameras — at a single target. Some attacks try to fill network pipes with raw volume. Others exhaust server resources with a flood of connection requests or with requests for pages that are costly to generate. The goal in each case is to leave no capacity for legitimate users.

Cloud providers defend against these floods by spreading and filtering traffic. Anycast routing lets the same address be announced from many locations. An attack's load is then split across sites instead of landing in one place. Filtering systems inspect incoming traffic and discard requests that match attack patterns before they reach the application. Microsoft offers this kind of protection to Azure customers through a service called Azure DDoS Protection.

Those defenses can still be strained. A very large or unfamiliar attack may take time to recognize and filter. Mitigation systems can also misfire and block real users along with attack traffic. Telling a hostile flood apart from an ordinary surge in demand, such as a spike after a major product launch, is not always straightforward.

A single failed component can look like Microsoft $MSFT going down everywhere because cloud services are built on top of one another. When many businesses run on the same small group of providers, one fault inside a shared layer reaches far beyond the product where it started.

Modern cloud platforms are assembled from internal building blocks. A storage service, a messaging queue, a monitoring system and a database may each support many customer-facing products. Engineers call these links dependencies. A product that looks independent on the surface often relies on several of them underneath.

Shared building blocks let a provider build a capability once and reuse it across email, collaboration tools and developer platforms. They also create a dependency chain. If a component near the bottom of the chain slows down or fails, every service stacked above it can stall in turn.

This pattern is known as a cascading failure. It rarely shows itself at the source. Users see Teams messages that will not send or an Azure dashboard that will not load. The actual fault may sit several layers deeper, in a system those users never touch directly.

Recovery can make things worse before it makes them better. Software is usually written to retry a request that fails. When thousands of clients retry at once, the combined traffic can overwhelm a service that is trying to come back online. Engineers call this a retry storm, or a thundering herd. Providers counter it with exponential backoff, which spaces out each retry over longer intervals. They also use circuit breakers, which stop calls to a failing component for a set period.

Customer concentration widens the impact. Much of the world's corporate computing runs on a few hyperscale providers, including Microsoft Azure, Amazon $AMZN Web Services and Google $GOOGL Cloud. When one of them has a problem, unrelated companies in different industries can lose the same tools at the same time. The disruption becomes a public event rather than a problem inside one company.

Concentration also reaches businesses that never signed a contract with the affected provider. A company may host its own website elsewhere but depend on a payment processor, a customer-support tool or a software vendor that runs on Azure. Those indirect links often stay invisible until something breaks.

Organizations plan around this risk in several ways. Some run critical workloads in more than one cloud region, so a fault in one geography does not take everything offline. Others adopt a multicloud strategy, spreading systems across two or more providers. That approach adds cost and engineering complexity. It also does not remove the shared dependencies inside each individual platform. A third approach is mapping which vendors a business relies on and writing down how it will operate if a key service goes dark for several hours.
