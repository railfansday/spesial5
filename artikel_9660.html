Building govulncheck for the BEAM: Function-Level CVE Reachability Over .beam Bytecode

Tanggal: 2026-11-24

If you run Elixir or Erlang in production long enough, you know this Monday morning routine. Dependabot or mix deps.audit turns CI red because a new CVE just landed in hackney, plug, or cowlib. You spend twenty minutes reading the advisory diff, only to find out the bug sits inside a multipart header parser or a SOCKS5 proxy helper that your JSON-only API never touches. Upgrading right away is blocked by a version constraint in another library, so somebody adds an ignore flag and hopes nobody forgets why it was added six months later.

Go solved a big chunk of this problem years ago with govulncheck. Instead of treating go.mod as a flat bag of equally dangerous packages, it walks the call graph and checks whether your code can actually reach the vulnerable function. The BEAM ecosystem didn't have an equivalent tool, even though our advisory feeds already contain the exact symbol data needed to build one.

So I built VulnCheck, an open-source, function-level vulnerability reachability scanner for Elixir, Erlang, and Gleam with zero runtime dependencies. Here is how it works under the hood, why naive call graphs are actively dangerous on the BEAM, three nasty compiler traps I ran into along the way, and what the honest precision/recall numbers look like on real projects.

For years, lockfile scanners like mix_audit had a fair excuse: older Hex security advisories only published a package name and a SemVer range. Without reading the patch yourself, there was no machine-readable way to know which module or function carried the bug.

That changed once the Erlang Ecosystem Foundation (EEF) became an official CVE Numbering Authority (CNA). Recent CVE 5.1 records for BEAM packages publish exact Module.fun/arity signatures inside programRoutines, along with affected module lists and occasional OTP runtime version bounds:

By pairing the OSV.dev Hex archive (for fast package and git-commit range matching) with EEF CNA / MITRE CVE 5.1 records, we know the exact target MFA. The hard part is answering a deceptively simple question: can a compiled BEAM release actually reach 'Elixir.Plug.Conn.Query':decode/4 or 'Elixir.Ash.Actions.Aggregate':run/4 at runtime?

When I first sketched this out, the obvious temptation was to run Code.string_to_quoted/2 across lib/ and deps/ and collect function calls from source files. That idea falls apart on the very first Phoenix app.

Half of the real call graph in an idiomatic Elixir codebase doesn't exist in .ex files as literal function calls. Macros generate it during compilation: use Phoenix.Router, plug Plug.Parsers, use Phoenix.Controller, use GenServer, Oban.Worker, Ash resources, Ecto schemas. Two lines of router DSL expand into match clauses, pipeline functions, and plug dispatch calls that only exist after compilation.

Fortunately, elixirc, erlc, and gleam build --target erlang all converge on .beam files containing the standard :abstract_code chunk in Erlang Abstract Format (:raw_abstract_v1), assuming debug info wasn't stripped. OTP's built-in :beam_lib reads those chunks straight off disk without loading the target module into the running VM:

Working at the :raw_abstract_v1 layer buys three things at once:

If you only wire up direct local calls, remote calls (Mod.fun(x)), and captures (&Mod.fun/2), you get a fast analyzer that produces terrible false negatives. For a security tool, noisy warnings are annoying, but telling an engineer that an exploitable CVE is UNREACHABLE is unforgivable.

Unlike Go, BEAM applications don't start at main() and walk down a tree of direct function calls. Control flows through OTP boot descriptors and implicit framework contracts:

To handle this soundly, VulnCheck runs a least-fixpoint entrypoint and behaviour synthesis pass (Entrypoints + Behaviours) over the raw call graph, wiring callbacks for GenServer, :gen_statem (including state_functions mode), :cowboy_rest, Plug, Phoenix, LiveView, Oban.Worker, consolidated protocols (defimpl), and configured adapters.

Here are three real traps that bit me while building and auditing that model.

Open any Phoenix controller and you'll see use Phoenix.Controller followed by normal functions like def index(conn, params). It looks like the router calls ReportController.index/2. It doesn't. use Phoenix.Controller injects an intermediate action/2 dispatcher:

To a generic bytecode walker, that line is apply(ReportController, unknown_atom, [conn, params]). Early on, this broke two things at the same time:

Fixing this properly meant teaching the walker and the fixpoint solver to recognize all three ways Plug and Phoenix compile routes across versions: direct Controller.call(conn, :index), Plug.Builder's Controller.call(conn, Controller.init(:index)), and Phoenix 1.7+'s __match_route__/4 4-tuple {metadata, prepare, pipeline, {Controller, :index}}. When every reachable route to a controller passes known exported action atoms (and action/2 itself isn't overridden with custom dynamic apply/3 hooks or bypassed via apply(Controller, :call, ...)), VulnCheck emits proven edges straight to the routed actions. The moment any route passes a dynamic value, it falls back to all /2 exports so soundness is never lost.

A stock Phoenix endpoint plugs Plug.Parsers with [:urlencoded, :multipart, :json], whereas internal JSON APIs usually restrict it to parsers: [:json]. When a multipart CVE drops, a JSON-only service shouldn't get paged for it.

The catch is how Plug.Builder compiles plugs when MIX_ENV=prod (where plug_init_mode defaults to :compile). In dev builds, .beam files contain a runtime call to Plug.Parsers.init(parsers: [:json]). In prod builds, Plug.Builder executes Plug.Parsers.init/1 at compile time and bakes the resulting options tuple directly into Plug.Parsers.call(conn, compiled_opts). There is no Plug.Parsers.init/1 call anywhere in the production bytecode. The analyzer has to inspect literal option terms on both init/1 and precompiled call/2 sites, including custom @behaviour Plug.Parsers modules.

In v1.0.1, I tightened how function values (cb.(arg)) are modeled. Because anonymous functions (fn x -> ... end) and captures (&Mod.fun/1) inside .beam modules already add edges at their definition site, invoking a variable cb.(arg) shouldn't force every vulnerability of matching arity across the entire lockfile to stay open. On real apps, that change cut a lot of false noise.

Then a critical soundness audit poked a hole right through that assumption: where can a BEAM process obtain an executable fun that was never constructed inside any analyzed .beam file?

In v1.0.2, the static config scanner extracts captures, MFA tuples, Erlang module keys, and calls inside config closures directly into entrypoint roots, while Solver re-enables :function_value escapes whenever binary_to_term, eval, or an unparseable dynamic config is present. Normal apps keep all the precision gains.

One rule I refused to compromise on: VulnCheck ships with zero production dependencies (deps(:prod), do: []). A security scanner shouldn't pull twenty extra Hex packages into your dependency graph.

Elixir 1.18+ and Erlang/OTP 27+ already ship with JSON, :beam_lib, :zlib, :zip, :erl_tar, :crypto, :httpc, and :ssl backed by :public_key.cacerts_get/0 (wrapped with strict TLS hostname verification, archive size/entry caps against zip/tar bombs, and SSRF redirect blocks covering HTTPS downgrades, loopback, 0.0.0.0, IPv4-mapped IPv6, 169.254.169.254, and RFC 1918 / RFC 4193 ranges). Severity scoring includes full CVSS v3.1 and CVSS v4.0 vector implementations from the FIRST specification.

The trickiest low-level constraint on the BEAM is the atom table. Atoms are never garbage-collected, and the VM defaults to a hard ceiling of 1,048,576 atoms. If you parse tens of thousands of OSV JSON entries, arbitrary mix.lock / rebar.lock files, .app descriptors, and mix.exs manifests with :file.consult/1 or default Code.string_to_quoted/2, untrusted strings turn into permanent atoms.

It's easy to cherry-pick a demo project with three unused HTTP adapters where noise drops by 80%. On umbrella repos and adapter-heavy services, that really happens.

To keep myself honest, the repository includes a reproducible harness (benchmarks/validate_real_world.exs) running against six pinned projects (phoenix_bandit, plug_cowboy_multipart, tesla_mint_hackney, a 3-app Mix umbrella umbrella_three_apps, a pure Erlang rebar3_hackney app, and bandit_tesla_gateway) and a frozen advisory bundle totaling 127 matched findings. Every (project, CVE) pair was manually labeled against the dependency source code at the pinned lockfile version to record whether the vulnerable routine can actually run.

The number that matters most is FN = 0 (100.0% recall): not a single reachable vulnerability was misclassified as UNREACHABLE. CI runs this harness on every push and fails if FN > 0 or if any project's noise-reduction floor shifts unexpectedly.
