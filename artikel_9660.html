Detecting Flaky Tests and Finding Their Root Causes with Strands Agents and Gemini

Tanggal: 2026-11-10

A few years ago (three years at most), one of the biggest challenges QA Engineers faced was: how do we convince the business and the team that we should invest in automated tests? Today, with AI, this issue has been mostly solved. We don't spend much time coding automated tests because we have AI to do it for us, but a new challenge appears: flaky tests. In this article, I will explain what a flaky test is, how I built a tool to help identify them, and how I used AI to run a first analysis.

Before going into more detail about the solution, let's understand what a flaky test is and why we should worry about it.

In a few words, a flaky test is an automated test that produces both passing and failing results without any change to the code or to the test itself.

If they pass, why should we monitor them? In the end, they pass.

That may be your first thought, but once you understand what a flaky test is, you see that in big projects it can hurt the team's trust in their own product and tests, real failures start being ignored, and the CI time and cost per pipeline go up.

Based on these concerns, I developed this project. The code is available on GitHub: flaky-test-detector.

Let's understand how the project scores and ranks the flaky tests. It starts by receiving a JUnit report in XML format (a standard output of most test frameworks, with one per executed test), and parsers.py is responsible for parsing the information in this file into the proper format:

If the file isn't a valid JUnit XML, an exception is raised; if it is valid, the parsing proceeds. When scoring.py is called, it uses the FlakinessScorer class, which is responsible for taking the TestResult objects and turning them into TestScore objects. Each result is grouped by test name and then by commit, and for each (test, commit) pair the scorer checks the outcome. It ignores:

Both failed and error count as a failure.

The script marks a test as flaky when, for the same commit, the outcomes are both {True, False}: the test failed and passed with the same code base. It then generates the data that the Ranker needs, in the following format:

When the FlakinessRanker class is called, it uses this data to rank the tests. It only considers tests with data from at least 5 commits (min_commits), so the score can be trusted, and it flags a test as flaky when its score is 0.1 or higher (threshold). Both values can be changed:

The score is the total of flaky_commits (the number of commits where the same test passed and failed) divided by the total of commits available for that test in the pipeline.

Ok, now it is possible to identify flaky tests and even analyze them. What can I do with this? First, you can start implementing it in your team. Monitoring your tests and flagging the flaky ones can help you improve the team's trust in what they are building, reduce CI costs, and avoid real bugs being ignored because the test passes on the second or third execution.

When should you run this? It depends on how your team works:

Flaky tests are not just an annoyance: they erode the team's trust in the tests and hide real failures. Measuring them is the first step to dealing with them, and a simple score per test and commit is enough to get started. The AI analysis gives you a first look at the possible root causes, but it doesn't replace a human reviewing the results, since failures caused by the infrastructure can also look like flakiness. Give it a try and see how your own pipeline behaves!
