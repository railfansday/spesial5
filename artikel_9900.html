Functional programming languages place a lot of emphasis on pure functions that are free of side effects. There's no question that such functions are easier to reason about, debug, and even optimize (by memoization). That said, the real world is messy and sometimes side effects are inescapable; monads help encapsulate side effects in functional programs.

The core idea is: side effects are encapsulated inside a Monad, which wraps the value returned from a computation. The bind method (or the equivalent >>= operator) lets us take a wrapped value and push it into the next computation in the sequence. This may look familiar from continuation-passing style (CPS). Continuations themselves can also be modeled with a monad [2].

Chaining multiple binds together is essentially a sequence of computations while keeping track of the side effects. A monad decouples what computations do from how they are sequenced. The programmer describes the sequence of computations and their dependencies, while the monad's bind implementation handles the bookkeeping necessary to combine their side effects.

In a language with mutable state, modeling side effects is easy - just assign some state (like a struct field or class member). In a functional language like Lean, however, we have to carry this state across the computations explicitly; monads help us do this with elegance - by hiding most of the mechanics of actually carrying the state around, the majority of the code remains free of bookkeeping.

Just like in Haskell, monads in Lean should obey certain laws. Those are:

Left identity: wrapping a value in pure and immediately passing it to f with bind should be equivalent to just calling f on the value:

Right identity: extracting a value from a computation and immediately wrapping it with pure again should not change the computation:

Associativity: the grouping of operations doesn't matter, as long as their order remains the same:

For left identity, pure v is some v and the bind implementation matches some x to next x, which is equivalent to f v.

For right identity, m >>= pure just rewraps a some value in pure, leaving none alone - this is equivalent to keeping things as they are.

For associativity, if m is none then both sides are none. If m is some v, the left side is f v >>= g, and the right side reduces to the same, so again they are equivalent.

While Lean doesn't enforce that a Monad instance obeys these laws, it has a separate type class called LawfulMonad which does require Lean proofs; this is useful for Lean's main use case - proving theorems about programs, expressed through its powerful type system.
