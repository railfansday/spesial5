Whisper turbo vs. medium on Arm and CUDA: The Faster Model Still Flipped Between CPU and GPU

Tanggal: 2026-11-18

Posted on Nov 18 • Edited on Nov 18 • Originally published at zenn.dev • AI-assisted

whisper.cpp v1.9.5, one recording, four builds (x86 CPU, Intel iGPU, Arm CPU, RTX Spark CUDA): medium was faster on both CPUs, turbo was faster or tied on both GPUs, and the per-phase timings had the same shape on all four.

This is an English adaptation of an article I originally published in Japanese on Zenn: whisper の turbo と medium、Arm の CPU と CUDA でも速い順は入れ替わった. The measurements and conclusions are mine; I used an AI tool to help translate and restructure the text, and I checked the numbers against the original.

Short version: on an x86 CPU and an Arm CPU, medium was faster than large-v3-turbo; on two different GPUs, turbo was faster (or tied in total), and the per-phase timings explained the flip the same way on all four.

This continues an earlier article (in Japanese): whisper の turbo と medium、速いほうが CPU と内蔵 GPU で入れ替わった. That one covers the method (same recording, same arguments, each condition run 5 times in a row with the first run discarded) and how to read the phase timings. There, on one PC, medium was faster on the CPU and turbo was faster on the integrated GPU. This time I added a second PC with a different CPU architecture and a different GPU family.

whisper.cpp at v1.9.5 on both machines, same recording, same arguments. Average of runs 2–5, in ms.

The previous comparison was within one PC, so I couldn't tell whether the explanation "where the encoder is heavy, the model with the smaller encoder wins" was specific to that PC. The same direction showed up on a CPU with a different instruction set and on a different family of GPU, so the explanation now covers a little more ground.

Both machines used the same recording (Japanese speech recorded with the watch's microphone, 6.635 s, 16kHz, mono, 16-bit) and the same arguments:

At first I built the Arm CPU version with MSVC. These are its numbers:

6.6 seconds of audio took 84 seconds. One line of system_info shows why:

With the MSVC I used, the list of predefined macros (cl /PD) had no __ARM_NEON. ggml's CPU backend switches code paths on whether __ARM_NEON is defined, so an MSVC build runs matrix multiplication and the like in generic C code. When I tried to work around it by passing /D__ARM_NEON=1 from outside, compilation failed in the NEON helper functions. (At least in v1.9.5, that means ggml's NEON path can't be used with MSVC.)

The whisper.cpp repository has a clang toolchain file for Windows on Arm, and specifying it gave NEON = 1. Other things I tried on the MSVC build, such as turning off flash attention or enabling llamafile's sgemm, made no difference.

Look at system_info before measuring speed. That's all it is, but if I had only looked at the totals, I would have stopped at "the Arm CPU is slow." As far as I found, when building this kind of library on Windows on Arm, the choice of compiler seems to make an order-of-magnitude difference.

From the phase timings whisper.cpp prints on exit, I took the encoder (encode) and the decoder side (batchd) and lined up turbo minus medium. Positive means turbo loses; negative means turbo gains.

turbo is large-v3 with the decoder cut from 32 layers to 4. The encoder stays the same as large-v3: 32 layers, 1280 dimensions (medium has 24 layers, 1024 dimensions). So turbo gains on the decoder side and loses in the encoder. Which of the two is larger flips with the environment.

On the CPUs the encoder loss is large. On the GPUs the encoder gap shrinks, so the decoder gain wins. On CUDA the encoder gap was down to 24ms, and the cost of turbo's larger encoder was barely visible.

On CUDA, 1,118ms of turbo's 1,537ms total is loading; only 419ms is computation. Re-ranked with loading excluded:

Both the integrated GPU, which looked like a tie in total, and CUDA, where loading is most of the time, show a clear order once loading is taken out. It also means the same models can rank differently depending on how you run them: starting a process every time (CLI) versus keeping one running and sending requests to it (resident server).

I also measured the round trip of sending the same recording over HTTP to a resident server. Loading then happens only once, at startup.

As a resident server, turbo was faster on both GPUs. Compared with the integrated GPU, CUDA returned in roughly a quarter of the time for turbo and roughly half for medium. Note that whisper-server defaults to greedy decoding when nothing is specified, while whisper-cli defaults to beam search with width 5: the defaults are opposite. (Last time, this left my conditions mismatched.)

As a third model, I measured turbo's q5_0 (quantized) version under the same conditions.

whisper.cpp sees 20 threads on the Arm PC (n_threads = 8 / 20 in the output), so I measured both -t 8 and -t 20.

Every total went down, but not evenly inside. The encoder is one call that passes the whole audio through at once, so it shrinks cleanly. The decoder side is more than 160 small calls, so it shrinks less, and for medium it actually grew. More threads don't make everything uniformly faster; that's what this table supports.

On variance: turbo fp16 at -t 20 ranged from 10,294 to 11,674ms (13%) even across runs 2–5, wider than the other conditions (a few %). If you measure only the total once and compare, any difference smaller than that spread disappears.
