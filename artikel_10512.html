Power BI MCP server: how to brief an AI agent to build accurate measures

Tanggal: 2026-11-21

Stay up to date with AI tools, model releases, and developer workflows that matter.

Power BI, Microsoft's reporting and dashboard tool, now lets an AI agent work on the data model behind a report. If you ask one to add a year-on-year revenue measure (a measure is Power BI's name for a saved calculation) with Microsoft's MCP server connected, it can write the formula and save it to the model without you opening the formula bar. When we tried this on a sample model, an agent inspected the model, wrote the measure, tested it and saved it in under four minutes.

The agent did a careful job, but its formula didn't follow the same rules the finance team uses to count revenue. Nobody had told it what "revenue" meant in this business, so it had to decide for itself. We then gave another agent a short brief that set out finance's rules for what counts as revenue and which date to count it by. The agent wrote the formula from those rules, and the result matched finance's figure exactly. The two results show how much difference it makes in how you brief an AI agent to build accurate measures.

We wanted to find out what an agent can see in a Power BI model and how to brief it so the measure matches the business's own definitions, with the setup arranged so that every change can be checked. Developers will know the principle from agents that write SQL or API code, where the brief ends up doing the job of a specification.

Because MCP (Model Context Protocol) is an open standard, the same server can be used from different AI clients, GitHub Copilot in VS Code and Claude among them, although some clients need extra sign-in setup for the hosted version.

Power BI has two current MCP servers, plus an older one, the Power BI Consumption MCP server, kept for existing integrations. The first of the current pair is the Power BI Authoring MCP server, which you may still see under the name of its package, powerbi-modeling-mcp. It lets an agent create and change the objects inside a semantic model, which is the layer of a Power BI report that holds the tables, the relationships between them and the calculations, kept separate from the charts on the page. It comes in two forms. The hosted version, still in preview, needs nothing installed. The local version is generally available and runs on your own machine, which makes it the one to use when the model is a file you hold yourself, whether that's open in Power BI Desktop, the free Windows app used to build reports, or saved as a project folder. Macs aren't supported by the local version, so on a Mac it has to be the hosted one, which works only with models published to Microsoft's cloud (a Fabric workspace).

The second is the Fabric IQ MCP server. Fabric IQ is part of Microsoft Fabric, the wider data platform that Power BI now sits within. It gives an agent read-only tools for finding published reports and models and running queries against them, within the permissions already set, so the agent can answer questions about the data but can't change a model.

Which one to use follows from the job. Anything that changes a model goes through the authoring server, whether that's a new measure, a relationship or a set of descriptions, and it has to be the local version if the model is a Desktop file or a project folder under source control. Fabric IQ is for agents that only need answers from models other people maintain.

An agent connected to a semantic model can see its metadata (table and column names, data types, relationships, existing measures and any descriptions someone has written) and can run queries against the data. Everything it produces is inferred from those clues. A model that has served a business for years carries names that made perfect sense to the people who built it, and a column called Amt on a table called Sales_v2 tells an agent far less than it tells them.

Names carry a lot of the meaning. A column called Amount could hold the value with VAT (the UK's sales tax) or without, before credit notes or after, and an agent asked for "revenue" has to pick one. If the model holds several revenue measures built for different reports, the agent has to choose between them, and the one it picks may have been built for a different purpose.

The formulas depend on context as well. Power BI measures use a syntax of their own called DAX, which stands for Data Analysis Expressions. A DAX result shifts with whatever the person viewing the report has filtered or clicked on, which is known as filter context. A developer might think of a measure as a function that reads implicit state set by its caller. The same measure can be right as a single total on a card and need different handling once it's split by product in a table or filtered by a date slicer (the on-page date filter), depending on how CALCULATE (the DAX function that changes which filters apply) is used. Which behaviour is correct depends on how the business wants the number to respond, and that's something the agent has to be told.

Relationships work the same way. Plenty of models have more than one date column on the sales table, say order date and dispatch date, with only one relationship active at a time. A DAX measure uses the active relationship unless it's written to switch to the other one, and the agent has no way of knowing which date your monthly reporting runs on unless something tells it.

In each case the agent can write a valid measure. Which of two valid measures matches the business's own definition is the part it can't see from the model.

To see this in practice, we built a small sales model in a Power BI Desktop file, working through the server itself, with invented data: 5,266 order lines, with order dates from January 2025 to October 2026. We gave the Sales table an Amt column holding each line's value after discount with 20% VAT added, next to LineTotal and Discount columns that excluded VAT, and an existing [Revenue] measure that summed Amt. There were two date columns, with the active relationship to the Date table on dispatch date and the order date relationship inactive. Orders stop at the end of October 2026, which made the current year a part year, a deliberate test. Nothing in the model had a description. In this made-up business, finance reports revenue net of VAT and discounts, by order date.

On 12 November 2026 we connected an AI agent (Anthropic's Claude Fable 5.2) to version 1.0.1 of the local server through a small Node.js script that speaks MCP over stdio. In all three runs the agent had the server's tools only, without Microsoft's powerbi-authoring plugin, which adds modelling guidance on top of them. It was also told that nobody was available to answer questions, so each measure was saved exactly as the agent wrote it, with no review in between. The first prompt was one sentence: "Add a year-on-year revenue measure."

Before writing anything, the agent listed the tables, relationships and columns, read the existing measure, sampled some rows and checked the date ranges. It worked out for itself that 2026 was a part year and limited the comparison to the same dates in 2025, which avoided a misleading result of -6.7%. From 15 sample rows it also spotted that Amt looked like the net figure plus 20%.

It returned growth of 21.5% for 2026, which is correct for revenue counted by dispatch date. On finance's definition, by order date, the answer is 18.6%, and the whole difference came from that choice of date. The VAT question made no difference to a percentage, because Amt was already net of discount and every line carried the same rate, although it would have overstated any figure in pounds by 20%.

We reset the model and repeated the run with a fresh agent, which made the same two choices and returned the same 21.5%. Both choices were reasonable readings of the model as it stood, and the DAX was sound. In their reports, both agents flagged the date basis and the VAT treatment as open questions, and both worked out that an order-date basis would give 18.6%. That's what a good analyst would do, and with those two answers they would have had everything they needed.

Think of a capable analyst on their first morning, someone who knows DAX well but has never seen your business before and knows nothing (or not a lot) about it. You wouldn't say "add a revenue measure" and walk off. You'd tell them which table holds the trusted figures, whether revenue includes VAT, which date drives the reporting calendar, and what they shouldn't touch. An agent needs that briefing for the same reasons, and getting good work out of it draws on the skills you'd use with any new starter. Developers do the same thing when they write a good ticket. A request for a measure is a requirement, and it needs the same definitions and constraints, plus a way to check the result.

Before you send a prompt, ask yourself whether you could do the task properly if you were given only the words in that prompt and the model itself. If the answer is no, then the agent is in the same position, and it will make its own assumptions.

The final line of the brief, asking to see the DAX before anything is saved, is there so that a person can see choices like that. In the test we approved that step in advance, to keep the run unattended.

One detail needs adjusting before this measure is reused on other data. Its guard checks that each comparison period starts on or after the first order date, which works here because the sample data has an order on 1 January 2025. When we swapped that date for 2 January 2025 in a copy of the measure, January 2026 and the 2026 row came back blank. Comparing against the first date in the Date table, as the first agent's measure did, brought the 2026 figure back, since the Date table starts on 1 January. That version doesn't confirm that sales exist for the whole comparison period, though, so the right check depends on whether the business wants growth shown only where a complete prior period exists. That's a decision for whoever reviews the measure.

We ran the one-sentence prompt twice and the detailed brief once, all with the same AI model and one small set of data, which is enough to illustrate the pattern but too little to say how often it happens.

Good briefs help, but you'll be writing the same definitions into prompts again and again unless they live in the model itself. Descriptions on tables, columns and measures are part of the metadata the agent reads, so filling them in is one of the cheapest ways to put business definitions in front of it every time. In our test, where nothing had a description, both agents given the one-sentence prompt noted that nothing confirmed what Amt contained. A description such as "Net sales value in GBP, excluding VAT, after credit notes" stays in the model, where the agent reads it without anyone retyping it.

Naming deserves the same attention. Spelling out abbreviated column names, hiding technical keys that no report needs, gathering measures into a single measures table, and removing measures that are no longer used all give the agent fewer things to choose between. These are the same habits that make a model easier for a new colleague to pick up, so asking someone outside the team to find a figure in it is a fair test of the result.

Microsoft has also added a set of Prep data for AI features (in preview) to Power BI Desktop and the service. They let you choose which fields Copilot, Microsoft's AI assistant, should consider and write AI instructions that explain your business terms, with verified answers available for common questions. They're aimed at Copilot, but deciding and writing down your definitions is the same work whichever AI tool reads them.

An agent working through the authoring server has the same access as the person signed in, so anything that person can change, the agent can change. Sign in with an account that has no more access than the job needs, and take a copy of the model first, as you would before any bulk edit.

Start with read-only mode. The local server takes a --readonly flag that blocks all write operations, which is the right setting while you're learning how the agent behaves on your models. When we tried to create a measure in this mode, the server refused and said it was running read-only. You'll need Node.js installed for the npx command. The server won't run other tools until its licence terms (the EULA) have been accepted. Once you've read them, you can either tell the agent to accept for you or add --accepteula to the args list.

The --readonly flag belongs to the local server. On a Mac the route is the hosted server and a copy of the model in a Fabric workspace, once a Fabric administrator has switched on the tenant setting that allows the MCP endpoint, and there the copy is the safeguard. For an enforced limit, sign in with an account that holds only Build permission on the model, which lets the agent read and query it and nothing more.

Read-write is the default, so check how confirmation behaves in the version you install. Version 1.0.1 skips confirmation prompts by default, which the project's README hasn't caught up with, and has a --require-confirmation flag to turn them on. The flag is listed in the server's own --help output. In our runs every edit went through without a prompt. When we added the flag to the args list, the server asked for confirmation before the first write, with a message beginning "Are you sure you want to perform operations that will modify your database", and answering no blocked the change.

Version control is the other safeguard. Saved in the Power BI Project format (PBIP), a report and its model become folders of text files instead of one binary .pbix file. Commit those before the agent starts and its work arrives as an ordinary diff, which you can review and revert like any other change.

Whatever the agent reads, including table and column names and the rows returned by any query, is passed on to the AI provider behind your client, which may sit outside Microsoft's compliance commitments. For a model holding customer or payroll data, check that the provider is approved under your data policies before you connect.

An agent can draft and test a measure in minutes, and someone still has to read what comes back. For a developer new to Power BI, that takes enough DAX to see what a measure's filters will do in a table broken down by month or product, and enough knowledge of the business to confirm the agent used the right column and the right date. Writing the brief takes the same knowledge. Ours could only have come from someone who knew the model had an inactive relationship and which columns carried VAT.

These are data modelling and DAX skills, which many learners find the hardest part of Power BI. If the person reviewing agent output hasn't had that grounding yet, it helps to know how to judge whether a Power BI course covers enough DAX and data modelling, because courses vary a great deal in how much time they give to those two subjects compared with building charts.

Take a copy of a model you know well and connect the local server to it in read-only mode. Ask the agent to describe every table and measure in its own words, then check those descriptions against what you know the model does. Wherever the two differ, the model needs a clearer name or a written description, and the corrected text can go straight into the description fields. With those in place before you allow any writes, the agent starts its first real task with the same definitions your finance team uses.
