"Do you know the closest ATM?" and "I was charged twice, the refund never arrived, and now my card is blocked" are both customer messages. Most AI apps send both to the same large model and pay large-model prices for each one.

Model routing fixes that. A router looks at each request and sends it to the cheapest model that can handle it, and keeps the expensive model for the requests that need it.

In this guide we'll cover what model routing is, how routers decide, and what it saves. Then we'll build a small router in about 60 lines of JavaScript and run it over 200 customer messages. At one setting it matched a large model's accuracy for about a third of the cost. At another it came within a point and a half for 89% less.

Model routing in AI is the practice of sending each request to the model best suited to it, instead of sending every request to one model. A router sits between your app and a pool of models, reads each request, and picks a model based on what you care about: cost, speed, or quality.

You'll also see it called AI model routing, LLM routing, or LLM model routing. They all mean the same thing. The pool might be a small and a large model from one provider, or models from several providers behind one API.

The idea rests on one observation: most requests are easy. A small model answers them as well as a large one, in a fraction of the time and for a fraction of the price. The router's whole job is finding the hard ones.

Model routing works in three steps: the router reads the request, decides which model should answer it, and forwards the request to that model. The middle step is where routers differ. Routing tools decide which model to use in one of four ways.

Rule-based routing uses rules you write by hand. Requests from free-plan users go to a small model. Anything tagged as code goes to a coding model. Prompts over a certain length go to a model with a bigger context window. It's simple, predictable, and free to run, but the rules only know what you thought of in advance.

Intelligent model routing uses a model to make the decision. A small, fast classifier reads each request and predicts which model in the pool will answer it well. You'll also see it called smart or dynamic model routing.

Two more terms come up here. Task-aware routing picks a model by the kind of job, like summarising, coding, or answering a support question. Context-aware routing also looks at what surrounds the request, like the conversation so far, the user, or the tools available.

The big platforms work this way. Microsoft describes its Foundry model router as "a trained language model" that picks a model for each prompt in real time. Google says Gemini Notebook uses its new Decisions API as a real-time router, serving everyday queries with up to 40% lower latency. I've tested the Google Decisions API against Jev on the same messages we'll use below.

Cascade routing tries the cheapest model first and only moves up when the answer isn't good enough. The usual test is confidence: if the cheap model is sure, keep its answer. If it isn't, send the request to a stronger model. It's also called confidence-based routing, and it's what we'll build below.

A cascade needs no separate classifier, because the first model's own confidence does the routing. The trade-off is that escalated requests pay for two models and wait for both.

Fallback routing is about staying up, not saving money. If a model times out, hits a rate limit, or its provider has an outage, the router sends the request to the next model on a list. Most production routers combine fallbacks with one of the three methods above.

The main benefits of model routing in AI systems are lower cost, faster responses, and fewer outages, without giving up quality on the hard requests.

A note on method: I ran every message through both models once and saved the answers, then replayed the router over them at each threshold. That's how you compare thresholds without paying for the same test four times.

Then I ran the router live to check. At 0.95 it scored the same 95.0% and sent 61 messages to Opus. At 0.8 it scored 93.5% and sent 20, a point under the replay. Two answers moved: one of Jev's confidence scores landed at 0.82 instead of 0.78, just over the line, and Opus changed its answer on one message. Scores near the threshold shift a little between runs, so leave yourself a margin.

The choice of cheap model matters less than you'd think. With Google's Gemini Decision 1 in first place instead of Jev, a 0.7 threshold reached the same 95% for US$0.28 per 1,000 messages.

Model routing can cost a little quality, and the threshold decides how much. In our test the gap to Opus ranged from nothing at 0.95 to two points at 0.7.

The loss comes from one place: answers the cheap model got wrong while feeling sure. At the 0.8 threshold, Jev kept five wrong answers because its confidence was above the line. Opus got four of those five wrong as well, so only one was a real loss: "Do all ATMs take this card?", which Jev filed under card acceptance with a confidence of 0.91.

Escalating isn't risk-free either. On one message, Jev had the right label with a confidence of 0.44, and Opus overruled it with the wrong one.

Several inference providers have multi-model routing built in, and most AI gateway platforms support model routing too, so you don't have to write your own. As of November 2026, these are the top model routing solutions for AI apps. Each name links to the tool's model routing docs:

Hosted model routing platforms for large language models decide for you, which is the fastest way to start. A hand-built router like ours takes more work, but you choose the signal and you can see why every request went where it did.

An LLM router is the component that does model routing for large language models. It can be a function in your own code, like the one in this guide, a hosted model such as Microsoft Foundry's model router, or a feature of an AI gateway.

Smart model routing is another name for intelligent model routing: a model, not a hand-written rule, decides where each request goes. Dynamic model routing means the same thing.

The ROI of AI model routing depends on how much of your traffic a cheaper model can handle. In our test, a 0.8 threshold kept 89.5% of messages on the cheap model and cut the cost per 1,000 messages from US$1.96 to US$0.22, for about a point of accuracy. The build was about 60 lines of code.

OpenRouter's auto model routing works through its Auto Router. You set the model to openrouter/auto, and a decision model picks a model and a reasoning effort for each request. You pay the standard rate of whichever model it selects, with no extra fee.

OpenClaw model routing is a primary model plus an ordered list of fallbacks. In the OpenClaw model routing configuration you set agents.defaults.model.primary and agents.defaults.model.fallbacks, and an agent can override the fallback list. When a model fails, OpenClaw first rotates auth profiles on the same provider, then moves to the next model on the list, as its model failover docs describe. That makes it fallback routing, not cost-based routing.

An AI gateway simplifies model routing by putting every model behind one API, one set of keys, and one place for logs. Your app calls the gateway, and the routing rules live in config instead of code, so changing a model doesn't need a deploy.

Mid-stream failover is when a router switches models after a streamed response has already started, because the first model failed partway through. It's the hardest kind of failover, because the user has already seen part of an answer. Many routers only fail over before the first token arrives and return an error after that, so check what your gateway does.
