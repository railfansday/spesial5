From a security point of view, was fetching an unused dependency a potential attack vector? (like changing global state even without calling exported functions or using global data).

I don't know Rust enough to be sure but I don't think so. It only affect the package manager and not the compiler.

There is a risk in Cargo from unused dependencies - Cargo has a build graph based on the declared dependencies in Cargo.toml, and chooses what build steps to run based on that graph. One thing a crate can contain is a build script - which is code that's built and run on the build host at the time of compilation, and can do anything that code running as part of the build system can do.

In theory, an unused dependency can contain a build.rs that's got a security-relevant bug in it; that would then cause a security issue on the build host if you built the unused dependency. Removing it means that's not a problem :-)

Nobody in their right mind is going to write >::into(foo) or >::from(foo). (Those latter syntaxes exist to disambiguate the case where multiple traits define from() or into() methods or associated functions, or where Foo and Bar have inherent implementations of those methods or associated functions. But From and Into are well-known stdlib traits, so such a collision is unlikely in practice. It would be more plausible with more obscure traits, and fully qualified syntax is commonly used in macros because you can't know ahead of time that a collision is impossible.)

The shadowing feature for variables looks to me a bad practice. It should be: one variable name, one usage.

Here's an example from my coding today, to illustrate why shadowing helps prevent errors.

I got annoyed that Rust wouldn't let me do some things that I could have done in C.

BTW, Rust is really good at forcing a good internal architecture, having a tree of values instead of a sea of objects. I sometimes say A DAG of components instead of a spaghetti architecture.

E.g., in a protocol that allows different nodes to publish and re-publish data-objects (a common pattern in networking); - given a neighbour, you must be able to retrieve the subset of data-objects which were received from it (e.g., so you can clean up data-objects if a neighbour goes away, etc.) - given a data-object, you must be able to retrieve the subset of neighbours you received the data-object from - independently of any neighbours, you must be able to retrieve the set of all data-objects (data-objects can have lifetimes independent of neighbours) One approach is to directly cross-link the data structures that represent neighbours and data-objects, so you can always do the necessary walk (even if inefficient), as long as you maintain at least one general index of all neighbours, and/or of all data-objects. However, you can not do this in safe Rust. Another approach is to maintain multiple indexes. E.g., a set data-structure for all neighbours, a set data-structure for all data-objects, a map of lists for neighbour->list of data-objects, a map of lists for data-object -> list of neighbours. AFAIK, you can't do this in safe Rust either - even assuming you have safe sets, lists, maps [and allowing those to use unsafe internally] from your library. You can't share mutable references between indices, so you either need to unsafely store mutable references (but then why Rust?) or do a temporary remove-modify-reinsert for all indices plus an unsafe cast to mutable to modify either a neighbour or data-object. Or you do what (AFAICT) nearly all long-lived, safe, Rust code does that has to manage non-trivial relations between objects that are simply intrinsic to /many/ problem domains: use reference-counting (but.... then why Rust?).
