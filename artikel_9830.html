SealedBench: A Protocol for Freezing AI Benchmarks Before the Questions Are Known

Tanggal: 2026-11-08

A frozen model manifest, a generator sealed with drand, and an Arweave record anyone can use to rebuild the exam and check its scores.

On 2026-10-17, a bundle carrying my encrypted generator reached an Arweave block. The generator was sealed to a drand round that had not been published yet. I wrote that program, so I knew it would produce integer word problems, short Python programs, and shortest-path questions. I did not know which ones. The questions depended on a beacon the drand network would publish later, at round 33170212, on 2026-10-18T09:00:00Z.

When the round arrived, the same beacon value unlocked the program and seeded it. Four open-weight models answered 360 completions each: 240 on newly generated questions and 120 on a frozen set of public GSM8K items.

But the first two batches I ran should not be cited, and it is worth saying why, because the reason is the most useful thing in this article.

The first batch, b1, was valid under its own release record. Its manifest bound the ciphertext with a SHA-256 hash, but it never bound the ciphertext's transaction ID. Calling that check a pass would be a mistake, and it is WEAK. The v2 protocol exists partly to close that gap.

The second batch, b2, fixed the binding and then failed on the grader. The rule I sealed said an integer answer counts only when the last line is #### followed by nothing but the number. llama.cpp writes its end-of-text marker onto that same line, as #### 392 [end of text]. The registered grader threw the whole line away. Most of b2's arithmetic and GSM8K scores measure that rejection, not the rate at which models produced correct integers.

The ciphertext was already sealed by then, and the grader could not be changed in place. That constraint is the entire point of the protocol, and it applies to me too. So I made b3: a new commitment, sealed before its own round, with the normalization written into the scorer the manifest hashes.

So if you want a number from this project, take one from b3, and take the registered primary accuracy, which counts an answer as wrong when it cannot be parsed and wrong when the output was truncated. Its index transaction is vlVlUfyBn4IUmbXjkSX8079QuySP-Qqr8rN8TbivzTg. That index was published after the run. It is a convenient entry point, not evidence: the evidence that the generator existed before the round is the earlier ciphertext and manifest.

Public benchmarks leak. Once the questions are online, a high score may only mean the model has seen them.

A private test set looks like the fix, but it hands the same power to one person: whoever writes, stores, selects and reports the questions. That person includes the evaluator, which is me. If I can see the scores and then quietly change the seed, the prompt, the model file, or simply decide which batch to tell you about, I can aim the headline wherever I want.

SealedBench tries to pin all of that down in advance. The generator, the model hashes, the prompts, the runtime settings and the scoring code are bound to one future beacon round. Unless drand's operators reach a threshold and collude to compute that round early, I cannot read the beacon before it is published. If the network stops, the batch never opens; that is the other half of the bargain. After the round, anyone can rebuild the questions from the Arweave record and re-score the answers I published.

Here is every move I could make, and what I gave up in advance to make it visible.

Ciphertext and manifest on Arweave before the round

The manifest freezes the drand chain hash and public key, the release round, the seed rule, a SHA-256 for every GGUF, the llama.cpp commit and build flags, the prompts, the decoding settings, the grader and the reporting policy. Every batch uses quicknet chain 52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971, genesis at unix 1692803367, period 3 seconds.

The generator is sealed to that round with drand time-lock encryption (tlock). The ciphertext and the manifest go up through the Turbo bundler. A receipt is not a commitment. The commitment is the L1 block.

Under the v2 rule a batch is valid only if the block holding its bundle is timestamped no later than unlock_unix − 600, the bundle ID appears in that block, and the data item's bytes hash to the committed SHA-256. Height, timestamp and block hash must agree on two independent gateways, and my own gateway ario.zigza.xyz does not count as either one. b1 used an earlier, simpler rule: manifest and ciphertext had to be in an L1 block before the release round, and a miss made the batch invalid, which I would still have had to report.

After the round, the beacon signature is checked against quicknet's fixed public key. The same beacon both decrypts the generator and enters the seed. One value doing two jobs is not two independent draws, and I do not claim otherwise.

b1's seed is a SHA-256 over a domain string, the chain hash, the round in decimal and the beacon randomness, with hex fields lowercased first. The exact sentence is in b1's manifest. v2 batches add a 32-byte secret stored inside the ciphertext, and hash length-prefixed fields: domain, chain hash, round, signature bytes and that secret. The JSON randomness field is not an input; it must still equal the SHA-256 of the signature. I chose the secret. It does not let me list the questions before the beacon exists. A successful tle -d only shows the ciphertext opens under the signature it was sealed to. The BLS check against the fixed public key is a separate step.

There is one specific gap in v1 worth naming. The November capsule cap and b1 share the same plaintext tarball, SHA-256 e054f1ab7824fde33e6ac399252098cf25c29815ff4ffacabbd311da05eac9c2. Once b1 opened, that program was public. Until 2026-11-15 the unknown is the beacon, not the program. v2 still hides its questions, because the secret sits inside the ciphertext.

Every family has a program for an oracle, so grading is code and not a judge model. arith_word produces two-to-five-step integer word problems; the oracle is a function of the sampling parameters, and the prompt contains no answer line. code_output produces short Python programs with no imports and no input, run in an interpreter with a step budget; the oracle is their stdout. graph_path asks for the weight of a shortest path on a random connected graph with edge weights from 1 to 9, always between nodes at least two edges apart; the oracle is Dijkstra.

The entropy check ran the generator over 1000 seeds and got 1000 distinct question sets, with 128,816 distinct prompts. That shows the seed changes the questions. It does not show the families are fair, or that they look unlike anything in training data. One caveat I want on the record: that check ran with a stand-in secret, not the sealed one, so it measures the generator's spread and not the exact bytes b2 and b3 committed.

All four models are official Q8_0 GGUFs, hashed locally against the published LFS object IDs before sealing:

Falcon3-1B is weak on purpose. It is a low anchor that makes a difficulty shift easier to see.

The runtime is llama.cpp v0.7.0, commit 620d2225cc436ab0b001e3200e590e3b286ef9ab, built CPU-only with AVX-512 on a Ryzen 7 7700 in a cgroup of about six CPUs and 18 GiB. Decoding is greedy: temperature 0, top-k 1, top-p 1, min-p 0, seed 42, -t 6 -b 2048 -ub 512.

Thread count and batch size are in the manifest because they change the output bytes. Repeated runs at -t 6 were byte-identical for all four models. Dropping to -t 4 changed 2 of 10 Qwen outputs. Changing to -b 512 -ub 128 changed Qwen, Gemma and Falcon. Ministral matched in all three comparisons. After release I replayed Qwen's first ten exam items: 10/10 byte-identical on b1, 10/10 on b2, 10/10 on b3. That is one model on one machine. Generating and grading are ordinary deterministic programs. I am not claiming your GPU would produce the same bytes.

At n=80 near one half, a Wilson interval is roughly 11 points wide. A gap inside that width is the difference between two unmatched sets of questions. The fresh and public items differ in wording, length and format.

Calling that gap contamination would need a control this run does not have. One overlap should be stated plainly: Phase 1 had already run the models on GSM8K-test items 0..49, and b3's reference set covers 0..79, so the first 50 reference items were familiar ground before b3 was sealed. Nothing in this run separates that familiarity from the ordinary difficulty difference between two unmatched question sets.

The repository is https://github.com/zigengZ/sealedbench, released as v1.0.0. You need Python 3.12 and Node.js 22. Leave SEALEDBENCH_ROOT unset.

Exit code 0 is PASS, 1 is a hard failure, and 2 is UNKNOWN, INVALID or WEAK. HTTP 404, 429 and timeouts all count as UNKNOWN. The command only reads gateways; it never uploads. It checks the published bytes, the inclusion deadline, the beacon signature and the grader hash, re-scores the published outputs, then decrypts the local ciphertext and rebuilds the question files. v2 requires https://ar-io.dev and https://turbo-gateway.com to agree. https://arweave.net takes no part in this check.

On 2026-10-24 a fresh clone of the release candidate printed RESULT PASS, exit code 0, in 26.15 seconds. The registered file results/batches/b3/verify_seal.txt still ends RESULT UNKNOWN, because ar-io.dev returned HTTP 404 for the manifest that day. The later file verify_recheck_20261024.txt ends PASS. An earlier attempt the same day was UNKNOWN. I did not overwrite the registered file with the later result.

b2's registered verify_seal.txt is UNKNOWN as well: the published scores and Ministral's completions returned 404. Its dated recheck is PASS. b1 was VALID in its 2026-10-18 release record, and the ciphertext-transaction-ID check is still WEAK. A b1 recheck on 2026-10-24 was never completed. From 2026-10-24T09:19:57Z every request this host made to arweave.net came back HTTP 429, including three attempts at b1's index. I stopped and did not restart it.

drand is an assumption. A threshold of operators could collude to compute a future round early. If the network stopped, the capsules would never open.

I know the question families. I know v2's secret. The entropy check shows new seeds give new questions. It cannot show the families are fair, or that the templates are absent from training data.

Decryption does not compel me to publish model answers. Declaring batches in advance makes a missing batch visible. It does not force me to release the answers.

The gap between fresh arithmetic and GSM8K is not a contamination measurement.

b2's registered integer scores are an artifact of the end-marker rule. The post-hoc block is labelled. b3 is the correction made after registration.

Closed models are outside this protocol. I cannot see their weights or their serving stack.

Once a round is published, anyone can copy its questions. The next batch needs a new round.

Very little of the machinery here is new on its own. Commitments, beacons, encrypted test sets and generated variants all exist. What I think is new is binding them into one scheduled future release and shipping the evidence.
