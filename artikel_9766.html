osFoundry कैसे पहचानता है कि Claude Code किसी permission prompt पर रुका है?

Tanggal: 2026-11-07

जब Claude Code 2.1.303 कोई command चलाने की अनुमति माँगता है, तो वह अपने terminal में यह लिखता है। ये bytes एक असली capture से हैं, जिसे osFoundry test fixture के रूप में रखता है (resources/agent-detection/fixtures/claude.blocked.raw):

(पढ़ने में आसानी के लिए line breaks जोड़े गए हैं। असली capture में कोई line break नहीं है।)

इसमें दो चीज़ें ऐसी हैं जो सबसे सीधा detector तोड़ देती हैं। "Do" और "you" के बीच कोई space नहीं है। \x1b[5G cursor को column 5 पर ले जाता है, और "space" बस एक ऐसा cell है जिसे छुआ ही नहीं गया। और कहीं भी \n नहीं है: हर row \r और cursor-down \x1b[1B से शुरू होती है। fixture फ़ोल्डर के सभी 11 Claude Code captures (हर एक 2,099 से 7,672 bytes) में एक भी newline byte नहीं है।

osFoundry का डेस्कटॉप ऐप अपने Sessions board के हर terminal pane के लिए यह सवाल हल करता है: "क्या यह agent मेरा इंतज़ार कर रहा है?" नीचे बताया गया है कि वह क्या करता है, क्यों करता है, और एक छोटा Python supervisor है जो एक live PTY पर तीन आम तरीकों (prompt patterns, output-idle timers, process state) की तुलना करता है। इस Mac पर claude binary नहीं है, इसलिए live हिस्सा एक fake agent चलाता है जो Claude Code के prompt के शब्द और redraw करने का तरीका कॉपी करता है। fixture वाला हिस्सा असली captured bytes इस्तेमाल करता है।

जो rule सबसे पहले match होता है वही जीतता है (runtime/detect.rs में CompiledManifest::evaluate)। blocked सबसे ऊपर है, क्योंकि prompt खुला होने पर भी Claude Code के footer में "esc to interrupt" लिखा रहता है। अगर working पहले test होता, तो prompt कभी दिखता ही नहीं। जिस screen पर कोई rule match नहीं होता, उसे idle बताया जाता है, कभी blocked नहीं।

फ़ाइल के comments बताते हैं कि क्या हटाया गया और क्यों। Would you like to हटा दिया गया, क्योंकि यह Codex के prompt के शब्द हैं, और Claude के आम जवाबों में "Would you like me to…" बार-बार आता है।

runtime/mod.rs हर write पर classify करने के बजाय हर 700 ms (SWEEP_INTERVAL) पर सभी panes का एक sweep चलाता है। spinner एक सेकंड में कई बार redraw होता है, तो हर write पर classify करने का मतलब होता एक ही जवाब पाने के लिए सेकंड में सैकड़ों बार regex चलाना।

ऊपर वाले bytes की वजह से। यहाँ rules को Python में port करके हर Claude Code fixture पर दो तरीकों से चलाया गया है। पहला तरीका आख़िरी 8 KB लेता है, escape sequences हटाता है, और हर line में आख़िरी \r के बाद का text रखता है। दूसरा तरीका bytes को 32×120 के screen emulator (लगभग 100 lines, नीचे vt.py) में डालता है और rows वापस पढ़ता है।

stripped tail सारे idle सही सिर्फ़ इसलिए बताता है क्योंकि idle fallback है। उसे prompt कभी दिखता ही नहीं। \n न होने से पूरा capture एक ही "line" बन जाता है, और आख़िरी \r के बाद का text रखने से आख़िरी टुकड़े के अलावा सब फेंक दिया जाता है। उस step के बिना भी शब्द आपस में चिपके हुए निकलते हैं: Doyouwanttoproceed?।

osFoundry का code भी यही कहता है। terminal_pty.rs हर session के लिए एक vt100::Parser रखता है, और sweep सिर्फ़ screen_text() को, यानी emulated screen को, classify करता है। उसके ऊपर रखी 200 rows की history जानबूझकर बाहर रखी गई है। वहाँ का comment कहता है कि जिस prompt का user जवाब दे चुका है और जो ऊपर scroll हो चुका है, वह "would report the agent as blocked forever"।

emulator का बहुत अच्छा होना ज़रूरी नहीं। यह वाला text, \r \n \b, cursor moves (A B C D E F G H f d) और erase (J K) संभालता है, और colours, modes और OSC titles को छोड़ देता है। यह हर cell में एक character रखता है, तो कोई wide glyph एक column खिसका सकता है। पूरी rows पर चलने वाले regex को इससे फ़र्क नहीं पड़ता। यह सभी 11 captures को rules के लिए काफ़ी ठीक render करता है:

ज़्यादातर लोग सबसे पहले यही detector लिखते हैं: अगर agent ने N सेकंड तक कुछ print नहीं किया, तो शायद उसे आपकी ज़रूरत है। इसे screen rules के सामने परखने के लिए एक supervisor agent को PTY में चलाता है और हर 50 ms पर log करता है कि हर detector क्या सोचता है।

agent है fake_agent.py, एक stand-in, क्योंकि इस Mac पर कोई claude binary installed नहीं है। यह वे आदतें कॉपी करता है जो मायने रखती हैं:

यह अपनी असली state एक side file में लिखता है जिसे सिर्फ़ scorer पढ़ता है। एक bot user बनकर हर prompt का जवाब उसके आने के 3 से 8 s बाद देता है, और turn ख़त्म होने के 3 से 10 s बाद अगला task type करता है। supervisor का मुख्य हिस्सा, छोटा करके:

seed 7 के साथ एक run: 30 tasks, 10.6 मिनट, 25 permission prompts, और उन पर इंतज़ार में 144 s। Latency वह समय है जो prompt draw होने से लेकर detector के "needs you" कहने तक लगता है। Linger यह है कि जवाब देने के बाद भी detector कितनी देर तक यही कहता रहा। false alarms को episodes / कुल सेकंड के रूप में गिना गया है, और इस हिसाब से बाँटा गया है कि agent असल में क्या कर रहा था।

idle timer के लिए कोई भी threshold काम नहीं करता। परिभाषा से ही उसकी latency उसका threshold है। 5 s से कम पर यह हर silent tool call पर fire होता है। 3 s तक के हर threshold पर यह सभी 30 turn ends पर fire होता है, क्योंकि "काम ख़त्म, अगले task का इंतज़ार" उतना ही शांत है जितना "permission का इंतज़ार"। 5 s और उससे ऊपर यह ऐसे prompts चूकने लगता है जिनका जवाब किसी ने समय पर दे दिया। 8 s वाली row सभी 25 सिर्फ़ इसलिए चूकती है क्योंकि bot कभी 8 s से ज़्यादा इंतज़ार नहीं करता, लेकिन जवाब देने का समय कुछ भी हो, pattern वही रहता है: detector या तो शोर करता है या देर से आता है।

"?" पर ख़त्म होने वाली screen line हर prompt पकड़ लेती है, और असली captures पर यह perfect दिखती: सिर्फ़ चार blocked fixtures में ऐसी line है। live run में यह agent के अपने सवाल, "Would you like me to add a regression test?", पर fire होती है, और वह line अगले task तक screen पर बनी रहती है। claude.toml ने Would you like to इसी वजह से हटाया था।

stripped tail इस run में prompts इसलिए पकड़ पाता है क्योंकि fake agent ❯ 1. Yes असली spaces के साथ लिखता है। फिर जवाब के बाद भी यह औसतन 77 s तक prompt report करता रहता है, क्योंकि मिटाए गए prompt के bytes आख़िरी 8 KB में तब तक रहते हैं जब तक लगभग 8 KB नया output उन्हें बाहर न धकेल दे। spinner के 600 bytes प्रति सेकंड और बीच के silent हिस्सों के साथ इसमें काफ़ी समय लगता है। emulated screen cursor-up और erase आते ही prompt भूल जाती है।

700 ms sweep की कीमत वही है जिसकी उम्मीद होगी: एक interval तक की latency (median 0.26 s, max 0.70 s) और एक interval तक का linger। जिस badge को कोई इंसान देखता है, उसके लिए यह ठीक है।

macOS पर नहीं। supervisor ने agent के लिए सेकंड में दो बार ps -o stat=,time= sample किया:

अपने terminal पर read() में blocked process और spinner frames के बीच सो रहा process, दोनों S हैं। wchan column, जो कुछ systems पर kernel wait channel का नाम बताता है, दोनों के लिए - print करता है। CPU time से भी फ़र्क नहीं पता चलता, क्योंकि spinner का ख़र्च लगभग शून्य है। Claude Code जैसा Node-based CLI काम करते हुए भी और न करते हुए भी अपने event loop में इंतज़ार करता है, तो उसका state letter और भी कम बताएगा।

process table जिस सवाल का जवाब देती है, वह यह है कि terminal किस program के पास है। osFoundry runtime/signals.rs में tty का foreground process group (MasterPty::process_group_leader, यानी tcgetpgrp) पढ़ता है। इससे उसे पता चलता है कि pane में claude चल रहा है, भले ही उसे किसी सामान्य shell में type किया गया हो। इससे यह भी पता चलता है कि agent कब exit हो गया और shell वापस सामने आ गया, जबकि agent का आख़िरी prompt अभी भी screen पर है।

हाँ: agent से ख़ुद बताने को कहिए। runtime/signals.rs तीन sources को तौलता है। जब osFoundry ख़ुद Claude Code launch करता है, तो runtime/integrations.rs --settings के ज़रिए hooks जोड़ता है। यह flag सिर्फ़ इसी एक launch के लिए settings जोड़ता है, और user के अपने hooks भी चलते रहते हैं।

Claude Code Notification permission prompt के लिए भी fire करता है और input का एक मिनट इंतज़ार करने के बाद भी। इसलिए osf-pane notify payload पढ़ता है और permission को blocked पर और बाक़ी सबको idle पर map करता है। ACP पर (claude.toml में declare किए गए claude-agent-acp adapter के ज़रिए), session/request_permission request का मतलब है कि agent सीधे permission माँग रहा है, यह अनुमान नहीं बल्कि तथ्य है।

दिलचस्प हिस्सा signals::combine का क्रम है। screen से पढ़ा गया blocked हमेशा टिका रहता है। उसके बाद agent की ताज़ा report आती है, फिर "shell वापस सामने है", फिर बाक़ी screen rules। report पुरानी हो सकती है या मौजूद ही न हो, जैसे जब कोई hook चुपचाप fail हो जाए। screen पर दिखता prompt एक सटीक rule है और वही एक alert है जिसे कभी दबाया नहीं जाना चाहिए।

इससे दो छोटे फ़ैसले निकलते हैं। notifications पर हर session और state के लिए 30 s का cooldown है (runtime/notify.rs), क्योंकि redraw होता prompt blocked → working → blocked के बीच झूल सकता है। और कोई भी tool किसी pane में type करे, उससे पहले runtime/tools.rs पिछले sweep पर भरोसा करने के बजाय नया classify_session चलाता है। जो pane blocked है वह सिर्फ़ runtime_answer लेता है, जिसे user confirm करता है, कभी सामान्य runtime_send नहीं।

code चार छोटी फ़ाइलों में है, vt.py, rules.py, fake_agent.py और supervisor.py, साथ में tables के लिए fixtures.py और analyze.py। नतीजा जिस screen पर दिखता है, वह osFoundry डेस्कटॉप ऐप में agent sessions का Sessions board है।
