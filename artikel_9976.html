Mutex poisoning is not for everyone

Tanggal: 2026-11-19

After some recent discussion on the topic of mutex poisoning and notably a blog post that I thought was interesting, thoughtful, exhaustive, yet completely disagreed with, I wanted to comment on the debate myself. To me, poisoning-by-default is one of biggest mistakes that were made in the language, next to some others that are a story for a different time.

In short, I believe that Mutex poisoning is the wrong choice for most applications, as

In theory, a mutex guards a critical section of the code. That code changes the state of a piece of data free from interference of concurrent threads, then releases the lock. That code might then encounter an error, and release the lock in the middle of doing its important work. For example:

The following code will work fine most of the time, but if the dice roll doesn’t go our way, the always_even mutex gets unlocked in an invalid state. In Rust, today, poisoning exists to handle this. If a guard is released abnormally (while panicking), it records that this happened in a boolean. Any future calls to lock() will return Err(PoisonError), which will trigger a panic when we unwrap it. The bad state is never observed and all is well.

You might have felt that the example I made up was somewhat contrived. That’s because it is. Real cases of this pattern can and do happen, but most of the use cases that involve mutexes are much simpler. Many critical sections are no longer than a variable assignment, or doesn’t have an invalid in-between state. There are cases in lower level programming where a mutex guards a piece of data that is not directly inside it, or is outside the view of the program entirely. In fact, I’ve written a wrapper for a C library that worked like that. Though I disagree with the notion that this is the common case.

I do recommend anyone Rain’s blog on the matter, as she has some good examples of how you can cause violations of these critical sections (even without mutexes) and I wholeheartedly support the idea of a Poison wrapper for the use cases that need it. I suspect the domains she works on lend themselves more towards these issues compared to mine. Rust’s default behaviour should make the common case easy and the rare case possible.

In Rust, for most platforms, mutexes are implemented using the futex2 system call. It allows for operations to remain purely in user-space as long as the mutex in question isn’t contended, which is nice for performance reasons.

Under the hood, a mutex is a simple 32-bit integer on most platforms even though it only holds three unique values:

Flow chart showing how a mutex acquisition is implemented in Rust, using atomic operations and futex primitives. Note how the uncontended case remains entirely in user-space and does not sleep the thread.

Rust implements this with a few atomic operations and the futex_wait call. Crucially, the path for locking a mutex that isn’t contended is a single atomic operation. The only operation that requires a context switch is futex_wait.

Unlocking is even simpler. The thread that holds the mutex first releases the lock, then optionally, if there was an indication that the lock was contended, wakes any sleeping threads so they can try to acquire the lock.

Flow chart showing how a mutex release in Rust. First, we swap the current value with 0, and depending on whether it was originally 1 (simply locked) or 2 (contended), we optionally wake any sleeping threads.

As discussed in too much detail above, (un)locking mutexes is cheap as long as they’re not contended, and when contended, they are at least cheap instruction wise. This is where poisoning mutexes get you.

In short, being able to poison is a cost that is always paid, but seldom used. To start, poisoning is essentially implemented by adding an AtomicBool field to every Mutex. Due to alignment, this grows the size of every mutex by anywhere from zero bytes to an additional pointer. This isn’t terrible but for use cases where you have many mutexes guarding small objects, this can add up.

You might have spotted a load-bearing “if” already. It’s kind of hard to guarantee your code does not panic. Array indexing, integer division, and a whole host of other features might panic unexpectedly.

This is hard for experienced developers, but for those learning it’s even worse. It also trains bad habits. Every time a beginner Rust developer writes unwrap() instead of handling their errors, a puppy steps on a Lego brick. Or causes a widespread internet outage. One of the two, I forget which.

We should not want to include APIs into the standard library that return a Result that is “expected” to be unwrapped. Infallible operations should not fail.

Poisoning protects against a task panicking in the middle of an invariant violation. But why must this be specific to mutexes? The example from before works just as well with a simple mutable borrow. Panics may still happen, and you may still catch them.

This is actually a fairly common problem. In a more recent blog post, researchers at Microsoft highlight various places they’ve found where even the standard library gets this wrong.

In most cases however, this is fine, as it is with the mutex example given in the beginning. You don’t need to poison this reference. But for applications where you do, it’s kinda nice to be able to.

It’s not hard to imagine a wrapper that adds poisoning behaviour when you want to have it. Crucially, this needs to be an additive wrapper. You can add a poisoning system to something. You cannot strip out the poisoning system from a primitive that has it. Poison safety is important for the specific use cases that need it, but most do not.

I don’t believe it’s worth it to saddle mutexes in particular with this overhead when the problem is near universal with any mutable state. State invariants are just hard that way.

One might draw a comparison between poison safety and buffer safety. In Rust, we always do bounds checking, relying on the compiler to optimise it out in cases it can be proven redundant. Can’t poison safety be the same? And the answer, it turns out, is no.

The compiler cannot optimise poisoning away. It requires any mutex carry additional data to track it. Maybe the compiler can figure out one particular critical section cannot panic, and therefore it can leave out the setup and clean-up, but in general it cannot avoid checking the state. This is overhead that always applies, and hurts, especially in environments where code size is more restricted.

In C++, there are a few choices in the standard that make certain containers less efficient than they could be4. Because of how standardisation works, the containers can never be “fixed”. This causes third party implementations, such as Abseil and Boost, to become the de facto standard.

Mutexes in Rust suffer from the same problem. The standard library has poisoning, but people don’t want poisoning, so instead they opt for crates like parking_lot. I believe this is bad for the ecosystem as a whole. When the standard library offers a feature, it should be an uncontroversially good choice, unless you are doing something hyper specific. We don’t have to be “batteries included” but the parts that are there should be a good fit.
