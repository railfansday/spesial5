Running my agent's code through DigitalOcean's Action Gateway

Tanggal: 2026-11-19

I use Claude Code as my MCP client, so when DigitalOcean Managed Agents went into public preview, the part I wanted to try first was not the hosted runtime. It was Action Gateway, the piece that hands an agent tools through one MCP endpoint, because that is the part a coding agent actually touches.

Action Gateway exposes a small set of meta tools instead of its whole catalogue. action_search finds tools for a described task, action_invoke calls them, and action_code runs Python in a sandbox that can call tools itself. The docs list 16,000+ tools behind that endpoint. I connected it to Claude Code and measured what came back.

I asked for two things in one request: Droplet sizes, and regions with their availability, five results each.

Both top hits were the right tool, each with its input schema attached, so the agent can call it without guessing argument names. The whole response for ten candidates was roughly 3 KB. Lower in the list were near misses that make sense, like digitalocean_db-cluster-list-options and a Harness Runtime tool for sandbox sizes. A region tool from Daytona, a third-party provider in the catalogue, also showed up at 0.58, which shows the search covers more than DigitalOcean's own tools.

The docs say action_search carries no tool-call charge, and that is the right design for this. Searching is the step an agent repeats most, and it is the step that keeps 16,000 schemas out of the context window.

Two vCPUs, about 4 GB of memory and a lot of free disk. pip install orjson finished in 1.4 seconds, so pulling a package for one job is cheap.

Each call starts clean, as the limits page says. I wrote /tmp/marker in one call and checked for it in the next:

I also read /proc/uptime at the start of six separate calls. It said between 8.34 and 8.96 seconds every time. That is how long the VM had existed by the time my first line ran, not necessarily how long I waited, because I can't see whether a VM was prepared before my request arrived. It is consistent, though, which is what you want from something an agent calls in a loop.

My first real tool call from inside the sandbox was digitalocean_size-list. It stopped and asked for an account link, because I had not connected a DigitalOcean account to the gateway yet. The error is worth showing, trimmed of the link and code:

It came back in 102 ms. More useful than the speed is the shape: a class, a retriable flag and a recovery_hint, plus a link and a verification code for the human. An agent can stop and ask its user to authorise, instead of retrying blindly or inventing a workaround. The credential never passes through the model, which is the point of the gateway.

The limits page says code execution has a timeout that includes time spent calling other tools. I wanted a comfortable size for one call, so I ran a job that checks the machine and then sleeps for 45 seconds. It finished and returned everything it printed:

That shaped how I write action_code jobs now: short steps that each finish and return their own result, chained by the agent. A sandbox call is cheap to start, so splitting a job costs almost nothing, and every step hands back something the agent can use. Long-running work belongs in a Harness Runtime session, which is built for it, with pause, resume and fork.

I assumed the gateway's DigitalOcean tools would use the DigitalOcean API token I already had. They don't. Action Gateway uses its own OAuth connection per provider and user, which keeps each connection scoped to the person who approved it. The error message above walked me through linking it.

What impressed me most is how much I didn't have to build. One MCP connection gave my agent a tool search that found the right tool first time, a clean Linux sandbox for every run, and access to accounts without the agent ever holding the keys. That is the part of agent infrastructure I would otherwise be writing and maintaining myself, and Action Gateway handles it well.

Next I want to try the other half, Harness Runtime, and see how these sandbox numbers look when the whole agent runs inside it.
