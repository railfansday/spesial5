JetBrains finds agents may cheat with open source

Tanggal: 2026-11-25

AI coding agents caught peeking at GitHub answers, stumble when JetBrains hides the crib sheet

JetBrains has revamped a benchmark for evaluating large language models after suspecting too many agents gamed their tasks the first time round.

The company labelled this agentic practice "reward hacking" in a post summarizing the results of its revised evaluation.

Like its predecessor, Kotlin Benchmark 2.0 is a collection of tasks that evaluates how well AI coding agents work with the Kotlin programming language, in order to help Kotlin programmers decide which agent-model configurations to use. The tasks include fixing tricky problems in Kotlin code across different domains, and making corrections to multiple files.

The revised benchmark now includes 30 Kotlin multi-file code problems that have not been exposed to the public in any way before. The revised test all but guarantees that the agents have not encountered this set of problems, or potential solutions, before. Another 70 tasks are based on code that resides in public repositories.

The test also blocked all network access for the open source tasks, except for what was needed to communicate with the model itself. This minimized the possibility that the agent could look for an existing answer already posted, perhaps through a patch or pull request.

Overall, the agents were significantly less accurate when solving problems on codebases they had never encountered. Top resolution rates dropped rather suspiciously from 86.2 percent on tasks based on open source repositories to 60  percent on those based on closed source repositories.

Although the agents lacked network access, JetBrains boffins theorized that they might have benefited from encountering and internalizing these open source repositories during training. Only the private repositories were completely new to them.

Also curious was how a different set of models excelled at the closed source problems, compared to those models that usually did better on the open source tasks.

When restricted to closed source tasks, two dark horse models rose to the top: Gemini 3.8 Flash, via Antigravity CLI, topped the list with a 60  percent success rate, closely followed by DeepSeek V4.1 Flash (running on OpenCode) at 58.9 percent.

Of the two, the open weight DeepSeek was far cheaper (at $0.08 per task) than the closed weight Gemini ($1.74 per task), however.

In contrast, Opus 5.5 completed only 53.3 percent of the tasks at $1.21 per task, and Fable 5.1 completed only 44.4 percent of the tasks, at a luxurious $3.27 per task. Claude Code harnessed both of these models.

Claude’s lackluster completion rates on closed source tasks are somewhat sus given how both of these Anthropic models scored significantly higher on tasks using open source materials.

In fact Claude ran the table when it came to open source: Fable 5.1 topped the charts with 86.2 percent accuracy, closely followed by Opus 5.5 at 84.8 percent accuracy.

(Kotlin users will pay dearly for the extra sliver of Anthropic accuracy: The average cost of Fable completing a Kotlin cleanup task runs $2.38, while Opus could do the job for $0.68.)

One possible interpretation of these disparate numbers is that models are drawing from their own knowledge bases instead of reasoning from scratch. Whether this is cheating or the models simply working as intended might be more a matter of philosophical debate.

Mark Hinkle, founder of the AIE Network consultancy, suspects the issue of integrity may go deeper.

"Private code doesn't stop reward hacking, it changes the shortcut," he wrote to The Register on LinkedIn.

"On public code the agent goes and finds the answer somebody has already published. On private code there's no answer to find, so it satisfies whatever is checking it. I treat these things like entry-level employees, and a sharp new hire figures out fast what the boss actually looks at."

JetBrains did not immediately respond to a request for comment, but concluded in its post that more investigation is needed. It promises that its people will pore over the open source results to see if any have been contaminated by the LLMs' own memory. It also plans to run its own static analysis tool, Qodana, against the results to check for errors.

Sireesha Pulipati, a staff data engineer and AI observer, suggested, also by LinkedIn, that JetBrains may have needed more specificity in its agent instructions.

"Out of the box [an agent] tends to reach for generic patterns. But when we give it instructions and skills that tell it where to look for our patterns and context, it follows them. A well-controlled harness, with those standards built in, is what makes the agent useful," Pulipati wrote.

So good on JetBrains for providing Kotlin users some information about working with AI, but, as always, AI benchmarks should be approached with extreme side-eye. ®
