Slow Postgres, part 2 of 8. The SQL and raw numbers for every test are on GitHub.

Postgres guessed that 300 users live in Lisbon. There are 15,000. That one line of the plan explains the rest: a Nested Loop that ran an index lookup 15,000 times, a sort that spilled to disk, and a query that takes 159 ms with the data in memory and 2.15 seconds when it comes off disk.

Part 1 was about how the planner prices a plan. This one reads what happened when it ran, and how much EXPLAIN ANALYZE itself adds.

PostgreSQL 17.12 in Docker, on the same 4-vCPU, 8 GB cloud VM as part 1. Every user has five orders, and orders.user_id has an index. The city decides the country: 15,000 users live in Lisbon, 5,000 in Porto, and those 20,000 are all of PT. The rows come from generate_series and setseed, so yours match mine. shared_buffers is 1 GB so everything fits in memory, and JIT and parallel workers are off to keep the plans short.

The report counts orders of Lisbon users by status:

EXPLAIN prints the plan with the planner's forecast for each node, cost and rows. EXPLAIN ANALYZE runs the query and adds what happened: actual time, actual rows and loops. BUFFERS adds the pages each node touched, and PostgreSQL 18 turns it on by default with ANALYZE. The result rows are thrown away, so Execution Time leaves out sending them to the client and turning values into text (the SERIALIZE option, new in PostgreSQL 17, measures the second part).

Writes run too, so wrap them in a transaction:

ROLLBACK brought back all 149,701 pending orders, but the work still happened: the DELETE dirtied 36,469 pages that still get written to disk. Sequences don't roll back either. After a rolled-back EXPLAIN ANALYZE INSERT of 1,000 rows, the next real row got id 1001.

The report's plan, with some lines cut (the full output is in 02_plans.out):

A plan prints top-down, but rows flow bottom-up. The users scan read a million rows and kept 15,000. For each of them, the Nested Loop ran the index scan on orders. The inner Sort ordered the 75,000 orders by status, GroupAggregate collapsed them into four rows, and the top Sort ordered those.

Each node has two sets of parentheses. cost=31744.11..31747.86 rows=1500 is the forecast, in planner units that are priced in pages and don't convert to milliseconds. actual time=201.037..205.049 rows=75000 is what happened: milliseconds until the node's first row and until its last. The inner Sort's first row came at 201 ms because a sort returns nothing until it has read all its input.

Times are cumulative. The Nested Loop finished at 190 ms, 47 ms of which was the users scan, so the 15,000 index lookups took about 143 ms. To find the slow node, subtract each node's children from it and look for the biggest remainder. Buffers add up the same way.

The users scan expected 300 rows and returned 15,000. The 300 comes from pg_stats: PT is 2% of users, Lisbon is 1.5%, and the planner treats the two conditions as independent and multiplies them, 1,000,000 × 0.02 × 0.015 = 300. Every Lisbon user is also in PT, so the country condition removes nobody.

Go up one node. The Nested Loop was planned for 300 index lookups returning 1,500 orders and ran 15,000 lookups returning 75,000. The Sort above it was planned for 1,500 rows, got 75,000 and spilled to disk. So walk up from the leaves comparing the two rows= and start at the lowest node where they differ by 10x or more. Under a LIMIT a node stops early, so fewer actual rows there is expected.

Did the wrong guess hurt? Drop the redundant country = 'PT' and the planner estimates 74,999 joined rows against 75,000 actual, and switches to a Hash Join: read all five million orders once and match them against a hash of the 15,000 users. I timed both plans without EXPLAIN, with the data in three places:

In memory the plan built on the wrong guess won, 159 ms against 344, because 15,000 index lookups in RAM cost less than reading five million rows. From disk it lost, 2.15 s against 455 ms. The planner can't see what's cached, and its page costs put 15,000 scattered lookups far above one pass over the table, which is how they behaved cold. A warm EXPLAIN ANALYZE shows only one side of that trade. Where estimates come from and why they drift is part 3.

The index scan on orders says rows=5 loops=15000: the Nested Loop ran it once per user. actual time and rows are averages per loop, like the estimate next to them: 5 × 15,000 = 75,000 rows in about 0.009 × 15,000 = 135 ms, close to the 143 ms from the subtraction above.

Buffers is a total over all loops. Its 120,000 pages are 8 per lookup: three levels of the B-tree plus five heap pages for five orders spread through the table. PostgreSQL 18 adds an Index Searches line to index scans, also a total.

Per-loop averages are rounded, too. The same join, keeping only failed orders:

rows=0 doesn't mean the scan found nothing. 3,071 rows over 15,000 loops is 0.2 per loop, which PostgreSQL 17 rounds to 0 and 18 prints as rows=0.20. Rows Removed by Filter: 5 is per loop too, about 72,000 rows in all. Parallel workers count as loops: with them on, a Parallel Seq Scan on orders showed rows=1666667 loops=3, the leader and two workers.

In the report, Rows Removed by Filter: 985000 on the users scan means Postgres fetched a million rows and checked each one to keep 15,000. The orders scan has an Index Cond instead: the index found the rows, and nothing was thrown away.

On a Seq Scan, a large count is where an index might help (part 1 covers when it won't). On an index scan, it means the index covers only part of the WHERE clause and the rest is checked row by row. In the failed-orders join, the index found all five orders of each user and the filter threw away 96% of them. Which index fits a query like that is part 4.

shared hit is a page found in shared_buffers. read is a page Postgres asked the OS for, which came from the OS page cache or from disk, and BUFFERS can't tell which. The counts aren't distinct pages: a page visited twenty times is twenty hits. The report's Nested Loop plan in all three states:

I/O wait is the median from the EXPLAIN runs, query time from the plain ones. Both restarted runs read the same 41,801 pages, and the second was seven times slower because those reads went to disk.

The I/O wait comes from track_io_timing, which is off by default and which a superuser can turn on for the session. Every node then gets an I/O Timings line. From the median cold run of each plan, costs cut:

The index scan waited almost 2 seconds for 32,367 pages, about 60 µs each, as its lookups jumped around the table. The Seq Scan read 37,101 pages of the same table front to back in 65 ms, under 2 µs each. All 87,633 hits are repeat visits inside the index scan, like the top of the B-tree on every lookup.

Two kinds of lines say an operation didn't fit in memory. A sort gets work_mem, 4 MB by default, and a hash twice that, since hash_mem_multiplier defaults to 2. The report's inner Sort shows Sort Method: external merge Disk: 1640kB: it wrote sorted runs to temp files, the temp read=205 written=205 in its Buffers (205 pages of 8 kB). A Hash shows it as batches. This one joins all 200,120 failed orders to users, sorted by amount:

Batches: 16 means the hash table was split into 16 parts and 15 of them waited in temp files. The final sort spilled too, 7,448 kB.

At 64 MB of work_mem (128 MB for the hash) both fit in memory, the hash in one 66,782 kB batch, and on the cloud VM the query got slower: 425 ms to 578 ms with TIMING OFF, median of seven. On my M3 Max laptop it got faster, 418 ms to 341 ms. I haven't found out why. CPU cache was my first guess, since a 4 MB batch fits in it and a 66 MB table doesn't, but that doesn't explain the laptop, so it stays unconfirmed.

The report's own 1.6 MB spill cost nothing I could measure: 158.6 ms at 4 MB, 158.0 ms at 64 MB. A Disk: line says a node spilled, and only a rerun with more work_mem, on the machine that serves the query, says whether the spill is slow. Each sort and hash in each connection can take that much, so raise it per session or per role.

The report spent 0.25 ms planning and 210 ms executing, the usual split for a slow query. Planning Time counts on queries that run in microseconds, like a primary-key lookup on users right after a restart:

The first plan in a new connection reads table and index details from the system catalogs, 73 pages here, and took five times longer than the query. After that, planning still took twice as long as execution. If a lookup like this runs thousands of times a second over short-lived connections, a pooler that keeps connections open removes that first cost.

To time each node, EXPLAIN ANALYZE reads the clock before and after every call into it, twice for every row each node returns. If millions of rows pass through a cheap node, the clock reads can cost more than the work.

On my laptop, the cloud VM, an AlphaVPS server in Los Angeles and an ARM server at netcup, I ran pg_test_timing, which ships with Postgres and times a loop around one clock read, then SELECT count(*) over 10 million rows, seven times each way.

pg_test_timing gave 18 to 40 ns per loop, and EXPLAIN ANALYZE still made count(*) 2.4 to 3.0 times slower everywhere. The extra time per row followed the clock: 24 ns on the laptop, 44 on the VM, 59 on the Xeon, 74 on the ARM server, or 1.3 to 1.9 times the pg_test_timing figure. On the VM, switching the clock source from tsc to kvm-clock raised both, to 28 and 50 ns, and the slowdown to 3.2 times. A nested loop with a million index lookups does more work per row, and there EXPLAIN ANALYZE added 4% to 15%. The report lost 7%, 159 ms to 170.

I expected a bigger gap between machines, but all four clocks were fast. The pg_test_timing docs show a slow one, acpi_pm, where a loop took 723 ns and EXPLAIN ANALYZE turned a 9.8 ms count into 115.9 ms. The AlphaVPS server offers acpi_pm too, but I didn't switch a live server's clock.

The overhead also skews comparisons between plans. Under EXPLAIN ANALYZE the Hash Join version of the report took 591 ms and the Nested Loop 170 ms, 3.5 times apart. Run plain, they took 344 ms and 159 ms, 2.2 times apart. The Hash Join pushes five million orders through its Seq Scan node, ten million clock reads, while no node in the Nested Loop plan returns more than 75,000 rows.

TIMING OFF keeps rows, loops and buffers and drops the per-node times. It still counts every row, so count(*) ran 16% to 19% slower than plain even then. Inside one plan the per-node times are the best map you have, but the nodes passing the most rows carry the most overhead.

The walkthrough plans come from one 4-vCPU AMD EPYC cloud VM with 8 GB of RAM and PostgreSQL 17.12 in Docker, so your milliseconds will differ while the row counts match. The work_mem check also ran on my M3 Max laptop (Homebrew PostgreSQL 17.7), and the overhead test ran on the laptop, the VM and an AlphaVPS server in Los Angeles, a 4-vCPU Xeon Platinum 8176 with 8 GB of RAM (PostgreSQL 17.12 from conda-forge), and a netcup server with 6 ARM Neoverse-N1 cores and 8 GB of RAM (PostgreSQL 17.12 in Docker).
