How //go:embed Works: From Source Files to Binary

Tanggal: 2026-11-04

Since its release in Go 1.16 (2021), //go:embed has quickly proven to be one of the most loved features of the Go language. Russ Cox and Brad Fitzpatrick originally designed the feature in 2020 to embed files and directories into Go binaries using a go directive (more on what that is later). It allows engineers to quickly embed anything they want instead of using awkwardly formatted constant string literals or reaching for flaky third-party tooling to bake data directly next to their program.

Feedback on the proposal was overwhelmingly positive. It was quickly coined as one of the stand-out features of Go, not only because it’s an easy way to embed strings and byte slices, but because it also shipped with a read-only file system. That was the part that set it apart from other languages; D and Zig shipped expressions, but Go shipped a file system you could interact with easily, straight from the standard library.

The most important thing to note is that it satisfies the fs.FS interface, which means we can use it in many different ways. It makes it easy to plug and play across packages, such as http.FileServer to serve it as a static site or template.ParseFS to parse HTML templates.

Before we dive any deeper, let’s give ourselves a folder to work with. This is the example we’ll be coming back to all the way down to the linker, so it’s worth a proper look.

We’re serving a normal website. An index.html at the root, and some css and js in a folder called assets. No more, no less.

To embed that into the program, we create a string variable for the contents of index.html, and an embed.FS for the contents of the assets folder, and then just print them. In a production environment you’d serve these through a handler, but we’ve kept it simple for now.

The assets/* pattern gets us every file in that folder; naming the directory on its own (//go:embed assets) takes the whole tree instead. The difference isn’t only depth: naming the directory skips every file beginning with . or _ anywhere beneath it, where the /* glob still pulls those in at the top level. Write all:assets when you want the whole tree, dotfiles and all. There are more gotchas in the pkg.go.dev/embed docs.

Now that we know what //go:embed is, we’ve seen how it works. Let’s dive a little bit deeper to see how it’s constructed under the hood. If I were to show you a bunch of code from the Go compiler out of context in the next section, I’ll probably have you lost; like it did me for a few days researching into how Go is built (TLDR; it’s challenging but worth it).

Everything below was read against Go 1.27.1, and every file and line number links to that tag on GitHub, so the lines quoted here stay put even after the toolchain moves on.

So before we go anywhere near how go is built, let’s zoom all the way out. When you type go build, six steps run in order and out the other end comes a binary. This is the path that matters for //go:embed; it isn’t everything the toolchain does, just the part your files travel through.

I’m aware that there’s a whole heap of stuff that we’re not going into here such as SSA, inlining, escape analysis, etc… But none of it really touches the embed packages, because your data never becomes instructions; they are just bytes after all.

The first thing worth knowing is that there isn’t one program doing all of this. There are several, each responsible for its own thing, and go build is the one that runs the other two.

Notice the three different sections, that’s the bit that tripped me up for the longest, go runs once for the whole build, compile runs once per package, and link runs once at the end. It’s an important nuance to understand.

Check out go.dev/src/cmd/compile/README for more information.

So now, onto the juicy bits. Let’s start with how Go looks at your project. When you run go build it needs to know what files and packages exist, so it knows what to parse and build.

A package directory goes in, and a *build.Package comes out. So it walks your project, finds every .go file and then works out which package each one belongs to. For every file, it notes down where it lives, what it imports, and any directives (such as //go:embed) that it carries.

You can see our assets/ folder and index.html being skipped, because they aren’t Go files and this pass only cares about Go. main.go makes it through the condition into matchFile, and out the other side comes a Package which details its name, its Go files, and the position of every //go:embed pattern in it.

Reference: src/go/build/build.go ((*Context).Import, simplified)

Our //go:embed index.html and //go:embed assets/* have been spotted and recorded along with their file names and token positions.

But how did it spot the comment originally? This is where the lexer comes into play.

The lexer (or scanner, or tokeniser, whatever you fancy) is the first thing that actually reads your code as Go, rather than as a blob of bytes. It scans the file one character at a time and chops it up into little tokens, which are the pieces of code that mean something on their own. Such as func, var, =, a string literal, or a comment.

This is the stage that makes //go:embed actually possible. In Go, a comment is a real token (token.COMMENT).

Lexer: one character at a time, into tokens

Characters go in and tokens come out. The whole //go:embed index.html line becomes a single COMMENT token, and the two words of var indexHTML string become a VAR and two IDENTs.

The go command’s scan is deliberately inexpensive as it stops at the end of the import block, because that’s normally all it needs. Unless, however it saw import "embed" on the way past, in which case it reads on to the end of the file, picking out every comment starting //go:embed:

We’re in a different program now. Tokens go in, along with the path to that embedcfg, and what comes out is a tree with your directive attached to the right node.

The parser is where the real magic happens in the Go compiler. It takes those tokens and little bits of Go code and works out their structure. A bit like breaking a sentence down into a subject, verb and object.

The result is a syntax tree; you may have heard of the term AST before, which is short for abstract syntax tree. It’s the building blocks of our program. Every piece of your code (a function, a variable, an if statement) becomes a node within that tree.

Directives such as //go:embed get attached to the node, which is how Go knows which variable to put your embedded file in.

Now onto the nuts and bolts, the compiler. A tree goes in, and what comes out is an object archive, one per package, which is your code compiled but not yet runnable on its own. This is also the stage where your data is actually allocated.

Everything so far has been bookkeeping; finding files, expanding patterns and writing lists, but not one byte of your index.html has actually been allocated into your program. However, in this step, it does.

The compiler lays your variable out in memory and fills it with the file’s contents, as static data, that’s there before your program runs a single line of your app’s code.

Here we can see WriteEmbed switching on the variable’s data type. It then goes on to call a function called fileStringSym, which opens your file and returns a symbol for its contents, as well as the size.

Okay, but what’s a symbol? Forget []byte for a second. A symbol is a box with a name on it, what it’s called, how big it is, and where it lives in the binary. That’s what the linker actually needs to do its job, and it’s why fileStringSym hands one back rather than the bytes themselves. This is where your asset has stopped being a path and has actually become data.

The rest is ordinary compilation. The tree gets turned into machine code (cmd/compile/internal/ssagen), and out comes one object archive per package, which is code that can’t run yet, which is where the linker comes into play.

Although the linker has little to do with //go:embed, it plays a crucial part in the build process. It’s a separate program, located under cmd/link. Many .a files go in, and one executable comes out. All of the object archives that we mentioned above, now are joined together. It fills in all the gaps so every piece can find the others.

Which is where the Go runtime is injected. The runtime is built-in code that manages memory, goroutines and all of the stuff that makes Go, Go.

Three separate processes, and they don’t run the same number of times, go runs once for the whole build, compile runs once per package and link runs once at the end. That’s why embedcfg is written per package, immediately before each compile invocation.

And you don’t have to take my word for any of it. go build -x prints the real command lines and the temporary directory, so you can watch embedcfg being written and passed along, and ls $(go env GOROOT)/pkg/tool/$(go env GOOS)_$(go env GOARCH)/ shows you that compile and link really are separate binaries sitting on your disk. So the bytes are in the binary. The last question is what happens when your program actually opens them, because that depends on which of the three types you picked.

For a string or a []byte, there’s almost nothing to tell, and that’s rather the point. The compiler wrote a pointer and a length, and the pointer aims at bytes sitting in the rodata section we just watched the linker build. Reading the variable is an ordinary variable read.

An embed.FS is more involved, and it’s the more interesting half. Remember it’s a single pointer to a hidden list, and here’s what’s on the end of it:

Reference: src/embed/embed.go#L151-L212 (FS and file, simplified)

Each file’s contents are a string, pointing into the same read-only data our indexHTML did, so a 40MB asset isn’t sitting in your heap waiting for you.

Asking for a file is a search, not a syscall. The list is sorted, so lookup does a binary search over it, and readDir does two of them to find where a directory starts and ends, then hands back that stretch of the slice. There’s no disk involved at any point, which is why ModTime on an embedded file is the zero time. There’s nothing there to have been modified.

There’s one detail worth the whole section, though, and it’s the difference between the two ways of getting at your bytes. Open hands you back an openFile that reads straight out of that string, copying only as much as fits the buffer you gave it. ReadFile ends looking a bit like this:

Reference: src/embed/embed.go#L322-L332 (ReadFile)

That conversion is a copy, and a fresh one on every call. So the 40MB asset that wasn’t sitting in your heap a moment ago lands there the moment you call ReadFile on it. Open doesn’t; it fills your buffer a chunk at a time, which is the path http.FileServer and io.Copy take. Neither touches the disk, but only one of them allocates the file.

You’ve seen how it works and how it’s used, so let’s talk about what it costs you, because embedding isn’t free.

Remember what WriteEmbed did with those bytes. They’re read-only data in the object file now, which means your file isn’t really a file any more. So change one line of CSS, and you have to rebuild.

This can be a bit painful because nobody wants a full build on every save. The fix is the last in this section, so hold onto that.

And here’s the one that catches people out. Embedded bytes are just data in the binary, which means they’re readable:

Anyone with your binary has your file. So no .env, no private keys, no credentials. It might seem obvious, but it’s an easy one to forget when you’re embedding a whole config directory.

Now for the good news. Remember checkEmbed, that big switch statement? Bad patterns, no matching files, the wrong type, a variable inside a function; all of them are build failures. But the compiler knows the file exists. It doesn’t know it’s the file you meant. That’s where the standard library has a package that can help you out.

testing/fstest is the handy little package of the standard library that doesn’t get enough attention, which is a shame, as it works perfectly alongside embed. fstest.TestFS takes your FS and a list of paths you expect to find within it, and then does two jobs at once:

The trick is what you list. It shouldn’t be a whole inventory of the FS, just a handful of the files your code actually opens:

Only name what you’d notice missing; the template your handler executes, the migration directory, the default config. Everything else is just noise that makes the test brittle.

And this is the one thing I’d really like you to take away, and the answer to the rebuild problem we started this section with.

Take fs.FS in your constructors, not embed.FS. Your server doesn’t care where the files came from; it cares that it can open them. Which means a test can hand you an fstest.MapFS instead, with the files declared inline as a map.

And now you can ask the questions a good unit test should ask. What if this file is empty? What if it’s corrupt, or 40 megabytes? You can answer all of that without touching the disk or waiting on a build. It’s also how you sidestep the rebuild-to-change-a-byte problem in development: the same constructor takes os.DirFS("./assets") while you’re working and your embed.FS in production, and nothing else in your program needs to know which one it got.

So that’s the whole journey, from a comment in your source to bytes in the rodata section of a binary you can copy anywhere.

//go:embed is one of those quiet features about Go that makes it so easy to reason about. It’s a kind of feature that you didn’t know you needed until it came along. It makes for a great experience when you’re building a package that needs to ship some data with it.

I would really encourage you to have a look at the Go source code, although it can look scary at first (I spent some time dazed and confused looking at it). But it really makes you a better engineer for knowing how these constructs work.
