From a security point of view, was fetching an unused dependency a potential attack vector? (like changing global state even without calling exported functions or using global data).

I don't know Rust enough to be sure but I don't think so. It only affect the package manager and not the compiler.

There is a risk in Cargo from unused dependencies - Cargo has a build graph based on the declared dependencies in Cargo.toml, and chooses what build steps to run based on that graph. One thing a crate can contain is a build script - which is code that's built and run on the build host at the time of compilation, and can do anything that code running as part of the build system can do.

In theory, an unused dependency can contain a build.rs that's got a security-relevant bug in it; that would then cause a security issue on the build host if you built the unused dependency. Removing it means that's not a problem :-)

First and most important: Safety is cultural. Rust's safety culture uses Rust's safety technology to deliver safety, but you can't just apply that technology and magically get safety, you need the culture. You're damn sure not getting the culture from C. I was a C programmer for decades. Secondly and maybe more understandably to people focused on technology, ALL of Rust follows the same rules and those rules achieve safety. What's different about Safe Rust is that the compiler can check everything you have done in Safe Rust follows the rules, so in Safe Rust following the rules isn't your problem, the compiler will check that. The "safe subset" technology can't work without a language where everybody else is following the safety rules all the time. So leaving aside the harder culture problem, step one is to have safety rules for C and get everybody to follow them all the time. For me Rust is more a successor to C++, but less so for C.

The C language has a small core language, while both C++ and Rust have a larger set of core features (so without taking into account the standard library).

I use the C language in combination with GLib/GObject, where all symbols need to be used with their fully qualified names. For instance when reading a gtk_widget_set_visible() function call, you know that it comes from the GTK library (the namespace), from the GtkWidget class and it's the set_visible() method. For a project that I start alone, yes. Not really for bigger projects involving many collaborators where idiomatic Rust is already present.

Fully-qualified function call syntax is possible to use everywhere, again modulo unnameable types, but it looks quite ugly. While I agree that (for example) foo.into() is a bit ambiguous about what conversion we're performing, you can fix that by writing Bar::from(foo) if you prefer. Nobody in their right mind is going to write >::into(foo) or >::from(foo). (Those latter syntaxes exist to disambiguate the case where multiple traits define from() or into() methods or associated functions, or where Foo and Bar have inherent implementations of those methods or associated functions. But From and Into are well-known stdlib traits, so such a collision is unlikely in practice. It would be more plausible with more obscure traits, and fully qualified syntax is commonly used in macros because you can't know ahead of time that a collision is impossible.)
