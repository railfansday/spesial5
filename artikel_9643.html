How a Side-Channel Attack Exposed Hidden Data in OpenSearch

Tanggal: 2026-11-26

Tl;dr: In our research, we found an unauthorized data access vulnerability in OpenSearch that allowed an attacker to extract vector fields protected by field-level security using OpenSearch's vector search as a side-channel.

We reported the issue to OpenSearch team along with a proposed patch, and the vulnerability has since been fixed as of 3.10.

OpenSearch is an open source distributed search engine created by Amazon, a popular alternative proprietary Elasticsearch.

Besides the more traditional lexical search and analytics capabilities, it also functions as a vector database, which has become increasingly important for AI and ML applications — RAG, semantic search, recommender systems, etc.

One of the most common use cases of vector databases is to store and search for vector embeddings.

An embedding is a point or vector that represents some concept — e.g., a word, image, or something more abstract and opaque — in some high dimensional embedding space.

Tl;dr, vector databases are important, and OpenSearch is one such popular database technology.

OpenSearch has a security feature called field-level security (FLS) which allows you to control which document fields a role can read in an index.

For example, a cluster might have users with different roles, e.g., QA, support, MLEs, SREs accessing the cluster for different purposes, along with service principals representing different programatic workloads — documents might be composed of different data that not all should have access to even when they have access to an underlying document itself.

FLS essentially allows you to create different projections of an index with different fields visible or hidden to different users, without having to duplicate that data into a separate index per view.

In using FLS, we noticed something intriguing: while FLS hid the literal values of fields from users for whom that field was configured as excluded, and while those fields were completely disregarded by lexical search, if the field was a vector field, it was still eligible for vector search, and still influenced search candidacy, scoring, and ranking.

If you're familiar with the idea of side-channels in security, alarm bells should be going off in your head right now. 🚨

Any time you have an inaccessible secret, but you are able to indirectly learn information correlated with it, you have a potential side-channel vulnerability.

Two illustrative examples are that of acoustic cryptanalysis and power analysis.

The intensity/color of the power LEDs can be used to detect the beginning and end of cryptographic operations. This can be done because the intensity/brightness of a device's power LED […] correlates with its power consumption (which is affected by the CPU operations). This is caused by the fact that the power LED is connected directly to the power line of the electrical circuit which lacks effective means (e.g., filters, voltage stabilizers) of decoupling the correlation with the power consumption.

The technical root cause was a flaw in the k-NN plugin's implementation of vector search: unlike lexical search which completely disregards FLS-excluded fields for purposes of matching and ranking via filtered view, the k-NN plugin during vector search unwrapped the filtered view, accessing the raw reader underneath and thus considered as candidates vectors that should've been hidden by FLS, and returned their scores.
