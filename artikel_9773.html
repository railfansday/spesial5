A phishing site takedown is a routing problem. Three kinds of parties can kill a page impersonating your brand: the network serving it, the registrar that sold the domain, and the browser blocklists that can warn people away from it. Most reports stall because they reach the wrong party, or the right party through the wrong channel.

The second failure is more common than it sounds. In the May to July 2026 hosting-network data from Interisle's Cybercrime Information Center, 380,272 reported phishing attacks sat on Cloudflare's AS13335. That is about 26% of the 1,450,117 attacks reported that quarter. Look up the IP behind one of those sites, email the abuse address in its registry record, and you get an automated reply pointing you to a web form.

When you need to take down a phishing website, the lookups are the slow part. This post builds a Python script that takes a phishing URL and returns everything a takedown needs: captured evidence, every IP the domain resolves to, the network and abuse desk behind each IP, the registrar's abuse contact from RDAP, and a draft report per desk. It runs in a few seconds per URL.

Before any code, here is the routing table the script implements. Every row is a separate report, and none of them waits on the others.

Remove the content or suspend the account

Full URL, UTC timestamp, screenshot, what it impersonates

Abuse contact registered for the IP's network

Forward to the origin host; remove only content it hosts itself

Suspend the domain, which kills every URL on it

Screenshot showing what the phish targets, plus the complete URL

Warn users within the browser; content stays up

Google Safe Browsing, Microsoft, Netcraft, APWG

Which report lands first depends on what kind of site it is. In the same quarter, 914,576 of 1,129,248 unique phishing domains (81%) were registered by the attacker for the purpose. For those, a registrar suspension takes out the whole domain, including the paths you haven't found yet.

A compromised legitimate site is different. ICANN's own compliance advisory on the 2024 DNS abuse amendments walks through a phishing page on a franchisee's subdomain of a three-year-old dealership domain. The registrar weighs the collateral damage, decides suspension isn't appropriate, and notifies the domain owner instead. When the domain owner is a victim too, the host is your lever.

The registrars' own abuse reporting guide goes further and asks reporters to contact the host first, treating the registrar as a follow-up. For a compromised site, that's right. For a lookalike domain registered last week to copy your login page, there's no collateral to damage, and I'd send both reports on day one.

Phishing kits get moved, cloaked, and redeployed, sometimes within hours. Capture the page once, timestamp it in UTC, preserve a bounded copy of the bytes that were served, and hash that saved artifact. The hash lets you verify or compare the retained capture later; it is not useful as standalone proof if the underlying bytes are discarded.

The headers are there for a reason. A Server: cloudflare and a CF-RAY value in your evidence tell the recipient, and you, that the IP is an edge node and not the origin.

The script doesn't take screenshots, and registrars ask for them. The guide ICANN's advisory points to wants screenshots of both the phishing page and the real page it imitates, with the URL bar visible, plus the full URLs and, if you have it, the phishing email with complete headers. Take the screenshots in a real browser. Playwright works if you want them in the pipeline.

Pitfall: This script intentionally fetches attacker-controlled URLs. Run it only inside a disposable VM or container with no cloud instance role, no route to your internal network, and outbound rules blocking private, loopback, link-local, metadata and other non-public address space. The URL checks above are defense in depth, not a replacement for that network boundary. Never type credentials into the phishing form, and expect cloaking.

ping gives you one address. A phishing domain can have several, and the one you happen to get depends on your resolver.

I'll use example.com as the stand-in target throughout, because it is safe to query and, at the time of writing, it happens to sit behind Cloudflare, which is exactly the case that trips people up. It resolves to four addresses: two IPv4 and two IPv6. Two lookups a few minutes apart returned 104.20.23.154 and then 172.66.147.243. Same domain, same network, different answer.

Most of the addresses returned in one query land on the same provider. When they don't, you owe each provider its own report. Treat this as a snapshot from one resolver and one vantage, not a global inventory of every address the domain may return.

You can get the abuse contact for an IP from RDAP directly, but the five regional registries shape their records differently, and you end up walking nested entity roles per registry. RIPEstat, ipinfo, IPLocate and IPGeolocation all expose abuse contacts if you'd rather not. I'm using IPGeolocation's abuse contact data for the examples because one call returns the ASN, a CDN flag, and the registered abuse contact together, which is the exact trio this step needs.

The trade-off: lookup by domain, the abuse module, and the dedicated ASN endpoint used later are paid-plan features (there's a trial). If you handle a few takedowns a year, RIPEstat in a browser tab is fine. If takedowns are a queue, the API call is cheaper than your time.

Here is the domain lookup with abuse data. I'm excluding the time zone, currency, and country metadata objects the endpoint also returns, because none of them help route a report.

Three fields do the routing. network.is_cdn with cdn_provider_name tells you this is an edge, not an origin. abuse.emails is an array, not a string, so index it. And abuse.route is the block the abuse desk answers for, here a /13 that is far wider than the /20 the IP is routed in, which tells you the contact belongs to the network operator rather than to whoever runs the site.

The domain lookup resolves one IP per call, so the script calls the endpoint once per IP from Step 2 instead.

abuse_country is only a routing hint: it identifies the country attached to the registered abuse contact. It does not establish the origin server's location or legal jurisdiction, especially when the visible IP belongs to a CDN. Verify the relevant national CERT manually before escalating.

The abuse record above is accurate. abuse@cloudflare.com is Cloudflare's registered abuse mailbox. It's still the wrong place to send a phishing report, because Cloudflare's reporting page says it is "generally unable to process complaints submitted to us by email" and will auto-reply with a link to its form.

The form is worth using. Per Cloudflare's abuse approach page, a report about a site using its CDN or proxy gets forwarded to the website operator and the hosting provider, and the host receives the origin IP so it can find the content. If the site is on Pages or Workers, Cloudflare is the host and can remove it directly.

Tip: The phishing form lets you choose whether your report and your contact details go to the website owner. On a phishing site, the website owner is the attacker. Send it to the host; skip the owner.

Only Cloudflare is in the table because it's the only one whose policy I verified for this post. Fastly ranked second in the same Interisle quarter with 60,879 attacks, so it's the obvious next entry. Read its abuse page before you add it rather than guessing.

group_by_desk matters more than it looks. For example.com, four IPs collapse into one form submission. The registrars' guide says the same about URLs: group everything on one domain into one report, because one report per URL slows the response and risks duplicates landing in a spam filter. Four near-identical reports don't make action four times more likely; they make every report less readable.

WHOIS is the wrong tool now. ICANN made RDAP the definitive source for gTLD registration data on 28 January 2025, and RDAP returns JSON. The rdap.org bootstrap service redirects each query to the authoritative server, so you don't need to know which registry runs which TLD. It rate-limits at 10 requests per 10 seconds, which is plenty for takedowns.

The registrar's abuse contact sits in an entity nested inside the registrar entity, with role abuse. That nesting is the part people get wrong when they grep RDAP output for the first email address and end up writing to the registrant, who in this situation is the phisher.

Registrars now have a contractual duty here. Since the DNS abuse amendments took effect on 5 April 2024, an ICANN-accredited registrar with actionable evidence of phishing must "promptly take the appropriate mitigation action(s)" to stop or disrupt it. "Promptly" is doing a lot of work in that sentence. The DNS Research Federation measured registry and registrar mitigations from September 2024 to March 2025 and found an average of 8 days, with the share mitigated inside 24 hours rising from 11% to 22%. Report to the registrar, and don't plan around waiting for it.

Everything so far feeds a plan: evidence, desks, registrar, and drafts. Reports stay short and factual, with UTC times and defanged URLs so nobody clicks the link from a ticketing tool.

Install the dependencies with pip install requests tldextract. Run the normal compromised-site workflow as python takedown.py "https://login.example.com/signin" "ExampleCorp". Add --request-domain-suspension only after a human has determined that the registered domain itself was created for abuse rather than being a compromised legitimate site. Against example.com, host_desks comes back with a single entry: the Cloudflare form, listing all four IPs. The evidence block shows Server: cloudflare and a CF-RAY header, which matches the lookup.

The template is deliberately boring. Abuse desks triage a lot of mail, and the reports that get actioned are the ones a person can verify in under a minute: one URL, one time, one claim, one screenshot.

Removal takes hours to days. Every guide on how to report a phishing website starts with these forms, and they deserve the spot for one reason: browsers check them before rendering a page, so they protect users sooner. Submit to all four in the plan at the same time as the host and registrar reports.

Give a host 24 hours, then follow up once on the same thread. If that fails, the next lever depends on how big the host is, and the ASN data tells you.

If you're pasting along, put this and the next helper above the __main__ block. Each upstream comes back as as_number, description, and country. The count is the useful part. When I pulled DigitalOcean's AS14061, the response listed 95 upstreams, so no single transit provider is going to lean on it over one phishing page; the host's own abuse desk is the only lever there. A small host with two upstreams is a different story, and their abuse desks are worth a polite, evidence-first note. The ASN pivot playbook covers reading routes and upstreams in more depth.

For providers abroad that ignore the direct reports, a relevant national CERT can be an escalation path. Choose it from the confirmed provider or origin-host jurisdiction, not from the geolocation of a CDN edge, and verify the contact manually before sending the case.

A takedown isn't done when someone replies "actioned". Check it yourself at 24 and 72 hours.

client hold in the RDAP status means the registrar suspended the domain; server hold means the registry did. Those are the same signals the DNS Research Federation used to count mitigations. A 404 or 410 from the host with DNS still resolving means the content is gone but the domain is alive, so keep the registrar report open, because a live domain can serve a new kit tomorrow.

The FORM_ONLY table is the most valuable phishing takedown asset you'll build here, so keep it in version control and add a row every time an abuse desk bounces your email to a form. Store each evidence JSON with the case. Phishing kits get reused, and when the same page hash turns up on a new domain next month, you'll know the captured bytes or kit are the same. That is useful correlation, but it does not by itself prove the same operator is behind both domains.
