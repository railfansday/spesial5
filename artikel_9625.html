When an API gets breached, it’s rarely because an attacker found a zero-day exploit in your cloud provider’s load balancer. Usually, the API did the exact thing it was programmed to do: it took a request, saw a valid login token, ran a database query, and returned a 200 OK.

Automated security scanners are terrible at catching these bugs because scanners don't understand your product's business logic. They can't tell the difference between a user downloading their own invoice and a user downloading their competitor's invoice.

As a Product Manager, if you treat API design as an invisible engineering implementation detail, these logic gaps will ship to production. Here are five technical API bugs that routinely slip through sprint reviews, why they happen during normal feature work, and how to close them in both your PRDs and your architecture.

How it happens in a sprint: You’re shipping a feature that lets users export their monthly billing report. The acceptance criteria in the ticket says: "Logged-in users can click 'Download' to fetch their report via GET /api/v1/reports/{report_id}."

QA tests the happy path in staging, the download works, and the ticket gets closed.

The vulnerability: Your auth middleware checked who the caller was, but the query never checked if that caller actually owns report 9402. Any customer on a free trial can open Chrome DevTools, change 9402 to 9403, and pull another company's report. This is Broken Object-Level Authorization (BOLA), and it is still the #1 cause of API data leaks.

In the PRD: Stop allowing sequential integer IDs (9401, 9402) in external URLs—require UUIDv4 or ULIDs so attackers can't loop through your database with a Python script. And write negative acceptance criteria explicitly: "User A with a valid token must receive a 403/404 when requesting a report_id belonging to Tenant B."

How it happens in a sprint: You’re building a collaboration view where users can see who else commented on a ticket. The UI design only shows each commenter's firstName and avatarUrl.

To avoid writing a net-new backend serializer and delaying the sprint, the developer reuses the existing User ORM model and returns the raw object: return res.json(user). The React frontend grabs the two fields it needs and ignores the rest.

The vulnerability: The UI looks clean, so it passes product sign-off. Meanwhile, the raw JSON payload sitting in the browser's Network tab is leaking user.email, user.phone, user.role, user.mfaEnabled, and user.stripeCustomerId for every user on the thread.

The reverse happens on PATCH and PUT routes (Mass Assignment). If the backend takes the incoming JSON body and passes it straight into User.update(req.body), a user can intercept their own profile-update request, inject "role": "admin" or "plan_tier": "enterprise" into the JSON payload, and overwrite columns they were never meant to touch.

How it happens in a sprint: You’re launching an SMS OTP login flow, a PDF export feature, or an AI summary button powered by an LLM API. During the security review, someone asks about rate limiting. DevOps confirms that Cloudflare or Nginx is already configured to block any IP address that exceeds 1,000 requests per minute. Everyone checks the box and moves on.

The vulnerability: A blanket 1,000 req/min IP limit protects your infrastructure from a basic DDoS, but it does nothing to protect your product logic or your cloud budget:

How it happens in a sprint: As the product scales from a monolith to microservices, the team puts an API Gateway at the edge to centralize authentication. The gateway verifies the user's JWT, extracts the user ID, strips the token, and forwards the request inside the VPC with a plaintext header like X-User-Id: 4821. Internal microservices trust that header implicitly because "it came from inside our private network."

The vulnerability: This creates a hard shell with a soft center. If an attacker finds a Server-Side Request Forgery (SSRF) bug in a peripheral service—like a webhook tester, an image importer, or an outdated third-party library—they can trick that service into making internal HTTP requests across your cluster with any X-User-Id or X-Tenant-Id header they want, completely bypassing the API Gateway.

How it happens in a sprint: Your team rebuilds the checkout or user-management flow in /api/v2 with strict schema validation, better RBAC checks, and cleaner error handling.

When it’s time to turn off /api/v1, someone points out that an old iOS app build from 18 months ago—or one enterprise customer's custom webhook script—is still hitting the v1 routes. Nobody wants to deal with customer complaints, so PM and Eng agree to leave /api/v1 running quietly in the background.

The vulnerability: Six months later, nobody on the team remembers /api/v1 exists. It isn't included in new threat models, and when security patches are applied to v2 controllers, nobody backports them to v1. Yet that unmaintained v1 code is still wired directly into your live production database. When pentesters or attackers hit a wall on /api/v2/users/export, the very first thing they try is changing the URL to /api/v1/users/export or /api/beta/users/export.
