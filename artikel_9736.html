How to Fix Presigned Downloads: Filename, Content-Type, and Content-Disposition

Tanggal: 2026-11-19

Large receipt exports change the answer. A 20 KB CSV that opens in a tab is annoying; a 2 GB PDF that opens in a tab can pin a browser process and make a support ticket look like a storage outage.

TL;DR: set Content-Type and Content-Disposition on the object before creating a signed URL. Verify the stored metadata with a HEAD request, then issue a fresh private link. The URL is only a delivery token. It does not repair bad metadata.

Browsers make two decisions from response headers: how to render the bytes and what name to suggest when saving them. Object storage makes those headers from metadata saved with the object. A presigned URL normally signs a request for that object; it does not infer that receipt-2026-09.csv is a CSV just because the key ends in .csv.

The fix belongs in the write path. Set metadata at upload time, or immediately after upload if the producer cannot send headers. Then check it before signing. I keep this as a hard invariant in export jobs: an object is not downloadable until its metadata check passes.

The following adapter calls the storage capability over plain HTTP, but the application-facing contract is deliberately boring. If the storage provider changes, the receipt processor should still call setExportMetadata and presignExport.

The metadata call is idempotent, so a worker retry does not create a second export. The response is checked before the link is returned, and a 429 honors Retry-After with exponential backoff. In production I also call the object HEAD route between these two calls; it is cheap compared with reprocessing a failed export and catches the trap where a local object model changes while the already-uploaded object keeps old headers.

For an existing object, use the provider's metadata-update operation, then repeat the HEAD check before issuing another link. I test filenames with spaces, cafe-au-lait.csv, quotes, and a 180-character stem. I also run the same matrix at 50 MB, 500 MB, and 2 GB. The numbers are test inputs, not promises about throughput; they expose buffering, proxy limits, and browser behavior early.

The useful comparison is about operational shape, not a sticker price.

The unified contract is useful when the receipt worker may switch vendors without changing its call sites. Its practical advantage is one REST API and one key across many backend capabilities, so there is less glue around the storage adapter. It does not remove storage engineering. Keep the object private and mint a short-lived signed link for each user request. Public URLs are not a fallback here.

For large files, benchmark the complete path: producer upload, metadata write, HEAD verification, signing, and browser download. Measure time to first byte and peak memory separately. A fast upload with a proxy that buffers the download is still a bad export experience.

Single-request uploads are a reasonable first implementation. At larger sizes, use multipart upload where the backend supports it. Keep the finalization step idempotent, and record the object key plus an export ID in your database before publishing the link. If a worker retries, it should resume or safely replace the same planned object, not create a second receipt with a new name.

Retention is another throughput concern. Lifecycle rules help remove old exports, but a one-day minimum expiration is not the same as hour-level cleanup. Multipart parts can also need explicit abort handling. Track unfinished uploads as a queue metric instead of waiting for a storage bill to reveal them.

Do not use object metadata as a search index. If you need “all receipts for customer 481,” store that relation in your database; metadata is for delivery headers and small invariants, not server-side queries.

This pattern suits private, user-triggered downloads. It is the wrong foundation for a public image host, static-site origin, or an audit archive that requires WORM guarantees. Without versioning and object lock, an accidental overwrite is an application-level incident. Without conditional If-Match writes, strict concurrent ownership needs a queue or database lock. Without configurable CORS, browser-direct uploads need a controlled proxy or a platform that exposes the required bucket policy.

Those limits are design inputs. Write them into the decision record alongside your throughput test results. The practical rule is short: metadata first, HEAD second, presign third. Keep that sequence behind an adapter and the storage vendor becomes a replaceable implementation detail while the download behavior remains stable.
