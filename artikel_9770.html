Your agent has no tests. Here is how I gave mine a regression suite.

Tanggal: 2026-11-23

Posted on Nov 23 • Edited on Nov 23 • AI-assisted

A plugin that records real agent turns and replays them with every tool call answered from the recording.

Most teams ship an agent, then change one line (a model id, a system prompt, a temperature) and find out in production that it stopped doing the thing it used to do. There is no red build, because there is no build. The behaviour changed, and nothing was watching it.

hermes-regress is a Hermes Agent plugin that watches. It records the turns your agent actually runs, tool calls and tool outputs included, and later replays those same turns against a different model or config with every tool call served from the recording. Nothing on your machine gets executed twice. You get a verdict per case: pass, drift, regressed, error.

There are three common ways to test an agent, and all three miss the specific failure that hurts:

Meanwhile the cheapest possible test input already exists: the transcripts of what your agent did yesterday. Those turns contain the prompts, the exact tool arguments, and the exact outputs the model was reasoning over. If you can replay one of those turns and compare the new behaviour to the old one, you have a regression test that cost you nothing to write.

That is the whole idea. Capture passively, replay hermetically, compare honestly.

The important line in that diagram is the one going from pre_tool_call back into the model loop. Replay does not stub your tools. It runs the real agent loop, real prompting, real tool schemas, and intercepts at the hook that fires immediately before a tool executes. The model sees the same world it saw during capture, and the process sees nothing.

Capture never changes a tool call or an answer. It only observes. The one place it does intervene is on the way to disk: everything written into a case is redacted first.

A case file is a security artifact, because it contains real prompts and real tool output. So writes go through one function that chmods the temp file before the atomic rename:

And there is no home-directory guessing. regress_home() asks the same resolver the rest of Hermes uses, so a gateway running three profiles writes each profile's cases into that profile's home instead of one shared pile.

serve() is the whole safety story in about fifteen lines:

Out of scope means silence, not a veto. If the session does not belong to this replay, the hook returns {} and the agent behaves normally. A plugin that blocked every tool call whenever any case was armed would freeze every other session on the machine, which is what my first version did.

Failing closed is mandatory. If fixture matching throws, the exception must not escape into a path where Hermes ignores the veto and runs the shell command. block with an apologetic message is the only safe return.

Matching is by tool name and arguments, in order. Each recorded call can be consumed once, and an exact argument match wins over a loose one:

If the model calls a tool that never appeared in the capture, replay answers with a note saying exactly that and continues. You want to see the divergence in the transcript, not have the run crash on it.

Replay has to run inside a real Hermes process, which means the plugin cannot hold the armed state in memory. The CLI that arms a case and the gateway that serves the hooks are different processes, and a subprocess environment variable does not reach a hook running inside a long-lived gateway. My first attempt used an env token and appeared to work in tests while never firing in the runtime that mattered.

/regress run arms it with a TTL and spawns hermes chat -Q --oneshot --query-file prompt.txt. The next pre_llm_call sees a fresh session, compares the turn's message to the armed prompt, and if they match, claims the case for that session_id and task_id:

Every design choice in that function came from a review comment.

Plugins load at process start. Edit a plugin, and the running gateway is still executing the old code. Replay against that gateway and the veto hook never runs, which means the tool calls execute for real. That is the failure mode the plugin exists to prevent, so it happened to the plugin itself during development.

preflight() is a 30 line probe that proves interception before any case runs. It arms a synthetic case, asks the runtime to run echo regress-probe, and checks two things: the session got claimed, and the tool call hit the fixture path.

Both conditions, because either one alone is a false positive. Hooks firing without a claim means scoping is broken. A claim without a served call means the veto is not in the path.

If scoping is wrong and a tool runs for real, the plugin cannot take it back. The shell command already happened. What it can do is refuse to report that run as clean:

replay/hook.log gets a line for every call the hooks saw while a case was armed. An empty log during a run is the fingerprint of a runtime that never loaded the plugin. That log is the difference between "replay is safe" as a claim and as an observation.

Comparison is deliberately boring: normalised answer similarity, tool plan similarity, and optional expectation rules.

Four verdicts, because "the answer changed" and "the agent stopped doing the work" are different problems:

Expectations are plain substring rules, which sounds weak until you use them. expect: ["no action needed"] on a turn that should conclude cleanly is a better regression test than any similarity score.

/regress report writes Markdown with a table per case and a "What broke" section showing recorded answer, replayed answer, recorded tools, replayed tools side by side. /regress export adds JUnit XML for CI plus a ZIP whose manifest is hash chained, so a reviewer can tell whether the bundle was edited after the run:

The suite has 32 tests, and they exercise the parts that broke during review: claim exclusivity, late claim rejection, scoping by session and task, preflight routing through the claim path, fail-closed serving, redaction, and the honest live-execution report.

Being specific about limits, because a testing tool that oversells itself is worse than none:

/regress selftest proves interception in the runtime you are actually talking to. Run it first. Every hour you spend debugging "why did nothing replay" is an hour that command would have saved.
