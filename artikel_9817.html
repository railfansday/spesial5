Async work you can restart: who owes a reply, and how the runtime knows

Tanggal: 2026-11-21

Every async agent bug I've met is the same bug: the system forgot who owed whom what. Here is the smallest set of promises that fixes it — stated as mechanisms, so you can test them in your own runtime this week.

Post 7 was about what crosses the boundary when a lead hands a specialist a piece of work. Post 8 was about schedules you can trust to fire. There is a third thing, sitting between them and bigger than either, that almost nobody specifies: the asynchronous reply. A dispatch goes out, the parent keeps working, and at some point a result must come back. Whether that result arrives at all, whether the parent can answer without it, and what happens if the process dies in the gap — those are three separate properties, and most "multi-agent" systems quietly leave all three to the model's good manners.

I write for AgentParley, so read the product parts knowing that. The mechanism below is what I'd build into anything that dispatches work, including a system with no vendor in it. Everything I attribute to AgentParley is on a public docs page I've linked at the end.

You have seen it as a symptom. The agent answered "all done" while two helpers were still running. Or it said "all done" and one helper had failed quietly. Or the machine restarted, the reply never went out, and the work did happen — so the retry ran it twice. Each of those is a missing promise, not a bad prompt:

The rest of this post is one mechanism per promise, and a test for each.

The first thing to get right is that the parent's call to dispatch must not block. If dispatch() waits for the child, you have a function call with extra latency, and you have lost the parallelism you were paying for.

At AgentParley the tool is start_subagent. In the docs' words, it returns immediately with the child's id; the lead keeps working; the child's result arrives later as a message that wakes the lead. Independent specialists run in parallel up to the plan's concurrent-run limit, and beyond that they queue rather than fail.

That gives you a shape you can draw: parent → dispatch (returns an id) → parent continues → result arrives as an inbound message. Two consequences fall out, and both matter.

The parent must have somewhere to put "still running." A parent that dispatched and immediately needs the answer is a parent that will poll. Polling is a model call that learns nothing, which is the most expensive sentence in agent engineering. The dispatch should be fire-and-note: the runtime records the outstanding child id, and the parent gets on with the next piece. If the runtime is doing this right, the wait itself is an event, not a loop.

The report must not arrive only as a tool result. A tool return is bound to the turn that called the tool. If the answer can only come back as a tool result, then a long child forces either a blocked turn or a timeout. A child's report has to travel as an ordinary message into the parent's conversation — which is why it can land in a later turn, after the parent has done other work. This is also the property that makes async work survive a restart, which we'll come to.

At AgentParley the report path has a name — report_to_caller — and the docs are explicit about what happens when a child forgets to use it: in the default reply mode, its final message is delivered anyway. You can tighten that: reply modes are implicit (only what the agent sends), auto (default — its final message to whoever is owed one), and all (every message, streamed). If it fails, the lead is told rather than left waiting forever.

Take a moment on how specific that is, because it's the kind of sentence that separates a specification from a hope. "If it forgets, we deliver its last message anyway" is a statement about a recovery path. You can test it: give a child a task and instructions to never call the report tool. Did the parent hear anything?

The second promise is the one that decides whether your system's "done" means anything: a parent may not answer its human while a child it dispatched still owes a report.

Post 7 argued that this has to be enforced by the runtime, because a model asked politely to wait will, under pressure, decide it has enough and answer. The mechanism is worth stating precisely now, because it has more hooks than the sentence implies. In the docs: while any live subagent still owes it a report, or it has open to-dos, the lead's answer to its human is held back.

And the mechanisms come with their own honest edge, which the docs state rather than bury: a specialist-on-specialist message — message_agent — does not get an automatic reply in every case. Where the message lands matters. If the target answers the agent that messaged it this turn, the reply goes back there. If the target also talks to a person on a channel, the message may land in that channel chat, visible where the person reads it, and only the standing thread between two agents comes back automatically; in a channel chat the target answers with message_agent when it needs to. The docs draw the conclusion in as many words: a crew prompt must not count on an automatic answer. That is a real limit, and it means the gate protects the subagent-parent relationship, not an informal question between colleagues.

Here is the promise that makes the other two survive a restart.

A restart is only a resume if the system knows, after the crash, who still owed what. That means the interesting state is not "the parent is running" — it's the set of outstanding obligations: which child sessions are live, which parent sessions have an unanswered report, which saved replies were composed but not delivered.

The mechanism at AgentParley, in the crews page's words: every piece of work is written down before an agent is woken. If a worker dies mid-step, another picks the work up. A sweep re-wakes anything left unfinished, including open to-do lists and replies still owed. And the line I'd put in neon: a reply that was saved but not delivered is re-sent without paying for another model call.

Only the middle one is what "restart-safe" means, and notice that it requires the composed answer to be a durable artifact distinct from the turn that composed it. This is the same intent-before-effect rule as post 5, applied one layer up: the effect here is "the human is told", and the intent is "this reply exists and has not been delivered".

This is also where the restart interacts with cost in a way I want to be blunt about, because it's the easy place to imply something we don't claim. Re-delivering a saved reply saves a call because no call is made at all — not because anything was cached. Prompt caches live minutes, not days; a restart hours later is a cold start if it re-runs. The saving is zero calls versus one call, and that's the whole of it.

Two rules you can check in thirty seconds, because they tell you whether the async layer is a special case bolted on or part of the permission model.

Depth. By default at AgentParley a subagent cannot spawn subagents of its own — one level of hierarchy: lead → specialists. No crews of crews. That is a deliberate limit, and it matters for async work: an unbounded spawn tree is an unbounded set of outstanding obligations, and the completion gate has nothing to gate on if the tree has no shape.

Outcome as data, not an exception. The plugin-side call — host.session.subagent.spawn — returns { outcome: "created" | "forbidden" | "depthExceeded", sessionId } and never blocks. Forbidden reach and depth limits come back as values, in the same shape as success, so the calling code branches on a field instead of catching an error. The peer message call returns { isDelivered, isCanceled, cancelReason }, and "not delivered" is likewise data — including when a plugin vetoed it. If dispatch and delivery report their refusals as exceptions, the caller's error path is the part nobody tests.

And a fuse worth naming because it's exactly the kind of thing async systems get wrong: if plugin code reacts to a message by sending a message, each generation is a hop, and past 4 hops from one original event the platform-API members are withheld for that generation — so two agents ping-ponging die quietly instead of spending the night together.

Four tests, in the order I'd run them. Each one produces a specific observation, not an opinion.

I'd add one manual check that isn't a test so much as a habit: after a long mission, read the parent's transcript and the children's. If you can't tell from the record alone who was owed what at every point, no test will save you, because the bug will be invisible until it's a double send.
