AI helped us write more code. So why aren't we shipping more?

Tanggal: 2026-11-25

Posted on Nov 25 • Originally published at algogridlabs.com • AI-assisted

You've probably heard someone on your team say it, or said it yourself: "we're writing way more code with AI, but we're not really shipping faster."

It sounds like a feeling, but there's now data behind it.

So the code got written faster, and then it sat in a queue.

Writing code was never the only slow part of delivery. Someone still has to understand the change, check it against what was asked, test it and say yes. When an agent helps one developer open more pull requests, the same few reviewers suddenly have more to read. Nothing about their day got faster.

None of this means AI coding isn't worth it. It means the gain only shows up when the steps around the code keep up. Here's what we've seen make a difference.

1. Fix the ticket before the code. Spend five more minutes on the story: acceptance criteria, what's out of scope, and how someone will test it. An agent can draft that from a bug report, a screen recording or a feature brief, and a person reads it before work starts. A clear ticket removes a lot of "is this what we wanted?" in review.

2. Keep it to one story per pull request. Small pull requests get reviewed the same day. Big ones wait for "when I have a proper hour", which can be days.

3. Write your review rules down. Most teams keep them in a senior developer's head. Put them in a file: what blocks a merge, what's only a note, and what the linter already covers. Then let an agent do a first pass against those rules, so the person reviewing starts from a short list instead of a blank page. The person still decides.

4. Put a limit on the review column. If more than a handful of pull requests are waiting for review, the team reviews before anyone starts something new. It sounds simple, and it's the change that helped us most.

5. Make testing easy to check. A recorded walkthrough of each test case, or at least a clear test plan with results, saves the tester from repeating everything by hand.

6. Measure the wait, not the output. Pull requests opened per week is an easy number to grow and doesn't mean much on its own. Time from "ready for review" to "merged" tells you whether you're actually going faster.

AI made the writing quicker. The next improvement is in everything around the writing: clearer tickets, smaller changes, review rules that are written down, and testing someone can sign off quickly.

Where does work wait longest in your team right now? We'd honestly like to know.
