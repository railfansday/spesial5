Recording a Product Demo Video with Playwright: 6 Things That Break

Tanggal: 2026-11-17

Playwright can record a video of a browser session in three lines. That makes automating a product demo video look like an afternoon's work. The recording part is. Making it look like something you would put on a landing page takes a lot longer.

Demo Tool AI is a tool that makes narrated product demo videos by driving a web app in a cloud browser. This post looks at the recording half of that job: six things that break, and the code that fixes each one. All of it applies if you write the Playwright script by hand and never touch an AI model.

You can watch six demos recorded this way, of Notion, Plausible, EspoCRM, Grafana and the tool's own site, on its examples page.

The cursor is the easy one. Log every mouse move with a timestamp while the script runs, then draw your own cursor over the footage in the edit. The other problems took more work.

A demo zooms in on the thing being clicked, so the recording needs more pixels than the output. The obvious fix is deviceScaleFactor: 2 on the context.

That does nothing when the frames are captured through the Chrome DevTools Protocol screencast: they come back at CSS size whatever the emulated scale is. What works is setting the scale on the browser window itself and leaving the viewport unemulated:

A 1280×800 page is then recorded at 2560×1600, and a 2× zoom in a 1080p output is still sharp.

After a click in a single-page app, the route changes on the client. There is no new document, so waitForLoadState('load') has already passed, and networkidle often has too. The next action runs against the previous screen, or against a skeleton.

Fixed sleeps are the usual patch, and they are wrong in both directions: too short on a slow day, dead air in the video on a fast one.

A better approach is to wait until the page stops changing:

This removes most of the fixed sleeps from a script.

locator.fill() sets the value in one step. On camera that looks like text teleporting into the field, so you switch to keyboard.type() with a delay. About 55 ms per character looks natural.

The delay turned out to matter for correctness too. Editors that react to what you type, such as Markdown shortcuts or mention pickers, need the keystrokes to arrive one at a time. In Notion, typing ## at the start of a line turns it into a heading. Typed with no delay, the shortcut didn't fire and the line stayed as plain text with two pound signs in it. At 55 ms it worked.

If a flow passes at full speed and fails during the recording, or the other way round, check the typing speed first. It helps to rehearse every script at the same pace it will be filmed at.

A demo script gets replayed: once to rehearse, once to record, and again every time the UI changes. CSS classes do not survive that.

Each step in a Demo Tool AI script stores one way to find its element again, in this order of preference: test id, role and accessible name, placeholder, label, visible text, and a CSS selector as the last resort.

One trap: when two elements share a name, the role locator and the text locator pick different ones. Notion has an icon button and a sidebar row that are both called "New page". By role you get the icon, which opens a menu. By text you get the row. Choose on purpose.

The obvious order is to record the session, generate the voiceover, then line them up in the edit. Every change to the script then means redoing the alignment.

Demo Tool AI does it the other way round. The voice is made first. The narration carries markers for the word where each action should happen:

Speech is synthesized sentence by sentence, so the time of every marker in the audio is known. The recording is then paced to the voice:

The edit fixes whatever is left. If the picture gets there first, it holds on a frame. If the sound gets there first, it waits.

The narration itself is a writing problem. If you draft it with an LLM, there are prompts for each part of the script in making a product demo video with Claude.

Demos of real products need a login, and the recording shows everything on screen.

One more, if the URL comes from a user: route the browser's traffic through a filter that refuses local, internal and cloud-metadata addresses. A recording browser that will open any address is otherwise a way into your own network.

If you have one product, a handful of flows and an engineer who likes this kind of thing, the snippets above get you most of the way. You will still need text-to-speech, captions, the zoom and cursor pass, and an encoder, but none of it is exotic.

The script is the part that doesn't scale. Somebody has to write the steps and the narration for every flow, and rewrite them after every release. That is the part Demo Tool AI hands to an agent. With an AI demo video generator you paste a URL and say what to show, and the agent explores the app, writes the steps and the narration, then records, voices and edits the video.

It has limits: it records web apps only, so no desktop or mobile apps and nothing on localhost.

Bot checks on login pages. When a CAPTCHA appears, the run stops and asks a person. That is the honest answer, but it isn't automation.

And pauses. When the picture runs late, the voice waits for it, and if the marker sits in the middle of a sentence you can hear the gap. For now the rule is simple: give every marker enough words to cover its action, and put it at the start of a sentence when the action is slow. It works, but it is a rule, not a solution.

If you would rather not build this, Demo Tool AI does it from a URL, and the first video is free. If you are building it yourself: what do you use to decide that a page has finished loading?

Disclosure: I work on Demo Tool AI, so read the last section with that in mind. Everything before it works with plain Playwright and no AI.

One detail that didn't fit in the post: slow pages. The recording doesn't pause for a loading spinner. It films straight through, logs the wait as an event, and the edit cuts most of it out, keeping a short piece so the page change doesn't look like a jump.

A question for anyone who automates browsers: how do you decide that a single-page app has finished loading? Waiting for the DOM to go quiet works on most pages, but anything with a live ticker or a chat widget still needs a hard ceiling.
