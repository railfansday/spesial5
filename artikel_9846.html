I have been running production PostgreSQL systems for over sixteen years, and if there is one lesson that never gets old, it is this: a table that behaves beautifully at ten million rows can turn into a nightmare at five hundred million. Indexes stop helping as much as they used to, vacuum runs longer, and every maintenance window gets scarier. When I see queries slowing down despite solid indexing, partitioning is usually the next tool I reach for. Let me walk you through how I actually implement it.

Partitioning takes one logical table and splits it into several physical sub-tables called partitions. From the application side, nothing changes. You still insert into and query one table name. Behind the scenes, PostgreSQL decides which partition each row belongs to and routes reads and writes there automatically.

I like to compare it to a filing cabinet with labeled drawers. If everything is dumped into one drawer, finding last year's invoices means digging through everything ever filed. Label the drawers by year, and you go straight to "2024" and search only there. That is the entire value proposition, in one image.

PostgreSQL, from version 10 onward, gives me three built-in partitioning strategies. I pick based on the shape of the data.

Range partitioning splits rows by a range of values, most often dates or numeric IDs. This is my default choice for time-series data, things like orders, logs, or events that accumulate by day or month.

List partitioning splits rows by a discrete set of values, like country codes or status flags. I reach for this when the data naturally falls into named buckets rather than a continuum.

Hash partitioning spreads rows evenly across a fixed number of partitions by hashing the partition key. I use this when there is no natural range or list to key off of, but I still want the data spread out for performance and manageability.

One detail I always double check with new team members: the range bounds are inclusive at the bottom and exclusive at the top. A row dated exactly 2024-02-01 lands in orders_2024_02, not orders_2024_01.

I create indexes on the parent table, and as of PostgreSQL 11 they propagate down to every partition automatically. That saves me from having to remember to index each child individually.

I do not have to tell PostgreSQL which partition this belongs in. It reads the created_at value and routes it to orders_2024_01on its own.

A few things trip people up every single time, so let me save you the pain.

Your primary key has to include the partition key. PostgreSQL cannot enforce uniqueness across partitions unless the partition key is part of the key.

Foreign keys referencing a partitioned table are not supported. Foreign keys going out from a partitioned table are fine, but nothing else can point at it with a foreign key constraint.

Partition pruning only works if the partition key shows up in your WHERE clause. Leave it out, and PostgreSQL has no choice but to scan every partition.

Do not go overboard with granularity. Hundreds of tiny partitions will hurt planning time more than they help. For time-series data, I have found monthly or quarterly partitions to be the sweet spot in most systems I have run.
