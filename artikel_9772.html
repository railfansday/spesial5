For each of the 27 units we or together the digits it contains into seen. While we do that, we check if a digit was already there, and if so, the unit has a clash. No other solver in the series has needed this check so far, and youâll see in a minute why we need it now. Hint: it has to do with the parallel nature of the system.

The candidates are the usual not-yet-taken numbers, and we compute them for all cells. We end up with four answers:

This reads much like the solver loop weâve written many times, but it works completely differently, because there is no loop. The circuit that is synthesized has 81 candidate calculators and a long chain of comparators for the minimum that are all settling at once.

Why the clash check? Here, because of parallelism, forced fills in every forced cell in the same cycle. If two cells in the same unit are both set to the same number, we write both of those in the same cycle and nothing checks at the end. Instead, we check the unit for duplicates at the next cycle, and treat a clash like any other unsolvable branch.

So weâve successfully parallelized our work, including our mistakes! Fun!

RUN is our whole solver as an if chain. If the board is dead, we backtrack. If there are forced cells, we fill all of them and come back next cycle to continue our work. If the board is full, weâre done and set HALT and all our stopping variables.

We push the current board, the cell, and the remaining candidates, and then write the lowest candidate into the board. pick & -pick isolates the lowest set bit, and pick & (pick - 1) clears it, so together they split the mask into what to try now vs.Â what to try later. Otherwise we restore the saved board, try the next candidate, and go back to RUN. The entry stays on the stack with one fewer candidate, ready to come back if this oneâs a dud, too.
