Vibe coding accelerates prototyping dramatically, but "working" and "safe" are different properties. This playbook provides a repeatable, ordered checklist for auditing AI-generated Node.js applications before you run or ship them.

Vibe coding, the practice of prompt-driven development where a developer describes desired functionality and an AI model generates the implementation, accelerates prototyping dramatically. But "working" and "safe" are different properties, and AI models optimize aggressively for the former. A vibe-coded app security audit addresses the gap that opens when generated code ships without systematic review.

AI code generators pull from training corpora that include insecure patterns, deprecated APIs, and supply-chain antipatterns. The generated code often contains hardcoded secrets, unnecessary dependencies, overly permissive configurations, calls to eval(), disabled TLS verification, or lifecycle scripts that execute arbitrary commands during installation. None of this requires malicious intent from the model. It reflects the statistical reality that training data contains plenty of insecure-but-functional code, and the model has no threat model of its own.

The risk compounds because vibe-coded projects often include dependencies the developer never explicitly chose. The AI picks packages based on pattern frequency, not security posture, which means typosquatted or abandoned libraries can slip into a package.json without anyone noticing.

This guide targets Node.js and npm projects generated or scaffolded by AI tools. The goal is a repeatable, ordered checklist that answers two questions: "Is this safe to run?" and "Is this safe to ship?" The workflow chains together Git, npm script suppression, static analysis via Semgrep, dependency auditing, and Docker network isolation into a single copy-paste process. Every step builds on the previous one. Skipping steps weakens the guarantees downstream.

An AI-generated package.json may contain lifecycle scripts such as preinstall, install, or postinstall that execute arbitrary code the moment npm install runs. A postinstall hook pointing to curl ... | sh would download and execute a remote script with the permissions of the current user. Running this on a development workstation exposes SSH keys, cloud credentials, browser sessions, and anything else accessible to that user account.

Docker containers provide process and filesystem isolation, but they allow outbound network connections by default. A malicious script running inside a container can still exfiltrate data to an external server unless you apply additional flags. This step creates the isolated environment; later steps lock down network access and suppress script execution.

The --ignore-scripts flag tells npm to skip all lifecycle hooks during installation. This prevents preinstall, install, and postinstall scripts from executing untrusted code during dependency resolution. The npm docs for ignore-scripts say that npm does not run scripts specified in package.json files. Commands that explicitly run a script, such as npm start or npm test, still run it later, so the flag only protects the install step. Review any git-sourced dependencies in package.json manually, since they come from outside the npm registry.

Automated audits only catch known CVEs. Typosquatted packages, where the name is one character off from a popular library (e.g., lodasg instead of lodash), won't appear in vulnerability databases because they may not have been reported yet. Manual heuristics to flag suspicious packages: a first publish date within the last 30 days, only a single version published, fewer than 100 weekly downloads, or a name that is a slight misspelling of a well-known library.

This lists direct dependencies and their direct children (one level of transitive dependencies). Scan for names that look unfamiliar or suspiciously similar to popular packages. A project generated by an AI model may include packages the developer never heard of, and each one deserves a quick check on the npm registry page. For a complete tree, use --depth=Infinity (note: output may be very large for projects with many dependencies).

Semgrep matches code structurally using AST-based rules rather than regular expressions. In our experience, this produces fewer false positives for structural patterns like nested function calls or variable-flow tracking, though results depend on which community rulesets you use and how well-maintained they are. Semgrep ships with free, community-maintained rulesets covering JavaScript, TypeScript, and dozens of other languages. For AI-generated code, Semgrep has rules that cover the categories of issues models frequently produce: eval() calls, hardcoded secrets, insecure fs usage, disabled TLS verification, and dangerous child_process invocations.

Inside the container, Semgrep is already installed via the Dockerfile's virtual environment. Run the auto-configured ruleset, which selects community rules based on detected languages:

Important: --config=auto fetches rules from semgrep.dev at scan time and sends anonymized telemetry by default. The SEMGREP_SEND_METRICS=off environment variable is set in the Dockerfile to suppress telemetry globally within the container. For fully offline operation (e.g., when auditing proprietary code that must not be exposed to any external service), download rules while connected -- such as semgrep --config=p/javascript -- cache the resulting rules directory, and pass --config= instead of --config=auto. This step must be performed before applying --network none in Step 5, since network access is required to fetch rules.

Language detection triggers automatically with --config=auto, pulling the appropriate rule bundles for JavaScript and TypeScript files found in the scan path. Results appear inline with rule ID, severity, file path, and line number.

Semgrep output displays each finding with a rule ID (e.g., vibe-eval-usage), severity level (ERROR, WARNING, INFO), the file path, the line number, and the matching code snippet. Not every finding is a blocker. An eval() call inside a well-known JSON schema validation library's internals is different from an eval() on user-supplied input in an Express route handler. The next step provides a framework for making that distinction systematically.

Raw scan results need classification to become actionable decisions. The framework below splits findings into four categories based on two axes: how dangerous is the finding, and when must it be resolved.

Consider a Semgrep finding of vibe-eval-usage in routes/api.js at line 42, where user input from req.body.code is passed directly to eval(). That is a pre-run block: the application would execute arbitrary code from any HTTP request. Contrast that with the same rule firing inside node_modules/ajv/dist/compile/codegen.js, where eval is used internally by a widely adopted JSON schema validator. That falls into the accept category -- and with the paths.exclude on the custom rules above, findings from node_modules are already suppressed.

A finding of vibe-hardcoded-secret flagging const API_KEY = "sk-proj-abc123..." in config.js is a pre-ship block. It is safe to test locally in an isolated container, but deploying it would expose the key. The fix is to move the value to an environment variable before any merge to a shared branch.

By default, Docker containers connect to a bridge network with outbound internet access. As described in the Docker networking documentation at docs.docker.com/engine/network, the default bridge network provides NAT-based external connectivity. A malicious application running inside a default container can reach any external endpoint, so a malicious script can exfiltrate data to any server it can resolve.

After triaging all findings and confirming no pre-run blockers remain, copy the repository to the shared bind-mount so it is accessible from a new network-isolated container, then execute the application with network access completely disabled:

Removing all external network interfaces is exactly what --network none does. The loopback interface (lo) remains available inside the container, but no DNS resolution or outbound TCP/UDP traffic is possible. The application cannot make HTTP requests or reach any external endpoint.

When the application legitimately requires network access, such as connecting to a localhost database, create a user-defined network with docker network create --internal instead of reverting to the default bridge. Containers on an internal network can talk to each other but not to the outside. This permits container-to-container communication while still blocking internet-bound traffic.

1. mkdir -p "$(pwd)/app" && docker run --rm -it -v "$(pwd)/app:/audit/app" vibe-audit /bin/bash -- create host directory and enter disposable container

2. git clone --depth 1 /audit/repo && cd /audit/repo -- shallow clone (to a path separate from the bind-mount)

3. jq '.scripts' package.json -- inspect lifecycle hooks

4. npm install --ignore-scripts -- safe install

5. npm audit --omit=dev -- vulnerability check (requires npm >= 8.7.0; use --production on older npm)

6. NPM_MAJOR=$(npm --version | cut -d. -f1); [ "$NPM_MAJOR" -ge 7 ] && npm ls --all --depth=1 2>/dev/null || npm ls --depth=1 2>/dev/null -- dependency tree scan (version-aware)

7. SEMGREP_SEND_METRICS=off semgrep --config=auto /audit/repo || { echo "[FATAL] semgrep failed"; exit 1; } -- static analysis (requires network; run before Step 10)

8. semgrep --config=vibe-audit-rules.yml --validate || exit 1 && semgrep --config=vibe-audit-rules.yml /audit/repo -- custom vibe-code rules

9. Triage findings using the Pre-run / Pre-ship matrix

10. cp -r /audit/repo /audit/app/repo && docker run --rm --network none -v "$(pwd)/app:/audit/app" vibe-audit node /audit/app/repo/index.js -- isolated execution

This playbook covers only Node.js and npm. Python, Go, and Rust projects follow similar principles but require different tooling.

This playbook does not address full penetration testing, dynamic application security testing (DAST), or license compliance auditing.

The workflow also excludes runtime behavioral analysis tools such as strace or eBPF-based monitoring, which can detect malicious behavior that static analysis misses. Running strace inside Docker requires --cap-add=SYS_PTRACE and installation via apt-get install strace.

One practical caveat: --ignore-scripts may cause packages with native add-ons (such as bcrypt or sharp) to be non-functional because their compilation steps are skipped. Address these on a case-by-case basis after manually reviewing the build script for safety.

Vibe coding reduces initial coding time but shifts security responsibility entirely onto the developer who runs the output. Integrating this checklist as a CI pre-merge gate for any AI-generated pull request turns a manual discipline into an automated gate that blocks the merge on failure. When building that gate, use npm audit --audit-level=critical to fail only on critical vulnerabilities (rather than any finding), and use semgrep --error --severity=ERROR to control which severity levels produce a non-zero exit code. Run the checklist on every AI-generated PR before merge.
