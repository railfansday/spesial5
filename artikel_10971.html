A single transient database or CMS outage during Next.js ISR background revalidation can silently replace a perfectly valid cached page with a persistent 404. This is not a theoretical risk. Developers using Next.js ISR with notFound() have reported this exact failure mode, where a temporary infrastructure hiccup causes SEO damage and user-facing downtime that persists long after the underlying service recovers. The root cause is a common error-handling pattern that conflates "the data source is unreachable" with "this record does not exist." This article presents a concrete architectural fix that separates those two states, prevents Next.js from ever caching an error-driven 404, and provides an on-demand revalidation recovery strategy.

In the Next.js App Router, Incremental Static Regeneration operates on a stale-while-revalidate lifecycle. When you set a revalidate interval on a page, the first request generates and caches it. Subsequent requests within that window serve the cached version. Once the interval expires, the next request still receives the stale page, but Next.js triggers a background revalidation. This background render re-executes the page's data-fetching logic and, if successful, replaces the cached output with the fresh render.

The critical detail: the background revalidation replaces whatever is in the cache. If that render produces a 404 response, Next.js caches the 404 and overwrites the previously valid page.

The scenario, reported on Stack Overflow, follows a pattern that exists in countless Next.js codebases. A data-fetching helper wraps a CMS or database call in a try-catch block that returns null on any error, whether that error is a network timeout, a 500 from the upstream API, or a genuine "record not found" response. The page component then checks for null and calls notFound().

During a transient outage, the ISR background render hits the data-fetching error path, receives null, triggers notFound(), and the resulting 404 response is cached. The previously valid, fully rendered page is gone. When the infrastructure recovers seconds or minutes later, the damage is already done. The 404 persists until the next revalidation cycle, and if the timing is unlucky, users and search engine crawlers see a 404 for up to one full revalidation interval (60 seconds in this example, but potentially hours in production configs).

Here is the flawed pattern as it typically appears:

The getPost function treats a CMS outage identically to a missing blog post. Both return null. Both trigger notFound(). Both get cached as 404s.

When a Server Component calls notFound(), it returns a response with a 404 HTTP status code. Under ISR with a configured revalidate interval, Next.js treats this 404 as a valid cacheable response. From the framework's perspective, the page rendered successfully and produced a definitive answer: this resource does not exist. Next.js has no mechanism to distinguish between "this record genuinely doesn't exist in the database" and "an infrastructure error prevented the application from fetching it."

A successful background revalidation, including one that results in a 404, overwrites the existing cached page entirely. Next.js provides no built-in rollback mechanism when the page component returns a valid response (including a 404) without throwing an unhandled exception. If the revalidation completes without throwing, Next.js considers it successful and replaces the cache entry. An unhandled exception is the mechanism that prevents this overwrite -- the distinction the refactored code exploits. This is by design for the happy path but destructive when error handling collapses infrastructure failures into the same code path as legitimate missing records.

This fix hinges on a single architectural insight: when a data helper throws an unhandled exception, Next.js treats the background revalidation as failed and retains the previously cached page. This behavior is consistent with reported Next.js ISR behavior (see the Next.js ISR documentation and related community reports); run the local simulation test described in the Testing section to confirm on your deployment version. The distinction between throwing and returning null directly controls whether ISR preserves or destroys the cache.

The refactored data helper introduces a custom error class for infrastructure failures and only returns null when the upstream API explicitly confirms the record does not exist (a 404 response status). Network errors, timeouts, 500-level responses, and connection failures all throw, preventing ISR from caching the failure state.

Both files reside in the lib/ directory at the project root (i.e., lib/errors.ts and lib/data.ts).

Note on fetch caching: In some Next.js versions, fetch in Server Components defaults to force-cache, meaning the fetch itself may serve a cached response during ISR revalidation -- masking infrastructure failures. The refactored helper above uses { cache: 'no-store' } to ensure data is fetched live during each revalidation. If your data must be fetched live during each revalidation, add { cache: 'no-store' } or { next: { revalidate: 0 } } to your fetch call.

Only the fetch call itself sits inside the try-catch, handling network-level failures. HTTP error responses (non-404) are handled by explicit status checking after the response arrives. Only a 404 from the CMS returns null, signaling a genuinely missing record. A content-type check before JSON parsing prevents silent SyntaxError exceptions when the CMS returns an HTML error page.

The page component stays simple. It calls notFound() only when getPost returns null, meaning the CMS confirmed the record does not exist. Infrastructure errors thrown by the helper are not caught here. They propagate upward, causing the ISR background revalidation to fail gracefully and preserving the existing cache.

For direct visits (not background revalidation), an uncaught error would show the default Next.js error page. Adding an error.tsx boundary in the route segment catches errors from Server Components in the same route segment during direct page renders. It does not intercept errors during ISR background revalidation -- those are handled server-side and the user continues to see the stale cached page.

If a 404 was cached before implementing this fix, or due to an edge case where the fix was not yet deployed, on-demand revalidation provides a manual or automated recovery mechanism. Next.js exposes revalidatePath() and revalidateTag() for this purpose. revalidatePath() purges and regenerates the cache for a specific URL path. revalidateTag() invalidates all cache entries associated with a given fetch tag, useful for bulk invalidation across related pages.

A route handler that accepts a path or slug, validates an authentication secret, and calls revalidatePath() gives teams a deployable recovery tool.

Environment variable: Set REVALIDATION_SECRET in your .env.local file. Use a long, random string (e.g., 32+ characters generated with openssl rand -base64 32).

Wire this route to a CMS publish webhook so every content update purges the affected path. It also works as an admin dashboard button for manual recovery after an outage. For post-outage scenarios, teams can iterate over a list of affected slugs and trigger revalidation for each, effectively warming the cache with fresh, valid data once the infrastructure has recovered.

Cost consideration: Calling revalidatePath() for many slugs simultaneously triggers a full server-side render for each one. Revalidating 10,000 paths at once means 10,000 concurrent renders -- batch in groups of 50-100 with a delay between batches to avoid spiking compute and CDN costs.
