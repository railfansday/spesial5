Build an HTCondor Pool on Ubuntu and Run Your First Remote Job

Tanggal: 2026-11-13

Part 1 of 6 in Building and Operating an HTCondor Pool for Research Computing.

Suppose you have one training run per participant in a study and several workstations that could run them. With HTCondor, you can submit each run as a job and specify the CPU, memory, and GPU it needs. The workstations advertise what they can offer. HTCondor keeps each job in a queue until it can match it to a suitable machine. The machines that cooperate this way form a pool.

I administer the central manager for our lab’s pool. Our November 2026 inventory lists twelve machines. The workstation that hosts the central manager also accepts submissions and runs jobs. Some of the other workstations only run jobs, while others also accept submissions.

For this walkthrough, we’ll put each role on a separate Ubuntu 24.04 VM. You’ll submit a shell script and a text file from the access point (the submit node). The script will run on the worker and print its hostname and a line from the file. You’ll read both lines back on the access point.

Start with three fresh VMs on a private network. Each needs Bash, curl, sudo, and access to the Ubuntu and HTCondor package repositories. Run uname -m on the access point and worker and check that the results match. Allow TCP port 9618 between pool members. Before installing, check name resolution on each host. Substitute your own hostnames below and confirm that each resolves to its intended private address.

Start on the manager, then install the access point, then the worker. Enter the same pool password on all three. On each host, the installer uses that shared secret to generate a daemon token. The daemons use these tokens to authenticate to one another with HTCondor’s IDTOKENS method. Researchers submit jobs from their own local accounts on the access point.

If the wait times out, the job may still be queued or running. On the access point, check its state and recent events.

For workstations joining our existing lab pool, I issue the daemon token centrally. A colleague sends me the workstation’s network address. I create the token on the central manager with condor_token_create and give it to the colleague. They configure the workstation with our manager and trust domain and install the token under /etc/condor/tokens.d/ with restricted permissions.

Our central manager is configured with use ROLE : CentralManager, Submit, Execute. For a workstation that will both accept submissions and run jobs, our setup instructions specify use ROLE : Submit, Execute. I look for its schedd with condor_status -schedd and its execution slots with condor_status. Submitting a job from the colleague’s local account checks that the workstation’s schedd accepts jobs from that user. To see which workstation actually ran the job, check the hostname printed by the probe.

People also use these workstations at their desks. Our setup instructions use START = (Cpus > 0) && (LoadAvg / Cpus < 0.4) to decide when a slot can accept a new job. A workstation can remain visible in the pool while this condition prevents a new job from starting. On a partitionable slot, Cpus counts the CPUs still available. As jobs claim CPUs, the denominator gets smaller, so even an unchanged LoadAvg can bring the ratio up to the cutoff.

After the CPU test succeeds, you can configure HTCondor to let two jobs share one NVIDIA GPU. On the idle worker, check that nvidia-smi -L lists the expected card, then apply the settings below.

-divide 2 makes condor_gpu_discovery list the same device ID twice in DetectedGPUs and report half its usual GlobalMemoryMb value for matching. Two jobs that each request one GPU can therefore be assigned the same card. They share its VRAM, and either job can use more than the advertised half if enough memory is free. Once the worker advertises again, run condor_status -gpus on the access point to inspect the pool’s GPU resources.
