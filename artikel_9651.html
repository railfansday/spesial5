The path to AI FDE #25: API keys, authentication and rate limits

Tanggal: 2026-11-27

Posted on Nov 27 • Originally published at dhanushkumarsivaji.substack.com

This is a “From Zero” issue. So far, every API we’ve called has been open to anyone. Real AI APIs aren’t: they need to know who you are (so they can bill you) and they cap how much you can ask for (so one user can’t swamp everyone else). Today covers both.

You need the same setup as yesterday (#24): your api-practice uv project with httpx added (run scripts with uv run). Everything here is safe to run. We use httpbin’s practice login check, a fake API that runs entirely on your computer, and made-up tokens. No real key appears anywhere, and you shouldn’t paste one in either.

1. Authentication: proving who you are. An API key (or token) is a long random string the provider gives you. You send it with every request, and the server checks it. httpbin has a practice endpoint, /bearer, that accepts any token, so you can see both sides safely.

No key gets 401 Unauthorized, plus a WWW-Authenticate header naming the kind of credential it expects. With a key, you get 200. The standard calls this a bearer token for a reason: anyone who holds it can use it. Treat a real key like a password.

And as #23 warned: keys go in headers, never in the URL, because URLs end up in logs.

3. Keys stay on the server. Anything you ship to a browser or a phone app can be read by whoever uses it: open the browser’s developer tools, or unpack the app, and the key is right there. So the rule is simple: the provider key lives only on a server you control. The browser talks to your server, and your server talks to the provider.

4. Rate limits: how much, how fast. Providers cap how much each key can do: requests per minute, and for AI APIs often tokens per minute (tokens are chunks of text, a later issue) or per day. The limits usually depend on your account tier. Go over any of them and you get 429 Too Many Requests.

Requests four and five are turned away. (fortune.example is a reserved example name, and nothing leaves your machine.) Real limits reset over time, such as each minute, while this toy just counts.

5. Retry-After: the server tells you when. A 429 (or a 503) may come with a Retry-After header: how long to wait before trying again. The polite client reads it, sleeps, then retries, and gives up after a few tries:

Two honest caveats. Retry-After can also be a date rather than a number of seconds; this toy handles only seconds. And when there’s no header, the usual move is to wait a little longer after each failure (”backoff”). Proper retries get a full issue later in the series.

Check your understanding: your script gets 401 on one call and 429 on another. What does each mean, and should you retry either one?

Answer: 401 means the key is missing or wrong. Retrying won’t help, so fix the key. 429 means you’re over a rate limit. Wait (for Retry-After if it’s sent), then retry a limited number of times.

An API key proves who you are; send it in a header (Authorization: Bearer ... or the provider’s own name) and keep it on your server. 401 means fix the key. 429 means slow down: wait for Retry-After, retry a few times, then stop. Usage costs money, so set a spending limit before your first loop.
