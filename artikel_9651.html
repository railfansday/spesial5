SC-500 deep dive #3: "private" storage that still had a public door

Tanggal: 2026-11-28

Posted on Nov 28 • Originally published at gitlab.com

Every Thursday I post SC-500 practice questions. Every Saturday I take one exam topic and go deep: the real problem, how it works, the fix, and the exam traps. Week 3: private endpoints vs service endpoints, two features with similar names that solve different problems.

Lab story, lab names only (contoso.com). Screens are drawings, numbers are invented.

In this lab story, the storage account stlabhr01 holds HR documents. The network team said it was private: they had turned on a service endpoint for Microsoft.Storage on the subnet snet-lab-app, and set the storage firewall to Selected networks, allowing only that subnet.

None of this was a bug. A service endpoint was simply the wrong tool for what they wanted.

The key line is the last but two. A service endpoint says "traffic from this subnet to Azure Storage goes over the Azure backbone and shows up with the subnet's private address". It is about the route and source identity, for the whole service. It does not care which storage account, yours or someone else's.

A private endpoint says "this one storage account now lives at 10.20.3.4 inside my network". Traffic to it never needs the public endpoint at all, and other accounts are not reachable through it.

One private endpoint per sub-resource you use: blob, file, queue, table, dfs. The HR app only uses blob.

Create the private DNS zone privatelink.blob.core.windows.net, link it to the VNet, and add a DNS zone group to the private endpoint so the A record is managed for you. For the office over VPN, forward DNS queries for blob.core.windows.net from your on-premises DNS to a resolver in Azure (Azure DNS Private Resolver), or nothing changes for them.

Remove the office IP range that was added as a "fix", and remove the subnet rule and the service endpoint if nothing else on that subnet needs it.
