The FreeBSD Core Team is the governing body of FreeBSD.

FreeBSD Foundation: bapt@ (with most of core@ participating in monthly Foundation meetings)

We reached consensus to publish our public meeting minutes, which were previously only sent to the developers mailing list.

bapt@ created a survey for FreeBSD developers on the use of AI and LLMs. He presented the results to core@, and a summary was shared with developers. 140 developers responded.

Policy: 88% want the Project to adopt a policy, either a formal, written policy (49%) or light guidance and best practices (39%). 6% said that AI should be explicitly discouraged, and 3% that the existing contribution rules are sufficient.

AI-assisted code: 35% said it must be disclosed, 25% that it must be reviewed more strictly than human code, 22% that it should be treated like any other contribution, and 16% that it should be rejected outright.

Safeguards: mandatory human review (78%) and mandatory disclosure (69%) were requested most often, followed by provenance or licensing documentation (47%) and mandatory testing (39%).

Disclosure: 84% want AI use disclosed, either always (48%) or when its involvement is significant (36%). 79% want AI-assisted commits marked in the commit log, and 56% prefer a tag that names the tool.

Concerns: the main concerns about quality are correctness and subtle bugs (39%), licensing and provenance (26%), and maintainability (21%). 75% are somewhat or very concerned about copyright and licensing.

Principles: accountability, meaning that a human remains responsible (91%), and transparency (78%) were selected most often, and preserving code quality was the top-ranked goal for a policy.

Other uses: 65% would allow AI-generated documentation with human review. 54% would allow AI tools on Project infrastructure, most of them with restrictions, and 29% would not.

The FreeBSD Foundation asked for a core representative on the committee for the upcoming user survey. jrm@ volunteered.

On 2026-07-20, a 150 MB binary file was mistakenly committed to the ports tree. The commit broke mirroring to GitHub, which rejects files larger than 100 MB, and added a file of questionable licensing to the repository history. On 2026-07-21, core@ decided to freeze the ports repository to limit the number of commits that would need to be rewritten, and worked out a plan with clusteradm@, portmgr@, and the Git administrators. kevans@ published a signed statement on 2026-07-22 to explain the freeze and to make clear that the ports tree had not been compromised. The offending commits were removed by rewriting the history of the main branch, and package builds from the old hashes were stopped. New server-side hooks now guard against a recurrence.

The fts(3) directory traversal library, used by find(1), rm(1), ls(1), chflags(1) and other utilities, historically relied on path-based syscalls that fail in capsicum(4) capability mode.

This quarter fts gained a new fts_openat() entry point that accepts a pre-opened directory descriptor, a per-entry fts_dirfd field, and a conversion of its internals to fd-relative operations, with ABI compatibility preserved through ELF symbol versioning. A traversal can now run entirely inside a Capsicum sandbox.

As a first consumer, chflags was capsicumized to perform its work through chflagsat() on descriptors opened before entering capability mode, confining it to the hierarchies named on its command line.

This work was completed as a Google Summer of Code 2026 project.

Ongoing work on this project aims to integrate the existing proof-of-concept work into FreeBSD, and to add the following usability features:

a user-friendly configuration method to override individual bits, parts or even whole CPUID functions as needed, while keeping the rest of the host CPUID information or a pre-defined CPUID configuration

a user-friendly configuration method for the hypervisor signature reported by bhyve

a set of predefined CPUID configurations based on common x86 architecture levels, perhaps also including a set of CPUID data for a few real CPU models, and a user-friendly configuration method to choose one for a VM

There was a last minute change to the configuration syntax. Instead of using two different options cpuid.enable and cpuid.disable to enable or disable features by name, there is now a single cpuid.features option. This option accepts feature name, either prefixed with - to disable them, or prefixed with + or no prefix to enable a feature.

In addition to the abstract x86 architecture models, a number of CPU models have been implemented as pre-defined configuration file snippets. This currently ends with the Icelake generation for Intel and the Bulldozer generation for AMD.

Many more cpuid configuration options have been introduced to ease writing of CPU model configurations, such as cpuid.brand for the CPU Brand String or cpuid.vendor to override the vendor identification.

The constraints checks have been extended to allow defining bitmasks for values that can only be numerically lowered.

A new configuration option cpuid.check has been introduced to override the default action regarding the constraints checks. It takes the values fail (the default), warn, none, and fix.

Default cache configurations have been added to the x86 architecture models and all pre-defined CPU models.

A new cpuid.hypervisor option allows easy overriding of the hypervisor identification in CPUID function 0x40000000. The real hypervisor identification and feature flags can still be queried by guests from CPUID function 0x40000100.

Update manpages bhyve(8), bhyve_config(5), and bhyvectl(8).

Bhyvemgr is a bhyve management GUI written in Freepascal/Lazarus on FreeBSD. It needs a bunch of tools, mostly installed on base system, and some installed from ports/packages. The main goal is to be a desktop application with focus on desktop users to easily and quickly setup and run virtual machines on FreeBSD hosts.

Starting with version v2.0.0, bhyvemgr was migrated to client/server architecture. As a result, a server component was developed. This new component is called bhyvemgrd.

Bhvemgrd supports two ways to run privileged tasks: mac_do/mdo (FreeBSD >= 140000) and mac_do/setcred/exec_paths (only for FreeBSD >= 1501501). The process itself run under an unprivileged bhyvemgrd user.

During last two quarters, there were many bugfixes and improvements to Bhyvemgr.

These are some highlights that were added:

Add support to use VNC unix sock (vnc.sock) when FreeBSD >= 1500509

Add support for storage snapshot (only if zfs is enable)

Move to client/server architecture (unixsocket, json, etc). The bhyvemgr keeps like a client and a new bhyvemgrd app is used like a server.

Remove privileged functions/procedures. Now they are part of bhyvemgrd.

Remove sudo/doas support. It is not necessary anymore because privileged tasks will trigger from bhyvemgrd service.

Replace remote-viewer support (virt-viewer) with vncviewer (tigervnc-viewer). The vncviewer needs less dependencies and it can be ligther than virt option.

x11appjail is a specialized tool for creating, verifying, installing, and running AppJails. An AppJail is a CLI, TUI or X11 application that runs inside a FreeBSD jail but is perceived by the end user as identical (or at least very similar) to an application running directly on the host system.

This tool makes extensive use of appjail(1) as its engine; however, unlike the latter, the primary user in x11appjail is neither root nor a privileged user, but rather an unprivileged user. The fundamental goal of this project is to grant the user limited access to the jail, restricted solely to the execution of a CLI, TUI or X11 application.

This project began months ago as a prototype to establish a workflow leveraging appjail-x11(1); however, starting with version 1.0.0, it was rewritten from scratch into a unified tool that integrates all its projects, such as sysutils/appjail, sysutils/unixexec, archivers/appscript, and sysutils/jtransfer, among others. Even better, it allows for the execution of not only X11 applications but also CLI and TUI programs.

The most relevant project for x11appjail(1) is not only appjail(1), but also appscript(1). My goal with appscript(1) is to create an ultra-lightweight alternative to AppImage for FreeBSD that does not depend on FUSE, thus eliminating the need to configure vfs.usermount=1. appscript(1) allows you to create an elf(5) executable that contains everything necessary to run a self-contained executable.

The most significant changes and improvements for appscript(1) and x11appjail(1) are:

Executables created by appscript(1) extract the payload cooperatively: the leader process extracts the payload once using an exclusive lock, while other processes (if any) wait using a shared lock. Unlike previous versions, where the payload was extracted to a random directory upon every execution, this significantly improves performance by extracting the payload only once; furthermore, the resulting directory is removed by the last remaining process once no running processes remain.

appscript-verify(1) is a new command installed by archivers/appscript to verify executables signed with signify(1); it is particularly relevant to x11appjail(1)'s veriexec (see below).

x11appjail(1)'s veriexec is an internal tool used by x11appjail(1) to run an AppJail in portable mode only if it is signed with a trusted key. This tool is unrelated to NetBSDâs veriexec.

Both tools support the classic, battle-tested SHA-256 algorithm and the faster yet secure BLAKE3 algorithm. When sysutils/b3sum is available (the default if x11appjail(1) was installed from ports), BLAKE3 is the default choice, unless SHA-256 is explicitly specified in rc.conf(5).

The checksum algorithm is fundamental to both x11appjail(1) and appscript(1). In the case of x11appjail(1), the algorithm is used in internal operations such as veriexec, whereas appscript(1) uses it to verify executables. BLAKE3 has been selected as the default option because it offers greater speed without compromising security.

Attributes have been implemented in x11appjail(1) as a means for both the user and the system operator to manipulate the behavior of an AppJail. For example, a system operator can create the system attribute users.uid.perms, the content of which might be "enable_3d sound usb webcam". An unprivileged user can create the user attributes appname:profile.allow.enable_3d and appname:profile.allow.sound. Subsequently, when executing an AppJail, devices become visible or remain hidden depending on whether the user holds the corresponding permission and has authorized those permissions for the jail being created. In this case, the hardware acceleration and sound devices will become visible, provided the AppJail has incorporated the necessary logic to make them visible.

The Remote Direct Memory Access (RDMA) infrastructure provides high-performance interconnect between computing and storage nodes. It can operate over different physical networks, for instance Ethernet and Infiniband.

The implementation of the RDMA stack consists of several components. There is the core kernel infrastructure, and drivers for Host Channel Adapters (HCAs), providing access to the kernel verbs. Userspace applications never interact with the kernel devices directly, the core libibverbs library and vendor-specific userspace drivers provide unified and device-specific verbs.

Since RDMA intent of providing low-latency low-overhead operations, performant HCAs offload a lot of operations from CPU. Also, typical in-line operations like send and receive can be initiated and completed in userspace, where kernel only assists in the connection establishment and teardown. Due to this, the userspace RDMA software stack is crucial for its operations.

FreeBSD base system includes port of the so called OFED kernel core component, kernel drivers, as well as userspace core (libibverbs) and userspace drivers, for instance libmlx5 for managing Nvidia Connect-X4 and later HCAs. Over time, the kernel parts get some significant updates from the infiniband code in the Linux kernel, which become the home for updated OFED. Userspace part of OFED was converted into the rdma-core userspace project, that only supports Linux (and glibc). Since userspace drivers in rdma-core provide essential functionality, and since FreeBSD userspace RDMA components are quite outdated, the situation overall needs a resolution.

We attempted to update the in-tree userspace components by importing the series of rdma-core commits with dependencies, but it quickly proved to be not feasible. Instead we started looking at what it would take to make rdma-core compile and run on FreeBSD.

First, there were a number of missing glibc-specific APIs that were used in rdma-core, for instance, strdupa() and friends, main:tdestroy(3), some pthread functions. These were easy to handle in the base system, and addition of them benefited the whole FreeBSD porting story.

Next, and more serious, the unportable features of glibc were used everywhere in the sources, and trying to cover them all would cause huge porting patch, which is problematic to push upstream, even for cooperating upstream. Instead, the idea of using an approach similar to LinuxKPI for kernel code, was formed and developed, called LinuxAPI. Unlike LinuxKPI, which handles architectural mismatches between Linux kernel and FreeBSD kernel, in addition to the different C interfaces, LinuxAPI needs to smooth out the differences around extensions to the same core functionality defined by POSIX. It is mostly about bits that are not defined by POSIX but needed for RDMA to function, like networking interface enumeration, or discovery of the rdma-capable devices and their capabilities etc.

It seems that people consider the LinuxAPI useful outside the rdma-core porting efforts already, there is a project github.com/freebsd/linuxapi which takes the developed set of headers and extends it further. We are currently working on providing the permissive license to make the library useful without additional strings attached.

Our initial goal, also limited by the available hardware, is to have rdma-core work with the ConnectX-4 cards. Of course we welcome all vendors interested in RDMA on FreeBSD to improve the port to properly support their cards.

The result of the porting is available as the repository. Also we try to upstream the changes so that FreeBSD would become the second natively supported platform for rdma-core. The Pull Request to the github project is submitted. There is currently a blocking discussion about the way to organize CI for FreeBSD platform. Gleb Popov created the net/rdma-core port from the forked sources, which is already in the ports tree.

The kernel changes to get the port working were surprisingly small and contained. They mostly consisted of bug fixes for the code paths not previously exercised by userspace since there were no userspace. Most interesting part was perhaps the difference in ioctl(2) behavior between Linux and FreeBSD, where Linux can both return an error and copyout the data structure. The issue was already observed in the LinuxKPI, and the porting work provided the generic solution there.

The process descriptors API enhancements project continued, with the goal to allow complete process control using descriptors, in particular, debugging. I wanted to make it possible to stop reference pids as the process identifiers. The milestone for it should be a demonstration of enabling the capsicum mode for some non-trivial debugger, I selected truss(1) because it does not need neither filesystem nor network namespace accesses after attached to the target.

The semi-obvious solution there is to introduce pdptrace(2), which is equivalent to ptrace(2) but takes the process descriptor as the process designator. We need to be able to obtain the notifications of the process debugging events, which are provided by waitpid[2] syscall family for pid-based controls. And, we need a way to obtain the process descriptor for a new child forked from the debuggee, to continue tracing of all descendants.

Previously, the pdopenpid(2) system call was added, which allows to get a handle on an arbitrary process. Existing operations on the process descriptors are somewhat limited: handle owner can wait for the exit notification using kqueue(2), and with some luck retrieve the process exit status.

The last point requires some elaboration. Since the pdwait(2) call was added recently, there were some amount of hacks in the kernel to allow waitpid(2) calls on pidâs of processes created with pdfork(2). As result, the waitpid(2) caller might have reaped the process before owner of the process descriptor could call pdwait(2). Similarly, if there is more than one process descriptor opened on the same process, only the first pdwait(2) caller could retrieve the exit status with pdwait(2), making other descriptors useless.

The listed set of problems also made it very hard to correctly use the proposed pdptrace(2). The process being debugged could steal events from process descriptors and vice versa. Simply disallowing wait(2) on processes with the opened descriptors is not an option for two reasons: * backward compatibility, waitpid(2) was already allowed and existing binaries relied on it * if the debuggee used fork(2) to create a child, it expects to get the exit notification (e.g. SIGCHLD) and exit status from wait(2)

The solution was manyfold. First, we have to postpone reaping if there are either opened process descriptors, or if the process was created with fork(2), we should not reap until wait(2) is called on pid by the parent. Second, the exit status needs to be preserved in the process descriptors private data even after reaping, to allow pdwait(2) on any of the descriptors. This was implemented by providing a bitmap of the 'zombie refs' on the kernel struct proc. Each zombie reference prevents reaping, and cleared by corresponding call to waitpid(2) or pdwait(2). Only when all registered references are cleared, zombie can be reaped. If the process is created with pdfork(2) or opened with pdopenpid[2], it gets the procdesc zombie reference. If the process was created with fork(2), it gets the 'parent' zombie reference. By default, pdfork[2] also sets the parent reference to allow the waitpid(2), for compatibility. The new pdfork(2) flag PD_NOWAITPID prevents that.

Then, wait-like events must work with the process descriptors. The procdesc kqueue(2) event filter was extended with NOTE_PDSIGCHLD hints to report that pdwait(2) can retrieve tracing or exiting event on the descriptor.

Then, the pdptrace(2) was able to usefully control the target. A new ptrace call to retrieve the list of the attached processes PT_GET_CHILDREN allowed pdptrace(2) to get hold of forks.

With all the features implemented, it was possible to convert truss(1) to use only process descriptors to control the traced processes. The existing mode of using pids was preserved, and can be selected with the '-y' option as an emergency switch and to easy comparison and debugging of the new mode.

Most non-x86 platforms are relatively strict with regard to the proper alignment of the data types. On the other hand, x86 ISA allows any alignment for the operands of integer scalar operations.

Still, there is an AC control bit in the processor flags register which causes alignment exception (fault) on unaligned operations. Practically the bit is not too useful because most of the compilers generate code that relies on the freedom of the working unaligned access on x86.

Particularly interesting case of the unaligned access is when the disposition of the operand causes it to span two cache lines (which is impossible for naturally aligned data). Normal (unlocked) operations cause so called torn reads and writes. This effect become observable starting with Core2 Intel microarchitecture.

Even more interesting case is provided by the locked operations using the LOCK prefix on read-modify-write instruction with the mis-aligned data. To satisfy ISA guarantees in this case, the CPU has to either take more than one cache line for exclusive ownership in MESI-like cache coherence protocol, or exercise so called bus lock ensuring global cache ownership. Either option has very high cost and causes observable detrimental effects on other processes and virtual machines executing on the same physical host.

Since some time Intel provides a control for the lock operations that need to span more than one cache line (split locks). Turning the control on causes split locks to generate the same #AC exception as done by the AC flag, but only for the split locks, instead of all unaligned accesses.

The feature is controlled by the platform MSR and is per-CPU global, which precludes making the MSR directly available to userspace. The new sysarch(2) operation I386_SET_SPLITLOCK was developed that enables the control for the calling thread. The control is part of the machine state maintained on the context switch.

The intent is mainly to assist in catching bugs where improperly alignment locking structures are created, unlike Linux, which uses the feature to artificially penalize such processes by slowing them down. If the program code modifications are not possible, users and administrators can LD_PRELOAD a trivial shared object that turns the control on.
