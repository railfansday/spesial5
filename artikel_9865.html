Glasswing overwhelms maintainers with underwhelming findings (VulnCheck)

Tanggal: 2026-11-12

Patrick Garrity of VulnCheck has written a blog post that looks at vulnerabilities found by Anthropic's Project Glasswing since it launched on April 7, and finds it wanting:

Of the 37,966 findings Anthropic reports, only 7,349 (19.4%) have been made public. Just 217 of those have been marked fixed. The more glaring number is that 4.4% (1,654) of the project's findings have already been marked as duplicates, 7.5x more duplicates than fixes. On top of that, 419 findings have been withdrawn. It seems odd that the ledger now claims a 94.2% true positive rate, up from 90.8% at launch, when more findings have been withdrawn or marked as duplicates than fixed, likely a feedback loop missing to the triage rates listed as "True Positives".

[...] AI is a valuable tool for finding vulnerabilities, and I'm not discounting that. But seven months in, the evidence still doesn't match the launch narrative. The CVEs are a sliver of this year's total, almost none are being exploited, fixes have stalled while duplicates and withdrawals pile up, and the triage burden is shifting onto the open source maintainers Glasswing promised to help. The receipts keep coming in. They still don't reconcile.

So I'm not super surprised if not many of 40,000 potential security bugs have actually made it to "really fixed" yet.

Unusual/stale? Posted Nov 12, 2026 22:17 UTC (Thu) by Vorpal (guest, #136011) [Link] This very much matches my experience at my dayjob as well. For patch code review LLMs can be really good, with some false positives (but quite few). They find things (most) humans would never think about, especially about interactions with entirely different parts of the code base. That said, they also miss things humans wouldn't, for example about overall system design. And, as you said, the author generally have the code fresh in their mind making it easy to deal with the feedback. We have also tried finding security issues with LLMs and there it was much more of a mixed bag. A few were genuine bugs, but many of those weren't actually security issues or even worth fixing (e.g. "yes this is a theoretical bug in things we are sending, if you assume another part of the same application building on top of this staticly linked library is actively malicious, and since this is C++, almost everything assumes the API user isn't 'holding it wrong'."). And a fair share were straight up incorrect. And of course, typically no one knows exactly what the code does off the top of their heads (some parts of the code even date to the late 90s), so triaging takes way more time than dealing with feedback on a PR. It is interesting to me that LLMs does so much poorly in one area than another.
