Five Ways AI Has Changed The Case For Modernizing Legacy Manufacturing Systems

Tanggal: 2026-11-23

Dimitar Dimitrov is the founder and Managing Partner at Accedia, a leading European AI & Custom Software Development Company.

​Your company may still depend on plant, warehouse or warranty systems built 20 or more years ago. For those systems, AI has changed the case for replacing them. AI tools can now document what that software does and map how its parts connect before you approve a budget.

Most delays have two causes: Nobody knows what the old code does, and estimates for changing it are unreliable. Research shows that enterprises spend 30% of IT budgets on modernization, yet only three in 10 have modernized their core applications. Each year of delay also leaves fewer people who understand how these systems work.

Based on our recent delivery work at Accedia, I no longer advise manufacturers to fund a long discovery phase before legacy work can be estimated. AI now produces much of that analysis at the start of a project, so the estimate can be built on top of it.

AI-assisted legacy modernization in manufacturing is the use of AI to document and map the code of old plant systems before engineers change them. It shows how the parts of each system depend on each other and which code no longer runs. Engineers then replace the system in stages while it stays in use and remain accountable for every change.

AI can document legacy manufacturing software by reading the source code and describing the purpose and connections of each part in plain language. An AWS case study from March 2026 shows this at Toyota Motor Europe, which runs over 70 custom applications on legacy mainframes. The developers who know the languages behind those applications are retiring.

With Deloitte and AWS, Toyota used AI to document two of the 10 modules in its warranty application. That application contains over 1.3 million lines of code. Toyota’s remaining experts checked a sample of the output against the code and confirmed its business rules, which led to a production rollout.

For a CIO, this means the modernization decision no longer depends on what a few long-serving specialists remember. I believe documentation is the step manufacturers should fund first because every later decision depends on it.

AI now surfaces hidden dependencies and unused code before anyone sets the scope. Finding them by hand made scoping slow and expensive.

Around 30% of our application development projects in the last 12 to 18 months involved AI-assisted legacy work, according to Accedia’s 2026 AI Delivery Report. Manufacturing and automotive clients were among the main beneficiaries. In those projects, the dependency map was the most valuable output, showing which parts could change without affecting the rest. The map is now the first deliverable we expect on any legacy engagement.

Once AI has mapped the system, each component can be replaced while production continues. Until recently, only large programs could afford the analysis this approach needs. However, AI has made it affordable for smaller plant systems, too.

Across our legacy projects, most regulated clients would not accept a single large migration while operations kept running. Working in stages also means many small releases, each raising the question of who signs off on code that AI helped write.

AI tools are now standard on most of our projects. Senior engineers remain accountable for architecture, security and quality decisions, no matter how much code AI wrote. I recommend setting the same rule before the first component goes live and naming one person responsible for each change.

Legacy languages are no longer the main barrier because current AI tools can read and map code written in VB6, Windows Forms and early .NET. Together with Java applications from the same period, they make up most of the AI-assisted modernization work we have delivered recently.

In my experience, a system’s technology mix matters more to the effort than the age of its code. A system built on a single technology can be simpler to modernize than a newer one that combines several. When our engineers review a legacy scope, their first question is how many languages and platforms the system uses. Systems connected to production equipment need more effort because each connection must be tested against the real machines.

AI has moved the main risk from the code to the business reasons behind it, which only plant staff know. Plant software often contains rules that look unnecessary, such as a short pause before a command reaches one particular machine. The code shows the rule but not why it exists, so AI may treat it as safe to change and cause problems on the production line.

When we upgraded a warehouse system that a large U.S. food producer’s plant had used since the 1990s, our team made regular site visits. We needed to see the business rules and operating requirements that the code could not explain.

Before changing any component, have plant staff review the AI’s description and turn their corrections into tests. On one recent project, the AI that wrote tests worked from the requirements and never saw the source code. Its tests described what the business needed, while tests generated from old code tend to treat that code’s existing errors as correct.

Manufacturing technology leaders should pick the first component of their oldest plant system to replace and name who signs off on its AI-written code. Both decisions are now realistic because AI addresses the two main reasons for waiting: missing documentation and unreliable estimates. Bring both to your next budget review with a date for plant staff to check what the AI has documented.
