Hand an issue to an AI agent with your own model key: a checklist that keeps it safe

Tanggal: 2026-11-19

Disclosure: I work on Git A. The checklist in the first part works with any setup. The last part shows how Git A does it.

More teams are assigning issues to AI coding agents and getting a pull request back. Usually the agent runs in the cloud and uses a model you pay for with your own API key, often called BYOK (bring your own key). That's the right direction. You choose the model and the provider bills you directly.

But "assign the issue and wait" goes wrong in some predictable ways. Here is the checklist we use. Every point holds whatever tool you run.

The agent only knows what the issue says. Four short parts are enough:

The acceptance criteria are what a review checks the result against. Without them, "done" means whatever the agent decided.

The agent needs to call the model. It does not need to hold the key. If the key sits in the agent's environment, anything the agent runs can read it, including a dependency's install script. Prefer a setup where the platform makes the model calls on the agent's behalf, or where a gateway you control holds the key.

If you already run a gateway such as LiteLLM, point the agent at the gateway. Then you get one place for logging, budgets and switching models.

An agent stuck in a loop can burn an afternoon of tokens. Set two limits before the first task:

When a run hits a limit, it should stop and tell you. It should never quietly carry on.

Run each task on a clean machine or container that is thrown away afterwards. Then one task can't leave files, caches or credentials behind for the next. It also makes failures easy to reproduce: same issue, same starting point.

Ask for tests as part of the task, not as a follow-up. Then run your checks, the same CI a human change would go through, on the agent's branch. A green run of the agent's own tests alone proves little.

The agent that wrote the change shouldn't be the one that approves it. A separate review, by a person or a second agent with its own instructions, should answer one question: does this change do what the acceptance criteria say, and nothing else?

Choose a short list of paths an agent can never change without a human approving: CI workflows, deploy scripts, lockfiles, auth code. An agent should also never approve its own change.

What you want back is one reviewable change: the diff, the tests, the check results and a short summary of what was done and why. Then approving it is a decision, not an archaeology project.

At some point you'll want every running task stopped at once. Make sure you know where that button is before you need it.

Git A is built for many AI agents working on the same code at once. Every change lands on main without the rejected-push retry loop. The second half is the Agent factory: you hand an issue to an agent and get back one finished change to approve.

Agents are free: there are no per-agent seats. You prepay credit for what they use (machine minutes, storage). The model bill stays with your own provider.

The full step-by-step guide is at git--a.com/docs under "Hand an issue to an agent". Everything above is described there as it works today.

If you run several agents on one repository and want to see what the rejected-push loop costs you now, git--a.com/measure has a bash script that counts it on your own repo, using a throwaway branch. It never touches main and sends nothing to us.

What's on your checklist that isn't on mine? I'd like to hear what went wrong the first time you let an agent take an issue.
