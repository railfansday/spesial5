I built a topology map because I could not reason about agent failures from a config file

Tanggal: 2026-11-10

I have a bad habit of describing a multi-agent workflow in a config file and calling it done. The file lists the agents, the order they run, and which one hands off to which. It reads cleanly. It also hides the thing that actually breaks.

The failure I kept hitting was never inside a single agent. Agent three returned something slightly off-spec, agent four retried it with a stale context, and the whole run drifted into a state nobody had written down. When I tried to explain the incident to a teammate, I could not point at the edge where it went wrong, because I had never drawn the edges. I had a list of nodes and an assumption about the shape.

So I built a small tool that takes the graph I already have and makes me look at the shape. Paste an agent graph or a plain description of the workflow and AgentOrchestrator turns it into a topology: nodes, edges, and the direction of each handoff. It is not clever. It does the thing I was too lazy to do by hand.

A config file is a sequence. A workflow is a graph. Those are different objects, and the gap between them is where my incidents lived. In a sequence, every step looks equally important. In a graph, some paths are longer than others, and a single node can sit on every path from entry to result.

Once I had edges on a page, two questions became answerable. Which chain of steps determines whether the run finishes at all, and which node, if it fails, has no alternative route around it. The first is the critical path. The second is a single point of failure. I had been shipping workflows with both and no vocabulary for either.

AgentOrchestrator flags the critical path and raises SPOF alerts on the edges that have no redundancy. Seeing "this node sits on every path" in plain text changed how I wrote the next version. I added a fallback on that handoff, or I accepted the risk on purpose. Both are better than not knowing.

Here is the honest scope. You paste an agent graph or a description. You get a topology graph, a critical-path flag, SPOF alerts, and retry suggestions for the edges that look fragile. That is the whole feature set.

It reads what you give it. It does not attach to your running system, does not watch live traffic, and does not replay production traces. If the graph you paste is wrong, the topology is wrong, faithfully. I considered wiring it to a live orchestrator so it could observe real handoffs. I did not, for two reasons. First, that turns a ten-minute design check into an integration project with credentials and permissions. Second, the most useful moment to draw the graph is before the system exists, when changing an edge costs nothing.

The retry suggestions are heuristics on the shape of the graph, not a tested recovery policy. A suggested retry on an idempotent edge is a reasonable hint. On a step with side effects it is a starting point for a discussion, not an instruction to ship. I would not let a diagram choose my retry semantics without reading them first.

Static analysis of a description is cheap and portable, and it is also limited. It cannot tell you that an agent is slow, that a model is flaky under load, or that a handoff occasionally truncates a field. Those are runtime facts. A topology is a structural fact. I built for the structural question because that is the one I could answer without a deployment, and because the structural mistakes were the ones I kept repeating.

There is a second limit worth stating plainly. This is a decision-support tool. It is not legal advice, not a certification, and not a live audit harness. It helps you reason about a design; it does not certify that the design is safe. If a governance regime requires evidence about how an AI system is built and overseen, a topology diagram is one input among several, not the evidence itself.

I still think drawing the edges earns its keep. Most of my multi-agent bugs were architectural, and architecture is visible in a graph in a way it is not visible in a list. If you maintain a workflow you cannot draw, AgentOrchestrator will at least get the edges onto a page.
