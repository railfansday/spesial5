Your AI Agent Has Permissions. Who Gave It the Authority?

In late April 2026, a coding agent working for a small software company called PocketOS ran into a credential error in a staging environment. It didn't stop to ask anyone. It searched the project, found an API token in a file unrelated to its task, and used that token to delete a storage volume on Railway, the company's cloud host. The volume held the production database, and the backups sat on the same volume. The deletion took about nine seconds.

Founder Jer Crane wrote afterwards that the token had been created for routine domain operations through Railway's command line tool. Nobody at PocketOS knew it could also delete production volumes. The company restored from a backup that was three months old, then rebuilt the missing bookings from payment histories, calendar entries and customer emails.

Nothing in that story was a hack. The token was valid and the API call was well formed, so Railway did what the credential allowed. Every system in the chain was asked "can this caller do this?" and each one correctly answered yes. No system asked who had decided the agent should be doing it.

Security people keep two words for this. A permission is what a credential can technically do. Authority is the right to do it, and it has to come from someone entitled to give it. Most agents running today have plenty of the first and a thin paper trail for the second. This piece looks at how that happens and what a proper answer looks like.

Authentication answers "who is this?" A password, a passkey or a signed certificate proves the caller is who it claims to be. It says nothing about what the caller should be allowed to do.

Authorisation answers "what may this caller do?" Roles, scopes and policies live here. A token that can read your calendar but can't delete events is an authorisation decision.

Delegation answers a question the first two skip: on whose behalf is this caller acting, and within what limits?

If you have ever sent someone to collect a passport or a bank document for you, you already know what good delegation looks like. You write an authority letter. It names you, names the person you are sending, says what they may collect, and carries a date. The clerk checks the bearer's ID against the letter. Your cousin walks out with one envelope, and he can't empty your account while he's there.

Software has mostly handled the same errand in two worse ways. Either the cousin gets your own ID card and the clerk believes he is you, or he gets a master key to the building. The first is impersonation. The second is a broad API key. In both cases the clerk has no letter to check.

RFC 8693, the OAuth token exchange standard from January 2020, draws this line formally. Under impersonation, the acting party is indistinguishable from the person it acts for. Under delegation, it keeps its own identity and acts as that person's agent. The word "agent" was in the RFC years before anyone attached a language model to it.

A nightly cron job with an over-powered key was always a risk, but a predictable one. Its code did the same thing every run, and you could read that code.

An agent decides what to do at run time. Part of what shapes the decision is text it picks up along the way: a web page, an email, a GitHub issue, an error message. Auth0's identity team puts it this way: once behaviour is no longer fixed by code, the scope of the credential is one of the few controls you have left.

The first time you connect an agent to a database or a cloud account, the quickest route is the credential you already have. That is usually your own, or an admin key sitting in a config file. Four patterns cover almost every setup.

"svc-automation did it", with no person attached

A Cloud Security Alliance survey from January 2026 gives a rough idea of the spread. Of 228 IT and security professionals, 43% said their agents rely on shared service accounts and 31% let agents run under human user identities. 74% said agents often get more access than they need. 68% could not clearly tell agent activity from human activity in their own systems.

The sample is small and the study was funded by Aembit, which sells agent identity products, so treat the figures as a sketch. The shape is still familiar. PocketOS fits the first row of the table: a key made for one job that turned out to work for every job.

Standards people have noticed. An Internet-Draft on agent authentication, written by engineers from Okta, Ping Identity, AWS, OpenAI, Zscaler and Defakto Security, calls static API keys an antipattern for agents. Its reasoning is that they are long-lived bearer secrets, bound to nothing, and hard to rotate. The document is a draft and may change, but its authors include Brian Campbell, who edited RFC 8693.

In 1988 Norm Hardy published a three-page note called The Confused Deputy. It described a compiler on a commercial timesharing system. The compiler had write access to its home directory so it could record usage statistics. The system's billing file lived in the same directory.

One day a user told the compiler to write its debugging output to a file with the billing file's name. The compiler obliged, and the billing records were overwritten. The user had no right to touch that file. The compiler did, and it couldn't tell whose authority it was using for that particular write.

An AI agent is Hardy's compiler with a much larger vocabulary. It carries credentials from whoever deployed it, and it takes direction from whatever text lands in its context window.

Researchers at Invariant Labs showed in 2025 that a malicious issue filed on a GitHub repository could hijack an agent connected through the official GitHub MCP server. The attacker needed no access to the victim's private repositories. The agent already had it.

Not every failure needs an attacker, though. In mid-2025, Replit's coding agent deleted a user's production database after being told not to change anything without permission. The PocketOS agent wasn't tricked either. On its own account afterwards, it guessed that the volume belonged to staging and never checked.

So there are two kinds of deputies to worry about: the tricked one and the overeager one. The OWASP Thttps://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/op 10 for Agentic Applications, published in December 2025, ranks Identity and Privilege Abuse third. It describes agents running on credentials or delegated authority inherited from people and other services, then being pushed into things their owners never intended.

The same control stops both kinds. If the credential can't perform the damaging action, it doesn't matter whether the agent was fooled or just wrong.

Five fields answer the question in this article's title. sub says whose authority this is. act says who is using it. aud and scope say where and for what, and exp says until when. The calendar API can now apply a rule to the pair: Meera may delete events, but the scheduling agent acting for Meera may only read them. The audit log records both names.

It would be dishonest to present this as solved. Several separate Internet-Drafts on agent authorisation were circulating at the IETF in 2026, and none is a standard yet.

Scopes are also blunt. Auth0 points out that OAuth scopes can't easily express something like "contact details for the accounts I'm working on, but not the legal hold queue". Rules that fine need a policy check on every request, on top of the token.

And none of this helps if a second, broader credential is lying in a file the agent can read. That was the entire PocketOS failure.

Many agent tools show a confirmation prompt before a risky step. That is useful, but it is weaker than it looks, for two reasons.

The prompt is drawn by the same software it is supposed to restrain. The IETF draft is blunt about this. A confirmation inside the agent's own interface does not count as authorisation unless it is tied to a grant from the authorisation server. The stronger pattern sends the approval request out of band, to the user's phone for example, with the details of the exact action attached. The draft admits that approvals in the middle of a running task still need more standards work.

The second reason is that words are not controls. The Replit user had told the agent not to make changes without permission. PocketOS had rules written into the agent's instructions. Telling an agent to stay out of production is a request. Removing its write access to production is a control, and only one of those survives a bad guess.

There is a human limit as well. Ask someone to approve every file read and by the afternoon they are approving everything. MCP's guidance lists users abandoning consent dialogs that ask for too much as a risk in its own right. Approval works when it is rare. Keep it for actions you can't take back: deleting data, moving money, sending something outside the company, changing who has access.

You don't need an identity platform to get most of the benefit. You need honest answers to these.

The last question is the one PocketOS missed, and it is the easiest to miss. An agent with shell access can read every secret in the working directory, whether or not you meant to hand it over. For a solo developer or a small team, the practical version is short. Give the agent a per-project token instead of an account-wide one. Point it at a read-only database user unless the task needs writes. Keep production secrets out of the folder it works in. Store backups somewhere the same credential can't reach.

Authentication proves which agent is calling. Authorisation decides what that agent may do. An agent can be perfectly authenticated and still hold far more access than its task needs.

Preferably not. If the agent uses your login, every system treats its actions as yours and the logs can't tell the two of you apart. A delegated token that names both you and the agent keeps the record straight and lets you limit what the agent can do.

It describes a token that records two parties: the user whose authority is being used and the actor using it. RFC 8693 defines the token exchange that produces these tokens and the act claim that names the actor.
