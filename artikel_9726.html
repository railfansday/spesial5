The most expensive part of asking an LLM about a PDF is usually the PDF. Ask 20 questions about a 100-page PDF in 20 separate API calls, and you've sent 2,000 pages of input. At Anthropic's estimate of 1,500 to 3,000 text tokens per page, that's 3 to 6 million input tokens before you even count a single page image. While prompt caching can help reduce the bill, you're still sending the whole file every time. That means each new question still has the model working out table structure from a text layer that doesn't even know what a table is.

The better pattern is to separate ingestion from answering questions. Parse the document once, store the result, and send the model the sections or fields it needs, with page references so every answer can be checked.

That's the job the Nutrient Data Extraction API is built for: it turns PDFs, scans, images and Office files into Markdown or structured JSON, and it can tie each extracted value back to the page and position it came from.

To see why this matters, start with what an LLM API actually receives when you send it a PDF.

Anthropic's and OpenAI's APIs handle PDFs in a similar way.

Anthropic's docs say Claude converts each page into an image, and the text from each page is extracted and provided alongside it. OpenAI's docs describe the same approach for vision-capable models: both the extracted text and page images go into the model's context.

That's surprisingly good for a quick question about a short document. It starts to fall apart when you need exact numbers, from long documents, or the same document queried again and again.

A PDF doesn't store tables. It stores bits of text at coordinates. In the text layer, a row like "Q3 revenue | 4.2M | 3.9M" can come out as a column of numbers with the labels three lines later. The page image helps, but the model has to rebuild the grid from pixels every time. That's where line items drift, merged cells collapse and a number lands in the wrong column. It gets worse when a table crosses a page break and comes back as several unrelated fragments.

Two-column papers, sidebars, footnotes and headers that repeat on every page all get stored in whatever order the PDF writer chose. A model reading the text layer can stitch the end of column one onto a footnote, then carry on into column two. Nothing in the output tells you it happened.

A scanned contract or a phone photo of a receipt usually has no text layer unless someone ran OCR on it first. The model gets only the image and does its own reading. When it misreads a digit, there's no text layer to compare against, so nothing flags the mistake.

Ask a model what the termination clause says and you'll get a fluent paragraph. Some APIs, including Claude's citations feature, can point to the passage an answer came from. That helps, but you're still trusting the model's reading of the page, and you don't get a typed value you can validate against a schema. For anything that gets audited, like finance, insurance, legal or healthcare, an answer you can't trace to a specific value and location is still a draft.

Anthropic estimates 1,500 to 3,000 text tokens per page, plus image tokens for each page image. OpenAI's docs also note that sending both text and page images can increase token usage. Prompt caching can cut the cost of repeat reads, but it doesn't fix the tables, the reading order or the scans. Anthropic's docs also warn that dense PDFs can fill the context window before you hit the page limit.

Data Extraction splits the job in two. It reads the document once and turns it into structure. Your LLM reasons over that structure as many times as you like. You keep whichever model you already use. It just stops doing the parser's job.

Sending the PDF straight to the model is perfectly reasonable when:

Parsing pays off when the same documents get queried more than once, when the numbers have to be right, or when someone has to prove where a value came from. The trouble starts when the raw-PDF pattern quietly becomes production: thousands of documents, exact figures, scans, and nobody checking. That's the moment to add Data Extraction to your pipeline.

LLMs are good at reasoning and not very good at being a PDF parser. Parse each document once with Data Extraction, keep the citations, and send the model tables and fields that are already in the right order. You stop paying to resend the whole file with every question, the answers are easier to check, and every value can be traced back to its source.
