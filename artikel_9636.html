A knowledge base for your repo and your AI agent

Tanggal: 2026-11-26

Posted on Nov 26 • Edited on Nov 26 • Originally published at Medium

The code tells you what a system does. It doesn't tell you why totals are rounded per line, why a declined card is never retried, or that someone already compared three payment SDKs last spring.

That knowledge usually lives in a wiki nobody reviews, or in one person's head. My AI coding agent has it even worse: every session starts from zero, so it happily suggests the approach we rejected a month ago. I wanted the reasons in the repo, where both people and agents read them, and a check that tells me when they stop being true. So I wrote knowledge_base.

It works with any language and any repo. Dart is only needed to run it.

init creates the docs folder, the three indexes, the glossary, an optional config file, and the agent wiring. It picks the agent setup your project already uses, or you choose with --agent claude, agents, both, or none. Files that already exist are kept, and running it again only updates its own block between two markers.

new starts a doc from a template and adds the index line for you. Decisions get the next free number, and research notes get today's date.

Those two fields are the whole trick. If a path matches no file, the code was moved or deleted. If git shows commits under those paths after the updated date, the code moved on without the doc.

It exited with code 1, so CI would fail on the two errors. The stale doc is only info by default. A doc can be right even after the code changes, so the tool asks you to re-read it instead of blocking the merge. If your team wants it stricter, one line in knowledge_base.yaml turns it into a warning or an error.

The for command goes the other way. Give it files and it lists the feature docs that cover them:

With --since it looks at everything your branch changed, which makes a good last step before a merge.

At the end of a task you type /capture in your agent, optionally with a topic, like /capture payment retries. The agent goes back over the session and tests each thing it learned against three questions. Would someone act differently for knowing it? Is it missing from the code, tests, and history? Is it still true at the end of the session?

Whatever passes gets a home: a decision, a feature doc, a research note, a glossary term, or a one-line note in the nearest CLAUDE.md. Then it shows you a plan with the files and the rule behind each one. It writes only after you approve, and it never commits.

The bar is high on purpose. Most tasks add nothing, and the skill says so plainly. I'd rather have ten docs that are true than a hundred that are noise.

The github format turns findings into annotations on the pull request. Give the checkout fetch-depth: 0 so the stale check can see the full history. There is also --format json for scripts and --only to run a subset of checks.

A knowledge base that lives in your repo, and a checker that keeps it true.

The code shows what a system does. It does not show why a decision was made which caveat will mislead the next reader, or what was already investigated and rejected. knowledge_base gives that knowledge a fixed place in the repo, as plain Markdown, reviewed in the same pull request as the code it describes It wires the docs into your AI coding agent, so the agent reads them before it works and proposes what to keep when it is done.

It works with any language and any repo. Dart is only needed to run it.
