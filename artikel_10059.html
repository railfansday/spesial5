A Look at Datastar

Tanggal: 2026-11-06

I have always been interested in frontend solutions for building web applications. Even though I’m more of a backend programmer, I really dig all the different techniques people come up with for creating browser-based apps that are both reactive (reflecting remote state in real-time) and interactive (responding to user actions).

Over the last few years, I’ve been looking at different frontend frameworks and libraries, to see how they work, and what I can learn from them. I adore Svelte, which is really smart and efficient. Its sister framework SvelteKit inspired the file-based routing in my own web framework for Ruby, Syntropy. I also really like the approach of the Phoenix framework to building reactive apps using LiveView, which is an amazing technology that builds on the solid concurrency foundation of Elixir/Erlang.

Many people have tried to recreate the same functionality for other languages or frameworks, with varying degrees of success. Recently, Marco Roth came up with ReActionView, which promises to bring reactive views to Rails apps, building on his previous work on Herb, a set of tools that improve on the developer experience of writing ERB templates for Rails apps.

All those different technologies are certainly impressive, but they all are tied to specific languages/frameworks: Svelte/SvelteKit is a JS framework, LiveView is for Phoenix/Elixir, ReActionView is for Ruby on Rails, LiveWire is for Laravel/PHP, etc.

And then there’s Datastar, which dubs itself “the Hypermedia framework”. It is somewhat similar to other frontend declarative frameworks/libraries such as HTMX or Alpine.js, in that interactivity/reactivity is done declaratively by adding attributes to HTML tags. But what is different about Datastar is that it insists on keeping state where it should be, such that it doesn’t try to copy server state to the client and keep it in sync with the server. Instead, the server continuously sends updates (in the form of HTML patches, or signal patches) to the client. In that respect, Datastar is more like LiveView, but without the coupling to Phoenix/Elixir. In fact, Datastar offers SDKs for different languages and frameworks, including Ruby (the Ruby SDK is maintained by Ismael Celis).

I find this approach so refereshing! With Datastar, you can use any backend technology in order to build reactive web apps. Furthermore, Datastar relies on SSE (server-sent events) for streaming updates from the server to the client, instead of the somewhat older approach of using a WebSocket connection used in technologies such as LiveView, or HotWire (the current go-to solution for Rails apps).

While SSE does not provide a full-duplex connection to the server (meaning, you can’t use an SSE request/connection to send data from the client to the server), it provides two important advantages over WebSocket: A WebSocket connection normally requires establishing a separate HTTP/1.1 connection to the server (there’s partial support for WebSocket over HTTP/2, but that depends on the browser and the server/reverse proxy used. HTTP/3 support is very limited as far as I could tell). In contrast, SSE requests can be multiplexed on top of an HTTP/2 or HTTP/3 connection, along with any number of other concurrent requests. Secondly, because SSE requests are just normal (streaming) HTTP requests, the server can use standard HTTP compression in order to achieve significant reduction in bandwidth.

The Datastar wire protocol is based on the SSE response format, where each event contains an (optional) event: entry and one or more data: entries. Distinct events are separated by double newline characters (\n\n). In this case, we’re sending a datastar-patch-signals event that tells the browser to update signal values. The patched values are expressed as a JSON object where the keys correspond to signal names and the values correspond to the signal values.
