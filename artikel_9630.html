Implementing Transactional API Idempotency With Node.js and PostgreSQL

Tanggal: 2026-11-27

Idempotency keys are supposed to make retries safe: the client sends the same key on every attempt, and the server runs the operation once and replays the saved response after that. Most implementations keep the keys in Redis, next to the API, while the operation itself writes to a database. If the server crashes after the database write and before the key is updated, the two disagree.

In my guide to idempotency in APIs with Node.js, I build an idempotent() wrapper for Express with an in-memory store and then a Redis store, and I mention this gap near the end: if the server dies after the work but before the response is saved, a retry can run the work again. This article picks up from there. I reproduce the double charge for real, and then close the gap by putting the key and the payment in the same PostgreSQL transaction.

Everything below was run with Node.js 24.21, Express 5.3.0, pg 8.23.1, the redis package 6.3.1, Redis 8.10.2 and PostgreSQL 18.6 (both in Docker), on Windows 11 with Git Bash, in November 2026. The output is copied from those runs.

That's two payments for one idempotency key. The lock expiration that frees a key after a crash is what lets the work run twice. The code does what it was written to do, but Redis and Postgres can't commit together, so the key says "not done" while the database says "done".

If the operation's side effects are writes to your own Postgres, the fix is to store the key there too and do everything in one transaction: claim the key, insert the payment, save the response, commit. If the process dies at any point before COMMIT, Postgres rolls back all of it, the key included. A retry then finds no key and no payment, and runs normally.

The important detail is that the handler receives db, the connection that holds the transaction, and must use it for its writes. If it used pool.query(), the payment would be committed on another connection, outside the transaction, and we'd be back to two systems that commit separately.

Notice there's no processing state anymore, and no lock with an expiration time. The uncommitted row is the lock, and it disappears when the transaction ends, whether it commits or the connection dies.

The INSERT into payments ran, but it was never committed. When the process died, its connection closed and Postgres threw the transaction away, so neither the payment nor the key exists. I restarted the server and retried with the same key, twice:

One payment in the table. The same key with {"amount":9900} returns 422 Unprocessable Entity, like in the guide. And no waiting for a lock to expire: the retry worked right after the restart.

With the Redis store, a retry that arrives while the first request is still running gets 409 right away, and the client has to try again later. With Postgres, the second INSERT ... ON CONFLICT DO NOTHING sees a row with the same key that isn't committed yet, so it can't know whether that row will exist or not. It waits. When the first transaction commits, the INSERT does nothing and the wrapper replays the saved response. If the first one rolls back, the INSERT goes through and the retry does the work itself.

For short operations that's nicer for the client. For long ones it's a problem: every waiting duplicate holds a connection from the pool, and pg.Pool has 10 by default. A client stuck in a retry loop could use up the pool by itself.

The trade-off is that it only works when the side effects live in the same database as the keys. When they don't, it doesn't matter where the keys live: you still need to pass the key downstream.
