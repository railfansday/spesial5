LLM structured output remains one of the most persistent pain points in production systems. Developers building on top of large language models routinely encounter inconsistent response structures, missing fields, hallucinated keys, and malformed JSON that breaks downstream logic. A single unexpected null where an array was expected can cascade through an application and take down an entire pipeline. The core issue: LLM outputs are, by default, untyped free text masquerading as structured data.

Two levels of structured output support differ in what they guarantee. JSON mode, available in providers like OpenAI and Gemini, guarantees that the model emits syntactically valid JSON. It does not guarantee any particular shape. The model might return {"foo": 42} when the application expected {"sentiment": "positive", "rating": 5}. Valid JSON is not the same as correct JSON.

Schema-constrained mode goes further. It enforces a declared JSON Schema at the token-generation level: the provider guides token decoding to produce output conforming to a specific structure. OpenAI supports this through the response_format parameter with type json_schema. Google Gemini offers it via generationConfig.responseSchema. vLLM provides schema-constrained decoding through its guided_json parameter. The strictness and subset of JSON Schema supported varies across providers, but the core mechanism is the same: constrain token sampling so only schema-valid sequences are generated.

Function calling (also referred to as tool calling) provides an alternative path to structured output. When a tool is defined with an input_schema, the provider forces the model to emit arguments matching the declared schema. This is Anthropic's primary structured output mechanism for Claude, which does not offer a dedicated response_format JSON schema mode. Instead, developers define a tool whose input schema matches the desired output structure, and the model returns the structured data inside a tool_use content block.

Use function calling when the application also needs to route actions based on the model's decision. Use response_format schema when the goal is purely typed data extraction. Both mechanisms benefit from the validation layer described below.

TypeScript's type system operates entirely at compile time. It erases all type information at runtime, which means a JSON.parse call returns any regardless of what interface was declared. Zod fills this gap by providing runtime type safety: it validates that a parsed object actually conforms to the expected shape, with rich error messages that pinpoint exactly which field failed and why. When an LLM returns "rating": "five" instead of "rating": 5, Zod reports the exact path, expected type, and received value. This level of detail is essential for debugging malformed LLM responses.

The zod-to-json-schema library converts a Zod schema into a standard JSON Schema object, enabling a single schema definition to drive both runtime validation and provider-level schema constraints.

This ProductReviewSchema becomes the single source of truth. The same Zod object validates LLM responses at runtime, generates the JSON Schema sent to providers, and infers the TypeScript type used throughout the application. There is no separate interface to keep in sync.

OpenAI's response_format parameter with type json_schema provides token-level schema enforcement. The JSON Schema generated from Zod is passed directly into the API call.

When strict: true is set, OpenAI requires that the schema include additionalProperties: false and that all fields appear in the required array. Zod excludes .optional() fields from required by default; restructure them using .nullable() or a union to satisfy strict mode. Verify the JSON Schema output before sending it to the API for any schema that uses optional fields. The returned content is a JSON string that can be passed to JSON.parse and then validated with Zod.

The same JSON Schema works with Google Gemini's generationConfig.responseSchema, demonstrating the portability of the Zod-driven approach.

Gemini's schema support has notable subset limitations. It does not support $ref for schema references, and its handling of complex oneOf constructs is limited. The $refStrategy: "none" option passed to zodToJsonSchema earlier inlines all references, which avoids the $ref problem. For schemas involving discriminated unions, test against Gemini specifically to confirm support.

Anthropic's Claude models do not expose a response_format JSON schema mode. Structured output is achieved by defining a tool whose input_schema matches the target JSON Schema. The API call includes a tool definition with the ProductReview JSON Schema as its input schema, and the model returns the structured data inside a tool_use content block within the response.

The tool_use block's input field holds the structured object, not the top-level response content. Extract that specific block rather than attempting to JSON.parse the entire response body. The same Zod schema validates the extracted object identically.

Even with schema-constrained generation, responses still fail validation. A provider might not support strict mode for a particular schema feature. The model might truncate long responses, producing incomplete JSON. Function calling can return partial arguments when the model's context window is exhausted. For these reasons, the architecture follows a three-step flow: send request, parse and validate with Zod, and on failure, retry with the validation error injected into the prompt so the model can self-correct. A hard upper bound on retry attempts prevents infinite loops and runaway API costs.

The function is generic over T, which is inferred from the Zod schema. The fetchResponse callback abstracts away the provider entirely, accepting an optional feedback string that gets injected into the prompt on retry attempts. Parse errors and Zod validation errors are both handled, with feedback constructed from structured Zod issues rather than raw error text. The buildFeedback function caps the number of issues and truncates the message length to prevent overly long or adversarial content from being re-injected into the prompt. The StructuredOutputError thrown on final failure carries the last set of Zod issues for observability and logging.

Note that each retry incurs an additional API call with associated token cost and latency. The maxRetries parameter controls the number of retry attempts after the initial call, so maxRetries: 2 results in up to 3 total API calls.

The returned value carries the full ProductReview type. No type assertion or manual casting is needed. The same pattern applies to Gemini, Anthropic, or any other provider by swapping the callback implementation.

For production systems, combining response_format JSON Schema with the Zod validation wrapper provides the strongest guarantees. The provider-level constraint eliminates most malformed responses at the source, while the Zod layer catches edge cases and provides type safety that persists regardless of which provider is in use. The retry mechanism acts as a safety net that fires infrequently when both layers are active, keeping costs and latency low.

Schemas beyond 3 levels of nesting increase token usage and raise failure rates during constrained generation. Flatten object hierarchies where possible; doing so reduces truncation probability and gives Zod simpler error paths to report on validation failure.

Never use open-loop retries with LLM APIs. Two to three retries (three to four total API calls) is a practical default when provider-level schema constraints are not active. With schema-constrained generation enabled, a single retry handles the most common failure mode: truncated output from long responses. Log every failure with the full Zod issue set for observability so your team can identify schemas that consistently cause problems.

The JSON Schema acts as a contract between the application and the LLM provider. When it changes, re-test against each provider. A field added to the Zod schema that Gemini cannot express, or a constraint that triggers an OpenAI strict mode rejection, will only surface at runtime. You will only catch these failures before production if you validate schema changes against each provider as part of your CI or deployment process.

Forget to set additionalProperties: false on an OpenAI strict mode call? The API rejects the schema outright, with an error message that does not always point to the root cause. OpenAI strict mode also requires every field in the required array. Gemini does not support $ref or complex oneOf constructs, making inlined, flat schemas the safer choice. Anthropic's tool use returns the structured object inside a tool_use content block. Attempting to JSON.parse the entire API response rather than extracting the specific block is a common source of bugs.

The pattern presented here forms a three-layer defense. Provider-level schema constraints catch malformed output at generation time. Zod runtime validation catches anything the provider misses. Bounded retry with error feedback gives the model a chance to self-correct. The Zod schema is the single source of truth powering all three layers, eliminating the synchronization burden of maintaining separate type definitions, JSON Schemas, and validation logic.
