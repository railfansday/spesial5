How to Build Multi-Tenant SaaS in Symfony Without Sacrificing Database Isolation

Database-per-tenant is the safe way to build a B2B SaaS on Symfony. Every workspace gets its own PostgreSQL database, its own queue and its own bucket, so a missing WHERE tenant_id = ? cannot leak anything and a big customer can be moved to a bigger server by changing a DSN. The usual price is a deployment per tenant: a php-fpm pool, a couple of Messenger workers and a scheduler, always on, whether the tenant is used or not.

That price is fine while every tenant pays. It stops being fine the day you add a free plan. In our case two out of three workspaces had no paid plan, most of them had not been opened in weeks and their always-on processes were the main reason the nodes ran out of memory. Cost grew with the number of tenants, not with their usage and at a few hundred free tenants it would have eaten half the revenue of the paying ones.

The standard fixes trade the isolation away. Merging everything into one database with a tenant_id column means a data migration for every table and a leak waiting for every forgotten filter. A schema per tenant keeps the data apart but needs a search_path per connection, which breaks behind a transaction pooler and still runs N migrations.

This article takes the third road: keep a database per tenant, share the processes. One Symfony 8.1 deployment serves every free tenant placed on it. Each HTTP request and each queued message names its tenant and three small adapters follow that name: a DBAL connection that reconnects to the tenant's database, a cache decorator that namespaces by tenant and a Messenger transport that reads every tenant's stream. The same image still runs a dedicated deployment for paying tenants, with one environment variable flipped. Controllers, handlers and repositories do not change.

We'll build it step by step on a small demo, measure what a tenant switch costs and talk about when you should not do this.

Everything that used to come from a dedicated deployment's environment is derived from one uuid:

The current tenant lives in a static holder:

A static holder is unfashionable and here it is the right tool. The database connection and the cache decorator need the tenant below the level where services are injected and the value is per request or per message, not per service. Injecting a "current tenant" service into a hundred constructors would give you a hundred places that captured the wrong tenant the moment a worker handles two tenants in a row.

Which brings us to the one rule everything else depends on. Read the tenant at call time, never in a constructor and never into a property. A worker keeps its services alive across messages and in shared mode consecutive messages belong to different tenants. In the production codebase this rule is a unit test that scans src/ for constructors touching the tenant.

The $default slot is what makes the dedicated deployment work unchanged. current() never falls back to "some" tenant: on a shared deployment with nothing set, it throws. A request that reaches tenant data without a tenant is a bug and a loud NoTenantException is cheaper than a quiet row in the wrong database.

SingleTenantResolver::boot() calls TenantContext::setDefault(new Tenant($uuid)) in single mode and setDefault(null) in multi mode. It is the only class that reads TENANT_UUID. A dedicated deployment therefore runs every request, command and message for its own tenant, exactly as it did before this work. A shared deployment has no default and must be told the tenant each time.

A shared deployment addresses a tenant as /tenant_/…. The obvious implementation is a route prefix and it is the wrong one: every path() call in Twig and every generateUrl() would need the tenant parameter. Symfony already has a mechanism for "this app lives under a sub-directory": the request's base URL. Make the prefix the base URL and routing sees the path without it while every generated URL keeps it.

Request::getBaseUrl() derives the base from SCRIPT_NAME, so rewriting SCRIPT_NAME to /tenant_/index.php is all it takes. The kernel applies it before anything else sees the request:

A listener at priority 2048, ahead of the firewall, turns the prefix into the tenant:

The rules are deliberately strict. On a dedicated deployment a prefix naming another tenant is a 404; a request without a prefix is fine, because its ingress strips it. On a shared deployment a request without a prefix is a 404 unless it is the health check and MultiTenantResolver answers 404 for a tenant that is not placed here. The resolver has no fallback branch.

Same process, same controller, no route parameter. notesUrl comes from generateUrl('notes_list') and carries the prefix because it is the base path. The database field is the next section.

Doctrine's DBAL has a wrapper_class option: your own subclass of Doctrine\DBAL\Connection, used for the connection service. DBAL calls connect() before every query, which gives us one place to pick the database:

The dedicated deployment is untouched. Its own tenant is the default, so databaseFor() returns the configured dbname from DATABASE_URL. Any other tenant gets tenant_ on the same server.

A tenant change inside a transaction is a bug, so it throws. Reconnecting would silently commit nothing and lose the first half of the work. If you hit this, the code that opened the transaction is holding a tenant across a boundary it should not cross.

There is one EntityManager. When the tenant changes, the worker clears it (next section), so no entity of tenant A survives into tenant B's message. Metadata and query caches stay global, because the schema is identical in every tenant database. The result cache, if you use one, goes into the tenant namespace like any other application cache.

Application caches hold tenant data: computed stats, rendered fragments, the scheduler's last-run state. Since Symfony 7.3 every cache adapter implements NamespacedPoolInterface, so a decorator can hand each tenant a sub-namespace of the same pool:

Again the dedicated deployment's keys do not change, so its caches stay warm through the deploy that introduces this.

One trap with tag-aware pools. Symfony stores tags in the pool's root namespace, shared by every sub-namespace. If tenant A invalidates the tag product_list, it drops tenant B's product_list entries too. Prefix the tags with the tenant namespace as well as the keys. The demo's pool has no tags; the production one does and this is where its decorator differs from the one above.

Caches that are platform-wide by design, such as a revoked-tokens list that other services write, must not be decorated. Decide per pool and write the decision down next to the pool.

This is where most multitenancy write-ups stop and where most of the cost sits. A dedicated deployment runs its own messenger:consume processes against its own Redis stream. We want a shared worker to read every placed tenant's stream, without changing the senders: other services push into tenant- streams today and they should keep doing exactly that.

The transport keeps its name. Only its DSN changes with the mode:

Routing, #[AsMessageHandler(fromTransport: 'async')] and the messenger:consume async command line are identical in both modes. A custom transport factory claims the tenant-multi:// scheme and builds this:

Reuse Symfony's RedisReceiver per tenant instead of writing a multi-stream XREADGROUP. Consumer-group creation, claiming of entries a dead worker left pending, ack, reject and keepalive then behave exactly as on a dedicated deployment and they are tested by Symfony, not by us. All the receivers share one phpredis client, so the connection count does not grow with tenants.

Rotate the starting tenant. $this->next moves past the tenant that just delivered, so a tenant with a deep backlog cannot starve the others out of a worker that polls in order.

Stamp the tenant from the stream name, nowhere else. The stream a message came from is the one trustworthy tenant id, because the sender chose it from the tenant's uuid. TenantStamp is added on receive and stripped on send; it never crosses the wire.

The worker side is a listener on three Messenger events:

The priorities are the point. Messenger's own retry and failure listeners run at 100 and -100. Setting the tenant at 1024 and clearing it at -1024 means a retry is sent back to that tenant's stream and a failed message is written to that tenant's messenger_messages table, because doctrine://default resolves through TenantConnection while the tenant is still set. The demo proves it with a job that always throws:

Tenant A's database has no messenger_messages table at all, because nothing of A ever failed. app:tenant:failed is twelve lines: set the tenant, run Symfony's messenger:failed:show|retry|remove, clear the tenant.

Sharing workers means sharing a budget. Without a limit, one tenant's automation that queues ten thousand messages holds every worker for an hour and the other ninety-nine tenants on the deployment notice. The rule we settled on is a cap per tenant and stream kind: at most TENANT_INFLIGHT_CAP messages of a tenant being handled at once across all shared workers. The rest wait on that tenant's own stream. Nothing is dropped, nothing fails and the paying tenants are on dedicated deployments anyway.

get() skips a tenant at its cap, ack() and reject() release the slot, keepalive() refreshes the key's TTL while a long handler runs. The demo queues four 4-second jobs for tenant A and posts a note for tenant B half a second later, with two shared workers and a cap of 1:

B's note was handled in the same second by the second worker. A's jobs ran one at a time on the first, 16 seconds for the burst, while a worker stayed free for everyone else.

The trade-off is in that expire(…, 180). A worker that dies between took() and done() leaves the slot taken until the key expires, so that tenant's queue pauses for up to three minutes. The alternative, a lease per message with a heartbeat, costs more Redis traffic per poll than the cap saves. We took the three minutes and run workers with --keepalive so a long legitimate message keeps its slot alive.

A shared deployment needs to know its tenants and a tenant needs to be movable between placements without redeploying anything. A Redis hash does both: tenant:placement maps each uuid to a placement name, shared-1, shared-2 or dedicated. The service that creates tenants and handles plan changes writes it; the deployments only read it.

Workers call tenants() and amortise one HGETALL over 30 seconds of polling. A php-fpm request starts with an empty process and asks about one tenant with one HGET, because reading the whole registry per request would cost a call per placed tenant.

Moving a tenant is a change of one hash field. Its streams keep their names, so senders notice nothing; the workers of the new placement start reading them within 30 seconds and the entries the old workers left pending are claimed after redeliver_timeout, the same way a rolling deploy already behaves. Its database and bucket do not move at all.

A release must migrate every placed tenant's database before the new pods start. The obvious loop, "for each tenant, set the context, run the migrator", shares one process across tenants and a migration that fails half-way for tenant 17 leaves the process in a state you do not want tenant 18 to inherit.

So each tenant gets its own process, running as a dedicated deployment of that tenant:

The child sees TENANT_MODE=single and a plain DATABASE_URL pointing at tenant_, so Doctrine's own commands run untouched and --concurrency bounds how many run at once:

A failed tenant is reported and the others continue. In production the command also writes a migration-blocked: flag that the request resolver turns into a 503 for that tenant alone, until a later run succeeds.

The tenant switch is a reconnect. app:bench:switch runs SELECT 1 three hundred times on one tenant, then three hundred times alternating tenants, against Postgres in Docker on a laptop:

Six milliseconds per switch. A web request switches at most once, at its first query, so it pays a connection it would have paid anyway under php-fpm. A worker pays it on every message whose tenant differs from the previous one, which with the rotation in section 6 is most messages. For free tenants doing a few hundred background jobs an hour that is noise. If your shared tenants process thousands of messages a minute, add a small per-worker pool of open connections keyed by database before reaching for PgBouncer, whose transaction mode you would have to check against advisory locks and session settings first.

Memory is where the saving is. In dev mode on PHP 8.4 a Messenger worker of this demo sits at 49 to 65 MB RSS and a web process at 42 to 55 MB. A dedicated deployment needs its own set of those per tenant, idle or not. A shared deployment needs one set per placement. With a hundred idle free tenants the difference is a hundred sets of always-on processes against one.

The multi-mode bugs that reached our production did so because tests used in-memory transports and asserted what was dispatched, not where it landed. The demo's test boots the real kernel in multi mode against two real tenant databases and reads the result back through HTTP:

Use the real messenger.yaml, the real bus and routing and assert the destination: the row in the tenant's table, the entry in the tenant's stream, the failed message in the tenant's messenger_messages. A test that checks a stamp on an envelope will pass while a worker writes into the wrong database.

Each piece above is a decision you can take separately.

If you run database-per-tenant Symfony and most of your tenants are idle, start with the connection wrapper and the request listener, put two test tenants behind one php-fpm pool and measure. The workers are the second step and the bigger saving.
