Content-Length on Our API Host: 47 Answers Carry It, 4 Are Chunked, and gzip Flips Two More

Tanggal: 2026-11-10

Our API host uses two different ways of telling the client how long the body is, and the split falls on the size of the answer.

47 of the 51 answers I fetched carry a Content-Length header. The other 4 arrive chunked, with no length at all.

The boundary sits between two measured values: the largest body that carried Content-Length was 471 bytes, and the smallest chunked body was 1,771 bytes. I did not find the exact byte where the server switches, so I am not claiming one.

Here is the part that surprised me. I asked the same routes for a compressed copy, with Accept-Encoding: gzip.

So the smaller the body gets, the more likely it is to arrive with no length at all. The rule is not "small answers get a length". The rule is closer to: an answer that is produced in one piece and can be held in memory gets a length, and anything the server streams gets chunked.

For the record, the two big routes stayed chunked when compressed: /api/config/feature-flags came back at 520, 523 and 524 gzipped bytes, and /api/products at 1,776, 1,777 and 1,778.

A HEAD request to our API routes answers 200 with a zero-byte body, the JSON content type and no length header at all. That part is not new.

What is new to me is what it costs. I sent five HEAD requests to /api/products in a row, and the remaining-counter header fell by exactly one each time: 71, then 70, then 69, then 68, then 67. The next GET answered 66. A HEAD returns nothing, and it still spends a request from the same 120-request budget that a full GET spends. If a client is probing a list of routes to see which ones exist, those probes are billed like reads.
