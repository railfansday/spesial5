Attackers Target .NET Developers With Poisoned Job Assessments

Tanggal: 2026-11-27

Researchers discovered 13 malicious NuGet packages as part of a fake recruitment campaign that spreads malware and gives attackers access to developers' machines.

A coordinated supply chain campaign is targeting .NET developers with fake coding assignments, weaponized software dependencies, and GitHub-hosted malware capable of stealing browser credentials and establishing remote access.

Researchers at Socket discovered the campaign, which involves 13 malicious NuGet packages designed to compromise Windows-based developer environments through seemingly legitimate job assessments, according to a report published this week. The packages use fake job "Home Assessment" projects to target Windows .NET developers, with most posing as button controls for WinUI 3 and WPF, which are user interface frameworks for building applications.

"In the versions we analyzed, building or running a project that uses them downloads files from GitHub, stages a DLL side-loading pair around the Microsoft On-Screen Keyboard (osk.exe), or downloads and runs an executable," Socket researcher Kush Pandya wrote in the report.

As in similar campaigns that weaponize developer repositories and code packages, attackers are exploiting developers' willingness to download, build, and run code they believe to be trustworthy. In this case, the malicious code is disguised as part of job-recruitment exercises for .NET developers. Such campaigns can turn routine development activities into infection vectors, potentially spreading malware and malicious code through the software supply chain.

NuGet is a package manager for .NET. Socket researchers traced the campaign across NuGet, GitHub repositories, and malicious code embedded in development projects, identifying packages linked through shared attack infrastructure and techniques.

The most recent example they found was a GitHub repository created on Nov. 4 that contained a purported WinUI 3 assessment called "Mini File Vault & Tracker." The project instructed candidates to complete a three- to four-hour development exercise using a supplied Visual Studio project. However, its dependencies contained malicious code.

"Candidates are told that building the project shows the starter UI and that the work must be developed and tested on native Windows with Visual Studio 2026," Pandya wrote in the report.

Socket could not determine how the Home Assessment lures reached candidates, as researchers found "no recruiter message, email or job post for them," he added.

The attack involved two malicious NuGet packages working together. One executed code after every project build, while the other launched a staged executable when the application created its button control. This effectively turned an ordinary development workflow into an infection chain.

The investigation eventually uncovered 13 unique package names and 28 versions across those packages, as well as four NuGet publisher accounts linked to the operation.

Characterizing the campaign as posing a very serious threat to enterprises, Pandya says attackers could gain access to a "treasure trove" of sensitive information by compromising a developer's machine.

"A developer's machine holds source code, SSH keys, GitHub, package registry and cloud tokens, and browser sessions that have often already passed multifactor authentication," Pandya tells Dark Reading. "In this campaign, building the take-home project was enough to run the threat actor's code."

Beyond access to terminals and configuration files, many developers who work from a console have their command history automatically collected, he says. This can give adversaries insight into the commands developers have executed, as well as access to passwords and API keys that may have been inadvertently pasted into the command line, he adds.

Moreover, by disguising their activity as legitimate development work, attackers gain a degree of stealth and control once the malicious code is running on a developer's machine, he says.

"A threat actor could extract SSH keys and network configurations, but their access is still from an external host and must go through various security controls," Pandya explains. "If they are working directly from a developer's machine, they not only have the necessary access keys but also the expected IP address and geolocation to avoid suspicion."

As adversaries continue to weaponize code packages from legitimate sources to compromise the software supply chain, developers and security teams must remain vigilant. Socket has recommendations for both.

Developers should treat take-home coding assignments and unfamiliar projects as untrusted code, Pandya advises. Before building them, they should check for unfamiliar NuGet dependencies, additional package sources, and build scripts that could execute automatically.

"Open take-home tests and unfamiliar repositories only in a disposable virtual machine with no credentials," he recommends. "Restrict which package sources projects can use, scan dependencies before they are installed, and verify recruiters through official channels."

Organizations should also restrict which NuGet feeds developers can use and review third-party packages that contain build scripts capable of executing commands, according to Socket. They should also educate employees and job candidates about fake recruitment assessments to reduce the risk of attackers exploiting the hiring process to gain access to developer environments.

Security teams, meanwhile, should identify affected developer machines and treat suspected infections as potential credential and software supply chain compromises, rather than simply malware incidents, Pandya says.

"If a machine is compromised, isolate and reimage it, rotate credentials and tokens from a clean device, revoke active sessions, and review audit logs," he says.
