Refactoring Python ML Code With Pydantic, Modules, and Dependency Injection

Tanggal: 2026-11-18

Coming from a background in structured languages (like Go), I was shocked by the state of many AI code examples. Often, tutorials and prototypes live in Jupyter Notebooks — full of global variables, one-off code cells, and hidden state. This notebook style might be fine for quick experiments, but it falls apart in production. Code written in a linear, ad-hoc way is hard to debug, tough to reuse, and nearly impossible to maintain over time. In fact, seasoned practitioners warn that data scientists’ first draft notebooks are typically “messy and ad hoc”, and should never be handed off to engineers without cleanup .

Whether you’re a junior ML engineer, a data scientist transitioning to software engineering, or an experienced developer new to AI, the goal is the same: write cleaner, more maintainable AI code. In this guide, we’ll explore how to refactor a “messy” notebook into a production-grade Python project. We’ll cover moving from .ipynb scripts to proper .py modules, adding strict data validation with Pydantic, and using dependency injection to manage heavy resources like ML models. By applying these techniques, you’ll bring clean code principles into your ML projects — bridging the gap between exploratory analysis and reliable production systems.

In short, notebook code is like a rough draft of an essay — good for getting ideas down, bad for publishing. Just as an author must edit and restructure a draft before publishing, a data scientist or ML engineer should refactor and structure their code before deploying it. The good news: by adopting some software engineering best practices, you can dramatically improve your AI code’s quality without losing the agility of notebooks during development.

The first step toward clean, production-grade code is moving from notebooks to Python modules. Instead of one giant .ipynb file that does everything, you’ll create a proper project structure with .py files. This encourages you to encapsulate logic into functions and classes, making your code easier to read and reuse.

Production-grade AI code not only needs structure; it needs reliability. A common source of bugs in ML projects is invalid or unexpected data — maybe a field is missing, a string is in place of a number, or a value is out of range. In notebooks, we often assume our data is fine (or we hack around issues on the fly). In production, we should never assume: we should validate. This is where Pydantic comes in.

What is Pydantic? Pydantic is a Python library that uses the power of type hints (Python’s typing annotations) to validate data at runtime. You define Python classes that describe the schema of your data (by extending BaseModel), and Pydantic automatically checks that any input data matches that schema — throwing clear errors if not. It’s widely used in FastAPI for validating request/response data, but it’s just as useful in standalone ML code for ensuring data integrity.

It’s a way of bringing strong typing and validation to a dynamic language like Python, resulting in more robust pipelines. If you’ve ever spent hours debugging why your model crashed only to find an unexpected null or string in your input, you’ll appreciate how Pydantic could have caught the issue in milliseconds.

One of the biggest differences between a throwaway prototype and a production system is how they manage expensive resources. In AI applications, a prime example of an expensive resource is your trained model object. Often, the model can be large (hundreds of MBs or a 10GB model in extreme cases) and loading it from disk or initializing it can be slow. If load_model takes 5 seconds (or 5 minutes!), calling predict_one repeatedly will reload the model each time — an obviously terrible idea for production. Unfortunately, this pattern arises when data scientists wrap notebook code into functions without restructuring how the model is accessed. The notebook might have loaded the model once at top, but if you turn a cell into a function naively, you get re-loading on each call.

The solution is to apply a bit of dependency injection (DI). In plain terms, dependency injection means giving a function or class the things it needs, instead of having it acquire them itself . We want to load the model once, and then inject it into any function or component that uses it, rather than loading it inside those functions every time. This approach has two big benefits: it improves performance (load once, reuse in memory) and improves testability (you can inject a dummy or smaller model for testing).

The overarching principle is to avoid redundant work and shared mutable state. By loading the model once, you treat it as a dependency that you provide to your functions or endpoints. This not only speeds up your code, it also makes it more reliable. You won’t accidentally run out of memory by loading the model 100 times, and you won’t be surprised by differences between model instances (because there’s just one in use).

Another advantage of dependency injection is in testing. Suppose you wrote a function classify_image(img, model). In production, you pass in the real heavy model. In a unit test, you could pass a lightweight fake model (with the same interface) to quickly test that classify_image calls the model correctly. This is much harder if classify_image always reads the model from disk internally — in tests, you’d have to actually have a model file around. DI enables loose coupling of components, meaning you can swap out pieces easily . This is a hallmark of good software engineering and is very applicable to ML code as well.

Writing AI/ML code “like a software engineer” might sound tedious at first, especially if you come from a purely data science background. But adopting these clean code practices will pay dividends as your projects grow. By refactoring notebooks into modular code, you make your work reproducible and maintainable. By adding data validation with Pydantic, you catch errors early and build confidence in your pipeline’s outputs. By handling models and other resources with dependency injection, you avoid inefficiencies and create flexible, testable code.

In my own journey, this approach felt like connecting two worlds: my past experience writing structured, type-safe Go code and my present work in the Python AI realm. I realized that the discipline and quality mindset from traditional software development can (and should) be applied to machine learning projects. The result is code that not only accomplishes the task at hand but is also easier to debug, extend, and collaborate on.

No matter if you’re a junior ML engineer just starting out, a data scientist learning to productionize models, or an experienced developer dipping into AI — you can write clean, production-grade code. Treat your code as an asset, not just a byproduct of research. Structure it well, validate everything, manage your dependencies smartly. Your future self (and your teammates and users) will thank you when the “AI code” runs as smoothly and reliably as any other well-engineered software component. Quality code is the foundation of deploying successful AI solutions at scale, so don’t hesitate to bring some engineering rigor into your data science work. In the end, clean code isn’t just about pleasing your inner perfectionist — it’s about building AI systems that are robust and deliver value in the real world.
