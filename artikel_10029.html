Workflow dependency lockfiles

Tanggal: 2026-11-08

A lockfile pins every action your workflows depend on to a verified commit, so the code you reviewed is the code that runs.

Workflows often reference an action by a tag or branch, such as uses: octo-org/deploy-action@v3 or uses: octo-org/deploy-action@main. GitHub Actions resolves that reference to whatever commit the tag or branch points to at run time.

Tags and branches can move. As a result, the code that runs is not guaranteed to be the code that the workflow author originally reviewed. If an upstream maintainer's account is compromised and a tag is repointed, your repositories could run malicious code.

A workflow dependency lockfile pins a commit SHA to every action your workflows depend on, including transitive dependencies. It doesn't pin calls to reusable workflows (jobs..uses). To pin a reusable workflow, reference it by its full commit SHA. A lockfile controls which action code runs on the runner. The lockfile is defined in a repository at .github/workflows/actions.lock. It's generated by gh actions-lock, a GitHub CLI extension, and should never be edited by hand.

A lockfile covers the workflows in its own repository, including transitive dependencies (actions that your action dependencies use), except for dependencies of reusable workflow calls. Reusable workflows can have their own lockfiles too. A reusable workflow's dependencies are covered by the lockfile of the repository where it's defined, not by the lockfile of the repository that calls it.

The lockfile has two sections. workflows records which dependencies each onboarded workflow uses, and dependencies records which commit each of those references resolves to.

This structured format gives tools like Dependabot a machine-readable record they can use to manage dependency updates, without relying on YAML comments as version annotations.
