Running an AI agent on your own GPU sounds simple: point it at Ollama and stop paying per token. I set up OpenClaw, an open-source AI assistant, with a 9B model in Ollama on one RTX 3090 and connected it to Discord. Then I read the Ollama log for every request.

The agent worked. The numbers were not what I expected, though. A one-line question turned into a prompt of more than 18,000 tokens, the first reply took over a minute, and the small model sometimes guessed instead of using its tools.

This article covers what I measured and what each number means if you plan to run an agent on local hardware.

OpenClaw ran in Docker and reached Ollama on the host at http://host.docker.internal:11434. Discord was the chat interface, and OpenClaw's web panel showed the sessions and context use.

This article is about the results, not the installation. The full step-by-step setup is in a separate guide to running OpenClaw in Docker with Ollama and Discord. That guide covers the Compose file, the Discord bot and how to keep the ports off your network.

All timings below come from the Ollama log on the test machine. Ollama loaded the model with a 32,768-token context.

The Ollama log showed what that question cost. The model processed 18,415 prompt tokens and generated 33 tokens.

OpenClaw counts tokens with its own estimate, which was higher than the Ollama count. The gateway log estimated the prompt at 24,608 tokens, against a prompt budget of 24,576 tokens for this model. By OpenClaw's own count, the base prompt alone used up the budget before any conversation history.

The web panel showed a similar figure: 68 to 69 percent of the context window was in use for the Discord sessions after only a few messages.

Reply times on the test machine. Loading the model took most of the first reply.

The speed-up comes from prompt caching. The system prompt, tool definitions and workspace files at the start of the prompt stay the same between requests. Ollama kept that part cached and processed only the new tokens. The model wrote at 91 to 96 tokens per second in every test.

Ollama's documentation says models stay in memory for 5 minutes by default before they are unloaded. After that, the next message pays the load time again. You can change this with the OLLAMA_KEEP_ALIVE environment variable on the Ollama server, or with the keep_alive parameter per request. A negative value, such as -1, keeps the model loaded. I did not change this setting in the test.

If you run Ollama in Docker, pass the variable with -e OLLAMA_KEEP_ALIVE=-1 or in the environment: section of your Compose file.

Two things used the GPU besides my chat messages.

A heartbeat. OpenClaw's web panel listed one scheduled automation, heartbeat-main, which runs every 30 minutes. The agent wakes on that schedule, so the model gets called even when nobody chats. With Ollama's 5-minute default, the model is unloaded between heartbeats unless someone chatted recently, so a heartbeat most likely starts with a model load. I did not measure this.

An embedding model. During the first message, OpenClaw also called Ollama's /api/embed endpoint twice to index its memory. It used qwen3-embedding:4b, which was already installed on the Ollama server. I did not set OpenClaw to use that model; it picked it on its own.

That is 11.4 GB for the models alone, almost half of the RTX 3090's 24 GB.

What this means for you: plan GPU memory for the chat model, the embedding model and the context, not the chat model alone. If the GPU also runs other models, the heartbeat can compete with them.

After the restart, the bot claimed it had lost the earlier session. When asked to use its read tool, it read the file correctly.

The fix for the first problem was simple. When I wrote "use your read tool to open homelab-test.md", the model opened the file and listed all three points correctly. Naming the tool made it check instead of guess.
