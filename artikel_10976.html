Dark mode has become a baseline expectation, yet building it with plain CSS and JavaScript still catches experienced developers off guard. The core problems remain stubborn: the flash of wrong theme (FOUC) when a page loads before JavaScript can apply a stored preference, media query blocks scattered and duplicated throughout stylesheets, and the persistence logic needed to remember what a user actually chose. Building a no-flash dark mode CSS variables system without a framework has historically meant writing every color declaration twice inside prefers-color-scheme blocks, or leaning on JavaScript to do work that CSS should handle natively.

That changes with the CSS light-dark() function, which reached Baseline 2024 status (Baseline Newly Available, meaning supported in all major engines but not yet in the 30-month rolling-availability window), shipping in Chrome 123+, Firefox 120+, Safari 17.5+, and Edge 123+. You set the color-scheme CSS property on :root to signal the browser which color schemes the page supports. This is not merely a hint. It directly affects how the user agent renders built-in UI elements: form controls (inputs, selects, checkboxes), scrollbars,

elements, and system colors like Canvas, CanvasText, and ButtonFace all shift appearance based on the declared color-scheme css value.

The property accepts several keyword values. light declares that only a light scheme is supported. dark declares only dark. light dark (the most common for theme-switching pages) tells the browser both are supported, and the browser will choose based on the user's operating system preference. only light opts out of any forced darkening the browser might otherwise attempt.

Set this property on :root so the entire page's UA-styled elements respond correctly when the active scheme changes, as MDN documentation confirms.

The light-dark() CSS function accepts exactly two arguments: light-dark(, ). When the computed color-scheme resolves to light, the function returns the first value. When it resolves to dark, it returns the second. light-dark() accepts values only — this includes hex, hsl(), oklch(), named colors, and custom properties that resolve to colors. Non-color value types such as , , or are not supported and will silently fail.

There is a critical dependency: color-scheme must include both light and dark keywords somewhere in the cascade for light-dark() to toggle correctly. If color-scheme is set to only light or simply light, the function silently resolves to the first value regardless of the user's OS preference. This is a common source of bugs.

Not every browser in the wild supports light-dark(). Pre-2024 versions of Chrome, Firefox, and Safari will ignore it entirely, which means the browser resolves custom properties to their guaranteed-invalid value (equivalent to unset, not an empty string), and the page falls back to inherited or initial styles. The solution is to wrap light-dark() tokens inside an @supports block and provide a fallback outside it that uses prefers-color-scheme media queries with the same custom properties.

This approach ensures older browsers receive a fully functional dark mode via the traditional media query pattern, while modern browsers benefit from the streamlined light-dark() css syntax.

Note: Fallback values must use color formats supported by the target legacy browsers — avoid oklch() and lch() in fallback blocks, as browsers old enough to lack light-dark() may also lack oklch() support.

The flash of wrong theme occurs because the browser renders content using the default color-scheme (determined by the meta tag and OS preference) before any JavaScript can execute to apply a stored user preference. If a user previously chose light mode but their OS runs dark, the page briefly renders dark before JavaScript switches it, causing a visible flicker. This flash specifically affects users whose stored preference differs from their OS setting. Users with no stored preference experience no JS-driven flash, as the color-scheme: light dark meta tag handles their initial render.

Forgetting to declare color-scheme with both light and dark keywords is the most common bug. Without it, light-dark() silently resolves to the first value, and the dark theme never appears. No error is thrown.

Hard-coded colors in component CSS bypass the token system entirely. A single color: #333 in a component rule looks fine in light mode but turns nearly invisible against a dark background. Audit stylesheets for any color values that do not reference custom properties, and consider linting rules that flag raw color literals outside your token file.

Images and illustrations designed for light backgrounds often look jarring in dark mode. The element with media="(prefers-color-scheme: dark)" allows serving alternate assets per scheme, though this does not respond to the JavaScript-driven data-theme override. To serve theme-aware images that respond to JS overrides, use with JavaScript that swaps the src attribute based on the data-theme value, or use CSS background-image with selectors that key off [data-theme].

Important: Serve all pages via an HTTP server (e.g., python3 -m http.server or VS Code Live Server) rather than the file:// protocol, as localStorage is blocked on file:// in some browsers.

CSS is gaining additional features that will eliminate more manual theme work. The @media (prefers-contrast) media feature allows adapting to user contrast preferences with the same token-based approach. The contrast-color() function, which became Baseline newly available in April 2026 (Chrome 147, Firefox 146, Safari 26), returns black or white, whichever contrasts better with a given color. It can replace some manual dark-mode text-color pairing, though it only picks black or white, so it will not replace a designed palette.

Adopting light-dark() now, while it has reached Baseline status across all major engines, positions a codebase to absorb these future capabilities without architectural changes.
