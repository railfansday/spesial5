Compute is usually the biggest line on the AWS bill. It’s also the part nobody designs on purpose. Someone picks an x86 On-Demand instance during the first sprint, sizes it “with some headroom,” and that choice quietly sticks around for 2 years.

AWS names instances like m5.2xlarge, where m is the class, 5 is the generation, and 2xlarge is the size. Class is the part that matters most, because it sets the ratio of vCPU to memory.

If your service is CPU-bound, running it on M instances means paying for memory you never touch. If it’s memory-bound, C instances will force you to over-scale. Profile first, then pick.

Don't run everything On-Demand. Don't run user-facing APIs 100% on Spot either. The pattern that holds up in production is:

A lot of people still think of Spot as an auction where someone outbids you and your instance dies. That isn't how it works anymore. Prices now move slowly based on long-term supply and demand. You can still set a max price (it defaults to the On-Demand price), but most interruptions happen because AWS needs the hardware back for On-Demand or Reserved customers in that AZ, not because the price jumped.

A Spot capacity pool is one instance type in one Availability Zone. c8g.large in us-east-1a is a different pool from c8g.large in us-east-1b, and both are different from c7g.large in us-east-1a.

If your Auto Scaling Group or Spot Fleet only allows one instance type, you're depending on just a few pools. When those get squeezed, your whole tier goes down at once. So list several families and sizes that your service can run on.

With Spot in the mix, nodes will vanish. Users won’t notice if you handle two things well: draining traffic and storing data.

AWS warns you twice before taking a Spot node back:

Set ECS_ENABLE_SPOT_INSTANCE_DRAINING=true. When the two-minute notice arrives, ECS moves the node’s tasks to healthy nodes. The ALB stops sending new requests to that node and lets the open ones finish.

The catch is that the ALB waits 300 seconds by default, but Spot only gives you 120. If you leave the default, the node dies mid-drain, and users get 502s. Set the deregistration delay and stopTimeout to 60–90 seconds.

Also use awsvpc mode. Each task gets its own IP, so the ALB sends traffic straight to the task.

Anything written to the node’s own disk is lost when the node goes away. You have three choices:

an ECS cluster on a mixed-instance ASG using Graviton families

one On-Demand base node plus an 80/20 Spot/On-Demand split above it, using PRICE_CAPACITY_OPTIMIZED,

an ALB with a deregistration delay that fits inside the Spot window,

an encrypted EFS volume mounted into the tasks.

A couple of things worth calling out. spotInstanceDraining: true is the CDK way to set the agent flag, so you don't have to append it to /etc/ecs/ecs.config yourself. And the nodes run in private subnets, so the ALB is the only thing with a public IP.

Even with the right instances and purchase mix, a few networking line items can take back a big chunk of what you saved.

Cross-AZ traffic and NAT. Data crossing AZs costs $0.01/GB each way. With one NAT Gateway in us-east-1a and nodes spread across three AZs, about two-thirds of your outbound traffic pays that cross-AZ fee on top of the NAT's $0.045/GB processing charge. For real production traffic, run a NAT per AZ. Always add the free gateway endpoints for S3 and DynamoDB so that traffic never touches a NAT.

Public IPv4 addresses. AWS charges $0.005 per hour (about $3.65 a month) for every public IPv4 address, attached or not. Keep cluster nodes in private subnets and clean up unattached Elastic IPs.

The draining mismatch. This one is worth repeating because it's the most common one I see. The ALB's default deregistration delay is 300 seconds. A Spot interruption gives you 120. Leave the default and your users get 502s every time AWS reclaims a node. Set both the deregistration delay and stopTimeout to 60–90 seconds.

None of this is complicated on its own. The savings come from treating these choices as design decisions: right-size the instance family, default to ARM, cover your baseline with a Savings Plan, run peaks on diversified Spot, drain cleanly, and keep state off the host. Do that, and the bill goes down, and the system gets better at handling failure at the same time.
