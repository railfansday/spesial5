nsjail, bubblewrap and Firejail compared: three Linux process sandboxes, from their own docs

Tanggal: 2026-11-26

Posted on Nov 26 • Originally published at sandscale.dev

Not every piece of untrusted code needs a virtual machine. Sometimes you want something lighter on one Linux host: run this command with no network, a read-only view of the system, a time limit and a memory cap. Three mature open-source tools do that: nsjail, bubblewrap and Firejail.

They are built from the same kernel features, namespaces, seccomp and resource limits, but they were made for different jobs. This comparison relies on each project's README and documentation. We have not benchmarked them, and we do not rank them; the right one depends on what you are sandboxing.

All three share the host kernel with the sandboxed process. That is the main difference from a microVM, and it applies to every tool here: a kernel bug reachable through an allowed system call is reachable from inside.

nsjail fits server-side jobs: running submissions on a judge, running untrusted handlers per connection, or fuzzing. The protobuf config makes policies reviewable files rather than long command lines.

bubblewrap starts from a different problem. Its README explains that tools like Docker are not suitable to hand to unprivileged users, because that access can easily become root on the host. bubblewrap uses user namespaces so that any user can build a sandbox without privileges; the README notes the old setuid mode has been removed.

Its design is minimal by intent. Each sandbox starts in a new, completely empty mount namespace whose root is a tmpfs, and you build up the filesystem with command-line options. It turns off setuid binaries with PR_SET_NO_NEW_PRIVS. Flatpak is its best-known user.

The README is unusually clear about responsibility: bubblewrap "is not a complete, ready-made sandbox with a specific security policy", and the protection between sandbox and host "is entirely determined by the arguments passed to bubblewrap". Whatever builds those arguments owns the security model. Its limitations section adds specifics, such as needing --new-session (unless a seccomp filter blocks TIOCSTI) to prevent command injection into the outer terminal, and noting that everything mounted into the sandbox, a D-Bus socket for example, can potentially be used to escalate privileges.

--unshare-all includes the network namespace, so the job has no network unless you add --share-net. --clearenv keeps your environment variables, and any secrets in them, out of the sandbox. bubblewrap has no built-in time or memory limits; pair it with cgroups or systemd-run, or with a timeout in the caller.

bubblewrap fits as a building block inside a larger program that knows exactly what it wants to expose: a desktop app framework, a build tool, or your own job runner.

Firejail's README describes "a lightweight security tool intended to protect a Linux system by setting up a restricted environment for running (potentially untrusted) applications". It is an SUID program using namespaces, seccomp-bpf and Linux capabilities, works alongside SELinux or AppArmor, and integrates with cgroups.

Its distinguishing feature is a large library of ready-made profiles for common desktop applications such as Firefox, Chromium and VLC. You run firejail firefox and get a profile that someone has already tuned. Options like --net=none and the private-* family (private home, /tmp, /dev, /etc) restrict what a program sees.

The SUID design is the main trade-off to weigh for server use. A setuid-root program is itself attack surface for local users. Firejail has had privilege escalation bugs in that code, for example CVE-2022-31214, where a crafted fake container accepted as a join target by the setuid-root program in version 0.9.68 let a local attacker gain root. Bugs get fixed, but a design that needs root to start a sandbox carries that class of risk by construction.

Firejail fits desktop hardening: running a browser, a media player or a document viewer with less access than your user account has.
