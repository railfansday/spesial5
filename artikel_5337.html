How hidden text in emails and web pages can hijack a company AI assistant

Tanggal: 2026-11-18

Free daily briefing on global business news.

Prompt injection attacks let hidden instructions in emails, web pages and files hijack company AI assistants — here is how they work and how to contain them

A company that gives an AI assistant access to its inboxes, shared drives and internal systems is also giving that assistant a way to be steered by strangers. The assistant reads whatever lands in front of it. It cannot reliably tell an instruction from its owner apart from a sentence an outsider planted in an email, a web page or a file.

That weakness has a name: prompt injection. The Open Worldwide Application Security Project, the nonprofit known as OWASP, places it first in its Top 10 for LLM Applications. It holds the LLM01 spot in both the 2023 and 2025 editions of that list.

The danger grows as AI tools move from answering questions to taking actions. A chatbot that gives a wrong answer creates a correction problem. An assistant that can read private files, send messages and call company software creates a security problem. The same model that drafts a reply can be told, by text it was only meant to summarize, to do something its user never asked for.

This guide to prompt injection attacks walks through 10 attack methods and core concepts, a selection rather than a ranked or complete list. It starts with what the attack is and how malicious instructions reach a model, whether typed straight into a chat or hidden inside content the AI reads. It then looks at what attackers try to take, from confidential instructions to private data sent to outside servers. It also explains why AI agents connected to tools and third-party services raise the stakes, and how the attack differs from jailbreaking.

The final slide turns to defense, and the answer there is a partial one. No one has yet found a complete fix. Language models handle trusted instructions and untrusted text together, and no design yet keeps them apart with full reliability. The practical goal for any company deploying these tools is to limit what a hijacked assistant can reach, change or send. Every AI tool with access to company data should be treated as a system that outside text can influence.

Prompt injection is an attack in which text written by an outsider ends up in a language model's input. The model then follows that text as if it were a legitimate instruction from the people who built the tool.

Developer Simon Willison coined the term in September 2022. He modeled the name on SQL injection, a long-known class of web attack. In SQL injection, an attacker types database commands into a field meant for ordinary data, such as a login box or a search bar. A poorly built application then runs those commands against its own database.

The parallel is direct. An AI application starts with instructions from the company that built it. It then adds text from somewhere else — a customer's message, a web page or a document. If that outside text contains an instruction, the model may carry it out in place of the one its developer wrote.

One of the earliest public examples involved a Twitter $TWTR bot run by remoteli.io, a remote-work job site. The bot ran on OpenAI's GPT-3 model and was set up to reply to tweets about remote work. In September 2022, users found they could take it over with plain English. They told the bot to ignore its original instructions and do something else. It complied.

Many of the hijacked replies were jokes. The bot posted whatever strangers on Twitter told it to post, under the company's name.

The episode exposed more than one misbehaving social media account. The attack needed no code, no stolen password and no technical skill. It traveled through the same channel the bot used for normal conversation. Any user who could send the bot a message could also send it new orders.

That feature sets prompt injection apart from many older software flaws. The weak point is not a single faulty line of code that a patch can close. It lies in how language models handle the text they receive. A model that reads outside text can be handed new instructions inside it, whatever job its developer assigned.

Prompt injection comes in two forms. A direct injection is typed into the chat window by the person using the AI tool. An indirect injection hides inside content the AI reads on the user's behalf, such as a web page, an email or a file.

Direct injection is the simpler case. The attacker and the user are the same person. Someone types a message designed to override the instructions a developer gave the model. One example is telling a customer service chatbot to ignore its rules. The attacker needs access to the chat interface, and the hostile text arrives through that person's own session.

Indirect injection changes who the attacker is. The person chatting with the assistant is the victim, not the source of the hostile text. A third party plants instructions in material the assistant will later process. A user might ask the tool to summarize a document, read a message or look something up online. The planted text then enters the model's input alongside the legitimate request.

Kai Greshake and co-authors formalized this second category in a research paper titled "Not what you've signed up for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection." It was published in February 2023. The title names the core problem. Applications that connect a language model to outside data can be turned against the people who use them.

For companies, indirect injection is the larger concern. The attacker never has to touch the victim's chat. They do not need to log into a company system or persuade an employee to type anything. They only need to put text somewhere the AI tool will eventually read.

This widens the attack surface. With direct injection, the exposure is limited to whoever can reach the chat box. With indirect injection, every source an assistant pulls from becomes a possible entry point. That includes inbound email, shared documents, search results and third-party websites.

The two forms also aim at different targets. A direct attack generally targets the application's own rules. An indirect attack targets the employee relying on the tool, who may never see the instruction that redirected it.

A large language model receives its developer's rules and any outside text as a single stream of tokens in its context window. Nothing in that stream marks one part as a command and another as material to read. The model sees no hard boundary between the two.

Tokens are the small chunks of text — whole words or pieces of words — that a model processes. A workplace AI assistant assembles several kinds of text into that one sequence. The developer's system prompt sits next to the user's question. Retrieved emails, documents or web pages join the same sequence when the assistant needs them.

The model then generates a response from everything it has been given. Position and formatting can hint at where each piece of text came from. Those hints are patterns the model learned in training, not rules it is forced to obey. A line in a retrieved email that reads like a command can shape the answer, even though a stranger wrote it.

SQL injection, an older attack on databases, shows what a structural fix looks like. In that attack, a malicious string typed into a web form gets run as part of a database command. The software industry largely fixed it with parameterized queries. That technique sends the command and the user's input to the database separately. The database treats the input strictly as a value and never executes it as code.

No equivalent complete fix exists for language models. Their usefulness comes from reading natural language and acting on what it says. Instructions and data are written in the same human language. A strict separation at the input level is not available the way it is for a database query.

In 2024, OpenAI researchers published a training method called the instruction hierarchy. It teaches models to favor higher-priority instructions, such as a developer's system message, over lower-priority text like tool outputs. The method reduces the problem. It does not remove it, because the ranking is still learned behavior rather than an enforced barrier.

For companies, the practical result is that any text an AI tool reads is a possible source of instructions. A model asked to summarize a document may also treat that document as a set of orders.

Attackers can plant instructions where a person won't notice them but an AI model will still read them. Common hiding places include white text on a white background, very small fonts and HTML comments.

The trick works because people and language models do not see the same thing. A reader looks at the rendered page or document. A model typically receives the text pulled from the underlying file. That text does not carry the visual cues that tell a person what is meant to be seen.

White text on a white background is the simplest example. The words sit in the document like any other sentence. Their color matches the page. The human eye passes over them. Text set in a tiny font works the same way. It may look like a stray line or a blank gap to a reader, while a model takes in every word.

HTML comments add another layer. They are notes written into a web page's code that browsers do not display at all. A visitor scrolling the page never sees them. An AI tool that processes the page's source can still pick up whatever instructions they contain.

This is a form of indirect prompt injection, in which the attacker never types into the victim's chat. The attacker places text in content the assistant will read later on the user's behalf. That content might be a public web page, an email sent to an employee or a file shared with a team.

The exposure follows the everyday tasks companies hand to AI assistants. An assistant asked to summarize a web page reads the hidden text along with the visible article. One that triages an inbox reads every incoming message, including those from strangers. A research tool that gathers material from many sites reads whatever each of those sites contains.

In each case, the employee sees a clean page or a routine email. The assistant sees the same content plus the concealed instructions.

That gap also makes the attack hard to spot after the fact. An employee reviewing the original email or page will find nothing unusual on the screen. The instruction that changed the assistant's behavior only shows up when someone inspects the raw text or the code behind it.

For a business, the practical implication is that checking a file by eye does not show what an AI tool will read in it. A document can look harmless and still carry text written for the machine rather than the person.

Prompt injection can turn an AI chat window into a channel for stealing data. An injected instruction tells the model to build an image or link whose web address carries private information. When the interface displays it, that information travels to a server the attacker controls.

Markdown is a lightweight formatting language that many chat interfaces use to display text, links and pictures. In markdown, an image is written as a short line of text that points to a web address. When the chat interface renders that line, the user's browser or app requests the image from that address automatically.

The attack exploits that automatic request. A planted instruction asks the model to collect something private from the conversation or the files it can read. The model then adds that material to the end of an image URL as a query string. A query string is the part of a web address that follows a question mark. The attacker's server receives the request and records the full address, private data included. The image itself can be invisible or broken. The user may see nothing unusual.

Links work in a similar way, with one difference. A link sends data only when someone clicks it. The attacker must therefore also persuade the user to click. An image fetch needs no click at all.

Security researcher Johann Rehberger demonstrated variants of this technique against several AI chat products. His demonstrations showed that the pattern was not tied to a single vendor. It followed from a common combination: a model that outside text can steer, and an interface that renders whatever the model writes.

A 2025 case known as EchoLeak brought the pattern into a workplace product. Tracked as CVE-2025-32711, the flaw affected Microsoft $MSFT 365 Copilot, the AI assistant built into Microsoft's workplace apps. Researchers at Aim Security reported it. Microsoft fixed the flaw on the server side, within its own systems.

EchoLeak was described as a zero-click flaw. The victim did not need to open or click anything for the attack to work. That removes a safeguard companies usually rely on: an employee choosing not to open a suspicious message or click a suspicious link.

A system prompt is the hidden set of instructions a company gives its AI model, and users can sometimes extract it with prompt injection. Any business deploying a chatbot should assume the public can read its system prompt and keep secrets out of it.

A widely reported early example came in February 2023. Kevin Liu, a Stanford student, used a prompt injection to get Microsoft $MSFT's Bing Chat to disclose the initial instructions it had been given before any conversation started. Those instructions included an internal codename for the assistant: Sydney.

The leak did not require stolen passwords, insider access or specialist tools. Liu worked through the same chat interface that other Bing Chat users had. The only input was text. The model's own willingness to repeat what it had been told did the rest.

That detail makes system prompt leaks relevant to every company building on a language model. A system prompt sits in front of each conversation and shapes the assistant's behavior. It typically sets a persona and a tone of voice. It can list topics the assistant should avoid, describe products and policies, and explain how to use any connected tools.

Much of that material is harmless if exposed. A competitor that learns a support bot is told to stay polite gains little. The risk comes from what developers sometimes add for convenience. Credentials, API keys, internal URLs, pricing logic, unreleased product details and confidential business rules can all end up written into prompts.

Once such material sits in the prompt, it is only as private as the model's reluctance to repeat it. The Sydney episode showed how thin that protection is. Even an instruction to keep the prompt confidential is just more text the model has read. A well-phrased request can coax the rest back out.

The practical lesson is a design rule rather than a filter. Secrets belong in the systems around the model, such as server-side code and access controls, where the model never sees them. A system prompt should be written on the assumption that it will eventually be published. If a leaked prompt would embarrass the company or hand an attacker a working key, that content needs to move somewhere the model cannot reach.

An AI agent is most exposed to prompt injection when it has three capabilities at once: access to private data, exposure to untrusted content and the ability to communicate externally. Developer Simon Willison called this combination the "lethal trifecta" in June 2025.

When all three sit inside one agent, a single injected instruction can direct it to read sensitive information and send that information to an attacker.

Willison also coined the term prompt injection in September 2022. The trifecta is a test of what an agent can do, not of what its prompt says. Each ingredient on its own is an ordinary feature of a workplace assistant. The risk comes from the combination.

Private data covers anything the agent can reach that an outsider should not see. That includes an employee's inbox, shared drives, calendar, source code or customer records.

Untrusted content is any text the agent reads that someone outside the company could have written. An incoming email, a web page, a vendor's shared document or a customer support ticket all qualify. Any of them can carry an instruction aimed at the model.

External communication is any route for information to leave the company. Sending an email, calling a web address, posting to an outside service or producing a clickable link can each serve that purpose.

Take a hypothetical inbox assistant. An attacker emails an employee with an instruction telling the assistant to find recent contracts and forward them to an outside address. The assistant reads the message while processing the inbox, searches the mailbox and sends the files. The employee never has to open the attacker's email.

Tool access is what turns a misleading reply into a real action. An injected instruction runs with whatever permissions the agent holds on the employee's behalf. If the agent can send email, the attacker effectively can too. The same applies to updating a customer record, filing a ticket or approving a calendar invite.

Code execution widens the reach further. An agent that can run commands could be directed to touch files or systems well beyond the task it was given.

The trifecta also gives companies a plain audit question for any agent they deploy. What private data can it read? What outside content reaches it? How can it send information out? An agent with an answer to all three matches Willison's description. Removing any one of the three closes this particular route for data theft.

The Model Context Protocol, or MCP, is an open standard that connects AI assistants to external tools and data. Invariant Labs showed in April 2025 that malicious instructions hidden in an MCP tool's description can steer the agent that uses it.

Anthropic introduced MCP in November 2024. Each connection runs through an MCP server, which offers the assistant a set of tools along with a written description of each one.

A tool description is the short block of text that tells a model what a tool does and when to call it. The model reads that text as part of its working context. A person installing the tool may see only its name or a brief summary in an app's interface. That gap gives an attacker room to work.

In a tool poisoning attack, whoever writes or controls a tool slips extra instructions into its description. The text might tell the assistant to read a file it was never asked to open. It might tell the assistant to pass information along to a different tool. The model treats the description as guidance on how to behave. It can then follow those planted instructions even though the user asked for nothing unusual.

In May 2025, Invariant Labs reported a related attack on an agent using the GitHub MCP server. The setup was a malicious issue posted in a public repository. An agent connected to a user's account could read that issue. The planted text could then lead it to leak data from the user's private repositories.

The GitHub case relied on content the agent read, not on a doctored tool. The attack text arrived through a trusted, official connector.

This makes MCP a supply-chain problem as much as a model problem. Each MCP server a company connects is a piece of third-party software that speaks directly to its AI assistant. Its descriptions, and the data it returns, become text the model may act on.

One slide-specific step for security teams is to review each MCP server like any other software dependency. That review covers who publishes it, what its tool descriptions say and which accounts and data it can reach.

Jailbreaking tries to get a language model to break its own safety training, for example by producing content it would normally refuse. Prompt injection targets something else: an application that mixes a developer's trusted instructions with untrusted text from outside.

Developer Simon Willison, who coined the term prompt injection in September 2022, has drawn this distinction. The two attacks can look alike on the screen. They describe different problems.

In a typical jailbreak, the person typing is the one trying to misuse the model. The target is the set of guardrails the model's maker built in during training. A successful jailbreak produces an answer the model was trained to withhold. The person who asked for that answer is the one who receives it.

Prompt injection works differently. The attacker is often not the person using the tool. The attacker's words arrive inside text the application handles, and the model treats them as commands. The target is the application and the person relying on it, not the model's content rules.

The techniques overlap. Both rely on phrasing that persuades a model to set aside the instructions it was given. A message telling a model to ignore its earlier rules could appear in either kind of attack. The difference lies in who is being attacked and whose instructions get overridden.

That difference shapes who handles the risk inside a company. Resistance to jailbreaks sits largely with the model provider, which controls the safety training. Exposure to prompt injection depends on how a company builds and connects its own AI tools. That includes what data an assistant can see, what outside content it reads and what actions it can take.

A model that refuses every harmful request can still follow an injected instruction to forward an email or send a confidential file's contents to an outsider. Neither action breaks a safety rule. Each one breaks the application's intended behavior.

For security teams, the working test is short. A jailbreak changes what a model will say. A prompt injection changes whom the model works for.

Prompt injection has no complete fix today. The practical defense is containment: restrict what a hijacked AI tool can touch and do, so a successful attack does limited harm.

That changes the question security teams ask. They stop asking whether an assistant can be tricked. They assume it can be, and they plan for the moment it is. The controls that follow are familiar security practices applied to a new kind of software.

Least-privilege access is the starting point. An AI tool should hold only the permissions its job requires. A meeting summarizer does not need to send email. A coding assistant does not need access to payroll records. Every permission an assistant lacks is one an injected instruction cannot use.

Human approval adds a checkpoint before actions that are hard to undo. Sending an email, moving money, deleting files or changing account settings can each be held until a person confirms them. This step adds friction. It also means a hidden instruction cannot complete a sensitive task on its own.

Limiting outbound channels narrows the ways data can leave. An agent that can contact only an approved list of addresses or domains has fewer routes to an attacker's server. Blocking arbitrary web requests and unapproved links in an assistant's output closes off common exit points.

Logging tool calls gives security teams a record of what an assistant did and when. If an injection succeeds, those logs show which data was read and where it was sent. They also help teams spot unusual behavior sooner.

Red-teaming tests these controls before attackers do. Teams plant injection attempts in the documents, emails and web pages an assistant will process, then check whether it follows them. The tests need repeating after each model or tool change. A new version can respond differently to the same attack.

Input and output filters scan text for suspicious instructions and can catch known attack patterns. They do not offer complete protection. An attacker can reword an instruction in many ways, and a filter can flag only what it recognizes.

Longer-term fixes remain at the research stage. Google $GOOGL DeepMind published a design called CaMeL in 2025 that separates trusted instructions from untrusted data at the system level. The approach does not depend on the model to tell the two apart. CaMeL is a research proposal, not a deployed fix. Until an approach like it is proven in production, containment remains the main line of defense for companies running AI tools.
