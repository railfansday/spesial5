Playing with the STM32MP2

Tanggal: 2026-11-08

First off, an apology - this post is long overdue. I started writing it back even before the TCXO post, I think some time in December 2025. Thereâs just one problem: the STM32H7 FMC needs a lot of pins - 30+ if you want all the chip selects and address lines. And the TFBGA216 isnât any better, either.

For years, Iâve dreamed of a better way. My ultimate dream MCU, which doesnât exist because Iâm probably the only weirdo who would buy it, would be a 1 GHz Cortex-M7 or M85, probably made on TSMC 28LP, with a megabyte of NOR flash or ReRAM, a megabyte of SRAM, an RGMII MAC, multiple FPGA-style I/O banks with independent VCCIO rails, and an AXI Chip2Chip SERDES block that I could use for directly integrating with FPGA-based peripherals using only two differential pairs.

The STM32H735 paired with an external FPGA over FMC got close, but was annoying to use on a low-cost board (e.g. 4 layer batch fab) because the FMC is almost impossible to route on those constraints. Some other STM32H7 parts like the H75x line are available in an 0.8mm package which is doable (painfully) on batch fab design rules, but these have a lower max CPU speed (480 vs 550 MHz) and this is really just kicking the can down the road a bit rather than fully solving the problem. Youâre still burning a ton of pins.

A fast M7 with PCIe would almost be what I want (PCIe isnât exactly AXI, but bridging them is totally doable), but nobody makes those either. You can get Cortex-Râs with PCIe, which I seriously considered (and still want to check out) but it would still be a big jump from the familiar STM32 peripheral set. And a lot of these parts either donât have crypto acceleration or security-by-obscurity lock up the docs to the crypto accelerator, which is an absolute dealbreaker for me.

But then ST came out with the STM32MP2 line. This is a full applications processor SoC with a dual Cortex-A35, some slower auxiliary processors like an M33 and a M0+, a full GPU/NPU I may play with one day, and â most interestingly to me â a 5 Gbps SERDES with PIPE interface that could be configured to operate as either PCIe gen1/2 x1 or USB 3 depending on which internal protocol IP you connect to it (thereâs a register bit to mux them). It also kept most of the same familiar STM32 peripherals I already had lots of libraries for and experience working with, so the learning curve getting spun up on it would be short - including the same AES-GCM and TRNG IPs that I already had drivers for, and were reasonably well documented.

Itâs quite a beast with far more computing power than I needed, but I did want to have a part in my back pocket I could pull out for future designs that needed more oomph. And the PCIe would potentially allow easy memory mapping of an FPGA from firmware via only two differential pairs.

Thereâs just one problem: the STM32MP2 was clearly designed to run Linux, and the vendor BSPs included all kinds of u-boot, TrustZone, etc. stuff that I didnât care about. I just wanted a big microcontroller that could run a simple RTOS or even a while(1) { doStuff(); } event loop.

So I decided to see if I could convince the MP2 that it was, in fact, just a very fast MCU with some oddball peripherals like PCIe and LPDDR PHYs that garden-variety MCUs donât have.

I bought a STM32MP257 development board (STM32MP257F-EV1) and started out the same as I would with any other new STM32 part: added a linker script and header to stm32-cpp with the addresses of the peripherals that used the same register interface as other STM32 parts I already had supported in the library. The only difference was that the image base address was in SRAM rather than flash.

Then I built a simple LED blinky firmware for the Cortex-M33 auxiliary core and loaded it over JTAG just like I would for a regular STM32. There were a few false starts but I got a blinky running fairly quickly. Achievement #1 unlocked: I can talk to the chip and poke registers.

The next milestone was to actually boot the same blinky from flash. It took some digging through example code and wikis to figure out all of the fine points (for example, the internal SRAM is mapped at four different physical addresses with different TrustZone etc settings, but the boot ROM only lets you boot from one of them). Before too long I had a tool that took a flat binary RAM image and bolted on the necessary FSBL headers for the STM32MP2 boot ROM to load it from flash and execute. Then I made a little flasher utility that could be loaded into SRAM and would write an image from another SRAM location to flash, bootstrapping the whole process. Achievement #2 unlocked: the chip is booting from nonvolatile memory and doesnât need to be loaded over JTAG each boot.

A few things to keep in mind when preparing the FSBL image:

This firmware booted in âM33-TDâ mode, in which the boot ROM immediately transfers control to the M33 after loading the FSBL image, and the M33 has full TrustZone privileges. I chose this over âA35-TDâ (in which the A35 boots first) mostly because I wanted to do a staged bring-up of the platform and not have my first time working with the SoC also be my first time bringing up a bare metal Cortex-A.

I continued along the same way I would with any other new STM32 platform for a bit, bringing up a serial console, enabling caches, configuring the PLLs and clock tree, dumping a bunch of platform information to the console on boot, etc.

The code is all on my GitHub but a quick summary of what you need to do for bare metal bringup in M33-TD is as follows. None of the SoC setup code here requires custom assembly, it can all be done in C/C++ except for CPU configuration stuff like enabling/disabling interrupts or the FPU when youâre ready to do that.

Then it came time to get the A35 running, which I had to do before playing with the PCIe because the M33âs memory map did not allow it to talk to the PCIe BAR region â annoying, but something I could live with if the M33 is mostly acting as a management processor and all our application code is on the A35.

I had previously avoided working with Cortex-Aâs because the overhead involved in getting them set up was a lot higher.

First, once you have the A35 image in flash, you need to actually start it. Figuring this out took quite a bit of reading of various third party library code and such, the datasheet didnât make it obvious. The basic steps are:

The FSBL-A image in flash (at offset 0x0008_0000 for primary and 0x000c_0000 for fallback) itself then is launched in parallel on both cores in the cluster simultaneously in aarch64 mode (although there is a fuse you can blow to boot in aarch32 mode instead if you wanted to for some reason). The first part of this initialization does have to be done in assembly because thereâs a bunch of stuff needed that pokes hardware registers and initializes the stack etc.

Note also that this image has to be in flash: even if you have code executing on the M33 already, there does not appear to be a good way to just have the M33 dump an image into SYSRAM and have the A35 execute it: when the A35 is released to boot the ROM will check strap pins and load the image from the specified location (in my case SPI NOR flash); even though the M33 is already running the A35 is going to re-run the boot ROM.

At this point the lowest levels of the core are set up, but we donât know which core weâre on yet. So the next step is to read MPIDR_EL1 and figure out which one weâre on, since the subsequent steps vary depending on which core weâre on.

Youâll notice that I havenât said much about the DDR. Thatâs because I donât plan to use it. Itâs a Synopsys DDR3L/DDR4/LPDDR4 controller that requires a blob plus annoying PCB layout for all the data lines, uses a bunch of power, and is just all around overkill. The whole point of switching from the STM32H735 to the MP2 was to replace the parallel memory bus with PCIe and using DDR would negate most of those benefits.

Anywayâ¦ at this point, you basically have a STM32H7 on steroids:

The MP2 has the same FMC hard IP as the H735, so if I wanted to be silly I could interface it to the FPGA just like the H7. But then why go through all this trouble to bring up the more complex SoC? We want to do PCIe otherwise thereâs no point.

The STM32MP257F-EV1 has a mini PCIe slot meant for a wifi card or something, but I found some adapters to convert it to M.2. This allowed me to interface to a random old NVMe SSD for early testing, and to an M.2 FPGA module later on.

The datasheet provides some initial breadcrumbs on configuring things. We need to enable the COMBOPHY and PCIe IPs in the RCC like usual, then poke SYSCFG.COMBOPHYCR1 to specify whether weâre using the external reference clock (typically 100 MHz but the PLL can be configured for other multiplier/divide combinations) or using an internally generated clock from the RCC.

Once everything is turned on, itâs just a matter of configuring COMBOPHYCR2 to enable PCIe mode, poke COMBOPHYCR3 to calibrate the controlled impedance drivers/terminations, then wait for the other internal housekeeping to complete and the PHY to report everything is ready to go.

Finally, poke SYSCFG.PCIECR to specify the initial bus/device ID and enable the LTSSM so we can actually train the link, toggle PERST to the peripheral, and wait for SYSCFG.PCIESR1 to report successful training. Somewhat shockingly, thereâs no firmware blob or weird setup flow. It just works and trains the link with only a handful of register pokes.

Or at least, I thought it did. After some issues attempting to enumerate the bus I found it was flapping and retraining constantly.

Luckily I have a fast scope and ngscopeclient can decode PCIe and PCIe link training, so I went to work.

Looking at the startup process, everything seemed fine. The link trained up into L0 without any problems, then even passed a few TLPs before dropping into Recovery.RcvrLock, recovering for a bit, then dropping again. After that it stayed up for a while, dropped, and stayed down until the end of the waveform.

But why was it dropping? The first question was which side of the link was initiating the drop. It was pretty clear after zooming in that the STM32 was dropping (transitioning from idles in L0 to sending training sets) the first time, for no obvious reason while the link partner was still sending valid idles. So the problem was at least being detected, if not caused, on the STM32MP2.

I wondered if it might be signal integrity problems. So I fired up a quick eye pattern of both legs of the link. The RX lane (peripheral to STM32) looked fine. A bit overequalized since it was short and I was probing right at the mini-PCIe connector, but wide open with over 200 mV of eye height.

The TX (STM32 to peripheral) eye looked like nothing I had ever seen before. It was clear and wide open most of the time, but the entire eye was closed with a pretty uniform 1e-4 BER. Iâm used to seeing eyes that are squished horizontally due to jitter, vertically due to noise or reflections, etc but in such a scenario itâs usually consistent, the eye wonât have clear top and bottom bars or rising/falling edges.

The only thing I could think of was something intermittent. Maybe the signal is fine most of the time, the link comes up, then something happens - a noise burst, maybe - that blanks it out briefly before it comes back.

So I looked at the second, longer drop in the same waveform. This one was weirder: the link was fine then all of a sudden out of nowhere, the STM32MP2 started sending absolute nonsense - bit patterns that decoded as invalid scrambler values or sometimes not even well-formed 8b10b symbols at all! Then 40 Î¼s or so later the link partner noticed and went into re-training.

When I zoomed in further looking at just a few symbols on either side of the link drop, the problem immediately jumped out at me. Look at the relative phases of the purple Threshold_5 signal (a simple thresholding of the analog waveform) and the green squarewave below it (a clock recovered from the analog waveform by a DSP PLL).

At left, everything is happy. The recovered clock edges are 90Â° phased to the data allowing it to be cleanly sampled with plenty of setup and hold margin. But right about the middle of the screen, things start going sideways, literally. By the end of the D15.2 symbol the clock edge is only about 58 ps after the data edge (instead of the ideal 200ps setup/hold window for a 400ps UI at 2.5 GT/s). And by the end of the D11.7 the clock and data are on top of each other leaving no setup/hold window at all and the protocol decode starts seeing bit errors.

Both the DSP and real physical CDR PLL have limited bandwidth, so if theyâre handed this large a phase shift in <20 UI thereâs no way they will be able to keep up (although they will try).

Plotting TIE (time interval error, essentially the difference between where the CDR PLL expects a UI boundary to be compared to the actual level crossing in the real waveform) for the RX side shows pretty uniform jitter without any weird artifacts. But the TX side shows TIE jumping all over the place, railing at Â± 200 ps (half a UI - the max error possible before the edge is considered to be part of the next UI) and the CDR slewing frantically over 30 MHz above and below the nominal data rate trying and failing to stay synced.

Putting all the evidence together, itâs pretty clear that the SERDES PLL in the COMBOPHY is losing lock intermittently. Everything is fine for a while then something happens internally within the SERDES and the PLL VCO starts jumping around for a bit. This causes the transmit data to jump around (causing the link partner to fail to receive it, as seen in the scope captures) but it also will likely have similar effects on the receiver - causing the STM32 to misread incoming, well formed data as well.

Thereâs only a handful of registers for configuring the COMBOPHY PLL and everything I was writing to them looked fine according to the datasheet, so I was pretty sure it wasnât a misconfiguration. The dev board was a ST reference design which I assumed had to be fine as well.

So if itâs not hardware and itâs not software, what is it? There was really only one other thing to look at, the reference clock. I had configured the COMBOPHY to be clocked via the RCC (ck_ker_usb3pciephy, set to 25 MHz) with SYSCFG.COMBOPHYCR1 set to 0xc8 to get the 2500 MHz required VCO frequency (no spread spectrum, multiplier 100).

But the STM32MP257F-EV1 also had a dedicated 100 MHz reference clock available. Poking COMBOPHYCR1 to 0x33 to select the external clock and multiply it by 25 gave me the same 2500 MHz VCO frequency, but without the added jitter of the internal PLL (TSMC PLLTS16FFCLAFRAC2 fractional-N PLL) and RCC clock distribution network, plus perhaps the external crystal not having tight enough tolerances for this use case.

Andâ¦ it worked perfectly. The link came up, trained happily to 2.5 GT/s gen1 x1 (I figured Iâd save gen2 for later), and everything looked fine.

After this, things get a lot more tricky because the IP isnât really documented at all, at least publicly (as usual, portions of the datasheet and register map have probably appeared in various corners of the internet). Luckily I was able to find some breadcrumbs in uboot and Linux kernel code that gave me a better idea of how things are set up: the PCIe IP block has a register block on AHB5 with a standard PCIe root complex register set (these registers are mostly documented in the PCIe base spec; thereâs a bunch of vendor proprietary ones too but we donât need them to get things functional), then the actual PCIe devices are mapped into a 256 MB chunk of physical AXI address space from 0x1000_0000 to 0x1fff_ffff.

I had never worked with PCIe enumeration before so it took a bit of time to piece together the required steps. The code for this is in stm32-cpp/src/peripheral/PCIE.* and src/cpu1-a35/bsp/hwinit.cpp if you want to poke around in detail but Iâll summarize it here.

First, I read a bunch of standard registers like link status, speed, hardware IP version, etc and log them. Not strictly necessary, but helps with troubleshooting.

Thereâs a bunch of basic configuration within the standard PCIE address space that needs to be done next (after writing a magic unlock value to MISC_CONTROL_1 to remove write protection). Pick a bus number for the root complex, specify the memory limit, etc. But now we need to actually talk to the registers in the link partner. How does that work?

It turns out, the PCIe IP has an âinternal address translation unitâ (iATU) that is essentially a sort of IOMMU. It takes incoming and outgoing TLPs and translates addresses within the AXI block to PCIe BAR or configuration addresses and adds the appropriate TLP type.

So the next step is to set up a chunk of AXI space (I chose 0x1fff_0000 to 1fff_ffff, the last 64 kB of the AXI range) and configure the iATU to map this to configuration accesses to device 01:00.0 (which is the bus and device weâre going to assign to the link partner). I didnât plan to implement a full featured stack with PCIe bridges and the like, since Iâm intending to only ever be wiring the STM32 directly to an FPGA. So a lot of the configuration could be hard coded.

Then I set up a second range of AXI space (0x1000_0000 to 17ff_ffff, the first 128 MB of the AXI range) and mapped it to PCIe address 0x0000_0000. This is where weâre going to put the BAR of the link partner.

We should now have a standard PCIe configuration address block mapped at 0x1fff_0000 that we can walk and print out. I wrote some code to print out a few registers to sanity check andâ¦ got back all zeroes.

Something was clearly broken in the upper levels of the stack. The link was up, I could see DLLPs flowing and the eye was wide open. The iATU was at least configured close to valid, because I wasnât seeing any segfaults like I would if I had a completely bogus memory mapping.

I still had my probes on the PCIe signals (this testing somewhat overlapped with the clock jitter / PLL troubleshooting, but I wanted to tell the story in a more linear order to make it make sense) so the next step was to try to protocol decode some test reads and writes.

I wrote some test firmware that wrote 0xdeadbeef to the start of the configuration space, and the configuration write TLP came out of the STM32 with a valid address and an all-zero payload.

I tried writing 0xfeedface to a location in the BAR range. It also came out with the correct address and an all-zero payload.

Even more confusing, I tried readingâ¦ and the device responded! With a valid read completion TLP, and a decidedly nonzero payload. But my firmware saw the read come back as all zeroes.

So in summary: every write TLP I send to either configuration or data space has all header fields correct, but the payload is all zeroes. Every read TLP goes out normally, the device responds as it should, but my firmware sees all zeroes.

This points to something inside the STM32, either in the PCIe IP or the AXI fabric, zeroing out the data payload only without changing the address. What could possibly do this???

Looking at the STM32MP2 reference manual, there was an obvious suspect: the Resource Isolation Slave unit for Address space protection, Full (RISAF).

It sits right on the AXI bus between the PCIe and the main AXI interconnect fabric, and passes traffic through unless it sees something it doesnât like (e.g. TrustZone nonsecure domain accessing secure resource) in which case it blocks the request and fires a fault interrupt that the secure domain can handle as it sees fit.

So I threw together a quick monitor task on the M33 that polled the IASR register on RISAF5 (which is the instance protecting the PCIe AXI interface) andâ¦ sure enough, it threw a fault the moment I touched the PCIe BAR region from my firmware (which was running in EL3 secure mode since I never dropped privileges).

Just to confirm, I added a few register pokes in BSP_Init() on the M33 (the only core that is allowed to touch the RISAF configuration in M33-TD mode since itâs considered the system root of trust in that mode) that enable both privileged and unprivileged reads and writes to the entire AXI address range from the A35 in secure mode.

And everything worked perfectly. My write TLPs had the correct values as seen by the scope, and reads returned normal data to my firmware. I wrote up a basic single-device-only bus enumeration code path that dumped a bunch of information and everything worked great.

At this point, there was little doubt in my mind that I was sitting on a silicon errata that was a potential TrustZone bypass. So I poked our disclosure team at work and got the ball rolling to send an advisory out to STMicroâs PSIRT (while I found this bug in my off time, I figured it was better to have a company name and lawyers in the disclosure path in case anybody got cranky).

I wrote up an advisory and sent it off to ST, then mostly shelved things until they published something so I could talk about things in detail.

After quite some time, they published an advisory and errata, now documented as errata 2.3.33.

First: what real world deployments or use cases, if any, are potentially vulnerable? What combination of PCIe peripherals and TrustZone monitor would either not notice the issue or not react fast enough, and be possible to exploit by read side effects and/or all-zero writes, to gain privileges or escalate in some way?

Second, more interesting: is RISAF5 the only affected instance? The ST advisory and errata talks about RISAF5 but this may just be because RISAF5 is the only one that I have a working PoC for. I donât know if ST tested the others and confirmed theyâre not vulnerable to the same bug, or if nobody looked.

RISAF1 controls the backup SRAM, RISAF2 the OCTOSPI, and RISAF4 the DDR controller. There does not appear to be a RISAF3 (if it exists, itâs not mentioned in the datasheet). Writing a zero value to the right location in backup SRAM, OCTOSPI PSRAM, or external DDR is likely a much easier privilege escalation (perhaps by replacing some bytes of code or data used by the RISAF security violation exception handler itself, if this is in a cold cache line, with 0x00). If anybody is able to PoC a working exploit by this approach, and/or confirm the other RISAFs are vulnerable, I would love to see.

With PIO from the CPU, the maximum performance I was able to achieve with a software memcpy was about 1.77 Gbps (out of a theoretical peak 4 Gbps). Each strp instruction generates a TLP with 16 bytes of payload, and adding in the 20 bytes of headers + CRC we get 36 bytes of total packet size - only 44% of which is carrying useful data.

But this is already a huge boost over the FMC (which maxes out at 977 Mbps for 137.5 MHz clock and 9 bus cycles for a 64-bit APB write), to say nothing of the simplified PCB routing.

We can definitely do much better with DMA. The STM32MP2âs PCIe IP maxes out at 256 bytes per TLP (not the 4 kB max that the spec allows), which gives a 276 byte TLP and 92.75% efficiency, or ~3.71 Gbps theoretical peak. I havenât actually hit this in a benchmark but will probably try to test it at some point.

If I can get close to this, Iâll be at ~2x the throughput of PCIe PIO and ~3.8x the throughput of the FMC. Which is pretty decent.
