Setting Up AWS Control Tower? These SCP and Networking Mistakes Can Cost You Hours

Tanggal: 2026-11-22

Most landing-zone guides stop after "click Set up landing zone". This one keeps going. By the end, you will have a working multi-account AWS environment where every account has one job, the rules are enforced by Service Control Policies, and the network is owned by one account and shared with the others. Each rule is tested from the command line, so you can prove it holds.

Everything here was built in a real organization, including the parts that went wrong: an SCP that broke DNS, an "allow list" SCP that allowed everything, and a RAM share that failed for 40 minutes. The fixes are part of the steps and are collected in the Troubleshooting section.

This is part 1 of a series. Part 2 sets up the Build account (CodeCommit, ECR with cross-account pull, and CodeBuild inside the shared VPC), and part 3 runs the application on ECS in Dev and Production.

Seven accounts, grouped into Organizational Units (OUs), each with one responsibility:

The "must not" rules matter as much as ownership: each one becomes a Deny statement in an SCP, so it holds even for an administrator inside that account.

An AWS account is a hard boundary for IAM permissions, billing, service quotas, and the blast radius of mistakes. When dev, prod, networking, and CI/CD share one account, a developer who needs the dev cluster easily ends up with access to production, and costs can only be split with careful tagging. Separate accounts give you these boundaries for free, and OUs let you apply the same rules to a group of accounts at once: every account you add to the Workloads OU later inherits its guardrails.

The design follows one principle, ownership: for any resource, it should be obvious which account owns it and who is allowed to change it. The network belongs to the Network account, images belong to the Build account, and the running application belongs to the workload account. Images are built once and only pulled by Dev and Production, so Production runs exactly what was tested in Dev.

This article builds only Dev and Production. A Staging account can be added later in exactly the same way.

The NAT gateways are almost all of the bill. If you build this only to learn, follow the Cleanup section when you are done, or delete the NAT gateways between sessions.

Control Tower creates the organization structure, the two shared accounts in the Security OU, an organization-wide CloudTrail trail, and AWS Config in every enrolled account. Everything later in this article builds on it.

Before you start: if IAM Identity Center is already enabled in the management account, Control Tower must be set up in the same Region. Choose the home Region carefully. Changing it later means decommissioning the landing zone.

Sign in to the management account and open AWS Control Tower → Set up landing zone.

On the first page, choose your home Region and Automatic account enrollment. With automatic enrollment, accounts that join the organization later (and accounts you move between OUs) get the Control Tower baseline and controls without manual enrollment.

On the second page, keep the recommended Sandbox OU. It is a place for experiments with fewer restrictions, and we will also use it to test new SCPs before they reach other OUs.

Next, Control Tower asks for the two shared accounts in the Security OU:

The setup takes about 35 minutes. You can follow each step on the landing zone page:

Control Tower created the Security and Sandbox OUs. Create the other three under Root in Control Tower → Organization → Create resources → Create organizational unit: Infrastructure, Deployments, and Workloads. Create them through Control Tower, not the Organizations console, so that they are registered and get the Control Tower controls.

If you expect many workloads, you can nest OUs later, for example Workloads/web and Workloads/ai, and attach different policies to each.

Use Control Tower → Account Factory → Create account for each workload account:

Account Factory provisions accounts one at a time, so creating all four takes a while. When it's done, Control Tower → Organization should show every OU as Registered and every account as Enrolled:

Control Tower configures IAM Identity Center. It creates groups such as AWSControlTowerAdmins, AWSSecurityAuditors, and AWSLogArchiveViewers, and permission sets such as AWSAdministratorAccess, AWSPowerUserAccess, and AWSReadOnlyAccess. In every enrolled account, your user gets AWSAdministratorAccess directly, while the AWSControlTowerAdmins group only gets AWSOrganizationsFullAccess. That direct assignment is how I sign in everywhere in this article:

For a team, don't give everyone administrator access. Create groups by role and assign each group only to the accounts it needs:

In the console: IAM Identity Center → Groups → Create group, then AWS accounts → select the accounts → Assign users or groups → choose the group and the permission set. The same assignment from the CLI:

For the command line, add one profile per account to ~/.aws/config, then sign in once with aws sso login --sso-session lz. One sign-in covers all profiles:

Tip: use the role name that you actually see in the access portal. In my organization the management account has AdministratorAccess while member accounts have AWSAdministratorAccess. A wrong role name fails with "ForbiddenException: No access".

Also check that no AWS_ACCESS_KEY_ID or AWS_SESSION_TOKEN environment variables are set in your shell. The CLI uses them whenever a command has no --profile, so a single forgotten flag silently runs that command against a completely different account. I had exactly this situation, with keys for an unrelated organization in my shell.

Service Control Policies (SCPs) are guardrails in AWS Organizations. They define the maximum permissions available to IAM users and roles in the accounts of an OU, regardless of what their IAM policies allow.

We use them to enforce the Region, to block dangerous actions (leaving the organization, disabling security services), to enforce ownership (only the Network account builds connectivity), and to remove risky shortcuts (root user, long-lived access keys). SCPs say "what's possible", IAM policies say "who can do it".

We don't attach our policies to the Security OU. Control Tower manages the Audit and Log Archive accounts and already protects them with its own guardrails (the aws-guardrails-* policies you can see in the list).

Every Deny statement below has an exception for the AWSControlTowerExecution role and the stacksets-exec-* roles. Control Tower uses these roles to manage the accounts, and blocking them would break enrollment and drift repair.

Go to AWS Organizations → Policies → Service control policies → Create policy, and name it BaselineGuardrails :

The Network account owns connectivity. FullAWSAccess already allows that, so we only add what it must not do: run applications or CI/CD.

The Build account owns pipelines and container images. It must not create its own network connectivity (Transit Gateway, peering, VPN, Direct Connect) and must not run application services or databases.

Dev and Production run the application. They may attach their VPC to a Transit Gateway shared by the Network account, but cannot build their own connectivity, create ECR repositories, push images, or create pipelines. Images are built once in the Build account and only pulled here.

Select the policy → Actions → Attach policy, and choose the OU:

Leave FullAWSAccess attached. Our policies only take permissions away from it.

The final picture for the Workloads OU should be: FullAWSAccess, the Control Tower aws-guardrails-* policy, BaselineGuardrails, and WorkloadsECSPolicy:

Always test SCPs right after attaching them. EC2 supports --dry-run, which checks permissions without creating anything:

The error message names the exact SCP that denied the request, which makes troubleshooting much easier. Section 7 has a script that tests all guardrails at once.

Tip: before attaching a new SCP to a production OU, attach it to the Sandbox OU or a test account first. A wrong Deny statement affects every account in the OU immediately.

With the guardrails in place, we can build the network. The Network account owns all VPCs, subnets, route tables, NAT gateways, and internet gateways. Dev, Production, and Build don't create VPCs. They receive subnets from the Network account through AWS Resource Access Manager (RAM).

One shared VPC for everyone would put Dev and Production on the same network. Instead, each environment gets its own VPC, shared only with its own account, and we don't need a Transit Gateway yet.

Before creating anything, plan the IP ranges. VPCs that may need to be connected later (with Transit Gateway or peering) must not overlap. Control Tower created a VPC in every account with the same 172.31.0.0/16 range, and these VPCs can never be connected to each other.

We reserve a /16 range for each environment:

Each environment VPC uses two Availability Zones and three subnet tiers:

The app subnets are larger (/20, about 4,000 addresses) because every ECS task on Fargate gets its own IP address. Production uses the same layout with 10.20.x.x. The build VPC needs only two public and two private subnets (10.30.0.0/24, 10.30.1.0/24, 10.30.16.0/20, 10.30.32.0/20).

Control Tower's Account Factory created an empty VPC named aws-controltower-VPC in every new account. We don't need them, so delete them in the Network, Build, Dev, and Production accounts (VPC → Your VPCs → select aws-controltower-VPC → Actions → Delete VPC).

To prevent Control Tower from creating these VPCs in future accounts, go to Control Tower → Account Factory → Network configuration → Edit, and set the maximum number of private subnets to 0.

Sign in to the Network account, open VPC → Create VPC, and choose VPC and more. This wizard creates the VPC, subnets, route tables, internet gateway, NAT gateway, and VPC endpoints in one step.

Expand Customize subnets CIDR blocks and enter the CIDRs from the table above. The wizard's defaults would give the public subnets /20 ranges, which wastes addresses we want to keep for ECS tasks.

ECS tasks in private subnets need outbound access to pull container images, send logs, and call external APIs. This is the job of the NAT gateway. The wizard offers three options:

We make a different choice per environment:

For prod, choose Regional instead of Zonal. There is no AZ selection for a regional NAT gateway, because AWS manages its availability across zones:

Choose S3 Gateway. Gateway endpoints are free. Amazon ECR stores image layers in S3, so most of the traffic when ECS pulls an image goes through the endpoint instead of the NAT gateway, which reduces NAT data processing costs.

We don't create interface endpoints (ECR, CloudWatch Logs, STS) yet. At about $0.01 per hour per AZ each, five of them in two AZs cost more than the NAT gateway they would replace.

Keep DNS hostnames and DNS resolution enabled.

Before creating the VPC, check the Preview panel on the right. It shows every resource the wizard will create. You should see six subnets, one internet gateway, one NAT gateway, and private route tables with a 0.0.0.0/0 route to the NAT gateway.

Click Create VPC. Creating the NAT gateway takes a minute or two.

Open the VPC and look at the Resource map tab. It shows the whole design on one screen: six subnets in two AZs, the public route table pointing to the internet gateway, and the private route tables pointing to the NAT gateway and the S3 endpoint.

Repeat the same steps for prod (10.20.0.0/16, Regional NAT gateway) and build (10.30.0.0/16, 2 public and 2 private subnets, Zonal NAT gateway in 1 AZ).

First, allow RAM to share resources within the organization. In the management account, open Resource Access Manager → Settings and enable Enable sharing with AWS Organizations. Without this setting, resources can only be shared through invitations.

When I created the first share, it failed with this error, even though organization sharing was enabled a few minutes earlier:

The message suggests waiting for onboarding to finish, but mine still failed after 40 minutes, from every account. The real hint came from the CLI: sharing with the organization as principal returned UnknownResourceException: Organization o-xxxxxxxx. RAM had never imported the organization, even though the Organizations console listed RAM as a trusted service.

The fix was to reset RAM trusted access from the management account:

Run this only before you have any resource shares. Disabling trusted access affects existing organization-based shares. After the reset, sharing worked within a minute.

Before that, I ruled out our own SCP by detaching BaselineGuardrails from the Infrastructure OU for a minute. A good habit in a governed account: rule out your own SCPs first. The error message names the denying SCP, as in this example where the region lock blocks CloudTrail in us-east-1:

Sign in to the Dev account and open VPC → Subnets. The shared subnets appear with the Network account as the owner.

Every problem I hit while building this part, in one place:

If you built this only to learn, delete it in this order. Participants must remove their resources from shared subnets before the owner can delete them.

Dev, Production, and Build accounts: delete anything you launched into the shared subnets, including security groups.

Network account: delete the three RAM shares. Then delete the NAT gateways and release their Elastic IP addresses (this stops most of the cost), and delete the three VPCs.

Management account: detach and delete the four custom SCPs. To remove everything, decommission the landing zone in Control Tower, then close the member accounts. Closed accounts stay suspended for 90 days.
